# 26. 옷장 도우미 (대리 등록·관리) 개발 계획

> 작성일: 2026-10-25 · 이슈 [#11](https://github.com/showzone83/wearly/issues/11) · 상태: **1~7단계 구현함** (연결·대리 작업·알림·앱 연결 관리·주인 옷장 화면·관리자 사이트·문서 정리). 실제 휴대폰 두 대 확인은 아직

가족·연인처럼 가까운 사람의 옷을 대신 등록·관리하는 기능이다. 스마트폰이 어렵거나 시간이 없는 사람(옷장 주인)의 옷을 다른 사람(돕는 사람)이 자기 휴대폰으로 찍어 주인 옷장에 넣는다. 화면 이름은 "옷장 도우미"로 한다.

이 문서는 이슈 #11 본문을 코드와 대조해 단계별 작업으로 나눈 것이다. 2장 결정은 2026-10-25에 제안값대로 확정했다. 구현한 단계는 그 장을 실제 내용으로 고친다.

## 1. 지금 코드에서 바뀌어야 하는 전제

- 모든 회원 API는 토큰의 `sub`(= `@CurrentUser long userId`)를 데이터 주인으로 쓴다. 남의 데이터는 쿼리(`findByIdAndUserId`)에서 걸러져 404가 된다.
- 이번 기능은 "누구 데이터인가(owner)"와 "누가 했나(actor·helper)"를 나눈다. 단, **기존 컨텍스트(wardrobe·image)의 서비스 시그니처는 그대로 두고**, 새 `pairing` 컨텍스트가 권한을 확인한 뒤 `ownerId`로 기존 유스케이스를 부른다. 사진 경로(`ImageKeys`의 `users/{userId}/…`)와 업로드 한도도 `ownerId`로 그대로 주인 기준이 된다.
- 토큰에는 아무것도 추가하지 않는다. 역할처럼 **매 요청 DB에서 연결·권한을 확인**한다.
- 앱 `useStore`는 내 옷장 하나만 담고 다른 회원으로 로그인하면 `resetAll()` 한다. 주인 옷장은 저장하지 않는 별도 스토어에 둔다.

### 1단계 — 백엔드: 연결(페어링) — 구현함 (2026-10-25)

#### 4.1 흐름

| 코드를 만든 쪽 | 코드를 입력한 쪽 | 결과 |
|---|---|---|
| 주인 | 돕는 사람 | `PENDING` 생성 → 주인에게 요청 푸시 → 주인이 권한을 골라 승인(`ACTIVE`) 또는 거절 |
| ~~돕는 사람~~ | ~~주인~~ | ~~주인이 입력하면서 권한을 고른다 → 바로 `ACTIVE`~~ — [#18](https://github.com/showzone83/wearly/issues/18)에서 없앰 (8단계) |

- 코드는 Valkey에 둔다 ([`ValkeyPairingCodeAdapter`](../backend/src/main/java/app/wearly/pairing/adapter/out/valkey/ValkeyPairingCodeAdapter.java)): `wearly:pairing:code:{코드}` = `"{회원}:{자리}"`, `wearly:pairing:issuer:{회원}:{자리}` = 그 회원의 지금 코드, 둘 다 TTL 24시간. 새로 만들면 같은 자리의 이전 코드를 지운다(Lua 하나로).
- 코드 입력 순서 ([`PairingService.join`](../backend/src/main/java/app/wearly/pairing/application/service/PairingService.java)): 빈 코드(400 `code` `REQUIRED`) → 시도 한도 → 코드 값 읽기(지우지 않음) → 주인 코드인지(#18 전 돕는 사람 코드면 404 `PAIRING_CODE_INVALID`) → 자기 자신 → 코드를 만든 회원이 있는지 → 같은 두 사람 사이 연결 → 인원 → **코드 지우기**(값이 그대로일 때만, Lua) → 연결 저장. 앞 확인에 걸리면 코드는 남아 다시 입력할 수 있다.
- 글자 규칙(8자, 헷갈리는 0·1·I·L·O 제외)은 친구 초대와 같다. 두 컨텍스트가 함께 쓰도록 공유 커널 [`ShortCodes`](../backend/src/main/java/app/wearly/sharedkernel/shortcode/ShortCodes.java)로 옮기고 `InviteCodes`는 이를 부른다 (컨텍스트 사이에는 `port.in`으로만 의존하는 규칙 때문).
- 입력 시도 제한: 회원당 1시간 10회, 맞는 입력도 센다 ([`ValkeyPairingAttemptAdapter`](../backend/src/main/java/app/wearly/pairing/adapter/out/valkey/ValkeyPairingAttemptAdapter.java), 첫 시도부터 고정 창).
- `PENDING`은 7일이 지나면 만료로 본다: 목록·인원 수에서 빼고 승인·거절할 수 없다. 같은 두 사람이 다시 요청하면 만료된 대기를 `ENDED`(`ended_by = EXPIRED`)로 바꾸고 새로 만든다. 정리 스케줄러는 두지 않았다.
- 거부: 자기 자신, 이미 연결(대기 포함), D1 인원 초과. 동시에 같은 두 사람이 연결하면 부분 고유 인덱스에 걸려 409 `CONFLICT`가 된다. 인원 확인은 잠그지 않으므로 아주 드물게 동시 요청으로 상한을 하나 넘을 수 있다.

#### 4.2 테이블 (`V27__closet_pairing.sql`)

| 컬럼 | 형식 | 값 |
|---|---|---|
| `pairing_id` | BIGINT PK (IDENTITY) | |
| `owner_id` · `helper_id` | BIGINT NOT NULL, `tb_user` CASCADE | 서로 달라야 한다 (`ck_closet_pairing_self`) |
| `permission` | VARCHAR(10) | `VIEW` · `EDIT`. 승인 전(`PENDING`)이면 NULL, `ACTIVE`면 필수 |
| `status` | VARCHAR(10) NOT NULL | `PENDING` · `ACTIVE` · `ENDED` |
| `issued_by` | VARCHAR(10) NOT NULL | 코드를 만든 쪽 `OWNER` · `HELPER`. #18부터 새 연결은 모두 `OWNER`, `HELPER`는 그 전 연결의 이력 |
| `notify_owner` | BOOLEAN NOT NULL DEFAULT TRUE | 돕는 사람의 작업을 주인에게 알릴지 (3단계에서 쓴다) |
| `created_at` · `approved_at` · `ended_at` | TIMESTAMPTZ | `ENDED`일 때만 `ended_at`이 있다 |
| `ended_by` | VARCHAR(10) | `OWNER`(해제·거절) · `HELPER`(해제·취소) · `EXPIRED`(대기 만료) · `ADMIN`(관리자 강제 해제, V29) |

- 부분 고유 인덱스 `uq_closet_pairing_unended (owner_id, helper_id) WHERE status <> 'ENDED'`: 같은 두 사람 사이에 끝나지 않은 연결은 하나. 방향이 반대(B가 A의 옷장을 돕는 것)는 따로 둘 수 있다.
- `ENDED`도 지우지 않고 남긴다(2단계 작업 기록이 이 연결을 가리킨다). 탈퇴는 CASCADE로 함께 지운다.
- 관리자 강제 해제(6단계)를 위해 `V29`에서 `ended_by`에 `ADMIN`을 더했다 (`ck_closet_pairing_ended_by`).
- 모든 테이블·컬럼에 한국어 `COMMENT ON` (doc/08).

#### 4.3 API (`/api/v1/pairings`, 회원 전용)

| 메서드·경로 | 누가 | 내용 |
|---|---|---|
| `POST /codes` `{role?}` | 누구나(옷장 주인 자리) | 201 `{code, role, expiresAt}`. `role`은 `OWNER`만 되고 비우거나 본문이 없어도 `OWNER`. `HELPER`는 400 `VALIDATION_FAILED`(`role` `NOT_ALLOWED`, #18) |
| `POST /join` `{code}` | 누구나(돕는 사람 자리) | 201 연결 `PENDING` (주인 승인 대기) |
| `GET /` | 누구나 | 200 `{asOwner: [...], asHelper: [...]}` 최근 순 |
| `POST /{id}/approve` `{permission}` · `POST /{id}/reject` | 주인 | 200 연결 · 204 (대기 중일 때만) |
| `PATCH /{id}` `{permission?, notifyOwner?}` | 주인 | 200 연결. 권한은 `ACTIVE`일 때만, 알림은 대기 중에도 |
| `DELETE /{id}` | 양쪽 | 204 (`ENDED`) |

연결 응답은 요청한 회원 쪽에서 본 모양이다: `{id, role, partnerId, partnerName, permission, status, issuedBy, notifyOwner, createdAt, approvedAt}`. 상대 정보는 이름(`tb_user.name`)만 준다 (D5). 자세한 계약은 [05](05_백엔드_API.md) 6장 "옷장 도우미 연결".

#### 4.5 권한 확인

- pairing의 입력 포트 [`ClosetAccessUseCase`](../backend/src/main/java/app/wearly/pairing/application/port/in/ClosetAccessUseCase.java): `requireView(helperId, ownerId)`·`requireEdit(helperId, ownerId)` → `ClosetAccessDto(pairingId, ownerId, helperId)`. `ACTIVE` 연결이 없으면(대기 중·끝남·방향이 반대·자기 자신 포함) **404 `NOT_FOUND`**(연결 여부를 숨김), 보기 권한으로 바꾸려 하면 **403 `FORBIDDEN`**(기존 코드). 매 요청 DB에서 확인하므로 권한을 바꾸거나 해제하면 바로 반영된다.
- `record(access, ProxyAction, itemId, itemName)`: 작업 기록. 부르는 쪽 트랜잭션에 합류한다.

#### 4.6 API (`/api/v1/owners/{ownerId}/…`)

| 경로 | 권한 | 컨트롤러 → 유스케이스 |
|---|---|---|
| `GET /wardrobe/items`, `GET /wardrobe/items/{id}` | VIEW | wardrobe `OwnerWardrobeController` → `OwnerWardrobeUseCase` → `WardrobeUseCase.list/get(ownerId, …)` |
| `POST /wardrobe/items` | EDIT | → `create(ownerId, …)` + 기록 `ITEM_CREATE` |
| `PATCH /wardrobe/items/{id}` | EDIT | → `patch(ownerId, …)` (사진 바꾸기 포함) + `ITEM_UPDATE` |
| `POST /wardrobe/items/{id}/retire` · `/restore` | EDIT | → `retire/restore(ownerId, …)` + `ITEM_RETIRE`·`ITEM_RESTORE` (이미 사용 중인 옷의 다시 사용은 기록하지 않음) |
| `POST /images/upload-url` · `/images/{imageId}/complete` | EDIT | image `OwnerImageController` → `OwnerImageUploadUseCase` → `ImageUploadUseCase(ownerId, …)`: 사진이 주인 경로(`users/{ownerId}/…`)·주인 업로드 한도로 |
| `POST /wardrobe/items/analyze` (JSON `{imageId}`만) | EDIT | ai `OwnerAiAnalyzeController` → `OwnerAnalyzeImageUseCase` → `AnalyzeImageUseCase.analyzeStored(quotaUserId = 돕는 사람, imageOwnerId = 주인, imageId)` (D7) |

- `DELETE /wardrobe/items/{id}`, `bulk`, `stats`, multipart 사진 분석은 만들지 않았다. 완전 삭제를 시도하면 405 `METHOD_NOT_ALLOWED`.
- 사진 원본 보기(`GET /images/{id}/original`)는 원래 HTTP API가 없어 뺐다. 옷 응답의 서명 URL로 본다.
- 요청·응답 모양은 기존 `/wardrobe`·`/images`·`/wardrobe/items/analyze`와 같다(같은 Request·Response 클래스). 앱은 경로 앞부분만 바꿔 쓴다. AI 응답의 `remainingToday`는 돕는 사람의 남은 횟수다.
- **구조:** 처음 계획(컨트롤러·서비스를 pairing에 두기)과 달리 **각 컨텍스트(wardrobe·image·ai)가 자기 대리 컨트롤러·서비스를 갖고 pairing의 입력 포트를 부른다.** 컨텍스트 사이에는 `port.in`으로만 의존해야 해서, pairing에 두면 옷장의 Request·Response 클래스를 쓸 수 없기 때문이다. 의존 방향은 wardrobe·image·ai → pairing 한쪽뿐이다(pairing은 옷장을 모른다).
- 트랜잭션: `OwnerWardrobeService`는 한 트랜잭션 안에서 **권한 확인 → `WardrobeUseCase`(합류) → 작업 기록**. 옷 저장이 실패하면 기록도 남지 않는다. 사진 올리기·AI 분석은 기록하지 않고, AI 호출은 트랜잭션 밖이다.
- 기존 코드 변경은 `AnalyzeImageUseCase`에 `analyzeStored(quotaUserId, imageOwnerId, imageId)`를 더한 것 하나(기존 `analyzeStored(userId, imageId)`는 같은 값으로 위임).

### 3단계 — 백엔드: 알림 — 구현함 (2026-10-25)

- **푸시 일반화:** `PushMessage`에 선택 필드 `channelId`·`ttlSeconds`(null이면 D-1 알림의 `plan-d1`·12시간)를 더했고 4인자 생성자를 남겨 D-1 코드는 그대로다. [`ExpoPushSenderAdapter`](../backend/src/main/java/app/wearly/notify/adapter/out/push/ExpoPushSenderAdapter.java)가 메시지 값을 우선 쓴다.
- **일반 알림 포트:** notify의 입력 포트 [`PushNotifyUseCase.notifyUser(userId, PushNoticeDto)`](../backend/src/main/java/app/wearly/notify/application/port/in/PushNotifyUseCase.java). 회원의 모든 기기로 보내고(TTL 24시간) 죽은 토큰(`DeviceNotRegistered`)을 지운다. 서버 푸시가 꺼져 있거나 토큰이 없으면 보내지 않고, 실패해도 던지지 않는다 (알림은 부가 기능). 받은 기기 수를 돌려준다.
- **pairing → notify:** pairing은 출력 포트 `PairingNoticePort`로 부르고, 어댑터 `PairingNoticeNotifyAdapter`가 notify 입력 포트에 맡긴다. 연결 소식은 `sendAfterCommit`(트랜잭션 커밋 뒤에만, 롤백이면 보내지 않음), 묶음 알림은 `send`(기기에 닿았는지 돌려줌). 문구는 도메인 [`PairingNotices`](../backend/src/main/java/app/wearly/pairing/domain/PairingNotices.java).
- **알림 종류** (알림의 `data.type`·`data.pairingId`로 앱이 화면을 연다, 안드로이드 채널 `closet-helper`):

| 언제 | 받는 사람 | `data.type` | 문구 | 시점 |
|---|---|---|---|---|
| 돕는 사람이 주인 코드를 넣음 (`PENDING`) | 주인 | `closet-pairing-request` | "민지님이 옷장 도우미가 되고 싶어 해요" | 바로 |
| 주인이 승인 | 돕는 사람 | `closet-pairing-accepted` | "엄마님의 옷장을 도울 수 있어요" | 바로 |
| 주인이 거절 | 돕는 사람 | `closet-pairing-rejected` | "엄마님이 옷장 도우미 요청을 거절했어요" | 바로 |
| 연결 해제(연결된 뒤만, 대기 취소는 알리지 않음) | 상대 | `closet-pairing-ended` | "민지님과의 옷장 도우미 연결이 해제됐어요" | 바로 |

- **묶음 알림** ([`ProxyDigestService`](../backend/src/main/java/app/wearly/pairing/application/service/ProxyDigestService.java), 예약은 [`ProxyDigestScheduler`](../backend/src/main/java/app/wearly/pairing/adapter/in/schedule/ProxyDigestScheduler.java)): `scan-interval`(5분)마다 알리지 않은 작업(`notified_at IS NULL`)이 있는 연결 중 **마지막 작업이 `digest-delay`(15분) 이상 조용하거나 첫 작업이 `digest-max-wait`(1시간) 이상 지난** 연결을 찾는다. 연결마다 `UPDATE … RETURNING` 한 번으로 작업을 가져오며 `notified_at`을 채워(서버가 여러 대여도 한쪽만 받는다) 종류별 **서로 다른 옷 수**로 한 번 보낸다. 같은 옷을 등록하고 수정하면 두 줄에 모두 센다. 연결이 끝났거나 주인이 알림을 껐으면 표시만 하고 보내지 않는다. 보내기에 실패해도 다시 보내지 않는다 (작업 기록은 남아 있다).
- **설정** (`application.yml`): `wearly.pairing.notify.digest-delay` PT15M, `digest-max-wait` PT1H, `scan-interval` PT5M, `scheduler-enabled` true. 묶음 작업은 서버 푸시가 켜져 있을 때(`wearly.notify.push.enabled=true`)만 예약한다. 예약 실행기는 notify의 `NotifyConfig`가 켠다.
- **한계:** Expo Go에서는 원격 푸시가 제한된다 ([23](23_D-1_알림.md)). `provider=log`(기본)에서는 보내지 않고 건수만 로그에 남는다. 안드로이드 채널 `closet-helper`는 앱(4단계)이 같은 ID로 만들어야 알림이 보인다. 푸시를 보내는 동안(Expo 응답 대기 최대 10초) 요청 스레드가 막히지만 커밋 뒤라 응답 내용에는 영향이 없다.
- **테스트:** `PairingNoticesTest`(문구 3개), `PairingServiceTest`에 연결 소식 1개, `PairingNotifyIntegrationTest`(4개, 실제 DB·HTTP, Expo는 가짜 서버): 요청·승인·해제가 바로 가고 채널·TTL·`data`가 맞음 / 토큰이 없거나 실패한 요청은 조용함 / 대리 작업이 15분 뒤 한 번 묶여 가고 다시 불러도 안 감 / 알림을 끄면 표시만 하고, 첫 작업 뒤 1시간이 지나면 보냄. D-1 알림 테스트는 그대로 통과.
- **통합 테스트 인프라:** 테스트 컨텍스트(속성이 다르면 새로 만들어 캐시에 남고 연결 풀 10개씩 잡는다)가 늘어 테스트 PostgreSQL의 기본 `max_connections=100`이 모자라 `IntegrationTestBase`에서 300으로 올렸다.

### 5단계 — 앱: 주인 옷장 화면 — 구현함 (2026-10-25)

돕는 사람이 연결 목록의 "OO님 옷장 열기"로 주인 옷장을 보고, 등록·수정 권한이면 옷을 대신 등록·수정·사용 중지·다시 사용한다.

- **구조 결정:** 계획(옷장 대상 추상화 `closetTarget`로 `account.ts`·`item/new`·`item/[id]`를 분기)과 달리 **대리용 화면을 따로 만들었다.** 기존 `account.ts`의 `createItem`·`saveItem`·`retireItem`·`restoreItem`은 모두 내 옷장 스토어(`useStore`)·기기 사진·게스트 모드·착용 횟수 합치기에 얽혀 있어 주인용 분기를 넣으면 두 흐름이 서로 깨질 위험이 컸다 (doc 6장 위험 항목에서 예고한 대안). 폼·사진 처리·사용 중지 시트만 공유한다. 주인 옷은 **화면 상태로만 들고 저장하지 않으므로**(별도 스토어 대신) 내 `useStore`·`photos`·동기화와 섞이지 않는다.
- **API 모듈** `api.owners.{list, get, create, update, retire, restore, analyzeImage, uploadUrl, complete}`(첫 인자 `ownerId`, [05](05_백엔드_API.md) 6장 "대리 작업"과 같은 모양). 완전 삭제·여러 벌 등록은 없다. [`photoUpload.ts`](../mobile/src/lib/photoUpload.ts)의 `uploadPhoto`·`uploadPrepared`에 선택 인자 `ownerId`를 더해 주인 경로로 올린다.

## 5. 후속 이슈

- **A. 대리 코디 추천·예정 코디 (`PLAN` 권한).** 지금 추천 입력 중 착용 기록·좋아요/싫어요(`affinity`)·날씨 지역이 주인 기기에만 있어, 돕는 사람이 추천하면 다양성·취향 점수가 비고 날씨도 틀린다. 이것들을 서버에 둘지 먼저 정한다. 예정 코디는 이미 서버 저장(`/plans`)이라 주인에게 D-1 알림이 가는 부분은 그대로 동작한다. AI 추천 한도(하루 20회)를 누구 것으로 쓸지도 정한다.
- **B. 포인트·추천 보상.** 포인트는 코드·스키마에 아직 없다. 추천 수는 V26 가입 이력(`tb_invite_signup`)으로 셀 수 있다. 가짜 계정 남용 방지가 필요하다. D1 인원을 회원별로 올리는 컬럼(또는 표)을 붙이는 방식으로 연결한다.

## 6. 위험

- **대상 사용자 부담:** 옷장 주인도 가입·코드 만들기·보내기·승인을 해야 한다. 돕는 사람이 코드를 만들고 주인은 입력만 하던 흐름은 간섭이 될 수 있어 #18에서 없앴으므로, 스마트폰이 어려운 주인이면 돕는 사람이 옆에서 같이 눌러 주는 것을 안내 문구로 둔다. 실제 사용자 반응을 보고 다시 정한다.
- **화면 분기 증가(해소):** `item/new.tsx`(551줄)·`item/[id].tsx`(581줄)에 `owner` 분기가 늘어난다. 분기가 커지면 대리용 화면을 따로 만들고 폼·사진 처리만 공유한다.
- **권한 누락:** 대리 경로는 `Owner*Controller`(wardrobe·image·ai)마다 있고 각각 `Owner*UseCase`를 거쳐 `ClosetAccessUseCase.require*`를 부른다. 새 owner 경로를 더할 때 이 확인을 빠뜨리지 않도록 `OwnerClosetIntegrationTest`의 권한별 표(보기 권한 403·연결 없음 404)에 함께 넣는다.
