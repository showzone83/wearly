# 20. 오류 응답: 서버는 코드값만 보내고 화면 문구는 앱·관리자가 정한다

> 2026-10-18. 대상: `backend/`(`common/error`·`common/web`·`common/domain`, `error-codes.json`), `mobile/`(`src/lib/errorText.ts`, `src/api/errors.ts`), `admin/`(`src/lib/errorText.ts`, `src/api/errors.ts`), `harness/`.
> 클라우드 브랜치 `feat/error-handling`(PR #7)을 `dev`에 합쳤고(`6956af1`), 앱·관리자는 이어서 문구 표를 붙였다(`837fe16`, `362a0fb`, `2f90f2b`).
> [05](05_백엔드_API.md) 4장의 오류 형식 설명은 이 문서가 대신한다. 요청 흐름 안에서 오류가 처리되는 순서는 [10](10_백엔드_흐름.md) 2.2.

## 1. 배경과 결정

예전 응답은 `{ status, code, message, fieldErrors: [{ field, message }] }`였고 `message`에 서버가 만든 한국어 문장이 들어갔다. 문장 안에 모자란 칸 이름, 사용처 개수, 공급자 응답 일부 같은 상세가 섞였고, 문장을 앱이 그대로 보여 주거나 정규식으로 다시 풀어야 했다.

| 항목 | 결정 |
|---|---|
| 응답에 넣는 것 | `status`, `code`, `params`(있을 때만), `fieldErrors`, `traceId`. **문장(`message`)은 없다** |
| 상세 값 | 문장에 섞지 않고 `params`에 값으로 준다 (예: 모자란 칸 `missing`, 사용처 `usages`) |
| 화면 문구 | 앱·관리자가 `code`·`params`로 정한다. 기준은 `backend/src/main/resources/error-codes.json` |
| 서버 내부 정보 | 예외 메시지, SQL·DB 오류, 외부 AI 공급자 응답 원문, 클래스·필드 이름, 설정 이름, 스택은 응답으로 나가지 않는다. **같은 `traceId`로 서버 로그에서만** 본다 |
| 시스템 오류 | 화면에는 일반 문구와 "오류 번호 xxxxxxxx"(`traceId` 앞 8자)만 보인다. 문의할 때 이 번호로 로그를 찾는다 |

## 2. 응답 모양

```
{ status, code, params?, fieldErrors: [{ field, code, params? }], traceId }
```

| 필드 | 내용 |
|---|---|
| `status` | HTTP 상태와 같은 숫자 |
| `code` | `ErrorCode` 상수 이름. 이름은 바꾸지 않고 추가만 한다 |
| `params` | 그 코드의 상세 값. 값이 있을 때만 들어간다 (없으면 키 자체가 없다). 이름은 `ErrorCode`가 정한 것만 쓴다 |
| `fieldErrors[]` | 입력 검증 사유. 항상 배열이다 (없으면 `[]`). `field`는 JSON 경로(`items[3].subType`, `seasons[1]`, `context.fixed.TOP`, 본문 전체는 `body`), `code`는 `FieldErrorCode` 이름, `params`는 있을 때만 |
| `traceId` | 요청 추적 ID. 응답 헤더 `X-Request-Id`와 같다 (4장) |

예시 (실제 응답, `traceId`만 값이 다르다).

```jsonc
// 400 입력 검증: 가입에 이메일 형식·이름 길이·비밀번호 규칙 위반
{ "status": 400, "code": "VALIDATION_FAILED",
  "fieldErrors": [
    { "field": "email", "code": "INVALID_FORMAT" },
    { "field": "password", "code": "INVALID_FORMAT" },
    { "field": "name", "code": "TOO_LONG", "params": { "max": 20 } } ],
  "traceId": "docs-check-0001" }

// 401 토큰 없음: 필터 단계의 오류도 같은 모양이다
{ "status": 401, "code": "UNAUTHORIZED", "fieldErrors": [], "traceId": "64e03d450e9c406d9932abb206a3ceb7" }

// 400 업무 오류 + params: 코디를 만들 옷이 모자람
{ "status": 400, "code": "WARDROBE_INSUFFICIENT",
  "params": { "missing": ["TOP", "BOTTOM", "SHOES"], "alternatives": ["DRESS"] },
  "fieldErrors": [], "traceId": "5e4d6d86a1dd42a1800fd0fcb51335fd" }
```

코드마다 `params` 이름은 `error-codes.json`의 `params`에 있다. 문서마다 따로 적던 값 중 자주 쓰는 것만 옮긴다.

| 코드 | params | 값 |
|---|---|---|
| `WARDROBE_INSUFFICIENT` | `missing`, `alternatives` | 모자란 칸 코드 목록(`TOP`·`BOTTOM`·`SHOES`), 대신할 수 있는 칸(`DRESS`, 없으면 생략) |
| `CODE_IN_USE` | `usages` | `[{ kind: ITEM\|PROFILE\|SUB_TYPE\|PLAN, count }]` (`error-codes.json`의 설명에는 `PLAN`이 아직 없다) |
| `API_KEY_INVALID` | `reason` | `API_401`·`API_403`·`API_429` 등 `API_<HTTP 상태>`, `TIMEOUT`, `API_FAILED`, `API_CLIENT`, `INVALID_RESPONSE`, `BAD_RESPONSE` |
| `AI_LIMIT_EXCEEDED`·`AI_UNAVAILABLE` | `feature` | `ITEM_ANALYZE`(사진 분석), `OUTFIT_RECOMMEND`(코디 추천) |
| `IMAGE_INVALID` | `reason` | `FORMAT`(JPEG·PNG가 아님), `TOO_LARGE`(최대 크기 초과), `PIXELS`(화소 수 초과), `DECODE`(깨진 파일) ([18](18_사진_저장.md) 6장) |
| `WEATHER_LIMIT` | `kind` | `ON_DEMAND`(좌표 날씨), `SEARCH`(장소 검색) ([19](19_장소별_날씨.md)) |
| `WEATHER_UNAVAILABLE` | `kind` | `SEARCH`(장소 검색을 쓸 수 없음). 날씨 자체면 생략 |
| `WEATHER_NO_PROVIDER` | `reason`, `keyName` | 공급자 시험 호출(관리자)에서만. `KEY_MISSING`·`NOT_IMPLEMENTED`, 서버 설정 키 이름 |
| `PLAN_LIMIT` | `max` | 예정 코디 저장 개수 상한 500 ([21](21_예정_코디_저장.md)) |
| `PAIRING_LIMIT` | `side`, `max` | 옷장 도우미 연결 인원 초과. `OWNER`(주인의 돕는 사람 수)·`HELPER`(돕는 사람의 옷장 수)와 그 상한 ([26](26_옷장_도우미.md)) |

필드 오류 코드 21개는 `common/domain/FieldErrorCode`에 있다. `TOO_SHORT{min}`, `TOO_LONG{max}`, `OUT_OF_RANGE{min,max}`(날짜 범위는 `YYYY-MM-DD` 문자열, 사진 업로드 `size`는 바이트), `INVALID_FORMAT{format}`, `INVALID_TYPE{expected}`, `NOT_ALLOWED{allowed}`(고정 목록일 때만), `TOO_MANY{max}`, `INCOMPLETE{expected}`, `SLOT_MISMATCH{slot}`처럼 상세가 필요한 것만 `params`를 쓴다.

## 3. 오류 분류

`common/error/GlobalExceptionHandler`(`@RestControllerAdvice`)가 모든 예외를 위 모양 하나로 바꾼다. 응답은 `ErrorResponse.body()`가 만든다.

| 분류 | 예 | 응답 | 로그 |
|---|---|---|---|
| **기본 오류** (프로토콜·프레임워크) | JSON 파싱 실패·타입 불일치, 필수 값·파트·헤더 누락(400), 없는 경로(404), 405, 406, 413, 415 | 카탈로그 코드만. 400은 `VALIDATION_FAILED` + 필드 코드 | WARN `요청 오류 code=… METHOD PATH userId=… cause=<예외 클래스>: <Jackson·Spring 원문>` (스택 없음). 401·403은 INFO `인증·권한 오류 code=… METHOD PATH userId=…` (`ErrorResponseWriter`) |
| **업무 오류** (도메인 규칙 위반) | 이메일 중복, 옷 모자람, 사용 중지 옷 고정, AI 한도, 남의 리소스(404), 입력 검증 | `BusinessException(ErrorCode[, params \| fieldErrors])`, `DomainValidationException(fieldErrors)`의 `ErrorCode`·필드 코드·`params` | WARN `업무 오류 code=… METHOD PATH userId=… detail=…` (스택 없음) |
| **시스템 오류** (그 밖의 모든 예외) | DB·Valkey·외부 HTTP·IO·NPE … | **500 `INTERNAL_ERROR`**. 일시적 의존성 장애(`TransientDataAccessException`, `DataAccessResourceFailureException`, `CannotCreateTransactionException`)는 **503 `SERVICE_UNAVAILABLE`**. 외부 AI 장애는 서비스가 502 `AI_UNAVAILABLE`로 바꾼다 | ERROR `시스템 오류 code=… METHOD PATH query=… userId=…` + 스택 |
| 의미가 분명한 DB 예외 | 낙관적 잠금 실패(`OptimisticLockingFailureException`), 고유 제약 위반(`DataIntegrityViolationException` + SQLState `23505`) | 409 `CONFLICT` | WARN `DB 충돌 code=CONFLICT … cause=… sqlState=…` (스택 없음). 그 밖의 무결성 위반(NOT NULL·FK 등)은 시스템 오류(500) |

- 분류 규칙은 `SystemErrors.classify`가 한다. 새 예외를 409나 503으로 다루고 싶으면 여기에 더한다.
- **`/error`**: 컨트롤러에 닿기 전(필터)에 난 예외나 서블릿 컨테이너가 정한 오류 상태는 `ErrorPageController`(`${server.error.path:/error}`)가 같은 형식으로 쓴다. Spring Boot의 기본 `BasicErrorController`와 whitelabel 화면을 대신한다. 상태 → 코드는 `ErrorCodes.forStatus`: 400 `VALIDATION_FAILED`, 401 `UNAUTHORIZED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 405 `METHOD_NOT_ALLOWED`, 406 `NOT_ACCEPTABLE`, 409 `CONFLICT`, 413 `IMAGE_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA_TYPE`, 503 `SERVICE_UNAVAILABLE`, 그 밖 4xx `VALIDATION_FAILED`, 5xx `INTERNAL_ERROR`.
- **`application.yml`의 `server.error.*`**: `include-message: never`, `include-stacktrace: never`, `include-binding-errors: never`, `include-exception: false`, `whitelabel.enabled: false`. 기본 오류 본문에 아무것도 새어 나가지 않게 모두 끈다.
- **`BusinessException`**: 문장(`String`)을 받는 생성자가 없다. 생성자 `(ErrorCode)`, `(ErrorCode, Map params)`, `(ErrorCode, List<FieldError>)`와 정적 메서드 `notFound()`, `validation(FieldError)`, `validation(field, FieldErrorCode)`, `throwIfAny(errors)`. `params` 이름은 `ErrorCode`가 정한 것만 받고, 아니면 `IllegalArgumentException`을 던진다. `getMessage()`는 로그용 `CODE [field=CODE, …]`다.
- **`FieldError`**: `record FieldError(String field, FieldErrorCode code, Map<String,Object> params)` (`common/domain`). 도우미 `required`, `tooShort`, `tooLong`, `tooMany`, `outOfRange(min,max)`, `notAllowed([allowed])`, `invalidFormat([format])`, `invalidType(expected)`.
- **Bean Validation**: 애너테이션 메시지는 쓰지 않는다 (요청 DTO에 `message=` 속성이 없다). `ConstraintCodes`가 애너테이션 종류와 속성으로 코드·params를 정한다: `NotNull`·`NotBlank`·`NotEmpty` → `REQUIRED`, `Size` → 문자열 `TOO_LONG{max}`·`TOO_SHORT{min}`, 배열 `TOO_MANY{max}`, `Min`·`Max`·`Range` → `OUT_OF_RANGE{min,max}`, `Pattern`·`Email`·그 밖 → `INVALID_FORMAT`. `@Min`+`@Max`는 `@Range(min, max)`로 써서 min·max를 함께 준다.
- **JSON 본문**: 파싱 실패는 `body INVALID_FORMAT{format: json}`, 빈 본문은 `body REQUIRED`, 경로가 있는 타입 오류는 그 필드 `INVALID_FORMAT`(열거형 값이면 `NOT_ALLOWED`). 객체 수준 오류는 자바 객체 이름 대신 `body`로 낸다.
- **관리자 API**도 같은 규칙이다. 관리자에게만 필요한 상세는 `params`로 준다 (`WEATHER_NO_PROVIDER.keyName`, `API_KEY_INVALID.reason`). 공급자 응답 원문은 WARN 로그 `API 키 확인 실패 provider=… reason=… detail=…`에만 남는다.

## 4. traceId

| 구성 요소 | 하는 일 |
|---|---|
| `common/web/TraceIdFilter` | 가장 먼저 도는 서블릿 필터(보안 필터보다 앞). 요청 헤더 `X-Request-Id`가 `^[A-Za-z0-9._-]{8,64}$`이면 그 값을, 아니면 새로 만든다 (하이픈 없는 UUID 32자). MDC `traceId`에 넣고 응답 헤더 `X-Request-Id`로 돌려준다 (**성공 응답 포함**). `/error`로 다시 들어온 요청도 같은 값을 쓴다 |
| `auth/adapter/in/web/UserIdMdcFilter` | Bearer 인증 바로 뒤에서 회원 ID를 MDC `userId`에 넣는다 (`SecurityConfig`). 403 로그에도 찍힌다 |
| `common/error/TraceIds` | 헤더·MDC 이름과 형식 검사(`isValid`), 새 ID 만들기(`generate`) |
| `common/config/CorsConfig` | 허용 헤더와 노출 헤더(`exposedHeaders`)에 `X-Request-Id`를 넣어 브라우저(Expo 웹, 관리자 사이트)가 읽는다 |
| `application.yml` `logging.pattern.level` | `"%5p [traceId=%X{traceId:-} userId=%X{userId:-}]"`. 모든 로그 줄에 찍힌다 (요청 밖이면 비어 있다) |

형식에 맞지 않는 `X-Request-Id`는 버리고 새로 만든다 (로그 주입 방지). 보안 필터의 401·403(`ErrorResponseWriter`) 본문에도 `traceId`가 붙는다.

### 로그에서 찾는 법

화면의 "오류 번호 ab12cd34"는 앞 8자다. 사용자가 복사한 전체 `traceId`(길게 누르기·누르기, 7장)로 로그를 찾는다. 앞 8자만 있어도 `grep`은 앞부분 일치로 찾는다.

```bash
docker compose logs backend | grep <traceId>
```

2026-10-18에 실제로 확인했다. 요청 헤더에 `X-Request-Id: docs-check-0001`을 주고 가입을 잘못 보낸 뒤 위 명령으로 찾았다 (한 줄이 아주 길어 뒷부분은 줄였다).

```
wearly-backend  | 2026-10-18T18:59:09.918+09:00  WARN [traceId=docs-check-0001 userId=] 1 --- [wearly-backend] [nio-8080-exec-7] a.w.common.error.GlobalExceptionHandler  : 업무 오류 code=VALIDATION_FAILED POST /api/v1/auth/signup userId=null detail=Validation failed for argument [0] in public ...
```

- 오류 응답이 없는 요청(성공)도 응답 헤더 `X-Request-Id`로 같은 ID를 얻으니, 느린 요청을 찾을 때도 쓴다.
- 실행 중이 아니면 `docker compose logs`에 아무것도 없다. Mac에서 직접 띄웠다면(`./gradlew bootRun`) 그 터미널 출력에서 `grep`한다.
- 시스템 오류는 ERROR 줄과 스택이 같은 `traceId`로 이어진다 (`시스템 오류 code=INTERNAL_ERROR …`).

## 5. 카탈로그 `error-codes.json`

`backend/src/main/resources/error-codes.json`이 앱·관리자가 화면 문구를 정하는 기준이다. 오류 코드 57개(`errorCodes`)와 필드 오류 코드 21개(`fieldErrorCodes`)가 있다.

| 항목 | `errorCodes` | `fieldErrorCodes` |
|---|---|---|
| `code` | `ErrorCode` 이름 | `FieldErrorCode` 이름 |
| `status` | HTTP 상태 | 없음 |
| `description` | 언제 나오는지 | 〃 |
| `params` | 쓸 수 있는 params 이름 | 〃 |
| `message` | 권장 한국어 문구 (`{이름}`은 params 자리) | 〃 |
| `fields` | 없음 | 이 코드가 쓰이는 필드 예 |

`ErrorCodeCatalogTest`(Spring 없음)가 이 파일이 `ErrorCode`·`FieldErrorCode` enum과 빠짐없이 맞는지 확인한다.

- 코드 이름 집합이 같다 (빠진 코드도, 남은 코드도 없다)
- `status`와 `params` 이름이 같다
- 오류 코드의 `message`가 `ErrorCode`의 설명 문장과 같다
- 모든 `description`이 비어 있지 않다
- 필드 오류 `message`의 `{이름}` 자리가 그 코드의 `params` 이름이다
- 같은 `code`가 두 번 나오지 않는다 (`NOT_FOUND`와 `CONFLICT`는 오류 코드와 필드 오류 코드에 각각 있다)

`ErrorCode`의 설명 문장은 로그·문서용이다. 응답에 쓰면 ArchUnit이 실패한다 (9장).

## 6. 프론트 문구 표

서버가 문장을 안 주므로 앱과 관리자가 각자 `code`별 문구 표를 갖는다. 둘 다 카탈로그와 **빠짐없이 맞는지** 검사한다.

| | 앱 `mobile/src/lib/errorText.ts` | 관리자 `admin/src/lib/errorText.ts` |
|---|---|---|
| 서버 오류 코드 표 | `SERVER_TEXT` (57개 전부) | `SERVER_ERROR_TEXT` (57개 전부. 관리자 화면과 무관한 코드는 `null`로 명시하고 상태별 기본 문구를 쓴다) |
| 필드 오류 코드 표 | `FIELD_TEXT` (21개) | `FIELD_ERROR_TEXT` (21개) |
| 클라이언트가 만드는 코드 | `APP_TEXT` 5개: `UPLOAD_FAILED`, `NETWORK`, `HTTP_ERROR`, `RETIRE_UNSUPPORTED`, `IMAGES_UNSUPPORTED` | `CLIENT_ERROR_TEXT`: `NETWORK`, `HTTP_ERROR`, `NOT_ADMIN` |
| 문구 함수 | `errorText(e, ctx?)`, `fieldErrorText`, `statusText` | `errorText(e)`, `fieldErrorText`, `statusText` |
| params 해석 | 모자란 칸(`slotListText`), 날짜 범위, 바이트(`10MB`), 사진 사유 등 | API 키 사유(`apiKeyReasonText`), 코드 사용처(`codeUsagesText`), 날씨 공급자 사유 등 |
| 일치 검사 | `cd mobile && npm run check:errors` (`scripts/check-error-codes.mjs`) | `cd admin && npm run test:unit` (`tests/errorText.test.mjs`) |

- 표에 없는 코드(서버가 새로 더했거나 오래된 서버)는 상태별 기본 문구(`statusText`)를 보여 준다.
- `VALIDATION_FAILED`는 필드 오류를 덧붙인다 (앱은 첫 필드 오류, 관리자는 `field: 문구 / …`). 입력칸 아래에 따로 보이는 화면은 `fieldErrorText`를 쓴다.
- 앱 API 모듈(`mobile/src/api/errors.ts`)은 서버가 `message`를 안 주므로 `ApiError.message` 자리에 `code`를 담는다. **화면에 `e.message`를 그대로 보이지 않는다** — `errorText(e)`를 거친다.
- 일치 검사가 하는 일은 같다: 카탈로그의 코드가 표에 모두 있는지, 표에 카탈로그에 없는 코드가 남지 않았는지, 클라이언트 코드가 서버 코드와 겹치지 않는지, 문구에 `{이름}`이 남지 않는지(관리자). 어긋나면 실패한다.

```bash
cd mobile && npm run check:errors      # 오류 코드 표 OK: 서버 57개 · 필드 21개 · 앱 5개
cd admin && npm run test:unit          # tests/*.test.mjs 전체 43개 (errorText 일치·params 해석 포함, 2026-10-18 기준)
```

## 7. 오류 번호 표시 규칙

**시스템 오류에만** "오류 번호 xxxxxxxx"를 보인다. 업무 오류·입력 오류는 사용자가 고칠 수 있는 문구가 있으므로 번호를 보이지 않는다.

| | 앱 | 관리자 |
|---|---|---|
| 시스템 오류의 기준 | `INTERNAL_ERROR`·`SERVICE_UNAVAILABLE`, 또는 5xx인데 표에 없는 코드 (`isSystemError`). `WEATHER_UNAVAILABLE`(503)·`AI_UNAVAILABLE`(502)은 표에 있는 업무 오류라 번호를 보이지 않는다 | 모든 5xx (`status >= 500`, `isSystemError`) |
| 보이는 글자 | `traceLabelOf(traceId)` = "오류 번호 " + `traceId` 앞 8자 | `traceLabel(traceId)` 같은 모양 |
| 복사 | 문구 아래 작은 글자를 **길게 누르면** 전체 `traceId`를 복사한다 (`components/ui.tsx`의 `TraceLabel`, `expo-clipboard`) | 문구를 **누르면** 전체 `traceId`를 복사한다 (`components/ui.tsx`의 `TraceId`) |
| 어디에 | 오류가 나는 화면의 문구 아래 | 토스트(복사할 시간을 주려고 9초)와 `ErrorBox` |
| 글자만 쓰는 곳 | — | `errorTextWithTrace`가 끝에 " (오류 번호 ab12cd34)"를 붙인다 |

`traceId`는 응답 본문에서 읽고, 본문이 없는 오류(게이트웨이 502 등)는 관리자가 응답 헤더 `X-Request-Id`로 대신한다 (`admin/src/api/errors.ts`). 앱은 서버 응답이 아니면(연결 실패 등) `traceId`가 없어 번호도 없다.

## 8. 새 오류 코드를 더하는 순서

한 단계라도 빠지면 일치 검사가 실패한다. 이 순서로 하면 어디서 빠졌는지 바로 알 수 있다.

1. **`ErrorCode`**(`common/error`)에 상수를 더한다. 형식 `NAME(status, "권장 문구"[, "params 이름"…])`. 기존 상수 이름은 바꾸지 말고 **추가만** 한다. 필드 오류 코드면 `FieldErrorCode`에 더한다.
2. 던지는 곳에서 `new BusinessException(ErrorCode.NAME[, Map.of("이름", 값)])` (필드면 `FieldError`). 문장을 만들어 넘기지 않는다. 자세한 사정은 서비스가 로그로 남긴다.
3. **`error-codes.json`**에 같은 항목을 더한다: `code`, `status`, `description`, `params`, `message`(= `ErrorCode`의 설명 문장), 필드 오류는 `fields`(쓰이는 필드 예).
4. **앱 `mobile/src/lib/errorText.ts`**의 `SERVER_TEXT`(필드면 `FIELD_TEXT`)에 문구를 더한다. params를 쓰면 함수로 해석한다.
5. **관리자 `admin/src/lib/errorText.ts`**의 `SERVER_ERROR_TEXT`(필드면 `FIELD_ERROR_TEXT`)에 문구를 더한다. 관리자 화면과 무관한 코드는 `null`로 두고 이유를 주석으로 적는다.
6. 앱·관리자 `api/types.ts`(앱은 `errors.ts`의 `ApiErrorCode` 목록)에 코드 이름을 더한다.
7. 검사를 돌린다.

   ```bash
   cd backend && ./gradlew test --tests '*ErrorCodeCatalogTest'
   cd mobile && npm run check:errors && npm run typecheck
   cd admin && npm run test:unit && npm run lint
   ```
8. 이 문서 2장의 params 표와 [05](05_백엔드_API.md) 엔드포인트별 오류 설명에 코드를 적는다.

테스트는 `TestApi.expectError`(모든 통합 테스트의 오류 검사)로 `message`가 없는지, `traceId`가 `X-Request-Id` 헤더와 같은지, `fieldErrors` 항목마다 `field`·`code`가 있는지를 본다.

- 앱(`mobile/src/lib/errorText.ts`)은 관리자 사이트 전용이라 볼 일이 없지만 일치 검사 때문에 짧은 문구로 7개를 갖는다.
- 일치 검사: 앱 `npm run check:errors` → 서버 51 · 필드 21 · 앱 5, 관리자 `npm run test:unit` 43개(파일 7개). 하네스 시나리오 46번은 SSO가 꺼진 기본 동작(404 `NOT_FOUND`)의 오류 본문 형식을 `checkErrorBody`로 확인한다.

| `PAIRING_CODE_INVALID` | 404 | — | 연결 코드가 없음·만료(24시간)·이미 사용됨·코드를 만든 회원이 탈퇴함. 코드 추측을 막으려고 이유를 나누지 않는다 | 코드가 맞지 않거나 시간이 지났어요. 코드를 다시 받아 주세요. |
| `PAIRING_SELF` | 400 | — | 내가 만든 코드를 내가 입력함 | 내가 만든 코드는 내가 입력할 수 없어요. 상대에게 코드를 보내 주세요. |
| `PAIRING_EXISTS` | 409 | — | 같은 주인·돕는 사람 사이에 이미 연결됐거나 승인 대기 중 | 이미 연결됐거나 승인을 기다리는 상대예요. |
| `PAIRING_LIMIT` | 409 | `side`, `max` | 연결 인원 초과(대기 포함). `side` = `OWNER`(주인의 돕는 사람, 기본 1명) · `HELPER`(돕는 사람의 옷장, 기본 2곳) | 옷장 주인은 돕는 사람을 {max}명까지 연결할 수 있어요. / 옷장은 {max}곳까지 맡을 수 있어요. |
| `PAIRING_TOO_MANY_ATTEMPTS` | 429 | — | 코드 입력 시도가 회원당 1시간 10회를 넘음 (맞는 입력도 센다) | 코드를 여러 번 입력했어요. 잠시 후 다시 시도해 주세요. |

- `PAIRING_SELF`·`PAIRING_EXISTS`·`PAIRING_LIMIT`·권한 값 오류(400 `VALIDATION_FAILED`)에 걸리면 코드를 쓰지 않은 것으로 둬서 다시 입력할 수 있다. 코드는 모든 확인을 지난 뒤에만 지운다(1회용).
- 남의 연결을 승인·변경·해제하거나, 끝난 연결·만료된 대기를 건드리면 `NOT_FOUND`(404)다. 연결이 있는지 숨기려고 403을 쓰지 않는다.
