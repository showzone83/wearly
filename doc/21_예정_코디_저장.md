# 21. 예정 코디 서버 저장: `/plans` API와 앱 동기화

> 2026-10-18. 대상: `backend/`(`plan` 컨텍스트, `V14__planned_outfit.sql`), `mobile/`(`src/lib/planSync.ts`·`planSyncRules.ts`, `src/api/`), `admin/`(코드 사용처 '예정 코디', `PLAN_LIMIT` 문구), `harness/`(시나리오 51~53).
> [19](19_장소별_날씨.md)의 "다음 단계"로 남겨 둔 일이다. 예정 코디는 지금까지 앱 기기에만 있었다. 계정 모드에서는 서버에도 저장해 기기를 바꾸거나 다시 설치해도 남는다.
> 오류 응답 모양은 [20](20_오류_응답.md), 장소·날씨 출처는 [19](19_장소별_날씨.md).

## 1. 배경과 결정

예정 코디는 캘린더에서 날짜·시간대·장소를 정하고 코디를 붙여 두는 앱의 `PlannedEvent`다. V1에 `tb_planned_outfit`이 있었지만 쓰는 코드가 없어 비어 있었고 장소·날씨 출처·코디 칸이 없었다.

| 항목 | 결정 |
|---|---|
| 저장 위치 | 서버 `tb_planned_outfit`. 앱은 기기에 먼저 저장하고 서버에 보낸다 (게스트·목업 실행은 기기만) |
| 테이블 | V1의 빈 표를 지우고 V14에서 다시 만든다 (V12 `tb_item_image`와 같은 방식. 이미 적용된 V1~V13은 바꾸지 않았다) |
| 짝 맞추기 | 앱이 만든 예정 id를 `clientId`로 보낸다. 같은 회원 안에서 `clientId`가 같으면 같은 예정이다 (중복 없이 몇 번이든 올릴 수 있다) |
| 코디(`outfit`) | 앱 `Outfit` 모양 그대로 JSONB. 서버가 아는 것은 `items`(칸 → 아이템 id)뿐이고 점수·이유는 앱 값이다. 크기만 제한한다 |
| 지운 옷 | 옷을 지워도 예정의 코디는 그대로 두고, 응답의 `missingItemIds`로 알려 준다. 앱은 그 칸을 "지운 옷"으로 흐리게 보인다 |
| 개수 상한 | 회원당 500개. 넘으면 409 `PLAN_LIMIT` |

## 2. API

모두 로그인이 필요하다 (토큰 없으면 401 `UNAUTHORIZED`). **남의 예정·없는 예정은 404** `NOT_FOUND`이고 입력이 틀려도 404가 먼저다. 코드: `PlanController`, `PlanService`, `PlanRules`, `PlanOutfits`. 앱 API 모듈은 `api.plans.list/create/bulk/patch/remove`.

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| GET | `/api/v1/plans` | 쿼리 `from`, `to` (`YYYY-MM-DD`, 선택, 양 끝 포함) | 200 `{ items: PlanDto[] }` 날짜 → 시간대(AM·PM·EVENING) 순 |
| POST | `/api/v1/plans` | `PlanInput` | 새로 만들면 **201**, 같은 `clientId`의 예정이 있으면 그것을 고치고 **200** (모양은 같다) `PlanDto` |
| POST | `/api/v1/plans/bulk` | `{ items: PlanInput[] }` (최대 100개, 항목마다 `clientId` 필수) | 200 `{ items: PlanDto[], created, updated }` 요청 순서대로 |
| PATCH | `/api/v1/plans/{id}` | `Partial<PlanInput>` (`clientId` 제외) | 200 `PlanDto` |
| DELETE | `/api/v1/plans/{id}` | — | 204 |

```ts
interface PlanInput {            // 앱 PlannedEvent에서 id 대신 clientId
  clientId?: string | null;      // 1~64자 영문·숫자·. _ : - (bulk는 필수)
  date: string;                  // YYYY-MM-DD
  timeOfDay: 'AM' | 'PM' | 'EVENING';
  title: string;                 // 1~50자
  occasion: 'COMMUTE' | 'MEETING' | 'FIELD' | 'DINNER' | 'DAILY' | 'INTERVIEW' | 'WEDDING' | 'DATE' | 'TRAVEL' | 'GATHERING';
  concepts?: string[];           // STYLE 코드, 10개까지
  memo?: string | null;          // 500자까지
  place?: { regionCode?: string | null; label: string; lat: number; lon: number } | null;
  weather: { temp: number; min: number; max: number; rainProb: number; cond: 'SUNNY' | 'CLOUDY' | 'RAIN'; manual?: boolean };
  weatherSource?: 'FORECAST' | 'CLIMATE' | 'MANUAL' | null;
  weatherCheckedAt?: string | null;   // ISO-8601 (Z 또는 +09:00 같은 오프셋)
  forecastReady?: boolean;
  outfit?: { items: { [slot in 'TOP' | 'BOTTOM' | 'DRESS' | 'OUTER' | 'SHOES' | 'BAG']?: string }; [앱 값]: unknown } | null;
}
interface PlanDto extends Omit<PlanInput, 'clientId' | 'concepts' | 'place' | 'weather' | 'forecastReady' | 'outfit'> {
  id: string;                    // 서버 id (문자열)
  clientId: string | null;
  concepts: string[];
  place: { regionCode: string | null; label: string; lat: number; lon: number } | null;
  weather: { temp: number; min: number; max: number; rainProb: number; cond: string; manual: boolean };  // manual은 항상 true·false
  forecastReady: boolean;
  outfit: object | null;
  missingItemIds: string[];      // 코디의 아이템 중 지금 옷장에 없는 id
  createdAt: string;
  updatedAt: string;
}
```

- 응답 키는 17개로 고정이다: `id`, `clientId`, `date`, `timeOfDay`, `title`, `occasion`, `concepts`, `memo`, `place`, `weather`, `weatherSource`, `weatherCheckedAt`, `forecastReady`, `outfit`, `missingItemIds`, `createdAt`, `updatedAt`. 없는 값은 `null`로 온다 (키를 빼지 않는다). `weatherCheckedAt`은 UTC(`2026-10-18T00:00:00Z`)로 바뀌어 돌아온다.
- **PATCH**는 보낸 필드만 바꾼다. 필드를 빼면 그대로이고, `memo`·`place`·`outfit`·`weatherSource`·`weatherCheckedAt`을 `null`로 보내면 비운다. `weather`는 통째로 바꾼다. `clientId`는 바꿀 수 없어 무시한다. 본문이 객체가 아니면 `body INVALID_TYPE`.
- **같은 `clientId`로 POST하면** 새로 만들지 않고 그 예정을 고친다 (이때 개수 상한은 보지 않는다). bulk도 같다.
- `GET /plans`의 `from`·`to` 형식이 틀리면 400(`from`·`to` `INVALID_FORMAT`), `to`가 `from`보다 앞이면 `to OUT_OF_RANGE{min: from}`.
- `memo`는 앞뒤 공백을 지우고 비면 `null`로 저장한다. `title`도 앞뒤 공백을 지운다.

### 2.1 검증 (`PlanRules`, `PlanOutfits`)

오류는 400 `VALIDATION_FAILED`의 `fieldErrors`로 한꺼번에 모아 준다. bulk는 필드 이름에 `items[3].`를 붙인다 (예: `items[3].title`).

| 필드 | 규칙 | 오류 코드 |
|---|---|---|
| `clientId` | 1~64자, `[A-Za-z0-9._:-]`. bulk는 필수. bulk 요청 안에서 중복 금지 | `REQUIRED`, `TOO_LONG{max: 64}`, `INVALID_FORMAT`, `DUPLICATE` |
| `date` | 필수, `YYYY-MM-DD`, **오늘(한국 날짜) 앞뒤 1년**. PATCH에서 날짜를 바꾸지 않았으면 범위를 보지 않는다 (1년 넘게 지난 예정의 메모만 고칠 때) | `REQUIRED`, `INVALID_FORMAT{format: YYYY-MM-DD}`, `OUT_OF_RANGE{min, max}` (`YYYY-MM-DD` 문자열) |
| `timeOfDay` | `AM`·`PM`·`EVENING` | `REQUIRED`, `NOT_ALLOWED{allowed}` |
| `title` | 1~50자 | `REQUIRED`, `TOO_LONG{max: 50}` |
| `occasion` | 위 10개 (코드 테이블 없이 고정) | `REQUIRED`, `NOT_ALLOWED{allowed}` |
| `concepts` | STYLE 코드, 10개까지, 중복 금지. 비활성 코드는 이미 저장된 값만 | `TOO_MANY{max: 10}`, `REQUIRED`(항목이 null), `DUPLICATE`, `NOT_ALLOWED`, `INACTIVE` (`concepts[1]` 꼴) |
| `memo` | 500자까지 | `TOO_LONG{max: 500}` |
| `place` | 있으면 `label` 1~50자, `lat` -90~90, `lon` -180~180, `regionCode`는 REGION 코드 | `REQUIRED`, `TOO_LONG`, `OUT_OF_RANGE`, `NOT_ALLOWED`, `INACTIVE` (`place.label`·`place.lat`·`place.regionCode`) |
| `weather` | 필수. `temp`·`min`·`max` -60~60, `rainProb` 0~100, `cond` `SUNNY`·`CLOUDY`·`RAIN` | `REQUIRED`, `OUT_OF_RANGE{min, max}`, `NOT_ALLOWED` (`weather.temp` 꼴) |
| `weatherSource` | `FORECAST`·`CLIMATE`·`MANUAL` (19 문서 `source`와 같은 말) | `NOT_ALLOWED{allowed}` |
| `weatherCheckedAt` | ISO-8601 시각 | `INVALID_FORMAT{format: ISO-8601}` |
| `outfit` | JSON 16,384자 이하(대략값), 깊이 10 이하. `items` 필수 객체, 칸은 `TOP`·`BOTTOM`·`DRESS`·`OUTER`·`SHOES`·`BAG`, 값은 비지 않은 64자 이하 문자열 | `TOO_LONG{max: 16384}`(`outfit`), `REQUIRED`(`outfit.items`·`outfit.items.TOP`), `INVALID_TYPE`, `NOT_ALLOWED`(`outfit.items.HAT`), `TOO_LONG` |

### 2.2 개수 상한 `PLAN_LIMIT`

- 회원당 500개 (`PlanRules.MAX_PLANS_PER_USER`). 새로 만들 예정이 상한을 넘으면 **409 `PLAN_LIMIT`**, `params.max` = 500. bulk는 하나도 저장하지 않는다.
- 쓰기는 회원별 잠금(`PlanQueryPort.lockUser` = `pg_advisory_xact_lock`, 트랜잭션이 끝나면 풀린다) 안에서 개수를 세고 `clientId` 중복을 확인하므로, 동시에 보내도 상한을 넘지 않고 같은 `clientId`가 두 번 생기지 않는다 (`ux_planned_outfit_client` 부분 유니크 인덱스가 마지막 안전장치).
- bulk에 이미 있는 `clientId`가 섞여 있으면 새로 만드는 수만 센다 (`created`).

### 2.3 `missingItemIds`

`GET`·`POST`·`PATCH`·bulk 응답이 모두 준다. 코디의 아이템 id마다 서버 옷장(`tb_wardrobe_item`)에 **그 회원의 것으로** 있는지 한 번에 묻는다 (`ItemExistenceUseCase.existingIds`, wardrobe 컨텍스트).

- 서버 id(양의 정수 문자열)인데 옷장에 없으면 포함한다 (옷을 완전 삭제한 경우).
- 서버 id가 아닌 값(기기에서 만든 `item-xxxx` 등)은 서버 옷장에 있을 수 없으므로 **항상 포함**한다. 앱은 기기 옷장에 있으면 지운 옷으로 보이지 않는다 (5.4).
- 코디는 지우거나 고치지 않는다. 사용 중지한 옷([13](13_옷_사용_중지.md))은 옷장에 있으므로 포함하지 않는다.

### 2.4 오류 코드

| HTTP | code | 상황 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 위 검증, `GET /plans`의 `from`·`to` |
| 401 | `UNAUTHORIZED` | 토큰 없음 |
| 404 | `NOT_FOUND` | 남의·없는 예정 (PATCH·DELETE) |
| 409 | `PLAN_LIMIT` | 회원당 500개 초과 (`params.max`) |

## 3. DB (Flyway `V14__planned_outfit.sql`)

`tb_planned_outfit`을 지우고 다시 만든다. 조회문은 [14](14_DB_명령.md) 3장 "예정 코디".

| 열 | 내용 |
|---|---|
| `planned_outfit_id` | PK, `BIGINT GENERATED ALWAYS AS IDENTITY` (API의 `id`) |
| `user_id` | 소유 회원. `ON DELETE CASCADE` |
| `client_id` | 앱이 기기에서 만든 예정 id. NULL 가능(서버에서 직접 만든 예정). `(user_id, client_id)` 부분 유니크 `ux_planned_outfit_client WHERE client_id IS NOT NULL` |
| `planned_date` · `time_of_day` | 예정 날짜, `AM`·`PM`·`EVENING` (CHECK) |
| `title` · `occasion` · `memo` | 제목(50), 상황 10종(CHECK), 메모(500) |
| `concepts` | `TEXT[]` 스타일 코드. 코드 테이블로 검증하므로 고정 CHECK는 두지 않는다 |
| `place_region_code` · `place_label` · `place_lat` · `place_lon` | 예정 장소. 네 칸이 함께: 모두 NULL이거나 이름·좌표가 모두 있다 (`ck_planned_outfit_place`, `regionCode`는 선택) |
| `weather` | JSONB 객체 (`ck_planned_outfit_weather`): `{ temp, min, max, rainProb, cond, manual, source, checkedAt }` |
| `forecast_ready` | 예보가 나오면 다시 확인할 필요가 없는지 (19 문서 "예보가 나오면 다시 확인") |
| `outfit` | JSONB 객체 또는 NULL. 앱 `Outfit` 모양 그대로 |
| `created_at` · `updated_at` | 시각 |

인덱스: `ix_planned_outfit_user_date (user_id, planned_date)`. 쓰기는 JPA(`PlanEntity`, `PlanJpaAdapter`), 목록은 MyBatis(`PlanMapper.xml`, `PlanMybatisAdapter`).

**코드 사용처 `PLAN`**: 예정이 쓰는 STYLE·REGION 코드는 삭제할 수 없다 (409 `CODE_IN_USE`, `usages`에 `{ kind: PLAN, count }`). 비활성화는 된다 (`PlanCodeUsageSource` → `PlanMapper.xml`의 `countByCode`·`countUsing`: STYLE은 `concepts`, REGION은 `place_region_code`, [06](06_코드_관리.md)). 관리자 사이트는 사용처에 "예정 코디 N개"로 보인다.

## 5. 앱 동기화 (`mobile/src/lib/planSync.ts`, `planSyncRules.ts`)

규칙(변환·합치기·오류 종류)은 `planSyncRules.ts`의 순수 함수(React Native·스토어를 쓰지 않는다)에 있고, 서버 호출·스토어 반영은 `planSync.ts`에 있다. **게스트·목업 실행(`npm run start:mock`)은 기기만 쓴다.** 동기화는 `authMode === 'account'`이고 세션이 살아 있을 때만 한다 (`canSync`).

### 5.1 기기 id 규칙

| 값 | 내용 |
|---|---|
| 기기 예정 id (`PlannedEvent.id`) | 앱이 만든 id. 서버에는 `clientId`로 올린다 |
| `serverId` | 서버가 준 예정 id. 없으면 아직 서버에 올리지 않은 예정이다 |
| 서버에서 받은 예정의 기기 id | 그 예정의 `clientId`. `clientId`가 없으면(서버에서 직접 만들었거나 다른 경로) `srv-<서버id>`. 기기 id가 이미 쓰이고 있으면 `srv-<서버id>`로 바꾼다 |

### 5.2 동기화 시점

| 시점 | 호출 |
|---|---|
| 로그인·온보딩 직후 | `syncPlans({ force: true })` (`lib/account.ts`) |
| 세션 확인이 끝난 앱 시작, 앱이 다시 활성이 될 때 | `syncPlans()` (`app/_layout.tsx`의 `usePlanSync`, 복귀는 마지막 동기화 후 30초 넘었을 때) |
| 코디 저장·다시 추천 | `savePlan` → 기기에 먼저 저장하고 `pushPlan` |
| 날씨 다시 확인 | `updatePlanWeather` 뒤 `pushPlan` (`lib/placeWeather.ts`) |
| 예정 지우기(캘린더) | `removePlan` |

`syncPlans`는 동시에 여러 번 불러도 한 번만 돌고 throw하지 않는다. 화면을 막지 않는다. 한 번에 하는 일은 이 순서다.

1. 지우기 기록(`planDeletes`) 중 서버 id가 있는 것을 서버에서 지운다. 실패하면 남기고 멈춘다.
2. 서버 id가 없는 예정(날짜가 서버 범위 안, 거절당하지 않은 것)을 `POST /plans/bulk`로 100개씩 올린다 (`clientId` = 기기 id).
3. `GET /plans` 전체를 받아 기기와 합친다 (5.3).
4. 합친 결과의 지울 서버 id를 지우고, 기기 쪽이 최신인 예정을 `PATCH`한다.

### 5.3 합치기 (`mergePlans`)

| 상황 | 결과 |
|---|---|
| 서버에만 있다 (다른 기기에서 만듦) | 기기에 추가 (5.1의 id 규칙) |
| 양쪽에 있고 기기에 보내지 못한 변경이 있으며 기기 `updatedAt`이 서버 `updatedAt`보다 늦다 | 기기 값을 쓰고 다시 보낸다 (`push`) |
| 양쪽에 있고 그 밖의 경우 | 서버 값 |
| 기기에만 있고 `serverId`가 있다 | 서버에서 지워진 것(다른 기기에서 삭제)이라 기기에서도 지운다 |
| 기기에만 있고 `serverId`가 없다 | 아직 올리지 않은 것이라 그대로 둔다 |
| 지우기 기록에 있는 서버 예정 | 기기에 넣지 않고 서버에서 지운다 |

짝 찾기는 `serverId` → 아직 `serverId`가 없는 기기 예정은 `clientId`(= 기기 id) 순이다. 결과는 날짜 → 시간대 순으로 정렬한다.

### 5.4 대기열·지우기 기록·거절

| 상태 | 내용 |
|---|---|
| `pending` | 기기에서 고쳤는데 서버에 아직 못 보냈다 (오프라인·서버 오류). 다음 동기화 때 다시 보낸다. 같은 `clientId`라 중복되지 않는다. `addPlan`·`updatePlanWeather` 같은 스토어 변경이 `updatedAt = 지금`, `pending = true`로 표시한다 |
| `planDeletes` (지우기 기록) | `{ clientId, serverId? }`. 계정 모드에서 지운 예정을 서버에서도 지울 때까지 남긴다. `serverId`가 없으면(올리는 중일 수 있다) 다음 동기화 때 서버 목록에서 `clientId`로 찾아 지운다. 서버에서 이미 없으면(404) 기록만 지운다 |
| `syncBlocked` | 서버가 입력 오류(400)로 거절한 예정. **다시 보내지 않고 기기에만 둔다.** 사용자가 다시 고치면(`touched`) 풀린다. bulk에서 틀린 항목은 오류의 `items[i]` 번호로 찾아 그것만 막고 나머지를 한 번 더 올린다 |
| 보낸 뒤 또 고침 | 응답이 올 때 `updatedAt`이 보낸 값과 다르면 기기 값을 두고 `pending`으로 남긴다 (`applySaved`) |
| 같은 예정을 보내는 중 | 끝난 뒤 한 번 더 보낸다 (`pushAgain`) |
| 다른 계정으로 바뀜 | 응답이 와도 반영하지 않는다 (`currentUserId` 비교) |

### 5.5 오류 처리 (`planErrorKind`)

| 종류 | 기준 | 동작 |
|---|---|---|
| `unsupported` | 405·501, 목록·만들기·bulk에서 404 (예전 서버) | 기기에만 쓰고 10분 동안 다시 묻지 않는다 (`createSupportMemo`) |
| `limit` | 409 `PLAN_LIMIT` | 대기열에 둔다. 코디 저장 화면에 "예정을 서버에 저장하지 못했어요 … 이 예정은 이 기기에만 있어요." 안내를 한 번 보인다. 지난 예정을 지워야 올라간다 |
| `invalid` | 400 `VALIDATION_FAILED` | `syncBlocked` (5.4). 같은 안내 |
| `notFound` | PATCH·DELETE 404 | PATCH가 404면 다른 기기에서 지운 예정이다. 방금 저장한 예정(`recreate`)이면 새로 만들고, 동기화에서 온 것이면 기기에서도 지운다. DELETE 404는 이미 지운 것으로 본다 |
| `retry` | 오프라인·시간 초과·5xx | 대기열에 두고 다음 동기화 때 다시 |

서버가 받는 날짜는 오늘 앞뒤 1년이다 (앱은 하루 여유를 두고 `inServerRange`로 거른다). 범위 밖 예정은 서버에 올리지 않고 기기에만 둔다.

### 5.6 계정 모드에서 지운 옷

기기 옷장에서 옷을 지울 때 게스트는 예정 코디에서도 그 옷을 뺀다. **계정 모드는 빼지 않는다** (`keepPlanRefs`): 서버가 예정을 그대로 두고 `missingItemIds`로 알려 주기 때문에 기기 예정이 서버와 어긋나지 않는다. 캘린더·예정 카드(`OutfitMini`)는 `goneItemIds`(서버가 준 `missingItemIds` + 기기 옷장에 없는 id)로 그 칸을 "지운 옷"으로 흐리게 보인다 (기기에 아직 있으면 흐린 사진, 없으면 빈 칸). 코디를 다시 꾸미는 화면은 옷장에 있는 것만 불러온다 (`app/look/new.tsx`의 `ownedOnly`). 새로 저장한 코디는 지금 옷장으로 고른 것이라 예전 `missingItemIds`를 버린다.

## 6. 관리자 사이트

- 코드 관리의 사용처 표시에 "예정 코디 N개"(`kind: PLAN`)가 보인다 (`admin/src/lib/errorText.ts`의 `codeUsagesText`).
- `PLAN_LIMIT`은 회원 API 코드라 관리자 문구 표에서 `null`(상태별 기본 문구)이다.
- 관리자 사이트에 예정 코디 화면은 없다.

## 7. 확인 내역 (2026-10-18)

- 백엔드 테스트 470개, 하네스 53개 통과. 예정 코디는 `PlanIntegrationTest`(API 전체), `PlanRulesTest`(검증 규칙)가 지킨다.
- 하네스 시나리오 51~53 (원시 HTTP, `harness/src/scenarios/plans.ts`, [harness/README.md](../harness/README.md)): 등록·목록·PATCH·삭제, bulk, 검증·남의 예정·지운 옷.

- 앱 동기화(`planSync.ts`)는 시뮬레이터·실제 휴대폰에서 아직 확인하지 않았다. 단위 점검은 없다.

## 8. 알려진 한계

| 한계 | 내용 |
|---|---|
| 충돌 해결이 단순하다 | 마지막에 고친 쪽(`updatedAt`)이 이긴다. 필드별로 합치지 않는다. 두 기기가 같은 예정을 서로 다른 값으로 고치면 늦은 쪽이 덮는다 |
| 기기 시계에 기대한다 | `updatedAt` 비교에 기기 시각을 쓴다. 기기 시계가 크게 틀리면 오래된 값이 이길 수 있다 |
| 범위 밖 날짜는 기기에만 | 오늘 앞뒤 1년 밖의 예정은 서버에 올리지 않는다 |
| 상한 500개 | 넘으면 올라가지 않고 대기열에 남는다. 앱이 지난 예정을 대신 지워 주지는 않는다 |
| `missingItemIds`에 기기 id | 기기에서만 만든 옷 id(`item-xxxx`)는 서버가 항상 "없음"으로 센다. 앱이 기기 옷장과 맞춰 본다 |
| 코디 내용은 검증하지 않는다 | `outfit`은 `items`의 칸 이름과 id 모양만 본다. 점수·이유 같은 앱 값은 그대로 저장한다 |
| 동기화 실패는 조용하다 | 오프라인 등 일시 오류는 사용자에게 알리지 않고 다음 동기화 때 다시 한다. `limit`·`invalid`만 안내한다 |
| 관리자 화면 없음 | 회원의 예정을 보거나 고치는 관리자 화면은 없다 (DB 조회는 14 문서) |
