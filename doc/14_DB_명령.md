# 14. DB 명령 모음 (로컬 PostgreSQL)

> 로컬 개발 DB를 들여다보고 고칠 때 쓰는 명령. 2026-10-18 기준 스키마(Flyway V1~V17·V20~V23 — V15 관리자 2단계 인증 `tb_user_mfa`·`tb_user_mfa_recovery_code`, V16 로그인 이력 종류 4개 추가, V17 푸시 토큰 `tb_push_token`·`tb_push_send_log`, V20 옷 보조 색·구입일·초봄/초여름/초가을 코드, V21 나의 정보 칸·코드 3그룹, V22 날씨 이력 `tb_weather_daily_history`, V23 테이블·컬럼 코멘트; 앞의 V1~V14는 6차에서 V8 앱 설정·V9 옷 사용 중지, 7차에서 V10 로그인 세션을 Valkey로·로그인 이력 `tb_auth_event`를 더함, V11 날씨, V12 옷 사진 `tb_item_image`, V13 장소별 날씨 `tb_weather_place_snapshot`·`tb_weather_climate`, V14 예정 코디 `tb_planned_outfit`을 다시 만듦). 조회문은 모두 실제로 돌려 확인했다 (2026-10-18 20시대, V21까지 적용된 로컬 DB).
> Refresh 토큰·로그인 세션은 7차부터 DB가 아니라 **Valkey**(`wearly-valkey`)에 있다 → 7장.
> 옷 사진 파일은 DB가 아니라 **MinIO**(`wearly-minio`)에 있고 DB에는 메타데이터(`tb_item_image`)만 있다 → 3장 "옷 사진", 8장.

### 옷 사진 (18 문서)

사진 파일은 오브젝트 스토리지에 있고 `tb_item_image`에는 상태·크기·오브젝트 키만 있다. 상태는 `PENDING`(URL만 받음)·`READY`(처리 끝)·`DELETED`(버림, 정리 작업이 지움).

```sql
-- 상태별 사진 수
select status, count(*) from tb_item_image group by status order by status;

-- 회원별 사진 수·상태와 저장 용량(READY의 original.jpg 크기 합)
select u.email,
       count(g.*) filter (where g.status = 'READY')   as ready,
       count(g.*) filter (where g.status = 'PENDING') as pending,
       count(g.*) filter (where g.status = 'DELETED') as deleted,
       coalesce(sum(g.size_bytes) filter (where g.status = 'READY'), 0) as bytes
from tb_user u left join tb_item_image g using (user_id)
group by u.email order by ready desc, u.email;

-- 사진이 붙은 옷 (최근 처리 순)
select i.item_id, i.name, g.image_id, g.width, g.height, g.size_bytes,
       g.ready_at at time zone 'Asia/Seoul' as ready
from tb_wardrobe_item i join tb_item_image g on g.item_id = i.item_id
where g.status = 'READY'
order by g.ready_at desc limit 20;

-- 서버에 사진이 없는 옷 (기기에만 있거나 사진 없음)
select i.item_id, i.name, u.email
from tb_wardrobe_item i join tb_user u using (user_id)
where not exists (select 1 from tb_item_image g where g.item_id = i.item_id and g.status = 'READY')
order by i.item_id limit 20;

-- 오늘(한국 시간) 회원별 업로드 URL 발급 수 (하루 한도 daily-upload-limit 계산과 같은 기준, 상태 무관)
select u.email, count(*) as issued_today
from tb_item_image g join tb_user u using (user_id)
where (g.created_at at time zone 'Asia/Seoul')::date = (now() at time zone 'Asia/Seoul')::date
group by u.email order by 2 desc;

-- 정리 작업이 지울 대상 (아이템에 안 붙고 1일 넘은 PENDING·DELETED·READY)
select image_id, user_id, status, created_at at time zone 'Asia/Seoul' as created, ready_at at time zone 'Asia/Seoul' as ready
from tb_item_image
where item_id is null
  and ((status in ('PENDING', 'DELETED') and created_at < now() - interval '1 day')
    or (status = 'READY' and ready_at < now() - interval '1 day'))
order by created_at limit 20;

-- 한 사진의 저장소 키 (MinIO에서 찾을 때, 8장)
select image_id, object_key, thumb_key from tb_item_image where status = 'READY' limit 3;
```

### 날씨 (17·19 문서)

```sql
-- 지역별 최신 저장값 (17개 시·도, 주기 수집). 받은 적 없으면 fetched가 비어 있다
select region_code, provider_code, fetched_at at time zone 'Asia/Seoul' as fetched, last_error
from tb_weather_snapshot order by region_code;

-- 공급자 상태와 최근 실행
select provider_code, enabled, priority, consecutive_failures, circuit_reason,
       last_success_at at time zone 'Asia/Seoul' as last_ok
from tb_weather_provider;
select run_id, trigger_type, status, success_count, fail_count, started_at at time zone 'Asia/Seoul' as started
from tb_weather_refresh_run order by run_id desc limit 5;

-- REGION 밖 장소의 예보 캐시 (장소별 날씨, 격자 키 = 소수 첫째 자리). 3시간 안이면 cache_fresh = t (그 안에는 공급자를 부르지 않는다)
select grid_key, label, jsonb_array_length(days) as days,
       days->0->>'date' as first_day, days->-1->>'date' as last_day,
       fetched_at at time zone 'Asia/Seoul' as fetched, last_error,
       now() - fetched_at < interval '3 hours' as cache_fresh
from tb_weather_place_snapshot order by fetched_at desc;

-- 평년값이 계산된 격자 (격자마다 12개월을 한 번에 넣는다)
select grid_key, count(*) as months, min(years) as years, min(source) as source,
       min(computed_at) at time zone 'Asia/Seoul' as computed
from tb_weather_climate group by grid_key order by grid_key;

-- 한 격자의 월별 평년값 (비 온 날 비율은 %). 서울 시청 격자는 37.6,127.0
select month, temp_avg, temp_min, temp_max, round((rain_day_ratio * 100)::numeric) as rain_pct, years, source
from tb_weather_climate where grid_key = '37.6,127.0' order by month;

-- 이번 달 호출 종류별 횟수 (FORECAST 주기 수집 · ON_DEMAND 좌표 예보 · SEARCH 장소 검색 · CLIMATE 평년값 자료)
select call_kind, provider_code, count(*) as calls, count(*) filter (where not success) as failed
from tb_weather_call_log where called_at >= date_trunc('month', now()) group by 1, 2 order by 1, 2;

-- 실행 밖 호출 (run_id가 없다): 좌표 예보·평년값 자료. 격자 키가 region_code 칸에 들어 있다
select called_at at time zone 'Asia/Seoul' as at, call_kind, provider_code, region_code, success, error_code
from tb_weather_call_log where run_id is null and call_kind in ('ON_DEMAND', 'CLIMATE')
order by called_at desc limit 20;
```

- 평년값은 `computed_at`이 400일을 넘으면 서버가 다시 계산한다. 값을 새로 받게 하려면 그 격자의 행을 지운다: `delete from tb_weather_climate where grid_key = '37.6,127.0'` (다음 요청에서 Open-Meteo를 다시 부른다).
- 장소 캐시를 비우려면 `delete from tb_weather_place_snapshot where grid_key = '...'`. 다음 좌표 요청이 공급자를 한 번 부르고 회원 하루 한도(Valkey, 7장)를 쓴다.

### 예정 코디 (21 문서)

```sql
-- 최근 예정 20개와 주인 (client_id가 있으면 앱이 기기 id로 올린 것, 없으면 서버에서 직접 만든 것)
select p.planned_outfit_id, u.email, p.planned_date, p.time_of_day, p.title, p.occasion, p.concepts, p.client_id
from tb_planned_outfit p join tb_user u using (user_id)
order by p.planned_date desc, p.planned_outfit_id desc limit 20;

-- 회원별 예정 수와 기간 (회원당 상한 500개, 넘으면 409 PLAN_LIMIT)
select u.email, count(*) as plans, count(p.client_id) as with_client_id, min(p.planned_date) as first_day, max(p.planned_date) as last_day
from tb_planned_outfit p join tb_user u using (user_id) group by u.email order by plans desc;

-- 한 회원의 남은 자리 (500 - 지금 개수)
select user_id, count(*) as plans, 500 - count(*) as room from tb_planned_outfit group by user_id order by plans desc limit 10;

-- 장소와 날씨 (weather는 JSONB: temp·min·max·rainProb·cond·manual·source·checkedAt). 장소가 없으면 '내 지역'
select planned_outfit_id, title, coalesce(place_label, '(내 지역)') as place, place_region_code,
       weather->>'cond' as cond, weather->>'temp' as temp, weather->>'source' as src, weather->>'checkedAt' as checked, forecast_ready
from tb_planned_outfit order by planned_outfit_id desc limit 10;

-- 코디의 칸별 아이템과 옷장에 없는지 (missing = t 이면 API 응답의 missingItemIds에 들어간다.
-- 숫자가 아닌 id(기기에서 만든 item-xxxx)는 서버 옷장에 없으므로 항상 missing)
select p.planned_outfit_id, p.title, s.key as slot, s.value as item_id, (i.item_id is null) as missing
from tb_planned_outfit p
cross join lateral jsonb_each_text(p.outfit->'items') as s
left join tb_wardrobe_item i on i.user_id = p.user_id and i.item_id::text = s.value
where p.outfit is not null order by p.planned_outfit_id, s.key;

-- 예정이 쓰는 스타일(STYLE 코드)별 개수. 이 코드는 삭제할 수 없고(CODE_IN_USE, kind PLAN) 비활성화만 된다
select c as style, count(*) from tb_planned_outfit, unnest(concepts) as c group by c order by 2 desc, 1;
```

- 위 조회문은 임시 회원·옷·예정을 넣고 돌린 뒤 `rollback`해 모양과 결과를 확인했다 (로컬 DB는 그대로).
- 예정을 SQL로 고치거나 지우지 않는다. 앱이 서버 id(`planned_outfit_id`)와 기기 id(`client_id`)로 짝을 맞추므로 행을 지우면 앱이 다음 동기화 때 서버에서 없어진 것으로 보고 기기에서도 지운다. 지우려면 앱에서 지우거나 `DELETE /api/v1/plans/{id}`.
- 회원을 지우면 그 회원의 예정은 `ON DELETE CASCADE`로 같이 지워진다.

### 관리자 2단계 인증·로그인 기록 (22 문서 4.1)

```sql
-- 관리자와 2단계 인증 등록 현황 (남은 복구 코드 수 포함). TOTP 비밀 암호문은 조회해도 의미가 없고 보여 주지 않는다
select u.user_id, u.role, (m.user_id is not null) as mfa_enrolled,
       m.enrolled_at at time zone 'Asia/Seoul' as enrolled,
       (select count(*) from tb_user_mfa_recovery_code r where r.user_id = u.user_id and r.used_at is null) as codes_left
from tb_user u left join tb_user_mfa m using (user_id)
where u.role = 'ADMIN' order by u.user_id;

-- 로그인 이력 종류별 건수 (LOGIN·LOGOUT·REFRESH_REUSED·FORCED_LOGOUT + V16의 LOGIN_FAILED·MFA_SUCCESS·MFA_FAILED·MFA_LOCKED)
select type, count(*) from tb_auth_event group by type order by count(*) desc;

-- 비밀번호 실패·2단계 인증 결과만 최근순 (관리자 화면 "관리자 로그인 기록"과 같은 표)
select e.created_at at time zone 'Asia/Seoul' as at, e.type, e.user_id, e.client, e.ip
from tb_auth_event e
where e.type in ('LOGIN_FAILED', 'MFA_SUCCESS', 'MFA_FAILED', 'MFA_LOCKED')
order by e.created_at desc limit 20;

-- 관리자 계정 보완 관련 변경 이력
select action, count(*) from tb_admin_audit_log
where action in ('ADMIN_BOOTSTRAP_CREATE', 'ADMIN_PASSWORD_CHANGE', 'ADMIN_MFA_ENROLL', 'ADMIN_MFA_RESET', 'USER_MFA_RESET', 'USER_ROLE_CHANGE')
group by action;
```

**휴대폰도 복구 코드도 잃은 혼자뿐인 관리자** (22 문서 4.1.7): 그 회원의 2단계 인증 행을 지우고 다시 로그인해 등록한다. 되돌릴 수 없으니 `user_id`를 먼저 확인한다 (이 두 줄은 실제로 실행해 보지 않았다. 위 조회문만 로컬 DB에서 돌려 확인했다).

```sql
delete from tb_user_mfa where user_id = 4;
```

## 4. 데이터 고치기

> **관리자 사이트나 API로 할 수 있는 일은 그쪽으로 한다.** SQL로 직접 고치면 변경 이력이 남지 않고, 서버의 코드·키 캐시가 바로 갱신되지 않는다(코드를 SQL로 바꿨다면 백엔드를 재시작). 고치기 전에 `begin;`으로 시작해 결과를 보고 `commit;` 또는 `rollback;` 한다.

```sql
begin;
-- 여기서 update / delete
select ...;   -- 결과 확인
commit;       -- 문제 있으면 rollback;
```

### 2026-10-17에 실제로 한 수정

```sql
-- 깨진 관리자 이름 바로잡기 (.env를 properties(ISO-8859-1)로 읽던 때 만들어진 계정)
update tb_user set name = '관리자', updated_at = now()
where email = 'admin@wearly.app';

-- 원피스 코드가 생기기 전에 등록돼 '하의·스커트'로 들어간 원피스를 원피스로

update tb_wardrobe_item set sub_type = 'SWEATSHIRT', updated_at = now()

```

옷을 고친 뒤에는 앱을 다시 열어야(또는 다시 로그인) 기기의 옷장이 서버 값으로 맞춰진다.

### 그 밖에 쓸 만한 것

`tb_item_image` 행이나 사진 객체는 직접 지우지 않는다. 행만 지우면 저장소에 객체가 남고(정리 작업이 행을 기준으로 찾는다), 객체만 지우면 DB가 없는 파일을 가리킨다. 사진은 앱에서 빼거나 옷을 완전 삭제하면 서버가 둘 다 지운다.

비밀번호 해시(`tb_user_local_credential.password_hash`), 웹 입력 키 암호문(`tb_ai_provider_secret.ciphertext`)은 직접 고치지 않는다. 키는 관리자 사이트의 AI 공급자 화면에서 넣고 지운다.

## 7. Valkey (로그인 세션 · Refresh 토큰 · 날씨 키)

7차(2026-10-17)부터 Refresh 토큰과 로그인 세션은 Valkey에 있다. 키 구조는 [16_세션_Valkey.md](16_세션_Valkey.md) 3장. 시각 값은 epoch 밀리초.

| 항목 | 값 |
|---|---|
| 컨테이너 | `wearly-valkey` (`docker compose up -d valkey`) |
| 호스트 접속 | `localhost:6380` (컨테이너 안은 6379), 비밀번호 없음 |
| DB 번호 | 개발 서버 `0`, 하네스 `1`(실행할 때마다 비움), 백엔드 테스트는 Testcontainers 따로 |
| 저장 | AOF 켬, 볼륨 `wearly-valkeydata` (재시작해도 로그인이 남는다) |

```bash
# 대화형 접속 (하네스 데이터는 -n 1)
docker exec -it wearly-valkey valkey-cli
docker exec -it wearly-valkey valkey-cli -n 1

# 줄임말 (~/.zshrc)
alias wkv='docker exec -it wearly-valkey valkey-cli'
```

`KEYS` 명령은 쓰지 않는다(키가 많으면 서버를 멈춘다). 목록은 인덱스(`wearly:sessions`)나 `--scan`으로 본다.

```text
# 살아 있는 세션 수 (만료된 멤버는 서버가 목록을 읽을 때 정리하므로 조금 많을 수 있다)
ZCARD wearly:sessions

# 최근 활동한 세션 10개 (score = lastSeenAt, epoch 밀리초)
ZREVRANGE wearly:sessions 0 9 WITHSCORES

# 세션 하나: userId, currentHash, client, userAgent, ip, createdAt, lastRefreshAt, lastSeenAt
HGETALL wearly:session:<sessionId>
TTL wearly:session:<sessionId>            # 남은 초 (Refresh 수명, 회전마다 연장)

# 한 회원의 세션 ID들 (userId는 tb_user.user_id)
SMEMBERS wearly:user:<userId>:sessions

# Refresh 토큰 상태: userId, sessionId, status(ACTIVE·ROTATED·REVOKED), replacedBy, createdAt
HGETALL wearly:rt:<currentHash>

# 세션 키 훑어보기 (KEYS 대신)
SCAN 0 MATCH wearly:session:* COUNT 100

# DB별 키 수
INFO keyspace
```

```bash
# 셸에서 한 줄로: 가장 최근 세션의 내용
docker exec wearly-valkey valkey-cli HGETALL "wearly:session:$(docker exec wearly-valkey valkey-cli ZREVRANGE wearly:sessions 0 0)"

# 하네스 Valkey(DB 1)만 비우기 (개발 DB 0은 그대로)
docker exec wearly-valkey valkey-cli -n 1 FLUSHDB
```

- 로그인을 끊을 때는 키를 직접 지우지 말고 관리자 사이트의 '로그인 사용자' 화면(또는 `DELETE /api/v1/admin/sessions/{sessionId}`·`/admin/users/{id}/sessions`)을 쓴다. 직접 `DEL wearly:session:<id>`만 하면 그 세션은 막히지만 인덱스·회원 집합·Refresh 토큰 상태와 이력(`tb_auth_event`·변경 이력)이 맞지 않는다.
- 모든 로그인을 한꺼번에 끊으려면(로컬에서만) `docker exec wearly-valkey valkey-cli -n 0 FLUSHDB`. 모든 기기가 다시 로그인해야 한다.

### 관리자 2단계 인증 키 (22 문서 4.1.4)

`docker exec wearly-valkey valkey-cli --scan --pattern 'wearly:mfa:*'`로 훑어본다 (2026-10-18에 실제로 돌려 확인 — 로그인 대기·등록·잠금이 없는 평소에는 키가 없다).

| 키 | 값 · 수명 | 내용 |
|---|---|---|
| `wearly:mfa:pending:<토큰 SHA-256>` | JSON, 5분 | 비밀번호가 맞고 2단계 인증을 기다리는 관리자 로그인 (MFA 대기 토큰). 원문 토큰은 어디에도 없다 |
| `wearly:mfa:setup:<userId>` | 암호화한 문자열, 10분 | 등록 시작(setup)에서 만든 TOTP 비밀. 코드를 확인하면 DB(`tb_user_mfa`)로 옮긴다 |
| `wearly:mfa:fail:<userId>` | 숫자 카운터, 마지막 실패에서 15분 | 틀린 횟수. 5가 되면 잠근다 |
| `wearly:mfa:lock:<userId>` | 문자열, 15분 | 잠금. 있는 동안 `MFA_LOCKED` (바로 풀어야 하면 `fail`·`lock` 둘 다 `DEL`) |

### 날씨 키 (17·19 문서)

`docker exec wearly-valkey valkey-cli --scan --pattern 'wearly:weather:*'`로 훑어본다 (2026-10-18에 실제로 돌려 확인).

| 키 | 값 · 수명 | 내용 |
|---|---|---|
| `wearly:weather:refresh:lock` | 문자열, 300초 | 주기 수집 잠금(한 번에 하나만 돈다). 평소엔 없다 |
| `wearly:weather:lock:place:<격자>` | 문자열, 60초 | 같은 격자의 좌표 예보를 한 요청만 받게 하는 잠금. 평소엔 없다 |
| `wearly:weather:lock:climate:<격자>` | 문자열, 60초 | 같은 격자의 평년값을 한 번만 계산하게 하는 잠금. 평소엔 없다 |
| `wearly:weather:usage:<ON_DEMAND\|SEARCH>:<날짜>:<userId>` | 숫자 카운터, 2일 | 회원의 그날(한국 날짜) 좌표 예보 호출 수(한도 30)·검색 호출 수(한도 100). 공급자를 실제로 부를 때만 오른다 |
| `wearly:weather:search:v3:<검색어>` | JSON 문자열, 1일 | 장소 검색 결과 캐시(소문자·공백 정리한 검색어). `v3`이 지금 형식이고 `v2`·접두사 없는 키는 예전 형식이라 쓰이지 않고 수명이 지나면 사라진다 |

```bash
# 검색 캐시 하나와 남은 수명(초)
docker exec wearly-valkey valkey-cli GET "wearly:weather:search:v3:부산"
docker exec wearly-valkey valkey-cli TTL "wearly:weather:search:v3:부산"

# 오늘 회원별 사용량 (userId는 tb_user.user_id)
docker exec wearly-valkey valkey-cli --scan --pattern 'wearly:weather:usage:*'
docker exec wearly-valkey valkey-cli GET "wearly:weather:usage:ON_DEMAND:2026-10-18:3"

# 검색 캐시만 비우기 (정렬 규칙을 바꾼 뒤 등. 키가 없으면 DEL 인자 오류가 나니 먼저 --scan으로 있는지 본다. 다음 검색은 공급자를 다시 부르고 한도를 쓴다)
docker exec wearly-valkey valkey-cli --scan --pattern 'wearly:weather:search:*' | xargs docker exec wearly-valkey valkey-cli DEL
```

## 8. MinIO (옷 사진 파일)

사진 파일은 MinIO(`pgsty/minio` 포크, 18 문서)에 있다. 키 구조는 [18_사진_저장.md](18_사진_저장.md) 5장.

| 항목 | 값 |
|---|---|
| 컨테이너 | `wearly-minio` (`docker compose up -d minio minio-init`) |
| S3 API · 웹 콘솔 | `localhost:9000` · http://localhost:9001 |
| 계정 | `wearly` / `wearly-minio-local` (로컬 전용) |
| 버킷 | `wearly-images`(개발 서버, 비공개), `wearly-images-harness`(하네스, 실행할 때마다 비운다) |
| 저장 | 볼륨 `wearly-miniodata` (재시작해도 남는다) |

`wearly-minio-init`은 버킷을 만들고 끝난 컨테이너(Exited 0)라 `docker exec`가 안 된다. 실행 중인 `wearly-minio` 컨테이너 안에 `mc`가 있어 이걸 쓴다 (`docker exec wearly-minio mc`로 확인했다).

```bash
# 목록·용량 (alias는 명령마다 만든다. 컨테이너 안이라 주소는 localhost:9000)
docker exec wearly-minio sh -c "mc alias set l http://localhost:9000 wearly wearly-minio-local >/dev/null; mc ls l"
docker exec wearly-minio sh -c "mc alias set l http://localhost:9000 wearly wearly-minio-local >/dev/null; mc ls --recursive l/wearly-images | head"
docker exec wearly-minio sh -c "mc alias set l http://localhost:9000 wearly wearly-minio-local >/dev/null; mc du l/wearly-images"
docker exec wearly-minio sh -c "mc alias set l http://localhost:9000 wearly wearly-minio-local >/dev/null; mc anonymous get l/wearly-images"   # private이어야 한다

# 같은 일을 별도 컨테이너로 (compose 네트워크 wearly_default 안에서 minio:9000으로)
docker run --rm --network wearly_default --entrypoint sh pgsty/mc:RELEASE.2026-09-16T00-00-00Z \
  -c "mc alias set l http://minio:9000 wearly wearly-minio-local >/dev/null && mc ls l"
```

- 웹 콘솔(http://localhost:9001)에서 위 계정으로 로그인하면 버킷과 객체를 볼 수 있다.
- 한 회원의 사진은 `users/{userId}/items/` 아래에 있다 (`userId`는 `tb_user.user_id`). `uploads/{userId}/`에 남은 객체는 올리다 만 것이다 (정리 작업이 지운다).
- 하네스 버킷만 비우기: `cd harness && ./run.sh --db-only` (DB·Valkey DB 1과 함께 비운다).
- ⚠️ 객체를 `mc rm`으로 직접 지우면 `tb_item_image` 행이 없는 파일을 가리켜 앱에서 사진이 안 뜬다. 개발 데이터를 한꺼번에 비울 때만 `docker compose down -v`로 DB와 함께 지운다.
