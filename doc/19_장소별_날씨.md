## 1. 배경과 결정

- 지금까지 날씨는 기기에 저장한 지역 하나 기준이었다(17 문서 5장). 출장·여행·지방 예식처럼 **다른 날, 다른 곳**의 코디는 맞출 수 없었다. 기획서 p.16 예정일 코디(PLAN A LOOK)는 날씨 예보를 붙이고 D-1에 다시 확인하게 되어 있다.
- 17의 원칙 "사용자 요청마다 외부 API를 부르지 않는다"는 **REGION(시·도 17개)에는 그대로** 둔다. REGION 밖 장소만 요청 시점 호출 + 격자 캐시 + 회원별 하루 한도로 절충한다(5장).

| 결정 | 내용 |
|---|---|
| 장소 | `place = { regionCode?, label, lat, lon }`. 시·도는 `regionCode`, 그 밖은 검색 결과의 좌표 |
| 날씨 출처 | 예보 범위 안 `FORECAST`, 밖 `CLIMATE`(그 달 평년값), 사용자가 체감 온도를 직접 고르면 `MANUAL`(서버가 만들지 않고 앱이 표시) |
| 평년값 자료 | Open-Meteo 과거 기상 API(키 없음). 지난 10개 완결 연도로 직접 계산해 DB에 저장 |
| 장소 검색 | 시·도 이름 → **전국 시·군·구 268곳 자료**(해운대·분당·부산 중구 같은 구·시·군 단위) → Open-Meteo 지오코딩(한글 검색어·한글 이름). 꺼지거나 실패하면 날씨 공급자(WeatherAPI) 검색(영어 이름) |
| 예정 코디 저장 | 이 문서를 만들 때는 **기기에만** 저장했다. 그 뒤 서버 저장을 만들었다 → [21_예정_코디_저장.md](21_예정_코디_저장.md) |
| 기존 API | `GET /api/v1/weather?region=`은 그대로(앱 홈이 쓴다) |

## 2. 구조 한눈에

```
앱 PLAN 모드 (장소 + 날짜) ─ GET /weather/day ─┬ region 방식: 저장된 스냅샷(tb_weather_snapshot)만 읽는다
                                               └ lat/lon 방식: 격자 캐시(tb_weather_place_snapshot) → 오래됐으면 공급자 한 번
                                                  └ 예보에 그 날짜가 있으면 FORECAST
                                                  └ 없으면 CLIMATE (tb_weather_climate, 없으면 Open-Meteo에서 계산)
앱 장소 고르기 ─── GET /weather/places ─── 시·도 이름 맞추기 → 시·군·구 자료(268곳) → Open-Meteo 지오코딩 → (실패 시) WeatherAPI 검색
```

## 3. `GET /api/v1/weather/day`

`?region=SEOUL&date=2026-10-25` 또는 `?lat=35.68&lon=139.69&date=2026-10-25`.

| 방식 | 인증 | 설명 |
|---|---|---|
| region | 공개 | 틀리거나 만료된 토큰이 같이 와도 무시한다(보안 설정의 토큰 해석에서 제외). `region`이 없으면 서울 |
| lat/lon | 로그인 필요 | `lat`·`lon` 중 **하나라도** 있으면 좌표 방식이다. 토큰이 없으면 입력 검증보다 먼저 401 `UNAUTHORIZED` |

**검증** (오류는 400 `VALIDATION_FAILED`, `fieldErrors`의 `field`·`code`·`params`. 문장은 없다, 20 문서):

| field | 조건 | 필드 오류 코드 |
|---|---|---|
| `date` | 필요, `YYYY-MM-DD`, 오늘(한국 날짜)부터 1년 안. 과거·1년 넘음·형식 오류 | `REQUIRED`, `INVALID_FORMAT{format: YYYY-MM-DD}`, `OUT_OF_RANGE{min, max}`(둘 다 `YYYY-MM-DD` 문자열) |
| `region` | 활성 REGION 코드만. 좌표 방식에서는 `region`을 함께 보낼 수 없다 | `NOT_FOUND`(없는 지역), `CONFLICT`(좌표와 함께 보냄) |
| `lat` · `lon` | 필요, `lat`은 -90~90, `lon`은 -180~180 | `REQUIRED`, `OUT_OF_RANGE{min, max}` |
| `q` (장소 검색) | 필요, 50자까지 | `REQUIRED`, `TOO_LONG{max: 50}` |

**응답 200**: 키 7개가 항상 있다(없는 값은 `null`).

```json
{
  "place": { "regionCode": "SEOUL", "label": "서울", "lat": 37.5665, "lon": 126.978 },
  "date": "2026-11-27",
  "source": "CLIMATE",
  "day": { "temp": 5.9, "min": 1.1, "max": 10.8, "rainProb": 20, "cond": null, "condText": null },
  "forecastUntil": "2026-10-20",
  "fetchedAt": "2026-10-18T08:24:10.286Z",
  "climate": { "years": "2016-2025", "rainDayRatio": 0.2 }
}
```

- `place`: region 방식은 REGION 코드의 이름·좌표. **좌표 방식은 `regionCode`가 `null`이고 `lat`·`lon`은 격자 좌표(소수 첫째 자리)**, `label`은 공급자가 알려 준 이름(영어, 예: `Tokyo`)이다. 앱은 검색할 때 받은 한글 `label`을 따로 저장해 쓰므로 이 `label`은 화면에 쓰지 않는다. 공급자 이름은 주지 않는다.
- `source`: `FORECAST` · `CLIMATE`. 기온은 섭씨 소수 첫째 자리, `cond`는 `SUNNY`·`CLOUDY`·`RAIN`.
- `forecastUntil`: 그 장소 예보의 마지막 날짜(예보가 없으면 `null`). 앱이 "N일 뒤부터 예보가 나와요"를 계산한다.
- `fetchedAt`: `FORECAST`면 예보를 받은 시각, `CLIMATE`면 평년값을 계산한 시각.
- `climate`: `CLIMATE`일 때만 `{ years, rainDayRatio }`(소수 둘째 자리), 아니면 `null`.

**답을 정하는 순서**: (1) 그 장소 예보에 `date`가 있으면 `FORECAST`. (2) 없으면 `CLIMATE`. (3) 둘 다 못 구하면 오류.

| 상황 | 응답 |
|---|---|
| 좌표 방식인데 회원 하루 한도(5장)를 넘어 공급자를 못 불렀고 캐시도 평년값도 없음 | 429 `WEATHER_LIMIT` `params.kind = ON_DEMAND` |
| 그 밖에 예보도 평년값도 없음(공급자 차단·키 없음·평년값 끔·평년값 받기 실패) | 503 `WEATHER_UNAVAILABLE` (`params` 없음. 앱은 체감 온도를 직접 고른다) |

## 4. `GET /api/v1/weather/places?q=` (장소 검색)

로그인 필요. `q`는 1~50자(공백 정리, 소문자로 바꿔 캐시 키로 쓴다). 응답 `{ items: [{ label, region, country, lat, lon, regionCode, parentRegionCode }] }`, 최대 10개. `parentRegionCode`는 시·군·구 결과의 상위 시·도 REGION 코드이고 그 밖의 결과는 `null`이다. 빈 검색어·51자 이상은 400 `VALIDATION_FAILED`(`q`).

처리 순서:

1. **시·도 이름 맞추기** (`KoreanRegionNames`): 검색어가 활성 REGION의 `label`·정식 이름·별칭(서울특별시·서울시·제주도 …)과 같거나, 두 글자 이상이고 그 앞부분(서울특 → 서울특별시, 충청 → 충북·충남)이면 그 지역을 **맨 앞**에 넣는다. 광주시는 경기도 광주시와 겹쳐 별칭에서 뺐다. 지오코딩이 "서울"·"제주"를 못 찾고 "부산"·"대구"·"인천"은 같은 이름의 작은 마을만 주기 때문이다. 이 단계에 맞았으면 한도 초과·공급자 실패여도 그 지역은 돌려준다.
1-2. **시·군·구 자료** (`KoreanDistricts`, 아래 "시·군·구 자료"): 시·도 이름 맞추기 다음, 지오코딩 전에 자료 파일의 시·군·구에 맞춘다. 맞은 곳은 시·도 결과 바로 뒤에 넣는다(맞춘 시·도와 같은 격자인 곳은 뺀다. 예: 제주 → 제주시). 이름 그대로이거나 줄기 이름으로 맞았으면(해운대구·해운대·분당) **지오코딩을 부르지 않는다** — 지오코딩은 구 이름에 공원·시설이나 다른 지역의 같은 이름 마을만 주고, 부르면 회원의 하루 검색 한도만 줄어든다. 앞부분만 맞은 검색어(해운·일산)는 지오코딩도 부른다. 시·군·구와 맞았으면 한도 초과·공급자 실패여도 그 결과는 돌려준다.
2. **Open-Meteo 지오코딩** `GET {base}/v1/search?name=…&language=ko&count=10&format=json`: 한글 검색어와 한글 이름(도쿄 → "도쿄 · 도쿄 도 · 일본").
3. **국내 결과 거르기·정렬** (`PlaceSearchRules`): 한글 검색어면 이름에 한글이 없는 국내 결과(로마자 'Pusan' 등)는 뺀다. 정렬은 한국의 행정 중심·인구 있는 곳 → 행정 중심(PPLC·PPLA…) → 도시·마을 → 공항·공원·산 같은 시설·자연, 같은 순위 안에서는 인구 순.
4. **국내 지명 보정**: 지오코딩은 "강릉"으로 찾으면 북한의 '강릉' 마을만 주고 "강릉시"로 찾아야 강원도 강릉시를 준다. 그래서 한글 검색어가 시·군·구·읍·면·동으로 끝나지 않고 결과에 한국의 행정 중심·인구 있는 곳도, 큰 해외 도시(PPLC·PPLA)도 없으면 "시" → "군"을 붙여 더 찾는다(최대 2번 더, 원래 검색까지 3번 호출, 한국 행정 중심이 나오면 멈춤). 시·도 이름과 맞은 검색어는 보정하지 않는다.
5. **중복 제거·개수 제한**: 같은 격자(`GridKey`)는 앞의 것만, 맞춘 시·도와 같은 곳(같은 격자이거나 30km 안의 행정 중심)도 뺀다. 최대 10개.
6. **`regionCode`**: 30km 안의 가장 가까운 REGION 코드를 붙이되 **행정 중심·인구 있는 곳에만** 붙인다(작은 마을에는 안 붙임). 시·도 이름으로 맞춘 지역은 그 코드가 붙는다. 그 밖은 `null`.
7. **지오코딩이 꺼져 있거나 첫 호출이 실패하면** 날씨 공급자(WeatherAPI) `search.json`으로 대신한다(영어 이름). 이 결과는 캐시하지 않는다(다음 검색에서 다시 한글로).

**시·군·구 자료** (2026-10-18, `4d65280`)

- 파일 `backend/src/main/resources/data/korea-districts.json`: 시·군·구 **268곳** `{ name, fullName, city, regionCode, lat, lon, approx, via }`. 서버는 실행 중에 이 파일만 읽고(`DistrictFileAdapter`, 포트 `DistrictCatalogPort`) 외부를 부르지 않는다. 일반구(성남시 분당구, 포항시 남구 …)는 `city`에 상위 시를 둔다.
- 생성 스크립트 `backend/scripts/build-districts.py`: 사람이 가끔(행정구역이 바뀔 때) 돌려 결과 JSON을 커밋한다. **테스트에서 실행하지 않는다.** Open-Meteo 지오코딩(키 없음)으로 정식 이름("해운대구") → 줄기 이름("해운대") → 힌트 지명 순으로 찾고, 결과의 대한민국·시·도·시·군·구가 맞는 곳만 받는다. 모두 실패하면 상위 시·도 좌표를 쓰고 `approx: true`. 요청 사이 0.2초, `--cache`로 같은 검색어를 다시 부르지 않는다. 2026-10-18 생성: 호출 약 710회. 2026-10 현행 행정구역(강원·전북 특별자치도, 군위군 대구 편입, 부천 일반구, 화성 일반구 4개, 인천 제물포·영종·검단구)을 반영했다.
- **근사 좌표 25곳**(`approx: true`, 시·도 좌표를 대신 쓴다. 날씨가 그 구 청사가 아니라 시·도 중심 격자 기준이다): 서울 마포구·구로구, 부산 중구·동구·영도구·부산진구·사하구·금정구·수영구·사상구, 대구 중구·남구·북구, 울산 동구, 경기 부천시 소사구·화성시 동탄구·안산시 상록구·안양시 만안구, 강원 태백시, 충북 진천군, 충남 계룡시, 경북 영천시, 경남 창원시 성산구·마산회원구·산청군. 지오코딩에 구 단위 행정구역이 없고 한글 이름이 없는 곳이 많아서다. 나머지 243곳도 "다른 검색 결과"로 잡힌 곳은 그 구 안이지만 청사에서 떨어진 마을일 수 있다(`via` 칸). 정확히 하려면 행정구역 중심 좌표 자료로 바꿔야 한다.
- **맞추기 규칙** (`KoreanDistricts.match`, `KoreanRegionNames`): 검색어의 **마지막 낱말**을 시·군·구와 맞춘다 — 이름 그대로(해운대구, 성남시) `EXACT` / 끝의 시·군·구를 뗀 이름(해운대, 분당, 성남. 두 글자 이상) `STEM` / 두 글자 이상 앞부분(해운, 일산 → 일산동구·일산서구) `PREFIX`. 맞춘 정도 순으로 정렬한다. 앞 낱말이 있으면 모두 그 곳의 시·도(부산·부산광역시) 또는 일반구의 시(성남·성남시)를 가리켜야 한다("부산 중구", "성남 분당", "경기도 성남시 분당구"). 검색어가 시·도 이름과 글자까지 같으면(부산) 앞부분만 맞은 곳(부산진구)은 빼서 시·도가 먼저 보이게 한다.
- **겹치는 이름**(중구·동구·서구·남구·북구·강서구·고성군)은 `label` 앞에 시·도 이름(부산 중구) 또는 일반구의 시 이름(포항 남구)을 붙인다.
- **결과 모양**: `label`=화면 이름, `region`=상위 이름(부산광역시, 경기도 성남시), `country`=대한민국, 좌표=자료 좌표, **`regionCode`=`null`**(앱이 좌표 방식 `GET /weather/day?lat=&lon=`으로 그 시·군·구 날씨를 받는다), **`parentRegionCode`**=상위 시·도(`BUSAN`). 앱 타입(`PlaceSearchResponse`)에는 `parentRegionCode`가 있으나 화면은 아직 쓰지 않는다.
- 테스트: `KoreanDistrictsTest`(맞추기), `DistrictFileAdapterTest`(파일 읽기·형식), `PlaceDistrictSearchTest`(검색 흐름: 지오코딩 생략·한도·실패 때도 결과), 하네스 시나리오 51(`parentRegionCode`, 해운대·중구 확인).

## 5. REGION 밖 장소: 요청 시점 호출 + 격자 캐시

좌표 방식(`lat`/`lon`)만 해당한다. REGION 방식은 17의 스냅샷만 읽으므로 외부 호출이 없다(평년값을 처음 계산할 때만 예외, 6장).

| 장치 | 내용 |
|---|---|
| 격자 키 | 위도·경도를 소수 첫째 자리로 반올림해 `"%.1f,%.1f"`(약 11km, 예: `"37.6,127.0"`). `-0.0`은 `0.0`으로. 같은 도시는 같은 키로 모인다 |
| 예보 캐시 | `tb_weather_place_snapshot`. `place-cache-ttl`(기본 3시간)보다 새로우면 외부 호출 0회 |
| 공급자 | 오래됐으면 17의 공급자(우선순위·차단·월 한도)로 `forecast.json`을 그 좌표로 한 번 부른다. 부를 수 있는 공급자가 없으면(차단·한도·키) 부르지 않고 예전 캐시나 평년값으로 답한다 |
| 동시 요청 | Valkey 잠금 `wearly:weather:lock:place:<격자>`(유지 60초). 못 잡으면 다른 요청이 받기를 끝낼 때까지 50ms 간격으로 확인하며 기다리고(최대 공급자 시간 제한 + 2초), 끝나면 그 결과를 쓴다 |
| 회원 한도 | 회원마다 하루(한국 날짜) `on-demand-daily-limit`(기본 30)회. Valkey 카운터 `wearly:weather:usage:<ON_DEMAND\|SEARCH>:<날짜>:<userId>`(2일 보관). **공급자를 실제로 부르기 직전**에만 차감하므로 캐시로 답한 요청은 세지 않는다 |
| 한도 초과 | 예전 캐시가 있으면 그 캐시 → 없으면 평년값 → 그것도 없으면 429 `WEATHER_LIMIT` (`params.kind = ON_DEMAND`) |
| 호출 기록 | `tb_weather_call_log`에 `call_kind = ON_DEMAND`, `run_id` NULL, `region_code` = 격자 키 |
| 실패 | 받기에 실패하면 이전 값은 두고 `last_error`만 바꾼다(`tb_weather_snapshot`과 같은 규칙) |

## 6. 평년값 (`CLIMATE`)

- **출처**: Open-Meteo 과거 기상 API `GET {base}/v1/archive?latitude=..&longitude=..&start_date=..&end_date=..&daily=temperature_2m_max,temperature_2m_min,precipitation_sum&timezone=auto`. 키가 필요 없다.
- **현지 날짜**: `timezone=auto`라서 해외 장소도 그 장소의 현지 날짜로 묶인다(처음 계획은 `Asia/Seoul`이었다). 요청한 `date`의 달로 그 달 평년값을 고른다.
- **계산**: 지난 **10개 완결 연도**(2026년이면 2016~2025)의 일별 자료로 월별 평균 최고(`temp_max`)·평균 최저(`temp_min`)·평균 기온 `temp_avg`((최고+최저)/2의 평균)·강수 1mm 이상인 날의 비율을 구해 **12개월을 한 번에** 저장한다. 응답에는 `day.temp` = 평균, `min`·`max` = 평균 최저·최고, `rainProb` = 비 온 날 비율 × 100(반올림), `cond`·`condText` = `null`.
- **언제 계산하나**: 그 격자·그 달 평년값이 필요한 첫 요청에서 계산한다(`ClimateService`, 격자별 잠금 `wearly:weather:lock:climate:<격자>`로 한 번만). 이후는 DB에서 읽고, `computed_at`이 **400일**을 넘으면 다시 계산한다.
- **실패**: 받지 못하면 예전 값이 있으면 그 값을 쓰고, 같은 격자는 10분 동안(서버마다) 다시 부르지 않는다. 구하지 못하면 `CLIMATE` 없음(3장 (3)). `wearly.weather.climate.enabled=false`면 `CLIMATE`를 주지 않는다.
- **호출 기록**: `provider_code = OPEN_METEO`, `call_kind = CLIMATE`, `run_id` NULL, `region_code` = 격자 키.
- **실제 값** (로컬 DB, 2016~2025): 서울(`37.6,127.0`) 11월 평균 5.95°(최저 1.07° ~ 최고 10.83°)·비 20%, 도쿄(`35.7,139.7`) 11월 12.38°(8.06°~16.69°)·비 29%.

**이용 조건**: Open-Meteo의 무료 API(평년값·지오코딩)는 **비상업용**이다. 상업 서비스로 바꿀 때는 유료 주소(`customer-archive-api.open-meteo.com`·`customer-geocoding-api.open-meteo.com`)와 `api-key`를 설정에 넣거나 끈다(`climate.enabled=false`, `geocoding.enabled=false`). 키는 `backend/config/application-local.yml`(git 제외)에 둔다. 견본은 `application-local.example.yml`. 호출 오류 문구에서는 `apikey=***`로 가린다.

## 7. 데이터 (Flyway `V13__place_weather.sql`)

| 테이블 | 내용 |
|---|---|
| `tb_weather_place_snapshot` | REGION 밖 장소의 최신 예보. `grid_key`(PK), `lat`·`lon`(격자 좌표), `label`(공급자 이름), `provider_code`, `current`·`days`(JSONB, 17의 `tb_weather_snapshot`과 같은 모양), `fetched_at`, `last_error`, `last_error_at` |
| `tb_weather_climate` | 격자·월별 평년값. PK `(grid_key, month)`, `temp_avg`·`temp_min`·`temp_max`·`rain_day_ratio`(모두 `DOUBLE PRECISION`, 0~1), `years`(`"2016-2025"`), `source`(`OPEN_METEO`·`MOCK`), `computed_at`. 12개월을 한 번에 넣는다 |
| `tb_weather_call_log` (변경) | `run_id`·`region_code`를 NULL 허용으로. `call_kind`에 CHECK(`FORECAST`·`ON_DEMAND`·`SEARCH`·`CLIMATE`)와 `FORECAST`는 `run_id` 필수 CHECK. 실행 밖 호출 보관용 부분 인덱스 `ix_weather_call_no_run` |

**호출 이력 `call_kind`** (관리자 날씨 → 호출 이력에 그대로 보인다):

| call_kind | 언제 | `run_id` | `region_code` | `provider_code` |
|---|---|---|---|---|
| `FORECAST` | 주기·수동·시작·시험 실행의 예보 호출(17) | 있음 | REGION 코드 | `WEATHERAPI` |
| `ON_DEMAND` | 좌표 요청 때 부른 예보 | NULL | 격자 키 | `WEATHERAPI` |
| `SEARCH` | 장소 검색 | NULL | NULL | `OPEN_METEO_GEO`(지오코딩) · `WEATHERAPI`(대신한 검색) |
| `CLIMATE` | 평년값 계산용 과거 기상 자료 | NULL | 격자 키 | `OPEN_METEO` |

- 실행 밖 호출은 실행과 함께 지워지지 않으므로, 17의 이력 보관 정리(`log-retention-days`, 매일 04:00)가 `run_id`가 없는 호출도 보관 기간이 지나면 따로 지운다.
- 관리자 호출 이력은 실행을 `LEFT JOIN`으로 붙이므로 실행 밖 호출은 **트리거 칸이 빈칸**이다.
- **관리자 호출 이력 필터** (`GET /admin/weather/calls?callKind=`): `FORECAST`·`ON_DEMAND`·`SEARCH`·`CLIMATE`(대소문자 무관)로 거른다. 그 밖의 값은 400 `VALIDATION_FAILED`(`callKind` `NOT_ALLOWED`, `params.allowed`에 4개). 관리자 화면은 "종류" 칸·필터(정기·수동 실행 / 다른 장소 날씨 / 장소 검색 / 평년값)를 두고 이 값을 서버에 보낸다. 격자 키는 "좌표 35.7, 139.7"로 보인다.
- **보조 공급자 사용량** (`GET /admin/weather/calls/summary`의 `auxiliaryMonths`): 공급자 표(`tb_weather_provider`) 밖인 `OPEN_METEO`(평년값)·`OPEN_METEO_GEO`(장소 검색)의 이번 달(한국 시간) 호출 수. 실패 포함, 월 한도 없음. 두 코드는 0이어도 늘 나오고, 이력에만 있는 다른 공급자 코드가 뒤에 붙는다. 관리자 "공급자" 탭의 Open-Meteo 카드와 "호출 이력" 탭 요약 칩이 이 값을 보여 준다. Open-Meteo 무료 API는 비상업 용도 전용이라는 안내도 같이 보인다 (6장). 지오코딩이 꺼져 있어 WeatherAPI로 대신 검색한 호출은 `WEATHERAPI`의 월 사용량(`months`)에 들어간다.

## 9. 앱 (`mobile/`)

**예정일 코디(`(tabs)/coordi.tsx` PLAN 모드)**
- 날짜 아래 **장소 줄**: 칩 `내 지역 · 서울`(기본, 홈의 날씨 지역) · 최근 고른 장소(최대 5개) · `다른 장소…`. 바꾸지 않으면 예전과 똑같이 동작한다.
- `다른 장소…`는 **장소 고르기 화면**(`app/place.tsx`, 제목 "예정 장소")으로 간다. 시·도 목록(코드 `REGION`)과, 로그인했으면 검색창(300ms 디바운스, `GET /weather/places`). 게스트·목업 실행은 목록만 보인다. 홈의 '날씨 지역'(`app/region.tsx`)과 **별개**라서 여기서 골라도 홈 지역은 바뀌지 않는다.
- 날씨 카드 제목에 장소 이름, **출처 표시**: 예보 / 평년 / 직접 입력(`SOURCE_LABEL`). `CLIMATE`면 "○○의 10월 평년 기온(최저 12° · 최고 20°) 기준이에요. 예보가 나오면 다시 확인할게요." 안내와 체감 온도 칩을 같이 둔다. 칩을 고르면 `MANUAL`, "예보로/평년 기온으로 되돌리기"로 돌아간다. 날짜·장소를 바꾸면 그곳·그날의 서버 날씨로 돌아간다.
- 서버 날씨를 못 받을 때(503·네트워크·`WEATHER_LIMIT`·로그인 필요·예전 서버)는 안내 문구와 함께 지금처럼 체감 온도를 직접 고른다. `Weather` 타입과 추천 엔진(`recommend.ts`)은 그대로다.
- 날짜를 빠르게 넘길 때 요청이 몰리지 않게 250ms 기다렸다 부르고, 같은 장소·날짜 응답은 10분간 다시 쓴다.

**저장**
- `PlannedEvent`(기기 저장, `wearly-store-v1`)에 `place?`, `weatherSource?`, `weatherCheckedAt?`, `forecastReady?`를 더했다. 예전 데이터는 `place` 없음 = 내 지역, `weatherSource` 없음 = `weather.manual`이면 `MANUAL` 아니면 `FORECAST`.
- `wearly-place-v1`(`usePlaceStore`): `recent`(최근 장소 5개)와 `spans`(장소별 예보 기간, 마지막 응답의 `forecastUntil`로 정함).
- 저장된 코디(`outfit.context`)는 **저장할 때의 날씨 기준으로 남는다.** 다시 확인으로 날씨가 바뀌어도 예전 코디는 그대로고, 사용자가 "다시 추천"을 눌러야 새 날씨로 바뀐다.

**다시 확인** (`recheckPlans`)
- 시점: 앱 시작(세션·저장값 복원이 끝난 뒤)·앱이 다시 활성이 될 때·캘린더 화면에 들어올 때.
- 대상: `CLIMATE`로 저장했고, 날짜가 지나지 않았고, 이제 그 장소 예보 기간(`spans`, 모르면 오늘+2일) 안에 들어왔고, 오늘 아직 확인하지 않았고, 이미 "예보가 나왔어요"가 아닌 예정. 좌표 장소는 로그인했을 때만.
- 판단: 예보가 나왔고 코디가 있는 예정이 **기온 3° 이상 차이나거나 비 여부(`rainProb` 50 기준)가 바뀌면** `forecastReady = true`, 아니면 조용히 `FORECAST`로 갱신한다. 아직 평년값이면 확인 시각만 남긴다. 같은 예정은 **하루 한 번**.
- `WEATHER_LIMIT`(429)면 그 예정은 오늘 확인한 것으로 표시해 오늘은 더 부르지 않는다(다른 예정은 계속 시도한다). 그 밖의 실패(네트워크·503)는 다음 기회에 다시 한다.
- 캘린더(`(tabs)/calendar.tsx`)의 날짜 표시와 예정 카드에 "예보가 나왔어요 · 다시 추천" 배지, 누르면 `/coordi?mode=plan&planId=<id>`로 그 예정의 PLAN 모드를 열어 새 날씨로 추천한다. 예정 행에는 `기온 (예보|평년|직접 입력)`과, 내 지역이 아니면 장소 이름이 붙는다.

**예전 서버·목업 실행**
- 목업 실행(`MOCK_MODE`)에서는 장소 줄을 숨기고 아무것도 부르지 않는다(지금처럼).
- 이 API가 없는 예전 서버는 로그인 요청이 404, region 요청(토큰 없음)이 공개 경로가 아니라 401 `UNAUTHORIZED`로 온다. 앱은 이를 "예전 서버"로 판단해 10분간 다시 부르지 않고 지금처럼 동작한다(새 서버는 region 요청에 401을 주지 않는다).

**앱 API 모듈** (`mobile/src/api/`): `api.weather.day(where, date)`(`where` = `{ region }` 또는 `{ lat, lon }`), `api.weather.places(q)`와 타입(`WeatherDayResponse`·`PlaceSearchResponse` 등), 오류 코드 `WEATHER_LIMIT`.
