# 19. 장소별 날씨: 예정일 코디에 장소를 고른다

> **제안 문서, 아직 구현하지 않음, 2026-10-18.** [17_날씨.md](17_날씨.md)(지금 날씨 설계)의 다음 단계다. 17의 서버 수집·저장 구조는 그대로 두고, "어느 장소의 날씨를 쓸지"를 날짜별로 고를 수 있게 넓힌다. 17의 담당자(kang6123)와 범위를 나눠야 하므로 9장을 먼저 본다.

## 1. 배경

- 지금 날씨는 기기에 저장한 지역 하나 기준이다 (`mobile/src/store/useWeatherStore.ts`, 17 문서 5장). 홈·AI 코디·예정일 코디가 모두 그 지역의 `forecast(date)`를 쓴다.
- 출장·여행·지방 예식처럼 **다른 날, 다른 곳**의 코디는 맞출 수 없다. 사용자 요구: "위치를 선택할 수 있는 기능이 필요하다. 미래 날짜에 다른 곳을 방문할 수도 있다."
- 기획서 p.16 예정일 코디(PLAN A LOOK)는 날짜·시간대·컨셉·상황을 받고 날씨 예보를 자동으로 붙이며, 동행/장소 메모를 적고, D-1 알림에서 최신 예보를 다시 확인하게 되어 있다. 지금 "장소"는 메모 글자일 뿐 날씨와 연결되지 않는다.

## 2. 지금 구조 (코드 확인 결과)

| 항목 | 현재 |

## 3. 제안 A. 예정일 코디에 "장소"

날짜를 고를 때 **장소(지역)** 를 함께 고른다.

- 기본값은 "내 지역"(17의 기기 저장 지역, 나중엔 프로필 지역). 바꾸지 않으면 지금과 똑같이 동작한다.
- 예정 코디에 `regionCode`(또는 5장의 C안 좌표)를 저장한다. 추천(날씨 점수 20점)과 캘린더 표시는 그 장소의 날씨를 쓴다.
- 장소 칩: `내 지역(서울)` · `다른 지역…`. 다른 지역은 `app/region.tsx`와 같은 목록(코드 `REGION`)에서 고른다. "가까운 지역 찾기"는 넣지 않는다 (미래 장소라서 의미가 없다).
- 메모의 "장소" 글자 입력은 그대로 둔다. 장소 칩은 날씨용, 메모는 사람이 읽는 설명이다.

## 4. 제안 B. 날짜 범위별 날씨 출처

한 예정의 날씨는 **날짜가 예보 범위 안인지**에 따라 출처를 나눈다. 응답과 화면에 출처를 표시한다.

| 날짜 | 출처 | 표시 | 추천 |
|---|---|---|---|
| 예보 범위 안 (지금 오늘부터 3일, 공급자·관리자 설정에 따라 `forecast_days`) | `FORECAST`: 그 지역의 저장 예보 | 기온·강수 확률 | 지금처럼 |
| 예보 범위 밖 | `CLIMATE`: 그 지역·그 달 평년 기온 | "평년 기온 기준 (예보가 나오면 다시 확인)" | 대략 추천. 일교차·비 확률은 평년값에 없으면 보수적으로(비 10%, 일교차 8°) 둔다 |
| 사용자가 직접 입력 | `MANUAL`: 체감 온도 칩 | "직접 입력" | 지금처럼 |

- **재확인 알림**: 예정일이 예보 범위에 들어오면(D-3~D-1) 그 장소의 최신 예보로 날씨를 다시 계산하고, 예보가 코디를 바꿀 만큼 달라졌으면(예: 기온 5° 이상, 비 확률 60% 경계를 넘음) 알림으로 알린다. 기획서의 D-1 알림과 이어지고, 푸시는 아직 목업 단계라(04 문서) 앱을 열 때 배지로 먼저 구현한다.
- **평년 기온 자료**: 확실한 API·URL을 지금 정하지 않는다. 후보와 상태:

| 후보 | 상태 |
|---|---|
| 기상청 평년값(30년 평균, 지점별 월 평균·최고·최저 기온) | 조사 필요: 제공 방식(공공데이터 파일/API), 지점 ↔ 시·도 대응, 이용 조건 |
| 공급자(WeatherAPI.com 등)의 과거·기후 API | 조사 필요: 제공 여부, 요금제, 호출량 |
| 직접 만든 월별 평균표 | 가장 간단하다. 아래 "우선은" 참고 |

- **우선은 간단하게**: `REGION` 코드의 `attrs`에 월별 평균 기온 12개 값을 넣는다. 예: `{"lat": 37.5665, "lon": 126.978, "monthlyAvg": [-2, 1, 6, 13, 18, 23, 26, 26, 22, 15, 8, 1]}`. 앱의 `SEOUL_MONTHLY_AVG`(`lib/weather.ts`)를 지역별로 넓힌 것이다. 관리자 코드 관리에서 고칠 수 있고, 나중에 기상청 평년값으로 값만 바꿔 넣으면 된다. 최고·최저는 `monthlyAvg ± 일교차`로 만든다.

## 5. 제안 C. 17개 시·도 밖의 장소 (해외 출장 등)

- 장소 검색(공급자의 검색 API 또는 지도 앱에서 받은 좌표)으로 장소를 고른다. 공급자 검색 API 이름은 조사 필요.
- 서버가 **그 장소만 요청 시점에 한 번 받아** 일정 시간(예: 1~3시간) 캐시하고 같은 장소를 찾는 사용자끼리 공유한다. 주기 수집 대상(활성 `REGION`)은 늘리지 않는다.
- 17의 원칙 "사용자 요청마다 외부 API를 부르지 않는다"와의 관계: 17 원칙의 목적은 사용자 수에 따라 호출이 늘어나는 것을 막는 것이다. C안은 이 원칙의 **예외 경로**다. 절충은 다음과 같다.

| 장치 | 내용 |
|---|---|
| 캐시 키 | 좌표를 소수 둘째 자리로 반올림(약 1km) + 날짜 범위. 같은 도시는 같은 키로 모인다 |
| 캐시 시간 | 기본 3시간 (관리자 설정). 캐시 안에서는 외부 호출 0회 |
| 회원당 한도 | 하루 새 장소 조회 N회(예: 20). 넘으면 429. 로그인 필요 (익명 조회는 17의 17개 지역만) |
| 전체 한도 | 이 경로 전용 월 호출 한도를 `tb_weather_provider.monthly_quota`와 별도로 둔다. 닿으면 평년 기온(`CLIMATE`)으로만 답한다 |
| 호출 기록 | `tb_weather_call_log`에 `call_kind = ON_DEMAND`로 남겨 관리자 화면에서 주기 수집과 구분한다 |
| 동시 요청 | 같은 키는 Valkey 잠금으로 한 번만 부른다 (17의 `RefreshLockPort` 방식) |

- 해외는 공급자가 좌표를 받으면 같은 `forecast.json`으로 대부분 된다. 한국 시간 기준 `observedAt`·날짜 계산이 현지 날짜와 어긋나지 않는지(`location.tz_id`) 확인이 필요하다.
- 1차 구현은 A+B만 하고 C는 따로 결정한다 (9장).

## 6. 데이터 초안

### `tb_planned_outfit` 변경 (Flyway 새 버전)

| 칸 | 내용 |
|---|---|
| `region_code VARCHAR(30)` | NULL = 내 지역(저장 시점의 기기 지역을 `weather`에 복사). 값이 있으면 코드 `REGION` |
| `place_name VARCHAR(80)` | C안 또는 표시용 장소 이름 ("부산", "도쿄") |
| `place_lat`, `place_lon NUMERIC(8,5)` | C안 좌표. `region_code`가 있으면 NULL |
| `weather_source VARCHAR(10)` | `FORECAST` · `CLIMATE` · `MANUAL`. 기존 행은 `weather->>'manual'`이 true면 `MANUAL`, 아니면 `FORECAST` |
| `weather` (JSONB, 기존) | 그대로. 마지막으로 계산한 날씨. 재확인 때 갱신 |
| `weather_checked_at TIMESTAMPTZ` | 마지막으로 예보를 확인한 시각 (D-1 알림 판단용) |

체크 제약: `region_code`와 좌표는 동시에 값을 가질 수 없다. 서버 예정 코디 API·저장 코드는 아직 없으므로(2장), 이 변경은 예정 코디 서버 저장을 만드는 작업과 같이 한다. 앱은 그 전까지 `PlannedEvent`에 `regionCode?`, `placeName?`, `weatherSource?`를 더해 기기에만 저장한다.

### API 형태 비교

| 안 | 요청 | 장점 | 단점 |
|---|---|---|---|
| ① 지역 코드 확장 | `GET /api/v1/weather?region=BUSAN&date=2026-11-03` | 17의 API·`ETag`·캐시를 그대로 쓴다. 인증 불필요 | 17개 지역만. 날짜는 응답에 맞는 날 하나만 골라 준다 |
| ② 좌표 | `GET /api/v1/weather/forecast?lat=35.18&lon=129.07&date=2026-11-03` | C안(해외·임의 장소)까지 한 API | 서버가 좌표를 가까운 REGION으로 붙일지, 요청 시점에 받을지 결정해야 한다. 인증·한도 필요 |

**제안**: 1차는 ①을 넓힌다 (`date`는 선택 칸, 없으면 지금과 같은 응답). C안을 하게 되면 ②를 인증 필요 API로 따로 둔다. 둘은 응답 모양을 같게 한다.

### 응답 초안

```json
{
  "region": { "code": "BUSAN", "label": "부산" },
  "date": "2026-11-03",
  "source": "CLIMATE",
  "day": { "date": "2026-11-03", "temp": 13.0, "min": 9.0, "max": 17.0, "rainProb": 10, "cond": "SUNNY", "condText": "평년 기온 기준" },
  "forecastUntil": "2026-10-20",
  "fetchedAt": "2026-10-18T03:00:11Z"
}
```

- `source`: `FORECAST`(저장 예보에 그 날짜가 있음) · `CLIMATE`(평년 기온) · `MANUAL`은 서버가 만들지 않고 앱이 표시한다 (사용자 입력).
- `forecastUntil`: 그 지역 예보의 마지막 날. 앱이 "N일 뒤부터 예보가 나와요"를 계산한다.
- 기존 `days` 배열 응답은 `date`가 없을 때 그대로 둬 앱 호환을 지킨다.

## 7. 앱 화면 초안

- **예정일 코디(`coordi.tsx` PLAN)**: 날짜 아래에 장소 칩 줄. `내 지역 · 서울` (기본 선택) / `다른 지역…` (목록 시트). 선택한 장소와 날짜로 날씨 카드가 바뀐다. 출처 배지: 예보 / 평년 기준 / 직접 입력. `CLIMATE`이면 "예보가 나오면 다시 확인해요" 문구와 "체감 온도 직접 고르기" 링크를 같이 둔다.
- **캘린더(`calendar.tsx`)**: 다가오는 예정 행과 선택한 날 카드에 `장소 · 날씨 아이콘 · 기온`을 보인다. 내 지역이 아니면 장소 이름을 붙인다. 날씨가 평년 기준이면 점선 아이콘으로 구분한다. 예보가 새로 나와 달라졌으면 "예보 바뀜" 배지.
- **홈 "오늘"**: 지금처럼 기기 지역 그대로. 오늘 예정이 다른 장소면 홈에 "오늘은 부산 출장 · 부산 날씨로 추천" 한 줄 안내를 더하는 것은 후속 결정으로 둔다.
- `lib/weather.ts`: `forecast(key)`·`hasForecast(key)`에 지역 인자(`regionCode?`)를 더하고, 기기에 저장한 지역 하나 대신 지역별 응답 캐시를 `useWeatherStore`에 둔다. 추천 엔진(`recommend.ts`)은 `Weather` 타입이 그대로라 바뀌지 않는다. `Weather`에 `source?: 'FORECAST' | 'CLIMATE' | 'MANUAL'`을 더한다 (지금의 `manual` 플래그는 `source === 'MANUAL'`로 대체).
