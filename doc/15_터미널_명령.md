# 15. 터미널 명령 모음

> 로컬에서 Wearly를 띄우고 확인하는 명령. 모든 명령은 저장소 루트(`/Users/showzone/Workspace/wearly`) 기준이다. DB·Valkey·MinIO 명령은 [14_DB_명령.md](14_DB_명령.md).

## 1. 한 번에 띄우기 (평소)

가장 쉬운 방법은 저장소 루트의 `./dev.sh`다 (Mac 전용). compose를 띄우고, 백엔드가 뜰 때까지 기다린 뒤, Terminal 창으로 로그와 Expo를 연다.

```bash
./dev.sh                # 전체 빌드·실행 + 로그 창 2개 + Expo 창
./dev.sh --no-build     # 이미지를 다시 빌드하지 않고 띄운다 (코드를 안 바꿨을 때 빠르다)
./dev.sh --no-expo      # Expo 창은 열지 않는다
./dev.sh --ios          # Expo를 iOS 시뮬레이터와 함께 연다 (expo start --ios)
./dev.sh logs           # 로그 창만 다시 연다
./dev.sh stop           # docker compose down (데이터 볼륨은 남는다)
```

| 단계 | 하는 일 |
|---|---|
| 1 | Docker가 켜져 있는지 확인한 뒤 `docker compose up -d --build` (`--no-build`면 `--build` 없이) |
| 2 | `http://localhost:8080/actuator/health`가 답할 때까지 최대 5분 기다림 |
| 3 | Terminal 창 "Wearly 백엔드 로그": `docker compose logs -f --since 1m backend` |
| 4 | Terminal 창 "Wearly 실시간 로그 (DB)": `python3 -I backend/scripts/live-log.py`. 이미 떠 있으면(`pgrep`) 같은 기록이 두 번 찍히므로 열지 않는다 |
| 5 | Terminal 창 "Wearly Expo": `cd mobile && npx expo start` (Xcode 경로 `DEVELOPER_DIR` 포함). 8081에서 이미 Metro가 돌고 있으면 열지 않는다 |

- 옵션 목록은 `./dev.sh --help`. 모르는 옵션이면 오류로 끝난다.

직접 명령으로 하려면:

```bash
# DB · Valkey · MinIO(옷 사진) · 백엔드 · 관리자 사이트를 새로 빌드해 실행 (로그를 보면서, Ctrl+C로 중지)
docker compose up --build

# 백그라운드로 띄우기
docker compose up -d --build

# 앱 (Mac에서 따로) — 휴대폰은 Expo Go로 QR, 시뮬레이터는 터미널에서 i, 브라우저는 w
cd mobile && npx expo start
```

| 서비스 | 주소 |
|---|---|
| 백엔드 API | http://localhost:8080 (헬스 체크 `/actuator/health`) |
| 관리자 사이트 | http://localhost:5173 (계정은 `backend/config/application-local.yml`의 `wearly.admin`) |
| DB | `localhost:5433` |
| Valkey (로그인 세션, doc/16) | `localhost:6380` (`docker exec -it wearly-valkey valkey-cli`) |
| MinIO (옷 사진, doc/18) | S3 API `localhost:9000`, 웹 콘솔 http://localhost:9001 (로컬 전용 계정 `wearly` / `wearly-minio-local`) |
| Keycloak (관리자 SSO 시험용, **`--profile sso`일 때만**, doc/22 4.2.5) | http://localhost:8180 (관리 콘솔 `admin` / `wearly-keycloak-local`, 로컬 전용 시험 값) |
| 앱 개발 서버 (Metro) | 8081 |

> 코드를 바꾼 뒤에는 `--build`를 붙여야 컨테이너에 새 코드가 들어간다. 빼면 예전 이미지로 뜬다.

## 2. docker compose

```bash
docker compose ps                     # 상태
docker compose logs -f backend        # 백엔드 로그 따라 보기 (admin, db, valkey, minio도 같음)
docker compose restart backend        # 재시작 (이미지는 그대로)
docker compose up -d --build backend  # 백엔드만 다시 빌드해 띄우기
docker compose stop admin             # 관리자 컨테이너만 멈추기 (npm run dev와 5173 포트가 겹칠 때)
docker compose up -d db valkey minio minio-init   # DB·Valkey·사진 저장소만 (백엔드를 Mac에서 bootRun으로 돌릴 때). minio-init은 버킷을 만들고 끝난다
docker compose down                   # 모두 내리기 (DB 데이터·로그인 세션·옷 사진은 볼륨에 남는다). profile 서비스(keycloak)까지 내리는지는 compose 버전마다 달라, 아래 Keycloak 끄기 명령을 따로 쓴다
docker compose down -v                # ⚠️ DB 데이터·로그인 세션·옷 사진까지 지우기
```

### 관리자 SSO 시험용 Keycloak (profile `sso`, doc/22 4.2.5)

평소 `docker compose up`에는 뜨지 않는다. 무거워서 필요할 때만 띄운다. 계정·비밀번호는 모두 로컬 전용 시험 값이다.

```bash
docker compose --profile sso up -d keycloak          # 띄우기 (처음엔 이미지를 받고 30초 안팎, 헬스체크가 healthy가 될 때까지)
docker compose --profile sso ps keycloak             # 상태 (healthy인지)
docker compose --profile sso logs -f keycloak        # 로그
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8180/realms/wearly/.well-known/openid-configuration   # 200이면 realm이 올라온 것
docker compose --profile sso stop keycloak           # 끄기 (realm 변경은 컨테이너 안에 남는다)
docker compose --profile sso rm -sf keycloak         # 지우기: 다음 up에서 infra/keycloak/wearly-realm.json으로 처음 상태가 된다 (콘솔에서 바꾼 것도 사라진다)
```

- 관리 콘솔 http://localhost:8180 (`admin` / `wearly-keycloak-local`), realm `wearly`, 시험 계정 `admin@wearly.local` / `WearlyAdmin1!`(관리자 그룹 → 로그인 성공), `viewer@wearly.local` / `WearlyViewer1!`(조회 그룹 → 403 `SSO_NOT_ADMIN`).
- Keycloak만 띄워서는 관리자 사이트에 버튼이 생기지 않는다. `backend/config/application-local.yml`에 `wearly.sso` 블록(견본 `application-local.example.yml`의 ①)을 넣고 `docker compose up -d --build backend`로 백엔드를 다시 띄워야 한다. 켜졌는지: `curl -s localhost:8080/api/v1/auth/sso/providers`가 `{"enabled":true,"providers":[{"id":"keycloak",…}]}`이고, 꺼져 있으면 `{"enabled":false,"providers":[]}`다.
- 포트 8180이 이미 쓰이고 있으면 `lsof -nP -iTCP:8180 -sTCP:LISTEN`로 확인한다.

## 3. 백엔드 (`backend/`, Spring Boot)

Java 21이 필요하다. 기본 `java`가 다른 버전이면 앞에 `JAVA_HOME`을 붙인다.

```bash
cd backend
export JAVA_HOME=/Users/showzone/Library/Java/JavaVirtualMachines/openjdk-21.0.2/Contents/Home

./gradlew bootRun            # Mac에서 실행 (실제 AI 공급자). 먼저 docker compose stop backend (8080 충돌), DB·Valkey·MinIO(minio-init 포함)는 떠 있어야 한다
./gradlew test               # 테스트 (Testcontainers로 PostgreSQL·Valkey·MinIO를 띄운다. Docker 필요)
./gradlew bootRunMock        # 목업 AI로 실행 (키 없이 개발)
./gradlew check              # 포맷 검사 + Checkstyle + 테스트 (커밋 전)
./gradlew spotlessApply      # Google Java Style로 자동 정리
./gradlew bootJar            # 실행용 jar (build/libs/)
```

- 비밀 값(AI 키·관리자 계정·마스터 키)은 `backend/config/application-local.yml`(git 제외). 견본은 `application-local.example.yml`. `.env`는 쓰지 않는다.
- 마스터 키 새로 만들기: `openssl rand -base64 32`. 관리자 2단계 인증(`wearly.admin.mfa.required` 기본 `true`)은 TOTP 비밀을 이 마스터 키로 암호화하므로 **마스터 키가 없으면 관리자 사이트 로그인에서 등록을 시작할 수 없다** (22 문서 4.1.6). 로컬에서 번거로우면 `application-local.yml`에 `wearly.admin.mfa.required: false`.
- 시작 로그에서 관리자 설정 확인: `docker compose logs backend | grep -E "관리자 2단계 인증|관리자 계정"` — "관리자 2단계 인증: 필수 (issuer=Wearly)", "관리자 계정: 관리자가 이미 1명 있어 설정 계정(wearly.admin.email)은 쓰지 않아요" 같은 줄이 나온다.
- D-1 서버 푸시 시험(23 문서): `application-local.yml`에 `wearly.notify.push.enabled: true`(provider는 기본 `log`)로 두고 백엔드를 다시 띄우면 시작 로그에 "D-1 알림 작업을 매일 19:30 (한국 시간)에 실행해요"가 나온다. 작업이 돌 때마다 "D-1 알림 2026-10-19: 예정 N개, 보냄 N개 …" 요약 한 줄이 남는다. 시각을 바꿔 바로 보려면 `WEARLY_NOTIFY_DAY_BEFORE_TIME=HH:mm`. 실제로 보내려면 `provider: expo`와 EAS 준비가 필요하다(23 문서 9장).

### 실시간 로그 (AI 분석·로그인·옷 등록·날씨·사진을 한눈에)

```bash
python3 backend/scripts/live-log.py      # DB 기록을 1초마다 따라 본다 (Ctrl+C로 종료)
docker compose logs -f backend           # 서버 로그는 이쪽에서
```

- AI 호출이 성공하면 서버 로그에 캐시 토큰까지 한 줄이 남는다 (프롬프트 캐싱, 18 문서 13장): `docker compose logs backend | grep "성공 provider"` → `AI ITEM_ANALYZE 성공 provider=… model=… ms=… input=… output=… cacheRead=… cacheWrite=…`. 같은 사진 분석을 5분 안에 두 번 하면 두 번째에 `cacheRead`가 0보다 커야 캐시가 맞은 것이다.
- AI 분석·로그인·옷 등록 외에 **날씨 수집 결과**(끝난 실행 한 줄)와 **실패한 공급자 호출**, **저장된 사진**(올리기를 마친 사진)도 보인다 (doc/17, doc/18). `./dev.sh`가 이 로그 창을 같이 열어 준다.

## 4. 앱 (`mobile/`, Expo)

```bash
cd mobile
npm install                 # 처음 한 번
npx expo start              # 실제 서버 연결 (기본)
npm run start:mock          # 목업 실행: 게스트 모드·기기 목업 분석, 서버 없이
npm run typecheck           # 타입 검사
npx expo-doctor             # Expo 설정·버전 점검
npm run check:errors         # 오류 문구 표가 서버 카탈로그(error-codes.json)와 맞는지 (20 문서, 지금 서버 51·필드 21·앱 5)
npm run test:unit            # 계절 테마 규칙 등 순수 함수 테스트 (tests/seasons.test.mjs, 11개)
```

- `CI=1`로 띄우지 않는다 (파일 감시가 꺼져 코드 수정이 반영되지 않는다).

## 6. 연동 하네스 (`harness/`)

앱의 API 코드로 실제 백엔드를 시험한다. 하네스 전용 DB(`wearly_harness`), Valkey DB 1(`wearly-valkey`, 없으면 `docker compose up -d valkey`로 띄움), 사진 버킷 `wearly-images-harness`(`wearly-minio`, 없으면 `docker compose up -d minio minio-init`), 18080 포트를 쓰므로 compose와 같이 돌려도 된다.

```bash
cd harness
npm install
./run.sh                                 # 전체 시나리오 (백엔드를 18080으로 직접 띄움)
HARNESS_BOOT_TIMEOUT=600 ./run.sh        # 첫 실행에 Gradle 내려받기가 길 때
./run.sh --list                          # 시나리오 목록
./run.sh --only 관리자                    # 일부만 (2단계 인증·SSO 꺼짐 시나리오는 "관리자"에 같이 잡힌다)
./run.sh --keep                          # 끝나도 백엔드를 남김
./run.sh --external http://localhost:18080   # 이미 떠 있는 서버로 (만료·관리자 시나리오는 건너뜀)
./run.sh --db-only                       # 하네스 DB만 다시 만들기 (Valkey DB 1·하네스 사진 버킷도 비움)
```

## 9. 포트 정리
