# 04. 목업 앱

> 작성일: 2026-10-15
> 대상: [mobile/](../mobile/) — Expo로 만든 웨어리 목업 앱 (백엔드 없음)

기획서의 부록 목업(p.39~45), UX 설계(p.13~21), 추천 로직(p.24~26)을 실제로 동작하는 앱으로 옮겼다. 목적은 두 가지다. 화면 흐름이 이어지는지 직접 눌러 보는 것, 그리고 규칙 기반 추천·진단이 실제 옷장 데이터에서 그럴듯한 결과를 내는지 확인하는 것이다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 프레임워크 | Expo SDK 57 (`expo ~57.0.29`), React Native 0.86, React 19.2 |
| 라우팅 | expo-router. `src/app/` 아래 파일이 곧 화면 경로 |
| 상태·저장 | zustand + AsyncStorage. 저장 키는 `wearly-store-v1`. 추천 결과 화면으로 넘기는 임시 데이터(`draft`)는 저장하지 않는다 |
| 그래픽 | react-native-svg. 옷 일러스트([GarmentArt.tsx](../mobile/src/components/GarmentArt.tsx))와 아이콘([Icon.tsx](../mobile/src/components/Icon.tsx))을 모두 SVG로 그린다 |
| 사진 | expo-image-picker (카메라·앨범), expo-image (표시) |
| 글꼴 | Noto Serif KR Bold (제목). 본문은 시스템 글꼴 |
| 디자인 | 기획서 목업의 시각 언어: 밝은 회색 바탕, 검정, 짙은 초록 포인트, 세리프 제목 ([theme.ts](../mobile/src/theme.ts)) |
| 언어 | TypeScript (strict) |
| 백엔드 | 없음. 모든 데이터는 기기 안에만 저장한다 |
| 로그인 | 없음. 소셜 로그인은 각 사 API 키 발급이 필요해 제외했다 ([02](02_기술_결정.md) D5) |
| 앱 ID | `app.wearly.mobile` (iOS·Android 공통, [app.json](../mobile/app.json)) |

## 2. 실행 방법

> 처음 한 번만 `npm install`을 하고, 그다음부터는 `npx expo start` 하나로 실행한다.

### 준비

- **Node.js** (v22에서 확인)
- 휴대폰으로 볼 경우 **Expo Go** 앱 (App Store / Play Store에서 설치)

### 1단계. 의존성 설치 (처음 한 번만)

mobile 폴더로 이동한다.

```bash
cd /Users/showzone/Workspace/wearly/mobile
```

의존성을 설치한다.

```bash
npm install
```

### 2단계. 개발 서버 실행

mobile 폴더에서 실행한다. 터미널에 QR 코드와 단축키 안내가 나온다.

```bash
npx expo start
```

### 3단계-A. 휴대폰에서 보기

1. 휴대폰에 Expo Go를 설치한다.
2. 휴대폰과 Mac을 **같은 Wi-Fi**에 연결한다.
3. 터미널의 QR 코드를 스캔한다.
   - iPhone: 기본 카메라 앱으로 스캔
   - Android: Expo Go 앱 안의 QR 스캔으로 스캔

### 3단계-B. 브라우저에서 보기

서버가 떠 있는 터미널에서 `w` 키를 누른다. 또는 처음부터 웹으로 띄운다.

```bash
npx expo start --web
```

넓은 화면에서는 앱이 휴대폰 폭(최대 480px)으로 가운데 정렬된다.

### 종료

터미널에서 `Ctrl+C`를 누른다.

### 문제 해결

| 상황 | 해결 |
|---|---|
| 8081 포트를 이미 쓰고 있다 | Expo가 다른 포트를 쓸지 물어본다. `Y`를 누른다 |
| 코드를 고쳐도 화면에 반영되지 않는다 | `CI=1`로 실행하지 않았는지 확인한다. CI 모드에서는 Metro가 파일 감시를 끄므로 수정이 반영되지 않는다. 직접 실행할 때는 위 명령을 그대로 쓴다 |
| iOS 시뮬레이터로 보고 싶다 | Xcode 27이 설치되어 있다. `xcode-select`가 Command Line Tools를 가리키고 있으면 `sudo xcode-select -s /Applications/Xcode.app`을 한 번 실행하거나, 명령 앞에 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`를 붙인다. 그 다음 `npx expo start --ios`를 실행하면 시뮬레이터를 부팅하고 Expo Go를 자동 설치한다. 처음에는 Expo Go의 개발 메뉴 안내가 뜨는데 `Continue`를 누르면 된다 |
| 시뮬레이터를 스크립트로 조작하고 싶다 | 탭·스와이프·문자 입력은 `idb`(`brew tap facebook/fb && brew install idb-companion`, `pip3 install --user fb-idb`), 스크린샷은 `xcrun simctl io booted screenshot 파일.png`. 좌표는 포인트 단위(iPhone 16 Pro는 402×874) |
| 휴대폰과 브라우저의 데이터가 다르다 | 정상이다. 데이터는 각 기기(웹은 브라우저 저장소)에 따로 저장된다 |

### 점검 명령

타입 검사 (`tsc --noEmit`):

```bash
npm run typecheck
```

Expo 의존성·설정 점검:

```bash
npx expo-doctor
```

오류 문구 표가 서버 카탈로그와 맞는지 점검 (서버 오류 36 · 필드 오류 21 · 앱 5, [20_오류_응답.md](20_오류_응답.md) 6장):

```bash
npm run check:errors
```

## 3. 처음 실행 시

스플래시 화면에서 둘 중 하나를 고른다.

| 선택 | 결과 |
|---|---|
| **샘플 옷장으로 둘러보기** | 샘플 옷 24벌(사진 18벌), 지난 착용 기록 2건, 다가오는 예정 2건으로 시작 |
| **내 옷으로 시작하기** | 빈 옷장으로 시작. 상의·하의를 1벌씩 등록하면 추천이 나온다 |

그다음 2단계 설정(1단계: 출근 복장·선호 분위기·자주 입는 색, 2단계: 근무 형태·근무 요일, '근무일엔 출근 코디로'·'쉬는 날엔 편한 데일리로' 토글)을 거쳐 홈으로 간다. '건너뛰기'를 누르면 기본값(비즈니스 캐주얼, 단정·미니멀, 네이비·베이지·화이트, 평일 근무)을 쓴다.

샘플 데이터([seed.ts](../mobile/src/data/seed.ts), [sample.ts](../mobile/src/lib/sample.ts))는 다음과 같다. 날짜는 모두 실행한 날 기준으로 계산한다.

| 데이터 | 내용 |
|---|---|
| 옷 24벌 | 상의 6 · 하의 7 · 원피스 1 · 아우터 4 · 신발 3 · 가방 2 · 액세서리 1. 18벌은 디자인 보드 옷장 격자의 옷 사진(`assets/samples/`), 6벌(셔츠·슬랙스·블레이저·로퍼·숄더백·시계)은 출근 코디가 돌도록 더한 사진 없는 옷(일러스트). 스트라이프 긴소매 티 1벌은 '세탁 중'. 사진은 `wearly-sample://<키>` 고정 주소로 저장하고 그릴 때 번들 이미지로 바꾼다(`lib/samplePhotos.ts`). 계정 모드는 bulk 등록 응답(요청 순서대로)의 서버 id에 같은 자리 사진을 붙인다 |
| 지난 착용 기록 2건 | 어제부터 거슬러 올라간 최근 근무일 2일. 그날 추천 1·2순위 코디로 만들었고 별점 4·칭찬, 별점 3·보통 |
| 다가오는 예정 2건 | 24일 뒤 '결혼식 하객'(코디 저장됨) · 8일 뒤 '외근 · 거래처 미팅'(추천 대기) |

데이터를 되돌리는 방법:

| 메뉴 | 동작 |
|---|---|
| 마이 > 처음부터 다시 시작 | 옷장·코디·기록·선호도·프로필을 모두 지우고 온보딩으로 돌아간다 |
| 마이 > 샘플 옷장 다시 불러오기 | 옷장·기록·예정·저장 코디를 샘플로 바꾸고 선호도를 초기화한다. 취향·근무 패턴은 유지한다 |

## 6. 추천 엔진

구현: [recommend.ts](../mobile/src/lib/recommend.ts). 색·종류 속성과 상황별 격식 값은 [constants.ts](../mobile/src/data/constants.ts)에 있다. 기획서 p.24의 초기 점수 모델을 그대로 옮겼다.

### 6.1 흐름

| 단계 | 구현 |
|---|---|
| 1. 조건 입력 | 상황·분위기·격식·날씨·기준 날짜, 선택으로 중심 아이템·고정 아이템·최근 착용 제외·피하고 싶은 색·컨셉. 홈은 근무 패턴으로 자동 설정한다: 근무일은 출근·단정·비즈니스 캐주얼, 휴무일은 데일리·편안·편한 데일리 ([context.ts](../mobile/src/lib/context.ts)) |
| 2. 옷장 조회 | 옷장 아이템, 프로필, 아이템별 선호도, 최근 7일 안에 저장·기록한 코디를 모은다 ([useStore.ts](../mobile/src/store/useStore.ts)의 `engineInput`) |
| 3. 후보 생성 | 칸(상의·하의·아우터·신발·가방)별 후보를 거른 뒤 상의 × 하의 × 아우터(없음 포함) × 신발을 모두 조합한다. 가방은 조합 수를 줄이려고 색상 조화 점수가 가장 높은 하나만 붙인다. 샘플 옷장에서는 수백 개 조합을 모두 평가한다 |
| 4. 점수 평가 | 5개 항목 점수를 가중합해 100점 만점으로 환산 |
| 5. 상위 선정 | 점수순으로 서로 충분히 다른 3안을 고른다 (6.5) |
| 6. 설명 생성 | 중심 아이템 → 색 → 날씨 → 다양성 순으로 이유를 모으고, 3개가 안 되면 상황 이유를 더해 최대 3개 |

추천 이유 예시: "네이비×베이지 조합이 안정적이에요", "일교차 11°C — 베이지 재킷을 더했어요", "34일 동안 안 입은 카키 치노 팬츠를 살렸어요".

### 6.2 가중치

| 색상 조화 | 상황 적합 | 날씨 적합 | 개인 취향 | 다양성 |
|---|---|---|---|---|
| 30% | 25% | 20% | 15% | 10% |

최종 점수 = 가중합 ÷ 가중치 합 × 100 (반올림). 날씨가 없으면 날씨 항목을 빼고 나머지 4개 가중치 합(80%)으로 나눠 재조정한다. 다만 목업에서는 날씨가 항상 있으므로(가짜 예보 또는 직접 입력) 이 경로는 화면에 나오지 않는다.

### 6.3 점수 항목

각 항목은 0~1 사이 값이며, 계산 후 0~1로 자른다.

**색상 조화** (기본 0.6)

| 조건 | 점수 |
|---|---|
| 상의·하의·아우터 색 중 '잘 어울리는 조합'(20쌍) 한 쌍마다 | +0.15 |
| 포인트 색(뉴트럴이 아닌 색)이 2개 이상 | −0.25 |
| 포인트 색 1개 + 다른 색 | +0.05 |
| 모두 뉴트럴이고 2색 이상 (톤온톤) | +0.10 |
| 상의·하의가 같은 포인트 색 | −0.15 |
| 상의·하의 밝기 차이 0.3 이상 | +0.10 |
| 무늬 있는 옷 2벌 이상 | −0.20 |
| 신발·가방이 같은 색이거나 둘 다 어두운 색 | +0.05 |

> 보조 색(이슈 #4, 2026-10-18): 옷은 색을 1~3개 가질 수 있고 위 표는 **주 색상**으로 계산한다. 보조 색이 있는 코디에만 마지막에 보조 색 짝(+0.05, 합계 최대 +0.1)·색 반복(+0.05)·보조 포인트 과다(−0.1)를 더하고 뺀다. 상수와 규칙은 [09_AI_코디_추천.md](09_AI_코디_추천.md) 2.1장, 기온별 계절 표(초봄·초여름·초가을 포함)는 2.2장.

뉴트럴은 네이비·블랙·차콜·그레이·화이트·아이보리·베이지, 포인트 색은 카멜·브라운·카키·라이트블루·버건디다.

**상황 적합**

- 목표 격식 = (상황 격식 + 선택한 격식) ÷ 2
  - 상황 격식: 출근 2 · 회의 2.5 · 외근 2 · 회식 1.5 · 데일리 1 · 면접 3 · 결혼식 하객 2.7 · 데이트 1.7 · 여행 1 · 모임 1.5
  - 선택한 격식: 편한 데일리 1 · 비즈니스 캐주얼 2 · 포멀 3
  - 아이템 격식은 등록할 때 1~3으로 정한다
- 아이템별 적합도: 목표보다 **덜 갖춰 입으면** 1 − 차이 × 0.8, **더 갖춰 입으면** 1 − 차이 × 0.4. 상의·하의·아우터·신발의 평균을 낸다.
  - 예: 회의 + 비즈니스 캐주얼이면 목표 2.25. 가디건(1)은 0점, 블레이저(3)는 0.7점이다.
- 점수 = 적합도 평균 × 0.8 + 분위기가 맞는 아이템 비율 × 0.2
  - 분위기별 스타일: 단정 → 단정·클래식·미니멀, 편안 → 캐주얼, 세련 → 미니멀·클래식
  - 분위기가 '편안'이고 스니커즈나 니트가 있으면 +0.05

**날씨 적합** (기본 0.7)

| 조건 | 점수 |
|---|---|
| 아우터가 필요한 날(기온 17°C 미만, 또는 일교차 10°C 이상이면서 최저 16°C 미만)에 아우터 있음 / 없음 | +0.2 / −0.4 |
| 24°C 이상인데 아우터 있음 | −0.4 |
| 보온 합계와 필요 보온의 차이 1당 | −0.08 |
| 계절이 맞는 옷 1벌당 / 안 맞는 옷 1벌당 | +0.03 / −0.10 |
| 강수확률 60% 이상인데 밝은 신발 | −0.15 |

- 필요 보온: 5°C 미만 5, 10°C 미만 4, 15°C 미만 3, 20°C 미만 2, 그 이상 1
- 보온 값(세부 종류별 고정): 티셔츠·스커트 0, 셔츠·가디건·슬랙스·와이드 팬츠·치노 팬츠 1, 니트·재킷 2, 코트 3. 상의·하의·아우터를 더한다.
- 기온별 계절: 24°C 이상 여름, 17~23°C 봄·가을·여름, 9~16°C 봄·가을, 4~8°C 가을·겨울, 4°C 미만 겨울

**개인 취향** (가방 포함 모든 아이템의 평균)

- 아이템마다 기본 0.5
- 선호 스타일(프로필의 선호 분위기 + 예정일 컨셉)과 겹치면 +0.3, 안 겹치면 −0.09
- 자주 입는 색이면 +0.1
- 선호도(−3~3) × 0.1 (6.7 참고)

**다양성** (상의·하의·아우터·신발의 평균)

- 0~2일 전에 입은 옷 0.2, 3~6일 전 0.6, 7일 이상 지났거나 안 입은 옷 1.0
- 최근 7일 안에 저장·기록한 코디와 상의·하의·아우터가 3개 같거나, 아우터 없이 2개 같으면 −0.3

| 제외한 색상 반영 | '피하고 싶은 색'의 아이템을 후보에서 뺀다 |
| 고정 아이템은 교체하지 않음 | 고정·중심 아이템이 있으면 그 칸은 그 아이템 하나로만 조합한다. 이 아이템에는 상태·피하고 싶은 색 조건을 적용하지 않는다. 홈에서 핀으로 고정한 아이템은 '전체 바꾸기'에서도 유지된다 |
| 최근 착용 아이템 제외 | **상의·하의·아우터에만** 적용한다. 기준 날짜로부터 3일 안(0~2일 전)에 입은 옷을 뺀다. 빼고 나서 상의나 하의가 하나도 남지 않으면 그 칸은 빼지 않는다. 신발·가방은 매일 같은 것을 쓰는 경우가 많아 제외하지 않는다. 홈에서는 항상 켜져 있고, AI 코디 화면에서는 스위치로 끈다 |

아우터는 '없음'도 후보에 들어간다(아우터를 고정했으면 그 아우터만). 액세서리는 추천에 쓰지 않는다.

### 6.5 상위 3안 선정

모든 조합을 점수순으로 정렬한 뒤, 이미 고른 코디들과 **상의·하의·아우터·신발 중 2칸 이상 다른** 코디를 차례로 고른다. 3개가 안 채워지면 1칸 이상 다른 코디로 마저 채운다. 1~3위가 신발만 다른 비슷한 코디로 채워지지 않게 하려는 장치다(기획서 p.15 "추천 품질·다양성 균형").

홈은 1안을 먼저 보여주고 '전체 바꾸기'를 누를 때마다 다음 안으로 넘어간다. 그날 저장한 코디가 있으면 그것을 먼저 보여준다.

### 6.6 한 벌 교체

교체 시트(`alternativesFor`)는 그 칸에 들어갈 수 있는 다른 '보유 중' 옷을 하나씩 넣어 코디 전체 점수를 다시 계산하고, 점수순으로 보여준다. 지금보다 몇 점 오르고 내리는지도 표시한다. 아우터와 가방은 '빼기'도 후보다. 교체 후보에는 피하고 싶은 색과 최근 착용 제외를 적용하지 않는다.

### 6.7 선호도 학습

아이템별 선호도(affinity)를 행동에 따라 올리고 내린다([useStore.ts](../mobile/src/store/useStore.ts), [OutfitView.tsx](../mobile/src/components/OutfitView.tsx)).

| 행동 | 변화 | 대상 |
|---|---|---|
| 저장한 코디에 '좋아요' | +1 | 코디의 모든 아이템 |
| 저장한 코디에 '별로예요' | −0.5 | 코디의 모든 아이템 |
| 교체 시트에서 바꿈 | −0.3 | 빠진 아이템 |
| 착용 기록 | (별점 − 3) × 0.4 + 주변 반응(칭찬 +0.5, 보통 0, 아쉬움 −0.3) | 입은 모든 아이템 |
| 칭찬받은 아이템 지정 | +0.5 추가 | 그 아이템 |

- 선호도는 아이템별로 −3~3 사이로 제한하고, 개인 취향 점수에 × 0.1로 들어간다(아이템당 최대 ±0.3).
- 예: 별점 5에 칭찬을 받으면 입은 옷마다 +1.3이다.
- 착용 기록은 착용 횟수(+1, 같은 날 중복 기록은 제외)와 마지막 착용일도 갱신한다. 이 값은 다양성 점수와 최근 착용 제외에 쓰인다.
- '별로예요'의 사유(색 조합, 격식 등)는 저장만 하고 아직 점수에 쓰지 않는다.
- '샘플 옷장 다시 불러오기'를 하면 선호도가 초기화된다.

### 7.3 처방

**① 내 옷장에서 교체**

- 코디에 있는 칸마다 교체 후보 상위 4개(추천 점수 기준)를 살펴본다.

### 7.4 진단 시점과 화면

- 착용 기록을 저장할 때 한 번 계산해 기록에 함께 저장한다. 나중에 옷장이 바뀌어도 다시 계산하지 않는다.
- 진단 조건은 그날 저장한 코디의 조건 → 예정일 코디의 조건 → 홈 기본 조건 순으로 가져온다. 최근 착용 제외는 끈다.
- 3축 비교(p.18)에서 주변 반응은 별점으로 바꿔 보여준다: 칭찬 5, 보통 3, 아쉬움 2.
- 칭찬받은 아이템이 있거나 별점이 4 이상이면 '다음 추천에 반영' 카드를 보여준다(실제 반영은 6.7의 선호도).

## 10. 알려진 한계

- 실제 휴대폰에서는 실행해 보지 않았다. 브라우저와 iOS 시뮬레이터에서만 확인했다.
- 카메라 촬영은 시험하지 않았다 (시뮬레이터에는 카메라가 없다). 앨범 선택은 시뮬레이터에서 확인했다.
- **사진 저장 방식 (2026-10-18 변경, [18_사진_저장.md](18_사진_저장.md))**: 처음 목업은 고른 사진의 URI를 그대로 두어 OS가 캐시를 비우면 사라질 수 있었다. 지금은 계정 모드(서버 연결)에서 사진을 JPEG(긴 변 1600 이하, 품질 0.8)로 바꿔 서버 오브젝트 스토리지에 올리고, 목록·상세는 서버 사진(`image.thumbUrl`·`url`, `imageId` 기반 캐시)으로 그린다. 게스트·목업 실행은 서버가 없어 기기에만 두되 앱 문서 폴더(`Paths.document/photos/{itemId}.jpg`)로 복사한다. 서버에 올리지 못한 기존 기기 사진은 앱이 시작하거나 복귀할 때 3장씩 서버로 옮긴다. 이 문서의 검증 기록(브라우저·시뮬레이터 확인)은 서버 사진 저장 이전 기준이다.
- 옷 상세에서 사진을 바꾸는 화면은 아직 없다 (서버 API는 있다).
- **오류 문구와 오류 번호 (2026-10-18, [20_오류_응답.md](20_오류_응답.md))**: 서버 오류 응답에는 문장이 없다. 앱은 `src/lib/errorText.ts`의 표(서버 오류 코드 44·필드 오류 코드 21·앱이 만드는 코드 5)로 `code`·`params`를 한국어 문구로 바꾸고, `ApiError.message`를 화면에 그대로 보이지 않는다. 표가 서버 카탈로그(`backend/src/main/resources/error-codes.json`)와 맞는지 `npm run check:errors`가 확인한다. 500·503 같은 **시스템 오류에만** 문구 아래에 "오류 번호 ab12cd34"(`traceId` 앞 8자)가 작게 나오고, 길게 누르면 전체 번호를 복사한다(`expo-clipboard`). 문의할 때 이 번호로 서버 로그를 찾는다.
- **예정 코디 서버 동기화 (2026-10-18, [21_예정_코디_저장.md](21_예정_코디_저장.md))**: 계정 모드에서는 예정 코디를 기기에 먼저 저장하고 서버(`/plans`)에도 보낸다. 로그인·앱 시작·복귀 때(`syncPlans`) 기기의 예정을 `clientId`(= 기기 예정 id)로 올리고(100개씩) 서버 목록과 합친다(양쪽에 있으면 더 늦게 고친 쪽). 오프라인 등으로 못 보낸 변경은 `pending`으로, 지운 예정은 `planDeletes` 기록으로 남겨 다음에 다시 보낸다. 서버가 입력 오류로 거절한 예정은 `syncBlocked`로 기기에만 두고, 500개를 넘으면(`PLAN_LIMIT`) 안내만 한다. 계정 모드에서는 옷을 지워도 예정 코디에서 빼지 않고 캘린더에 흐리게 "지운 옷"으로 보인다. 게스트와 목업 실행은 기기만 쓴다. 실제 휴대폰·시뮬레이터에서는 아직 확인하지 않았다.
- 예정일 코디의 날짜 칩 줄이 선택한 날짜로 자동 스크롤되지 않는다.
- 날씨와 AI 사진 분석은 가짜다 (8장).
