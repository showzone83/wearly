**남은 것**

- M2: 공급자 종류는 여전히 도메인 enum `AiProviderType`(옵션 목록 포함)과 DB CHECK `ck_ai_provider_type`에 있다. 기존 테스트가 enum과 그 검증을 고정하고 있고, CHECK를 빼면 DB가 모르는 종류를 막지 못하므로 남겼다. 새 공급자는 4곳 + 마이그레이션 1곳(전에는 6곳 + 1곳).
- L4: `UserProfile.Notify.toMap/fromMap`(저장 모양)은 도메인에 남았다(위).
- `ErrorCode` 한 enum에 컨텍스트 고유 오류가 모여 있다(8장의 낮음 수준 지적). 상태 번호를 가진 `ApiException`을 유스케이스가 던지는 타협(L1 본문)과 함께 그대로 둔다.
- `PersistenceClock`은 엔티티 콜백에 Clock을 넘기려고 정적 필드를 쓴다. 한 JVM에서 Spring 컨텍스트 여럿이 다른 Clock을 쓰면 마지막 것이 이긴다(지금은 모두 `Clock.systemUTC()`).
- M9의 "통합 테스트는 API 계약과 SQL 위주로 줄인다"는 하지 않았다. 기존 테스트는 기대값을 바꾸지 않는다는 5차 조건 때문에 그대로 두고 단위 테스트를 더했다.
- 관리자 AI 기록의 기능 필터 목록(`AdminDashboardService.FEATURE_NAMES`)은 ai 기능 + outfit 기능을 admin이 모아 만든다. AI를 쓰는 컨텍스트가 늘면 여기에 더한다.

## 0. 전체 평가

### 잘 된 점

1. **의존 방향과 패키지 모양이 7개 컨텍스트 모두에서 같고, 테스트로 강제된다.** 도메인 패키지에는 Spring·JPA·Jackson import가 하나도 없다. 컨텍스트 사이 import는 모두 상대 `application.port.in`으로만 간다. 코드 수준 의존 그래프에는 순환이 없다(`auth→user`, `user→code`, `wardrobe→code`, `ai→code,user`, `admin→ai,auth,code,user`, `outfit→ai,code,user,wardrobe`). [확인]
2. **JPA 엔티티가 영속성 어댑터 밖으로 나가지 않는다.** 모든 영속성 어댑터에서 엔티티와 도메인을 직접 바꾼다(예: `wardrobe/adapter/out/persistence/ItemPersistenceAdapter.java:52-69`, `user/adapter/out/persistence/UserPersistenceAdapter.java:43-46`). wardrobe·code·ai는 MyBatis 행도 어댑터 안에서 도메인 값으로 바꾼다(`ItemQueryAdapter.java:65-82`, `CodeSnapshotCache.java:81-109`).
3. **트랜잭션 경계를 의도해서 설계했다.** AI 호출 유스케이스(`AiAnalysisService`, `AiJsonGenerationService`, `OutfitRecommendService`)에는 `@Transactional`을 일부러 붙이지 않아 외부 호출 동안 DB 연결을 잡지 않는다. 관리자 변경과 감사 로그는 `Propagation.MANDATORY`로 같은 트랜잭션에 묶는다(`admin/adapter/out/persistence/AuditLogPersistenceAdapter.java:24`). 캐시는 커밋한 뒤에 다시 읽는다(`code/adapter/out/query/CodeSnapshotCache.java:66-79`).
4. **풍부한 도메인이 일부 있고, Spring 없이 테스트된다.** `auth.domain.RefreshToken`(회전·재사용 감지), `outfit.domain`(`OutfitPool`, `CandidateValidator`, `OutfitRequest.Weather`)은 규칙을 직접 갖고 있다. `JsonOutputHandler` 콜백 설계(`ai/application/port/in/JsonOutputHandler.java`)도 좋다. 호출하는 쪽(outfit)의 도메인 검증을 결과로 받아서 공급자 폴백을 정하므로, ai 컨텍스트가 코디 규칙을 몰라도 된다.
5. **기술 세부를 포트 뒤로 숨겼다.** Anthropic SDK·RestClient·AES-GCM·환경변수 조회는 각각 `AiModelPort`/`AiModelFactoryPort`, `SecretCipherPort`, `ApiKeyEnvPort`, `ApiKeyVerifierPort` 뒤에 있다. `MultipartFile`은 웹 경계에서 `ImageUpload`로 바뀐다(`common/web/Uploads.java`).

### H1. code 컨텍스트가 SQL로 wardrobe·user 테이블을 직접 읽는다 (숨은 역방향 의존) [확인]

**무엇이·어디서**: 코드 삭제 가드와 관리자 사용 수 집계가 `CodeUsagePort`(`code/application/port/out/CodeUsagePort.java:5-15`)를 거친다. 그런데 이 포트의 MyBatis 구현은 다른 컨텍스트가 가진 테이블을 직접 읽는다. `resources/mapper/code/CodeQueryMapper.xml:42-56`(`countItemUsage`, `tb_wardrobe_item` 7번), `:58-71`(`countItemsUsing`, wardrobe 컬럼 이름과 배열 구조를 그룹별로 하드코딩), `:73-80`(`countProfilesUsing`, `tb_user_profile.colors`·`moods`)이 그렇다. 자바 의존은 `wardrobe → code`(`CodeCatalog`), `user → code` 방향인데, 데이터 의존은 `code → wardrobe`, `code → user`로 반대 방향이다. 컨텍스트 수준에서 순환이다. 관리자 조회(`resources/mapper/admin/AdminQueryMapper.xml:36-40, 74-84, 102-127`)도 `tb_user`, `tb_wardrobe_item`, `tb_ai_analysis_log`를 직접 읽는다. 다만 이쪽은 `AdminQueryPort.java:12-14`에 "읽기 모델이라 여러 테이블을 함께 읽는다"고 의도를 적어 두었다.

**왜 문제인지**: wardrobe가 코드 값을 담는 컬럼을 하나 더 만들거나(예: `fit`) 프로필에 코드 배열을 하나 더 두면 code 쪽 XML도 함께 고쳐야 한다. 이를 잊어도 컴파일·ArchUnit은 통과한다. 그러면 `CODE_IN_USE` 가드(`CodeManagementService.java:169-186`)가 사용 중인 코드를 지우도록 놔두는 **데이터 무결성 문제**가 된다. 테이블 소유권이 컨텍스트 경계와 어긋나 있어서, 나중에 모듈을 분리하거나 스키마를 나눌 때 가장 먼저 깨질 곳이다.

**고치는 방향**: (1) 최소 대응은 08 문서에 "다른 컨텍스트 테이블을 읽는 SQL 목록"을 예외로 적고, 그 테이블을 가진 쪽 통합 테스트(새 코드 컬럼을 추가하면 실패하는 테스트)로 묶는 것이다. (2) 구조로 풀려면 의존을 뒤집는다. code가 "코드 사용처" SPI(`CodeUsageContributor`: `count(group, code)`)를 정의하고, wardrobe·user가 각자 자기 테이블로 구현한다. code는 등록된 구현을 모아서 합친다. 이렇게 하면 의존이 `wardrobe → code` 한 방향으로만 남는다. 다만 지금 ArchUnit 규칙("다른 컨텍스트는 `port.in`만", "출력 포트 구현은 자기 출력 어댑터")과 부딪히므로 규칙 예외를 하나 정의해야 한다. (3) 관리자 읽기 모델은 지금처럼 두되, `AdminQueryMapper.xml`이 읽는 테이블·컬럼 목록을 문서에 적어 두기를 권한다.

### H2. 회원·옷장 아이템의 불변식이 도메인 밖(웹 DTO·호출자)에 흩어져 있다 [확인]

**무엇이·어디서**:
- 옷장: `ItemInput`의 주석(`wardrobe/domain/ItemInput.java:6-9`)이 "필수·길이 검증은 웹 어댑터(요청 DTO)가 먼저 한다"고 적고 있다. 실제로 이름 필수·40자, 격식 1~3, 착용 수 0 이상은 `WardrobeDtos.ItemRequest`의 Bean Validation(`wardrobe/adapter/in/web/WardrobeDtos.java:23-39`)에만 있다. `WardrobeItem.apply`(`wardrobe/domain/WardrobeItem.java:73-86`)는 `in.name().strip()`(74행)을 그대로 호출해서, 이름이 null이면 NPE가 난다.
- 회원: `User`(`user/domain/User.java:42-52`)는 상태·역할을 아무 문자열이나 받는 setter다. `UserUseCase.changeAccess`는 주석으로 "검증은 부르는 쪽 책임"이라고 적는다(`user/application/port/in/UserUseCase.java:16-17`). 허용 값과 "자기 자신을 정지·강등할 수 없음" 규칙은 관리자 서비스(`admin/application/service/AdminUserService.java:35-36, 99-119`)에 있다. "이름 20자" 규칙은 세 곳에 따로 있다. `AuthDtos.java:29`(`@Size(max = 20)`), `ProfileDto.java:21-23`, 그리고 `AdminAccountService.java:43-45`(검증 대신 잘라 냄)다. `UserService.create`·`ProfileService.put`(`ProfileService.java:75`)은 이 규칙을 모른다.

**왜 문제인지**: 지금은 웹 어댑터 하나가 거의 모든 입력을 받으므로 겉으로 드러나지 않는다. 하지만 다음 할 일에 소셜 로그인(카카오·애플·구글)이 있다. 새 입력 어댑터나 다른 컨텍스트(이미 auth·admin이 `UserUseCase.create`·`changeAccess`를 부른다)가 유스케이스를 부르면, 규칙을 건너뛰고 DB 제약 위반(500)이나 잘못된 상태 값이 들어갈 수 있다. 헥사고날의 핵심 이점("입력 어댑터를 바꿔 끼워도 규칙은 그대로")이 이 두 컨텍스트에서는 성립하지 않는다.

**고치는 방향**: 형식 검증(JSON 타입·필수 필드)은 웹 DTO에 두고, **업무 불변식은 도메인 생성자·메서드로 옮긴다**. 예: `WardrobeItem.create/apply`에서 이름 1~40자, 격식 1~3, 착용 수 0 이상을 확인하고 `FieldError`를 모은다(코드 검증 `ItemCodeValidator`와 같은 방식). `User`는 상태·역할을 enum으로 바꾸고 `suspend()`, `changeRole(Role)`, `rename(name)`이 규칙을 지키게 한다. "자기 자신 정지 금지"는 관리자 정책이므로 admin에 남겨도 된다. 이렇게 옮기면 도메인 단위 테스트로 규칙을 검증할 수 있다.

## 2. 중간

### M1. 사진 분석의 업무 검증·프롬프트가 공급자 어댑터 안에 있다 [확인]

**무엇이·어디서**: `AiModelPort.analyze(AiImage, CodeSnapshot)`(`ai/application/port/out/AiModelPort.java:22-27`)는 "활성 코드 안의 값으로 제안을 만든다"는 업무 계약을 출력 포트에 지운다. 그래서 공급자 어댑터 셋이 각각 도메인 프롬프트·스키마를 직접 조립한다(`ClaudeAiProvider.java:143, 153`, `OpenAiProvider.java:160, 165`, `GeminiAiProvider.java:179, 183`). 결과 검증도 어댑터 패키지의 `SuggestionParser.parse`(`ai/adapter/out/ai/SuggestionParser.java:45-96`)가 한다. 여기에는 활성 코드 여부, 종류-세부 종류 짝, 격식 1~3, 확신도 0~1, 이름 40자 자르기가 들어 있다. 반면 같은 컨텍스트의 `generateJson`(`AiModelPort.java:34`)은 "JSON만 돌려주고 내용 검증은 호출한 쪽"이라는 일반 계약이다.

**왜 문제인지**: 같은 컨텍스트 안에서 "공급자 = 운송 수단"(JSON 생성)과 "공급자 = 업무 수행자"(사진 분석)라는 두 모델이 섞여 있다. 사진 분석 규칙이 바뀌면(예: 계절 최대 4개) 어댑터 패키지를 고쳐야 한다. 새 공급자 어댑터를 쓰는 사람은 옷장 규칙까지 알아야 한다. 검증 실패 사유도 공급자 오류(`AiProviderException("INVALID_OUTPUT")`)로 기록되어, 도메인 거부와 운송 실패를 구분할 수 없다.

**고치는 방향**: `analyze`를 "이미지 + 지시문 + 스키마 → JSON"으로 일반화한다(`generateJson`에 이미지를 붙인 형태). 그리고 `AnalysisPrompt` 조립과 `SuggestionParser`의 검증 부분을 애플리케이션/도메인(`AiSuggestionValidator`)으로 옮긴다. 그러면 `JsonOutputHandler`와 같은 방식으로 "검증 거부 → 다음 공급자"를 한 루프로 처리할 수 있다(L7 재시도 루프 중복도 함께 줄어든다).

### M2. 새 AI 공급자를 추가할 때 고칠 곳이 많고, 공급자 지식이 도메인에 있다 [확인]

**무엇이·어디서**: 예를 들어 `MISTRAL`을 추가하려면 다음을 고쳐야 한다.
1. 새 어댑터 클래스(`analyze`·`generateJson` 둘 다, M1 때문에 프롬프트·파서 연결 포함)
2. `ai/domain/AiProviderType.java:10-69` enum 상수와 옵션 명세
3. `ai/domain/ProviderDefaults.java:4-18` 기본 URL·토큰 상수
4. `ai/adapter/out/ai/AiProviderFactory.java:78-124`의 `switch`(switch 식이라 빠뜨리면 컴파일 오류가 나서 다행이다)
5. `ai/adapter/out/ai/ApiKeyVerifier.java:49-74`의 `switch`(`default`가 있어 빠뜨려도 **실행 중에야** `IllegalArgumentException`이 난다, 73행)
6. `ai/domain/AiProviderRules.java:39, 43`의 오류 문구 "CLAUDE, OPENAI, GEMINI 중 하나"
7. DB 마이그레이션: `V3__admin_ai.sql:25`의 `ck_ai_provider_type CHECK`

`AiProviderType`의 설명에는 "Anthropic Java SDK", "Responses API, REST", `output_config.effort` 같은 SDK·API 세부가 들어 있다(12, 27, 48행).

**왜 문제인지**: 공급자 선택·폴백 순서(`AiProviderSelection`, `AiProviderRegistry`)는 애플리케이션·도메인에 있어서 적절하다. 그런데 "어떤 공급자가 있고 어떤 옵션을 받는가"는 어댑터 지식인데 도메인 enum에 있어서, 공급자를 하나 추가할 때 도메인·어댑터·DB를 함께 고쳐야 한다. 5번처럼 컴파일러가 잡아 주지 않는 곳도 있다.

**고치는 방향**: 어댑터 쪽에 `AiProviderModule` 인터페이스(`type()`, `options(): List<OptionSpec>`, `create(setting, key)`, `verify(setting, key)`)를 두고 공급자마다 Spring 빈 하나로 등록한다. 팩토리와 검증기는 등록된 모듈 목록을 쓴다. 도메인의 `AiProviderType`은 문자열 값 객체로 줄이고, 허용 값은 `AiModelFactoryPort.supportedTypes()`로 받는다. 이렇게 하면 공급자 추가는 "모듈 1클래스 + (CHECK를 유지한다면) 마이그레이션"이 된다.

### M3. 관리자 MyBatis 결과 행이 `port.out`에 있고 XML이 문자열로 참조한다 [확인]

**무엇이·어디서**: `admin/application/port/out/AdminRows.java:6-72`은 공개 가변 필드를 가진 클래스 묶음이다("MyBatis가 setter 없이 필드로 채운다"). MyBatis XML이 이 클래스를 직접 결과 타입으로 쓴다(`AdminQueryMapper.xml:6, 24, 36, 42, 50, 74`, 예: `type="app.wearly.admin.application.port.out.AdminRows$AiLogRow"`). 서비스는 행 필드를 직접 읽는다(`AdminDashboardService.java:58-73, 142-171`, `AdminUserService.java:141-151`). 다른 컨텍스트는 행을 어댑터 안(`adapter/out/query/*Row`)에 두고 바꾸므로 방식이 다르다.

**왜 문제인지**: 08 문서 1장 "MyBatis 결과 행은 어댑터 밖으로 나가지 않는다"와 어긋난다. XML 문자열 참조라 ArchUnit도 못 본다. 컬럼 별칭 하나만 바꿔도 애플리케이션 서비스 코드가 영향을 받는다. 또한 `null` 가능한 `Long` 집계 값을 서비스가 직접 0으로 바꾸고 있다(`AdminDashboardService.java:69-70`). 이 처리는 어댑터가 해야 할 일이다.

**고치는 방향**: 행 클래스를 `admin/adapter/out/query/`로 옮기고, `AdminQueryPort`는 불변 record(예: `DashboardCounts`, `AiLogEntry`)를 돌려주게 한다. 변환은 `AdminQueryAdapter`에서 한다. 이 작업은 기계적이라 위험이 낮다.

### M4. PATCH 처리 방식이 두 가지이고, JSON 추상화가 도메인·유스케이스로 들어왔다 [확인]

**무엇이·어디서**:
- 방식 A (code·ai·admin): `common/domain/PatchBody.java:5-40`가 `isString`, `isInt`, `isObject`, `object(field): Map` 같은 **JSON 노드 API**를 정의한다. 유스케이스가 이걸로 타입 검사와 오류 문구를 직접 만든다. 예: `CodeManagementService.java:96-132`("정수여야 해요", "JSON 객체여야 해요"), `AiProviderAdminService.java:152-219`, `AdminUserService.java:92-120`.
- 방식 B (wardrobe): `port.in.ItemPatch`(`wardrobe/application/port/in/ItemPatch.java:5-13`)를 웹 어댑터가 구현한다(`JsonItemPatch.java:52-74`). 유스케이스가 트랜잭션 안에서 이것을 호출하므로(`WardrobeService.java:95-106`, 100행), Jackson 변환과 Bean Validation 같은 **웹 코드가 애플리케이션 트랜잭션 안에서 실행된다**.

**왜 문제인지**: A에서는 유스케이스가 "요청이 JSON"이라는 사실에 묶인다. 다른 입력 어댑터는 `PatchBody`를 흉내 내야 한다. B는 의존 방향은 지키지만(인터페이스는 `port.in`에 있다), 제어 흐름이 애플리케이션 → 웹으로 되돌아간다. 같은 문제를 두 방식으로 풀어서 새 컨텍스트를 만드는 사람이 어느 쪽을 따라야 할지 정해져 있지 않다.

**고치는 방향**: "보낸 필드 / 보내지 않은 필드 / null"을 표현하는 타입 있는 부분 명령으로 통일한다. 예: `record PatchCodeCommand(Optional<String> label, Patch<String> parent, Optional<Integer> sortOrder, …)`. 여기서 `Patch<T>`는 "없음 / null / 값" 세 상태다. JSON → 명령 변환과 타입 오류는 웹 어댑터에서 처리하고, 유스케이스는 업무 검증만 한다. `PatchBody`는 `common.web`으로 내리거나 없앤다.

### M5. JPA 쓰기 → MyBatis 읽기 일관성이 수동 flush에 걸려 있다 [확인]

**무엇이·어디서**: Hibernate의 AUTO flush는 Hibernate를 거치는 쿼리 앞에서만 일어난다. MyBatis는 같은 커넥션을 쓰지만 Hibernate가 모르는 JDBC 쿼리라서, flush하지 않은 변경을 보지 못한다. 그래서 코드 곳곳에 flush가 계약으로 박혀 있다.
- `CodePort.flush()`, `saveAllAndFlush`(`code/application/port/out/CodePort.java:23-30`). 서비스가 4번 직접 부른다(`CodeManagementService.java:78, 137, 192, 218`). 그 뒤 `info()`가 MyBatis로 사용 수를 읽는다(`:229-239`).
- `UserPort.save`의 계약은 "바로 flush한다"(`user/application/port/out/UserPort.java:11-12`). `AdminUserService.patch`는 JPA로 바꾼 뒤(`:124`) 같은 트랜잭션에서 MyBatis로 다시 읽어 응답을 만든다(`:130`).
- `ItemPort.save`도 "바로 flush"(`ItemPort.java:12-13`)다. 하지만 `ItemPersistenceAdapter.delete`(`:48-50`)는 flush하지 않는다. 지금은 삭제 뒤 같은 트랜잭션에서 MyBatis로 읽는 곳이 없어서 문제가 없다.

**왜 문제인지**: 08 문서 3장 "같은 DataSource·트랜잭션 매니저를 쓴다"만으로는 일관성이 보장되지 않는다. 실제 보장은 "모든 JPA 어댑터가 flush한다"는 암묵 규칙에서 나온다. `flush()`라는 JPA 개념이 포트 이름에 드러나 출력 포트가 기술 중립적이지 않다. 새 어댑터가 flush를 빠뜨리면 응답이 이전 값을 보여 주는 버그가 생기는데, 이는 단위 테스트로 잡기 어렵다.

**고치는 방향**: (1) 08 문서에 "JPA 쓰기 포트는 반환 전에 flush한다. MyBatis 읽기 전에 쓰기가 반영돼 있어야 한다"를 명시 규칙으로 올린다. (2) `CodePort.flush()`는 포트에서 빼고, `save`·`delete`가 flush까지 하도록 어댑터 계약으로 옮긴다. (3) 더 안전하게 하려면 MyBatis 쿼리 어댑터 앞에서 `EntityManager.flush()`를 호출하는 인터셉터를 두는 방법도 있다(MyBatis `Interceptor` 또는 쿼리 어댑터 공통 기반). 다만 매 조회마다 flush 비용이 드는 대가가 있다.

### M6. 키 저장 시 외부 HTTP 검증이 DB 트랜잭션 안에서 돈다 [확인]

**무엇이·어디서**: `AdminAiService.setKey`(`admin/application/service/AdminAiService.java:104-122`, `@Transactional`)가 `AiProviderAdminService.setKey`(`ai/application/service/AiProviderAdminService.java:239-262`)를 부르고, 그 안의 `verifier.verify(s, key)`(249행)가 공급자 모델 목록 API를 호출한다. 시간 제한은 공급자 옵션이나 `wearly.ai.timeout`을 따른다. 104행 주석이 이 사실을 알고 받아들였다고 적고 있다.

**왜 문제인지**: 관리자 기능이라 빈도는 낮다. 하지만 외부 API가 느리거나 멈추면 그동안 DB 커넥션과 `findById` 행(트랜잭션 격리 수준에 따라 다름)을 잡고 있다. 같은 패턴이 다른 곳으로 복사되기 쉬운 선례가 된다.

**고치는 방향**: 검증 단계를 트랜잭션 밖으로 뺀다. 예: `ApiKeyVerificationUseCase.verify(providerId, key)`를 트랜잭션 없이 먼저 부르고, 성공하면 `setKey`(트랜잭션)로 저장한다. 오류 순서(404 → 409 → 403 → 400) 계약은 admin 서비스에서 그대로 조립할 수 있다.

### M7. 일일 한도 확인과 성공 기록이 원자적이지 않다 [추정]

**무엇이·어디서**: 사진 분석은 `AiAnalysisService.java:72-76`에서 오늘 성공 수를 세고 한도를 비교한 뒤, 몇 초 걸리는 AI 호출을 하고, `:87`에서 성공을 기록한다. 코디 추천도 같다(`OutfitRecommendService.java:94-98` 확인 → `:113` 생성 → ai 쪽 기록). 사이에 잠금이나 예약이 없다.

**왜 문제인지**: 한 회원이 동시에 N개를 요청하면 모두 확인을 통과해 한도를 넘을 수 있다. 한도는 AI 비용을 막는 장치이므로 업무상 의미가 있다. 외부 호출을 트랜잭션 밖에 둔 결정(잘 된 점 3)과 맞바꾼 결과다. 실제로 재현하지는 않았다.

**고치는 방향**: 호출 전에 "예약" 행을 원자적으로 넣는다. 예를 들어 `INSERT … SELECT … WHERE (오늘 성공 + 진행 중) < limit`로 넣거나, 회원·날짜별 카운터 행에 `UPDATE … SET used = used + 1 WHERE used < limit`를 한다. 그리고 실패하면 되돌린다. 포트로는 `AiUsagePort.tryReserve(userId, feature, day, limit)` 정도가 된다. 한도를 대략으로만 지켜도 된다고 정하면, 08이나 07 문서에 "동시 요청 시 초과 가능"을 적어 두는 것으로도 충분하다.

### M8. `common`의 경계가 흐리다 [확인]

**무엇이·어디서**:
- `common/domain/code/`(`CodeSnapshot`, `CodeEntry`, `CodeGroups`, `CodeChecks`)는 사실상 **code 컨텍스트의 공개 모델**이다. `code.application.port.in.CodeCatalog`가 이것을 돌려준다. `package-info.java:1-5`에 "여러 컨텍스트가 같이 쓰므로 여기에 둔다"는 이유가 적혀 있다. 그 근본 원인은 도메인 규칙(도메인은 `common.domain`과 자기 domain만 볼 수 있다)이다. 그런데 이 안에 `CodeGroups.SLOTS`(`CodeGroups.java:19-21`, 코디 칸 = outfit 개념)도 있고, 같은 값이 `outfit/domain/OutfitCodes.java:22`에 또 정의돼 있다. `CodeChecks`의 "이전 값이면 비활성도 허용" 정책은 wardrobe·user가 공유하는 업무 정책이다.
- `common/domain`의 `Ids`, `Times`, `PatchBody`, `ImageUpload`는 도메인에서 하나도 쓰지 않는다(사용처는 `port.in`, 서비스, 웹 어댑터뿐). 각각 JSON ID 문자열, ISO 시각 문자열, JSON PATCH, multipart라는 **전송 형식 개념**이다.
- `common/config/SecurityConfig.java:3-6`는 `auth.adapter.in.web.*`를 import하고, `auth/adapter/out/security/JwtAccessTokenIssuer.java:4`는 `common.config.WearlyProperties`를 import한다. 그래서 `common ↔ auth` 패키지 순환이 있다. `ApplicationSettingsConfig.java:3-6`도 ai·auth·outfit 도메인을 안다. ArchUnit의 `CONTEXTS`에 `common`이 없어서 검사하지 않는다.
- `common/error/ErrorCode.java`에 `CODE_EXISTS`, `PROVIDER_EXISTS`, `WARDROBE_INSUFFICIENT`, `SECRET_KEY_MISSING` 같은 컨텍스트 고유 오류가 한 enum에 모여 있다(낮음 수준).

**왜 문제인지**: `common.domain`이 "아무도 소유하지 않는 공용 쓰레기통"이 되기 시작하는 모습이다. 지금은 크기가 작지만 규칙상 도메인이 `common.domain`만 볼 수 있으므로, 앞으로 공유가 필요한 것은 모두 여기로 들어오려는 압력이 생긴다.

**고치는 방향**: (1) `common.domain.code`를 **명시적 공유 커널**로 이름 붙인다(예: `app.wearly.sharedkernel.code`, 소유자는 code 컨텍스트). 08 문서에 "공유 커널에 넣을 수 있는 것: 불변 값·조회 메서드·두 컨텍스트 이상이 쓰는 정책"을 기준으로 적는다. `SLOTS`는 한 곳으로 합친다. (2) `Ids`·`Times`·`PatchBody`·`ImageUpload`는 `common.application`(또는 7장 결정에 따라 `common.web`)으로 옮겨 도메인 패키지에서 뺀다. (3) 보안 설정은 `auth/adapter/in/web/config` 같은 auth 쪽 구성 클래스로 옮기고, `common.config`는 컨텍스트를 모르는 설정만 남긴다. ArchUnit에 "`common..`은 컨텍스트 패키지를 모른다(`config` 예외 명시)" 규칙을 더한다.

### M9. 애플리케이션 서비스 규칙은 통합 테스트로만 검증된다 [확인]

**무엇이·어디서**: 테스트 147개(ArchUnit 규칙 12개 제외)는 다음과 같이 나뉜다.
- Spring 통합 테스트: 15클래스 69개. 모두 `IntegrationTestBase`(Testcontainers PostgreSQL + 실제 HTTP)를 쓴다.
- Spring 없는 테스트: 78개. 도메인 46개(outfit 17, ai 12, wardrobe 4, auth 4, code 3, common.code 4, user 2), 어댑터 28개(공급자 3종·목업·암호화·환경변수), 애플리케이션 서비스 4개(`ApiKeyServiceTest` 하나뿐).

`WardrobeService`(필터 검증·PATCH), `CodeManagementService`(색 짝 양방향 동기화 `:197-219`, 삭제 가드), `AdminUserService`(자기 자신 정지 금지), `AuthService`, `AiJsonGenerationService`(폴백 루프)는 HTTP 통합 테스트로만 검증된다. 폴백 루프는 `FakeHttpServer`로 실제 공급자 HTTP를 흉내 내서 시험한다(`AiProviderFallbackIntegrationTest`, `OutfitProviderFallbackIntegrationTest`).

**왜 문제인지**: 도메인 단위 테스트가 Spring 없이 도는 것은 잘 지켜졌다. 하지만 H2·M4처럼 규칙이 서비스에 많이 남아 있다 보니, 그 규칙을 바꿀 때마다 Docker·DB가 필요한 느린 테스트에 기대게 된다. 출력 포트가 인터페이스로 잘 나뉘어 있어서 가짜 구현으로 서비스를 단위 테스트하기 쉬운 구조인데도 그 이점을 쓰지 않고 있다.

**고치는 방향**: H2·M1의 규칙을 도메인으로 옮기면 대부분 도메인 테스트로 내려온다. 남는 오케스트레이션(폴백 루프, 한도, 감사 로그 순서)은 가짜 `AiModelPort`·`AiCallLogPort`로 서비스 단위 테스트를 둔다. 통합 테스트는 API 계약과 SQL(XML) 검증 위주로 줄인다.

### 이 모델이 지금 다른 용도로도 쓰이는 곳 [확인]

- **컨텍스트 간 계약**: outfit이 옷장을 `WardrobeUseCase.list`의 `ItemView`로 읽는다(`OutfitRecommendService.java:67-85`). 그래서 outfit 도메인의 아이템 ID가 문자열이다(`OutfitItem.id: String`, `OutfitPool.compareIds`로 숫자 정렬을 다시 구현함). 웹 응답 모양을 바꾸면 outfit이 영향을 받는다.
- **감사 로그 스키마**: `ProviderView`·`AdminCodeView`가 감사 로그의 before/after로 그대로 저장된다(`AdminAiService.java:78-80`, `AdminCodeService.java:69-71`. JSON 변환은 `AuditLogPersistenceAdapter.java:36-38`). API 응답 필드를 바꾸면 이후 감사 로그 모양도 조용히 바뀐다.
- **AI 기록**: `AiSuggestion`은 API 응답(`AnalyzeResult`)이면서 `tb_ai_analysis_log.result` JSON이고, 관리자 요약이 그 키를 읽는다(L6).

### 헥사고날 원칙상 의미

- 입력 포트의 결과 모델은 **애플리케이션이 소유하는 모델**이다. 애플리케이션이 "이 유스케이스는 이런 결과를 낸다"고 정의하는 것 자체는 원칙 위반이 아니다. 엄밀한 위반은 의존 방향이 바뀌는 경우(애플리케이션이 웹 타입을 import)인데, 그런 일은 없다.
- 쟁점은 그 모델에 **전송 형식 결정**(ID를 문자열로, 시각을 ISO 문자열로, 페이지 모양)이 들어 있다는 점이다. 이 결정은 "주도하는 쪽 어댑터(HTTP/JSON)"의 관심사다. 두 번째 입력 어댑터(배치, 메시지 소비자, 내부 호출, 앞으로의 MCP·gRPC)나 다른 컨텍스트가 같은 포트를 부르면, JSON 형식을 받게 된다.
- `Ids`·`Times`가 `common.domain`에 있는 것도 같은 결정의 흔적이다(M8).

### 유지할 때

- **장점**: 코드가 적다(웹 Response 중복 record와 매핑이 없다). API 모양의 정의가 한 곳(05·07 문서 ↔ `port.in`)이라 계약을 찾기 쉽다. 관리자처럼 "화면용 조회가 곧 기능"인 BFF·읽기 모델 컨텍스트에서는 뷰 모델이 사실상 유스케이스 결과다. 웹 어댑터는 얇은 상태로 남는다.
- **단점**: 위의 세 가지 결합(outfit이 API 모양에 묶임, 감사 로그 스키마가 API에 묶임, AI 기록이 API에 묶임)이 남는다. API 버전을 나눌 때(v2에서 필드 이름 변경) 애플리케이션을 고쳐야 한다. 코드베이스에 두 방식이 섞여 있다는 사실 자체가, 새 컨텍스트를 만들 때 판단 비용이 된다.

### 웹 어댑터 Response로 분리할 때

- **장점**: 애플리케이션 결과가 타입 있는 값(`long id`, `Instant`)이 되어 다른 어댑터·컨텍스트가 그대로 쓸 수 있다. API 형식 변경이 웹 어댑터 안에서 끝난다. auth·user·code와 방식이 통일된다. 감사 로그·AI 기록 스키마를 API와 따로 정할 수 있다(별도 기록 모델이 필요해진다는 뜻이기도 하다).
- **단점**: record와 매핑 코드가 늘어난다(admin만 해도 뷰 10여 개). 단순 CRUD에서는 거의 같은 모양을 두 번 쓰게 된다. 감사 로그가 "API 응답과 같은 모양"이라는 지금의 07 문서 계약을 유지하려면, 감사 기록용 매핑을 따로 맞춰야 한다.

### 중간 선택지 (참고)

1. `port.in` 결과는 유지하되 형식만 타입으로 되돌린다(`String id` → `long id`, `String createdAt` → `Instant`). 문자열 변환은 Jackson 설정(Long → String 직렬화, `Instant` 밀리초 ISO)으로 옮긴다. 변경량이 가장 작다.
2. **다른 소비자가 있는 모델만** 분리한다. 예: outfit용 `WardrobeUseCase` 조회 결과(`OwnedItem`)를 따로 두고, `ItemView`는 웹 전용으로 둔다. 감사 로그용 스냅샷 모델을 따로 둔다.
3. admin은 BFF 성격이므로 현행을 유지하고, 다른 컨텍스트만 auth·user 방식으로 맞춘다.
4. 전 컨텍스트를 분리한다.

## 5. 점검 항목별 정리

### 1) 도메인 순수성과 풍부함

- 순수성: 지켜졌다(ArchUnit + 수동 확인). 저장·기록 형식을 아는 곳 몇 개만 남아 있다(L4, L3의 `SearchText`).
- 컨텍스트별 풍부함:

| 컨텍스트 | 판단 | 근거 |
|---|---|---|
| outfit | 풍부 | `OutfitPool`, `CandidateValidator`, `Weather` 규칙, 단위 테스트 17개 |
| auth | 적절 | `RefreshToken.check/rotateTo/revoke`(`RefreshToken.java:53-83`) |
| ai | 함수형 규칙 모음 | `AiProviderSelection`, `ApiKeyRules`, `AiProviderRules`는 좋다. 사진 결과 검증은 어댑터에 있다(M1). 공급자 지식이 enum에 있다(M2) |
| code | 반쯤 빈 껍데기 | `Code`는 setter 묶음. 규칙은 `CodeRules`/`CodeAttrs` 정적 함수에 있다. 색 짝 양방향 불변식은 서비스에 있다(`CodeManagementService.java:197-219`) |
| wardrobe | 반쯤 빈 껍데기 | 정규화·코드 검증·통계 규칙은 도메인에 있다. 필수·범위 불변식은 웹 DTO에 있다(H2) |
| user | 빈 껍데기 | 문자열 상태·역할 setter, 규칙은 호출자에 있다(H2) |
| admin | 얇음(자연스러움) | BFF·읽기 모델 성격이라 도메인이 얇은 것은 문제가 아니다 |

### 2) 포트 설계

- **입력 포트 크기**: 대체로 적당하다. 좋은 예는 `AuthService` 하나가 소비자별 포트 셋(`AuthUseCase`, `AuthenticationUseCase`, `AccountUseCase`)으로 나뉜 것이다. `WardrobeUseCase`(6개, 자원 단위 CRUD)도 이 규모에 맞다. 큰 쪽은 `AiProviderAdminUseCase`(12개, 단계 노출, L10)다. 너무 잘게 쪼갠 포트는 없다.
- **출력 포트의 기술 냄새**: `CodePort.flush()/saveAllAndFlush`(M5), `ItemFilter.queryPattern`(LIKE, L3), 포트 Javadoc의 "(JPA)", "(MyBatis)" 표기(`ItemPort.java:6`, `CodeUsagePort.java:5` 등. 문서용 표기라 영향은 작다), `AiModelPort.analyze`의 도메인 의미(M1). `TransactionHooksPort`·`CodeSnapshotPort.refreshAfterCommit`는 트랜잭션 개념을 명시적인 기술 포트로 분리한 것이라 적절하다.
- `RecordAuditPort.record(…, Object before, Object after)`는 타입이 없다(7장의 감사 로그 결합과 연결된다).

### 3) 어댑터 책임

- JPA ↔ 도메인 변환: 모두 영속성 어댑터 안에 있다(잘 된 점 2).
- MyBatis 행 유출: admin만 유출된다(M3).
- 웹 어댑터의 출력 포트·리포지토리 직접 호출: 없다(ArchUnit + 수동 확인).
- 컨트롤러의 업무 로직: 거의 없다. `AdminCodeController.reorder`의 조합 정도다(L10). 반대로 웹 코드가 유스케이스 안에서 실행되는 경우(M4-B)와, 다른 컨텍스트의 명령을 그대로 받는 경우(L2)가 있다.
- 어댑터가 업무 규칙을 갖는 경우: `SuggestionParser`(M1). 어댑터가 API 오류를 던지는 경우: L1.

### 4) JPA(쓰기) / MyBatis(조회) 분담

대체로 지켜졌다. 예외와 타당성은 다음과 같다.
- `AiProviderPort.findAllOrdered`(목록을 JPA로 읽음, 매 분석 요청마다 `AiProviderRegistry.candidates` `:67-82`에서 호출): 작은 설정 테이블을 도메인 모델로 읽는 "집합 로드"라 타당하다.
- `CodePort.findByGroup/findIn/countChildren/maxSortOrder/exists`: 쓰기 경로 안에서의 로드·확인이라 타당하다.
- `ProfileService.get`(JPA 단건 로드): 규칙대로다.
- 반대 방향 위반(MyBatis로 쓰기)은 없다.
- 문제는 분담 자체보다 두 기술을 한 트랜잭션에서 섞을 때의 flush 계약이다(M5).

### 5) 트랜잭션 경계

- `@Transactional`은 `application.service`에만 있다. 예외는 `AuditLogPersistenceAdapter`의 `MANDATORY` 하나인데, 이것은 경계를 만드는 게 아니라 "경계 안에서만 부를 것"을 확인하는 가드라 적절하다. 컨트롤러에는 없다.
- AI 기록은 서비스 트랜잭션 없이 Spring Data 리포지토리의 기본 트랜잭션으로 한 건씩 저장된다(실패 기록이 남게 하려는 의도로 보이며 타당하다).
- 문제: JPA → MyBatis 일관성(M5), 트랜잭션 안의 외부 호출(M6), 한도 경쟁 조건(M7).
- 컨텍스트를 넘는 원자성은 잘 설계됐다. `AdminCodeService`·`AdminUserService`가 code·user·auth 유스케이스와 감사 로그를 한 트랜잭션에 묶는다(`AdminUserService.java:124-129`).

### 6) 컨텍스트 사이 의존

- 자바 수준: `port.in`만 쓰고 순환이 없다(잘 된 점 1).
- SQL 수준: code → wardrobe·user 역방향 의존과 순환이 있다(H1). admin → 여러 테이블은 문서화된 읽기 모델이다.
- `common`: 공유 커널과 전송 형식이 섞여 있고, `common ↔ auth` 패키지 순환이 있다(M8).

### 7) 입출력 모델

4장 참고. 입력 쪽도 섞여 있다. auth·wardrobe·user는 웹 DTO → 명령/도메인 값으로 바꾼다. outfit·admin(ai·code 명령)은 명령을 요청 본문으로 바로 받는다(L2).

### 8) 새 컨텍스트 outfit

- **규칙 준수**: ArchUnit을 통과한다. 도메인이 순수하고 풍부하며 단위 테스트가 있다. AI 호출을 트랜잭션 밖에 둔다. 가장 모범적인 컨텍스트다.
- **출력 포트 없이 다른 컨텍스트 입력 포트만 쓰는 구조의 적절성**: 자기 저장소가 없는 조립(orchestration) 컨텍스트이므로 출력 포트가 없는 것 자체는 자연스럽고, 08 문서 규칙("컨텍스트 사이 호출은 입력 포트로")과도 맞다. 다만 대가는 다음과 같다.
  - outfit이 다른 컨텍스트의 **화면용 모델**에 묶인다. `WardrobeUseCase.list`(필터 검증이 들어간 목록 조회)와 `ItemView`(API 모양)에 의존한다(`OutfitRecommendService.java:67-85`).
  - ai의 계약 세부(`JsonGenerationCommand`, `JsonOutputHandler`, `RejectedOutputException`, `AiFeatures`)가 outfit 서비스에 그대로 들어온다. ai 쪽도 outfit 기능 이름을 알아야 한다(L6).
  - 다른 컨텍스트의 `ApiException` 코드를 보고 다시 포장한다(L10).
- **대안(참고)**: outfit에 자기 출력 포트(`OwnedItemsReader`, `TasteReader`, `OutfitGenerator`)를 두고, 다른 컨텍스트 입력 포트를 부르는 어댑터(부패 방지 계층)로 구현할 수 있다. 지금 ArchUnit 규칙으로도 어댑터가 다른 컨텍스트 `port.in`을 부르는 것은 허용된다. 장점은 outfit 애플리케이션·도메인이 다른 컨텍스트 모델 변경에서 격리되고, 서비스 단위 테스트가 쉬워진다는 것이다. 단점은 클래스 3~6개가 늘어난다는 것이다. 최소안은 wardrobe에 outfit 전용 조회 포트(타입 있는 `OwnedItem` 목록)를 하나 두는 것이다.
- **입력**: `RecommendOutfitCommand`가 웹 요청 그대로(날짜·ID 문자열)이고, 형식 검증(`OutfitRequestValidator`)이 애플리케이션에 있다. 검증을 거친 결과(`OutfitRequest`)는 도메인 값이라 흐름은 명확하다.

### 9) AI 공급자 구조

- **위치가 적절한 것**: 공급자 선택 순서(`AiProviderSelection`, 도메인), 키 선택(`ApiKeyRules`, 도메인), 폴백·기록 루프(`AiAnalysisService`, `AiJsonGenerationService`, 애플리케이션), 클라이언트 생성·캐시(`AiProviderFactory`, 어댑터), SDK를 어댑터 밖으로 내보내지 않는 것(ArchUnit의 `com.anthropic..` 금지).
- **문제**: 사진 분석 검증·프롬프트가 어댑터에 있다(M1). 공급자 목록·옵션이 도메인 enum에 있다(M2). 재시도 루프가 셋으로 중복된다(L7).
- **새 공급자 추가 시 바꿀 곳**: 코드 6곳 + 마이그레이션 1곳(M2 목록). 그중 1곳(`ApiKeyVerifier`)은 컴파일러가 잡아 주지 않는다.

### 10) 테스트 구조

- 도메인 단위 테스트는 Spring 없이 돈다(46개). ArchUnit도 Spring 없이 돈다.
- 애플리케이션 서비스 규칙은 거의 통합 테스트(15클래스 69개, Testcontainers + 실제 HTTP)에만 기댄다(M9).
- 어댑터 단위 테스트(공급자 요청·응답 변환, 암호화)는 잘 갖춰져 있다(28개). MyBatis XML·JPA 매핑만 따로 검증하는 슬라이스 테스트는 없고, 모두 통합 테스트로 검증한다.
