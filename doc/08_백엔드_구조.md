# 08. 백엔드 구조: 헥사고날 + JPA + MyBatis

> 대상: `backend/`. 2026-10-17 결정. 그전에는 기능별 패키지 안에 컨트롤러·서비스·JPA 엔티티·리포지토리·MyBatis 매퍼가 섞인 계층형 구조였다.

## 1. 원칙

- **도메인과 유스케이스는 바깥 기술을 모른다.** Spring Web, JPA, MyBatis, Anthropic SDK, HTTP 클라이언트는 모두 어댑터에만 있다.
- **안쪽으로만 의존한다.** `adapter` → `application` → `domain`. 반대 방향 import는 금지하고 ArchUnit 테스트로 막는다.
- **쓰기는 JPA, 읽기는 MyBatis.** 둘 다 출력 어댑터다. 쓰기 포트(저장·단건 로드)는 JPA 어댑터가, 조회 포트(목록·검색·집계)는 MyBatis 어댑터가 구현한다.
- **JPA 엔티티는 도메인 모델이 아니다.** 영속성 어댑터 안에서 JPA 엔티티 ↔ 도메인 모델을 바꾼다. 도메인 모델에는 `@Entity` 같은 어노테이션을 붙이지 않는다.

## 2. 패키지

바운디드 컨텍스트(기능)마다 같은 모양을 쓴다. 컨텍스트: `auth`, `user`, `wardrobe`, `code`, `ai`, `admin`.

```
app.wearly
├── <context>
│   ├── domain/                    도메인 모델·값 객체·도메인 규칙 (순수 자바, Spring·JPA·Jackson 어노테이션 없음)
│   ├── application/
│   │   ├── port/in/               유스케이스 인터페이스 (XxxUseCase)
│   │   │   └── dto/               유스케이스 입력·출력 DTO (7장)
│   │   ├── port/out/              출력 포트 (예: SaveItemPort, LoadItemPort, ItemQueryPort, AiModelPort)
│   │   └── service/               유스케이스 구현 (@Service, @Transactional은 여기까지만)
│   └── adapter/
│       ├── in/web/                @RestController
│       │   ├── request/           XxxRequest: 요청 본문·쿼리, 검증·Jackson 어노테이션, toDto()
│       │   └── response/          XxxResponse: 응답 JSON 모양, static from(dto)
│       └── out/
│           ├── persistence/
│           │   ├── jpa/           XxxEntity · XxxJpaRepository · XxxJpaAdapter (쓰기·단건 조회 포트 구현)
│           │   └── mybatis/       XxxMybatisAdapter (조회 포트 구현)
│           │       ├── mapper/    XxxMapper 인터페이스 (@Mapper, XML은 resources/mapper/<context>/)
│           │       └── dto/       XxxRowDto: 매퍼가 돌려주는 조회 결과
│           └── <기술>/             예: ai/claude, ai/openai, ai/gemini, ai/mock, crypto, security
└── common
    ├── domain/                    여러 컨텍스트가 같이 쓰는 값 객체 (예: UserId)
    ├── error/                     오류 코드·예외·전역 예외 처리(웹 어댑터 쪽)
    ├── config/                    Spring 설정, 보안 설정
    └── mybatis/                   공용 TypeHandler
```

## 3. 규칙

| 대상 | 의존해도 되는 것 | 의존하면 안 되는 것 |
|---|---|---|
| `domain` | 자바 표준, `common.domain` | Spring, JPA, MyBatis, Jackson, 다른 컨텍스트의 `application`·`adapter` |
| `application` | 자기 `domain`, 다른 컨텍스트의 `port.in`(유스케이스 호출), `common.domain`·`common.error`, Spring의 `@Service`·`@Transactional` | 어떤 `adapter`, JPA 엔티티, MyBatis 매퍼, Web 타입(`ResponseEntity`, `MultipartFile` 등) |
| `adapter.in.web` | 자기 `port.in`·`port.in.dto`, 웹 request·response | 출력 포트·출력 어댑터 직접 호출 |
| `adapter.out.*` | 자기 `port.out`, `domain`, 기술 라이브러리 | 유스케이스 서비스, 웹 어댑터 |

- 컨텍스트 사이 호출은 상대 컨텍스트의 **입력 포트(유스케이스)** 로만 한다. 예: `admin`이 코드를 고치면 `code`의 유스케이스를 부른다. 다른 컨텍스트의 리포지토리·매퍼를 직접 쓰지 않는다.
- 이미지 업로드(`MultipartFile`)는 웹 어댑터에서 `byte[]`와 MIME을 담은 도메인 값으로 바꿔 넘긴다.
- 트랜잭션 경계는 `application.service`. JPA와 MyBatis가 한 트랜잭션에 함께 들어가도 같은 DataSource·트랜잭션 매니저를 쓴다.
- 감사 로그(`tb_admin_audit_log`)는 출력 포트(`RecordAuditPort`)로 남긴다.

## 4. 검증

- **ArchUnit 테스트**로 3장 규칙을 강제한다(`domain`·`application`이 어댑터·JPA·MyBatis·Spring Web을 import하지 않음, 컨텍스트 사이 의존은 `port.in`만).
- 구조를 바꾸는 단계에서는 **동작을 바꾸지 않는다.** API 계약(05·06·07 문서), DB 스키마, 기존 테스트 78개, 연동 하네스 29개가 그대로 통과해야 한다.
- 도메인 규칙(코드 검증, 토큰 회전, 공급자 선택 순서 등)은 Spring 없이 도는 단위 테스트를 둔다.

## 5. 코드 스타일: Google Java Style

2026-10-17 결정. [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)를 따른다.

- **포맷은 도구로 강제한다.** Gradle Spotless 플러그인 + `google-java-format`(Java 21 지원 최신). `./gradlew spotlessApply`로 고치고, `./gradlew check`에 `spotlessCheck`를 걸어 어기면 빌드가 실패한다.
  - 들여쓰기 2칸, 줄 길이 100자, 탭 금지.
  - import: static import 묶음 → 일반 import 묶음, 각 묶음은 ASCII 순서, 와일드카드(`*`) 금지, 쓰지 않는 import 금지.
- **포맷 도구가 못 잡는 규칙은 Checkstyle**(`google_checks.xml` 기준)로 검사한다: 이름 규칙(클래스 UpperCamelCase, 메서드·변수 lowerCamelCase, 상수 UPPER_SNAKE_CASE, 패키지 소문자), 한 파일 한 최상위 클래스, `switch` default, 빈 catch 금지 등. Javadoc 관련 항목은 경고(warning)로 두고 빌드를 막지 않는다. 그 밖의 위반은 빌드 실패.
- 주석·Javadoc 문장은 한국어로 쓴다(식별자는 영어).
- MyBatis XML과 SQL 마이그레이션은 이 규칙의 대상이 아니다.

## 6. 설정: yml 파일 (`.env` 쓰지 않음)

2026-10-17 결정. 백엔드 로컬 설정과 비밀 값은 `.env`가 아니라 yml로 둔다.

- **공통 설정**: `src/main/resources/application.yml` (git 포함, 비밀 값 없음).
- **로컬 비밀 설정**: `backend/config/application-local.yml` (git 제외). 서버는 `spring.config.import: optional:file:${WEARLY_LOCAL_CONFIG:./config/application-local.yml}`로 읽는다(기본은 `backend/`에서 실행할 때의 `./config/application-local.yml`). 커밋하는 견본은 `backend/config/application-local.example.yml`.
- **테스트·하네스 격리**: `build.gradle.kts`의 test 태스크와 `harness/run.sh`는 `WEARLY_LOCAL_CONFIG`를 없는 경로로 줘서 개발 PC의 로컬 비밀 설정을 읽지 않는다.
- **docker compose**: `backend/config`를 컨테이너 `/app/config`에 읽기 전용으로 마운트한다. 이미지에는 넣지 않는다(`backend/.dockerignore`). DB 주소는 `application-docker.yml`(비밀 값 없음).
- 속성은 이름 그대로 계층으로 쓴다. 예:

  ```yaml
  wearly:
    jwt:
      secret: ...              # JWT 서명 키 (비우면 개발용 기본값, prod 필수)
    secret-key: ...            # AI 키 웹 입력 암호화 마스터 키 (base64 32바이트)
    admin:
      email: admin@wearly.app
      password: ...
      name: 관리자
    ai:
      keys:                    # 공급자 행의 키 이름(api_key_env) → 키 값
        ANTHROPIC_API_KEY: ...
        OPENAI_API_KEY: ...
  ```
- **AI 공급자 키 조회 순서**: 웹 입력 키(DB) → 설정 `wearly.ai.keys.<키 이름>` → 같은 이름의 OS 환경변수. `tb_ai_provider.api_key_env`는 이제 "키 이름"이며 관리자 화면도 "서버 설정 키"로 표시한다.
- 운영 서버는 같은 속성을 Spring 표준 방식(OS 환경변수의 relaxed binding, Secrets Manager 등)으로 덮어쓸 수 있다. 로컬에서 `.env`를 읽던 `spring.config.import: optional:file:.env[.properties]`는 없앤다.

## 7. 입출력 모델 (요청 → DTO → 응답)

2026-10-17 결정. 웹 요청·응답, 유스케이스 DTO, DB 조회 결과를 모두 따로 두고 경계에서 바꾼다("완전 매핑").

```
HTTP JSON ─▶ XxxRequest ──toDto()──▶ port.in.dto(입력) ─▶ XxxUseCase ─▶ port.in.dto(출력) ──XxxResponse.from()──▶ HTTP JSON
                                                              │
                                     port.out ◀── XxxJpaAdapter (XxxEntity ↔ 도메인)
                                              ◀── XxxMybatisAdapter (XxxMapper → XxxRowDto → 도메인·DTO)
```

| 위치 | 이름 | 하는 일 | 알면 안 되는 것 |
|---|---|---|---|
| `adapter.in.web.request` | `XxxRequest` (record) | JSON·쿼리 바인딩, Bean Validation, `toDto()`로 입력 DTO 만들기 | 엔티티, 매퍼 |
| `adapter.in.web.response` | `XxxResponse` (record) | `static from(dto)`로 응답 모양 만들기: ID를 문자열로, 시각을 ISO-8601(밀리초, UTC) 문자열로, 노출할 필드만 | 엔티티, 매퍼 |
| `application.port.in.dto` | 입력 `<동작><대상>Dto` (예: `CreateItemDto`, `ItemSearchDto`), 출력 `<대상>Dto` (예: `ItemDto`, `WardrobeStatsDto`) | 유스케이스의 입력·출력. 자바 타입 그대로(`Long` id, `Instant`·`LocalDate` 시각) | JSON 모양(문자열 ID·시각 포맷), Jackson·Validation 어노테이션, 웹·DB 타입 |
| `adapter.out.persistence.jpa` | `XxxEntity`, `XxxJpaRepository`, `XxxJpaAdapter` | 쓰기·단건 조회. 엔티티 ↔ 도메인 변환은 어댑터 안에서 | 웹 DTO |
| `adapter.out.persistence.mybatis` | `XxxMybatisAdapter`, `mapper/XxxMapper`, `dto/XxxRowDto` | 목록·검색·집계. 매퍼는 `XxxRowDto`를 돌려주고 어댑터가 도메인 값이나 포트 DTO로 바꾼다 | 웹 DTO |

- 컨트롤러는 **항상 `XxxResponse`(또는 그 목록·페이지)** 를 돌려준다. 유스케이스 DTO를 그대로 응답으로 내보내지 않는다. 응답 JSON 모양은 05·06·07·09 문서의 계약 그대로다(필드 이름·문자열 ID·시각 형식·null 처리).
- 요청이 없거나 경로 변수뿐인 경우에는 `XxxRequest`를 만들지 않아도 된다. 입력 DTO는 유스케이스에 넘길 값이 둘 이상일 때 만든다.
- 여러 화면에서 같은 응답 모양을 쓰면 `XxxResponse` 하나를 같이 쓴다. 노출 범위가 다르면(앱 회원 정보와 관리자 회원 목록 등) 나눈다.
- DTO는 서비스 패키지가 아니라 **입력 포트 옆(`port.in.dto`)** 에 둔다. 포트가 자기 입출력 타입을 소유해야 포트 → 서비스 방향의 의존이 생기지 않는다.
- ArchUnit으로 강제: `@Entity`는 `adapter.out.persistence.jpa`에만, `@Mapper`는 `adapter.out.persistence.mybatis.mapper`에만, Bean Validation·Jackson 어노테이션은 `adapter.in.web` 아래에만, `@RestController`의 public 메서드 반환 타입은 `adapter.in.web.response` 타입(또는 그 컬렉션·`ResponseEntity`·`void`)만, `port.in.dto`는 `adapter`를 모른다.
