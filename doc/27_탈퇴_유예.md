# 27. 탈퇴 유예 기간 개발 계획

> 작성일: 2026-10-25 · 이슈 [#19](https://github.com/showzone83/wearly/issues/19) · 상태: **0~4단계 구현함**(결정 확정·백엔드 탈퇴 신청·취소·30일 뒤 예약 삭제·앱 탈퇴 화면·로그인 취소 창·관리자 탈퇴 기록), 5단계(마무리) 남음

회원이 탈퇴하면 바로 지우지 않고 30일 동안 "탈퇴 예정"으로 둔다. 그동안 다시 로그인하면 탈퇴를 취소할 수 있고, 30일이 지나면 지금과 같이 모두 지운다. 탈퇴 사유와 시각은 기록으로 남긴다.

이 문서는 이슈 #19 본문을 코드와 대조해 단계별 작업으로 나눈 것이다. 2장 결정은 2026-10-25에 확정했다. 구현한 단계는 그 장을 실제 내용으로 고친다.

## 1. 1단계 전 코드

- 탈퇴는 `DELETE /api/v1/users/me` → [`UserService.delete`](../backend/src/main/java/app/wearly/user/application/service/UserService.java)다. `tb_user` 행을 바로 지우고, FK `ON DELETE CASCADE`로 하위 데이터가 함께 지워진다. 그 뒤 `UserDeletedListener`가 DB 밖 데이터를 지운다: 로그인 세션(Valkey, `SessionCleanupOnUserDeleted`)과 옷 사진(MinIO, `ImageCleanupOnUserDeleted`).
- CASCADE로 함께 지워지는 데이터(이슈 본문):
  - 계정·로그인: 자격 증명, 소셜 연결, 로그인 이력(`tb_auth_event`), 2단계 인증·SSO 연결
  - 옷장·코디: 프로필·취향, 옷·사진 행, 코디·예정 코디, 진단·리포트
  - AI 기록: AI 분석 로그, 사용량 예약
  - 알림: 푸시 토큰, 푸시 발송 기록
  - 친구 초대: 초대 코드, 초대한 이력. 가입 이력의 추천인은 `SET NULL`로 남는다
  - 옷장 도우미: 연결(`tb_closet_pairing`)과 대리 작업 기록(V28). 돕는 사람이 탈퇴해도 그 사람이 대신 등록한 옷은 주인 옷장에 남는다 ([26](26_옷장_도우미.md) D9)
- 회원 상태 `tb_user.status`는 `ACTIVE`·`SUSPENDED` 두 가지다(`ck_user_status`). 로그인은 비밀번호가 맞을 때만 정지 여부를 알리고(403 `ACCOUNT_SUSPENDED`), 토큰 확인(`UserIdAuthenticationConverter`)도 활성이 아닌 회원을 막는다.
- 앱은 마이 탭 "회원 탈퇴" → 확인 창("되돌릴 수 없어요") → [`deleteAccount()`](../mobile/src/lib/account.ts)로 서버를 지우고 기기를 비운다. 사유는 받지 않는다.
- 탈퇴 기록은 어디에도 남지 않는다.

### 1단계 — 백엔드: 탈퇴 신청·취소 — 구현함 (2026-10-25)

**구현한 것**

- **V30** [`V30__user_withdrawal.sql`](../backend/src/main/resources/db/migration/V30__user_withdrawal.sql): `ck_user_status`에 `WITHDRAWN`, `ck_closet_pairing_ended_by`에 `WITHDRAWN`, 새 `tb_user_withdrawal`(FK 없음, 열린 기록은 회원당 하나 `uq_user_withdrawal_open`, 예약 삭제용 `ix_user_withdrawal_due`). 테이블·컬럼 코멘트.
- **user 컨텍스트**
  - 도메인: `UserStatus.WITHDRAWN`, `User.withdraw()`·`cancelWithdrawal()`, `User.changeAccess`는 `WITHDRAWN`을 넣지도, 탈퇴 예정 회원을 바꾸지도 못한다(400 `status` `NOT_ALLOWED`). `Withdrawal`(사유 검증·공백 정리·200자, `purgeAfter` = 신청 + 유예), `WithdrawalReason`, `WithdrawalPolicy`.
  - 설정: `wearly.user.withdrawal.grace`(기본 `P30D`, [`WithdrawalProperties`](../backend/src/main/java/app/wearly/user/config/WithdrawalProperties.java)).
  - [`WithdrawalService`](../backend/src/main/java/app/wearly/user/application/service/WithdrawalService.java)(입력 포트 `WithdrawalUseCase`): 신청은 입력 검증 → 상태 `WITHDRAWN` → 기록 → `UserWithdrawnListener`를 한 트랜잭션에서. 이미 탈퇴 예정이면 그 기록을 그대로 준다. 취소는 상태 `ACTIVE` + 기록 `canceled_at`·`canceled_by`(`USER`·`ADMIN`).
  - API `POST /api/v1/users/me/withdrawal` → 200 `{ requestedAt, purgeAt }`. `DELETE /users/me`는 없앴다. `UserUseCase.delete`(회원 행 삭제 + `UserDeletedListener`)는 2단계 예약 삭제가 쓴다.
- **신청 즉시 처리** (`UserWithdrawnListener` 구현 3개, 각 컨텍스트 `adapter/in/user`):
  - auth `SessionCleanupOnUserWithdrawn`: 로그인 세션 전부 끊기.
  - notify `PushTokenCleanupOnUserWithdrawn`: 푸시 토큰 전부 지우기(`PushTokenUseCase.unregisterAll`).
  - pairing `PairingCleanupOnUserWithdrawn`: `PairingUseCase.endAllOnWithdrawal` — 그 회원이 만든 연결 코드(Valkey)를 지우고, 끝나지 않은 연결을 모두 `ENDED`(`ended_by = WITHDRAWN`)로. 연결된 것만 상대에게 "○○님이 탈퇴해 옷장 도우미 연결이 해제됐어요"(커밋 뒤).
- **로그인** (`AuthService.login`): 비밀번호가 맞고 탈퇴 예정이면 403 `ACCOUNT_WITHDRAWN`(`params.purgeAt`). 본문 `cancelWithdrawal: true`면 `WithdrawalUseCase.cancel` 뒤 그대로 로그인.
- **초대**: 코드 주인이 탈퇴 예정이면 가입 때 추천인으로 잇지 않는다(`UNKNOWN_CODE`, `InviteCodeJpaRepository.findLiveUserIdByCode`).
- **오류 코드** `ACCOUNT_WITHDRAWN`(403, `purgeAt`): 서버 57개, 앱·관리자 문구 표 ([20](20_오류_응답.md) 15장).
- **앱·하네스(3단계 앞당김 일부)**: 즉시 삭제 API가 없어져 앱 API 모듈을 `api.users.withdraw({ reason, reasonText })`·`auth.login({ …, cancelWithdrawal })`로 바꿨다. 마이 탭 탈퇴는 3단계 탈퇴 화면 전까지 확인 창 문구만 "30일 뒤 삭제, 그 전엔 로그인해 취소"로 고치고 사유는 `OTHER`로 보낸다. 로그인 화면의 취소 창은 3단계. 하네스 "계정" 시나리오를 탈퇴 신청 → 401 → 로그인 403 → 재가입 409 → 취소 로그인 → 옷장·나의 정보 그대로로 바꿨다.

API 스냅샷의 `users.delete`를 `users.withdraw`(+ 사유 오류)로 바꿨다.

### 2단계 — 백엔드: 30일 뒤 삭제 — 구현함 (2026-10-25)

**구현한 것**

- **예약 작업** [`WithdrawalPurgeScheduler`](../backend/src/main/java/app/wearly/user/adapter/in/schedule/WithdrawalPurgeScheduler.java)(user `adapter/in/schedule`): `wearly.user.withdrawal.purge-cron`(한국 시간, 기본 매일 04:30)마다 `WithdrawalPurgeUseCase.purgeDue()`. `scheduler-enabled=false`면 만들지 않는다(통합 테스트는 끄고 시각을 넣어 직접 부른다). `UserConfig`가 `@EnableScheduling`을 켠다.
- **반복** [`WithdrawalPurgeService`](../backend/src/main/java/app/wearly/user/application/service/WithdrawalPurgeService.java): 기한(`purge_after`)이 지난 열린 기록의 회원을 기한이 이른 순으로 한 번에 `purge-batch`(기본 500)명까지 고르고, 회원마다 `WithdrawalUseCase.purgeIfDue`(별도 트랜잭션)를 부른다. 한 명이 실패해도 나머지는 계속하고, 결과(대상·삭제·건너뜀·실패)와 회원 ID만 로그에 남긴다. 남은 회원은 다음 날 이어서 지운다.
- **한 명 지우기** (`WithdrawalService.purgeIfDue`·`purgeNow`): ① 처리권 — 열린 기록에 `purged_at`·`purged_by`를 남기는 `UPDATE … WHERE purged_at IS NULL AND canceled_at IS NULL AND purge_after <= now`(서버가 여러 대여도 한 서버만 바꾼다, 그새 취소했으면 0행) → ② 회원이 탈퇴 예정인지 확인(아니면 예외로 기록도 되돌린다) → ③ `UserUseCase.delete` — 회원 행 삭제(CASCADE)와 `UserDeletedListener`(세션·사진)를 지금과 같이. 셋이 한 트랜잭션이라 지우다 실패하면 기록도 되돌아가 다음에 다시 한다. `purgeNow`는 기한을 보지 않고(`purged_by = ADMIN`) 4단계 관리자 "바로 삭제"가 쓴다.
- **설정** `wearly.user.withdrawal.purge-cron`·`purge-batch`·`scheduler-enabled` (`WithdrawalProperties`, application.yml).
- **테스트**: `WithdrawalPurgeIntegrationTest`(실제 DB 4개: 기한 전엔 남고 기한 뒤엔 회원·자격 증명·옷·프로필이 지워지고 기록은 `SCHEDULER`로 남는다·다시 돌려도 같다·지운 뒤 로그인 401·같은 이메일 재가입, 취소한 회원은 안 지운다, 돕는 사람이 지워져도 대신 등록한 옷은 주인에게 남는다, 관리자 바로 삭제), `WithdrawalPurgeServiceTest`(한 명 실패해도 계속·건수, 대상 없음).
- **확인**: 백엔드 `./gradlew check` 통과(테스트 736개).

**원래 계획(참고)**

- `WithdrawalPurgeScheduler` → `WithdrawalPurgeService`: `purge_after <= now`인 열린 기록을 하나씩 처리권을 잡고 `UserService.delete` → `purged_at`. 한 명이 실패해도 계속하고 건수만 로그에 남긴다.

## 5. 위험

- **기록에 개인정보가 남는 것:** 기록에는 회원 ID·사유·하고 싶은 말만 둔다. 하고 싶은 말에 회원이 개인정보를 적을 수 있으므로, 관리자 화면에서만 보이고 외부로 내보내지 않는다.
- **삭제 작업이 멈추는 것:** 예약 작업이 실패하면 30일이 지나도 데이터가 남는다. 관리자 "탈퇴 기록"에서 기한이 지났는데 남은 회원을 눈에 띄게 보여 주고, 바로 삭제할 수 있게 한다.
- **유예 중 문의:** 다른 사람의 옷장 도우미 연결은 신청 즉시 끝나므로, 취소해도 다시 연결해야 한다. 탈퇴 화면에 적는다.
