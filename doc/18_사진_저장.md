# 18. 옷 사진 서버 저장: 오브젝트 스토리지에 올리고 서명 URL로 받기

> 2026-10-18 (같은 날 크기를 2048에서 1600으로 줄이고 AI 전송 크기를 1024로 정했다, 3.1·12장). 대상: `backend/`(image 컨텍스트, 아이템·AI 분석 연동), `docker-compose.yml`(minio), `harness/`(시나리오 46~49), `mobile/`(사진 올리기·표시·옮기기).
> 코드의 주석에는 이 계약이 "17 문서"로 적혀 있다. 17번은 날씨가 먼저 써서 이 문서가 18번이 됐다.

## 1. 배경과 결정

지금까지 옷 사진은 앱 기기에만 있었다([04](04_목업_앱.md) 알려진 한계, [05](05_백엔드_API.md)의 "이미지 업로드·저장 제외"). 기획서는 사진을 서버에 두라고 한다.

| 기획서 | 내용 |
|---|---|
| p.28 | `TB_ITEM_IMAGE` 테이블 |
| p.29 | `POST /api/v1/images/upload-url` |
| p.30 | 이미지 파일은 Object Storage에, DB에는 메타데이터만. 업로드 URL 만료·권한·비용 제한 |
| p.31 | 이미지는 비공개 저장, 업로드 URL 만료·파일 검증, EXIF 위치 정보 제거, 탈퇴 시 삭제 |

| 항목 | 결정 |
|---|---|
| 저장소 | **S3 호환 오브젝트 스토리지** 하나. 로컬은 MinIO, 운영은 AWS S3·Cloudflare R2·네이버 클라우드 중 고른다. 바꾸는 것은 yml 설정뿐이다 (어댑터 하나: AWS SDK v2 `S3Client` + `S3Presigner`) |
| 공개 여부 | 버킷은 **비공개**. 앱은 백엔드가 준 서명 URL로만 올리고 받는다. 서명 없는 GET은 403 |
| 올리는 길 | 앱이 서명 URL로 저장소에 **바로** PUT한다 (백엔드를 거치지 않는다) → 백엔드 `complete`가 검증·축소·메타데이터 제거 |
| 파일 | 아이템당 사진 한 장. 긴 변 1600 이하 `original.jpg`와 긴 변 400 `thumb.jpg` (둘 다 JPEG 품질 0.8로 다시 인코딩, 크기·품질은 설정, 3.1) |
| AI 분석 전송 | 저장한 사진을 그대로 보내지 않고 긴 변 1024 JPEG(0.8)로 한 번 더 줄여서 보낸다 (이미지 토큰 절감, 7.4·12장) |
| 형식 | 저장은 JPEG·PNG만. 앱은 올리기 전에 JPEG로 바꾼다 (HEIC 대응). 기존 multipart 분석(`analyze`)은 그대로 jpeg·png·webp·heic |
| 게스트 | 서버가 없으니 기기에만 둔다. 단 선택기 캐시가 아니라 앱 문서 폴더에 복사한다 (OS가 캐시를 지워도 남게) |

`backend/config/application-cloud.example.yml`에 AWS S3·Cloudflare R2·네이버 클라우드 Object Storage 블록이 있다. 서버는 이 파일을 읽지 않는다. 쓸 블록 하나를 골라 배포 환경의 설정으로 옮긴다. 방법은 8장.

### 2.3 서명 URL 주소 (`public-endpoint`)

SigV4는 호스트를 서명에 넣으므로, 서명 URL은 **앱이 실제로 접속하는 주소**로 만들어야 한다.

| 조건 | 서명 URL의 주소 |
|---|---|
| `public-endpoint`가 있다 | 언제나 그 주소 |
| 없고 `endpoint`도 없다 (AWS S3) | AWS 기본 주소 (`https://<버킷>.s3.<리전>.amazonaws.com`) |
| 없고 `endpoint`가 있다 (로컬 MinIO) | **지금 요청의 Host 이름 + `endpoint`의 스킴·포트**. 요청 밖(정리 작업 등)이면 `endpoint` 그대로 |

로컬에서 백엔드는 compose 네트워크 안의 `minio:9000`으로 저장소에 붙지만(`application-docker.yml`), 앱이 받는 서명 URL은 요청 Host로 만든다. 그래서 iOS 시뮬레이터는 `http://localhost:9000/...`, 실제 휴대폰은 `http://<Mac LAN IP>:9000/...`로 받는다 (둘 다 동작을 확인했다).

**클라우드(R2·NCP 등 `endpoint`가 있는 공급자)는 `public-endpoint`를 `endpoint`와 같은 값으로 꼭 넣는다.** 비워 두면 API 서버의 Host 이름으로 저장소 주소를 만들어 앱이 엉뚱한 곳으로 간다. 호스트별 서명기는 32개까지 캐시한다.

## 3. 설정 (`wearly.storage.*`)

기본값은 `application.yml`. 환경변수로도 줄 수 있다. 비밀 값(`access-key`·`secret-key`)은 `config/application-local.yml`이나 배포 환경의 비밀 관리에 둔다 (로컬 MinIO 계정은 기본값이라 적지 않아도 된다).

| yml 속성 | 환경변수 | 기본값 | 설명 |
|---|---|---|---|
| `endpoint` | `WEARLY_STORAGE_ENDPOINT` | `http://localhost:9000` | 백엔드가 저장소에 붙는 주소. compose는 `http://minio:9000`. AWS S3는 비운다 |
| `region` | `WEARLY_STORAGE_REGION` | `us-east-1` | 서명 리전. R2는 `auto` |
| `bucket` | `WEARLY_STORAGE_BUCKET` | `wearly-images` | 버킷 이름 |
| `access-key` | `WEARLY_STORAGE_ACCESS_KEY` | `wearly` | 로컬 MinIO 계정. AWS는 비우면 기본 자격 증명 체인(IAM 역할 등) |
| `secret-key` | `WEARLY_STORAGE_SECRET_KEY` | `wearly-minio-local` | 〃 |
| `path-style` | `WEARLY_STORAGE_PATH_STYLE` | `true` | MinIO·R2·NCP는 true, AWS S3는 false |
| `public-endpoint` | `WEARLY_STORAGE_PUBLIC_ENDPOINT` | (빔) | 서명 URL 주소. 2.3 |
| `auto-create-bucket` | `WEARLY_STORAGE_AUTO_CREATE_BUCKET` | `false` | true면 시작할 때 버킷이 없으면 만든다 (테스트·하네스용. 로컬 compose는 `minio-init`이 만든다) |
| `upload-url-ttl` | `WEARLY_STORAGE_UPLOAD_URL_TTL` | `PT10M` | 업로드(PUT) 서명 URL 수명 |
| `download-url-ttl` | `WEARLY_STORAGE_DOWNLOAD_URL_TTL` | `PT1H` | 받기(GET) 서명 URL 수명 |
| `max-upload-bytes` | `WEARLY_STORAGE_MAX_UPLOAD_BYTES` | `10MB` | 올릴 수 있는 최대 크기 |
| `daily-upload-limit` | `WEARLY_STORAGE_DAILY_UPLOAD_LIMIT` | `200` | 회원당 하루 upload-url 발급 수 |
| `max-pixels` | `WEARLY_STORAGE_MAX_PIXELS` | `40000000` | 디코딩 전에 헤더의 가로×세로로 막는 상한 (4천만 화소) |
| `processing-concurrency` | `WEARLY_STORAGE_PROCESSING_CONCURRENCY` | `2` | 동시에 처리(디코딩·재인코딩)하는 사진 수 |
| `stale-after` | `WEARLY_STORAGE_STALE_AFTER` | `P1D` | 이 시간이 지나도 아이템에 안 붙은 사진을 정리 대상으로 |
| `cleanup-enabled` | `WEARLY_STORAGE_CLEANUP_ENABLED` | `true` | false면 정리 주기 작업을 만들지 않는다 (테스트·하네스) |
| `cleanup-interval` | `WEARLY_STORAGE_CLEANUP_INTERVAL` | `PT1H` | 정리 작업 간격 (끝난 뒤 이만큼). 시작 5분 뒤 첫 실행 |

### 3.1 사진 크기·품질 (`wearly.storage.*`, `wearly.ai.*`)

저장 크기와 AI 전송 크기는 따로 정한다. 값은 `WearlyProperties`의 `Storage`·`Ai`가 읽고 범위를 검증한다 (범위 밖이면 서버가 시작하지 않는다). **저장 크기를 바꿔도 이미 저장된 사진은 그대로 둔다.**

| yml 속성 | 환경변수 | 기본값 | 범위 | 설명 |
|---|---|---|---|---|
| `wearly.storage.original-max-side` | `WEARLY_STORAGE_ORIGINAL_MAX_SIDE` | `1600` | 64~8192 | 저장하는 `original.jpg`의 긴 변 최대 픽셀 |
| `wearly.storage.original-quality` | `WEARLY_STORAGE_ORIGINAL_QUALITY` | `0.8` | 0.1~1.0 | `original.jpg` JPEG 품질 |
| `wearly.storage.thumb-max-side` | `WEARLY_STORAGE_THUMB_MAX_SIDE` | `400` | 16~4096 | 목록용 `thumb.jpg`의 긴 변 |
| `wearly.storage.thumb-quality` | `WEARLY_STORAGE_THUMB_QUALITY` | `0.8` | 0.1~1.0 | `thumb.jpg` JPEG 품질 |
| `wearly.ai.image-max-side` | `WEARLY_AI_IMAGE_MAX_SIDE` | `1024` | 64~8192 | AI 공급자에 보내기 전 긴 변 (multipart 업로드·`{imageId}` 모두) |
| `wearly.ai.image-quality` | `WEARLY_AI_IMAGE_QUALITY` | `0.8` | 0.1~1.0 | AI 전송용 JPEG 품질 |

앱이 올리기 전에 만드는 크기(긴 변 1600, JPEG 0.8, `mobile/src/lib/photoUpload.ts`의 `MAX_SIDE`·`QUALITY`)는 서버 설정이 아니라 앱 상수다. 서버 `original-max-side`와 맞춰 두면 서버는 다시 줄이지 않고 JPEG만 다시 인코딩한다.

## 4. DB (Flyway `V12__item_image_storage.sql`)

날씨가 V11을 먼저 써서 사진 저장이 V12가 됐다. V1의 빈 `tb_item_image`(이미지 URL, 쓰지 않던 표)를 지우고 이 용도로 다시 만든다.

| 열 | 내용 |
|---|---|
| `image_id` | PK, UUID. 서버가 무작위로 만든다 (API의 `imageId`) |
| `user_id` | 소유 회원. 회원 삭제 시 `ON DELETE CASCADE` |
| `item_id` | 붙은 아이템. 올리기만 했거나 버린(`DELETED`) 이미지는 NULL. `ON DELETE SET NULL`은 안전장치(아이템 완전 삭제는 서비스가 먼저 `DELETED`로 바꾼다) |
| `purpose` | `ITEM` (CHECK) |
| `status` | `PENDING`(URL만 받음) · `READY`(처리 끝) · `DELETED`(버림). CHECK |
| `content_type` | PENDING일 때는 선언한 형식, READY부터는 저장한 original의 `image/jpeg` |
| `declared_size` | upload-url을 받을 때 선언한 크기(바이트) |
| `size_bytes` · `width` · `height` | 저장한 `original.jpg`의 크기·가로·세로 (READY부터) |
| `upload_key` | `uploads/{userId}/{imageId}` |
| `object_key` · `thumb_key` | `users/{userId}/items/{imageId}/original.jpg` · `.../thumb.jpg` (READY부터) |
| `created_at` · `ready_at` · `deleted_at` | 시각 |

- CHECK: READY면 저장 정보가 모두 있다(`ck_item_image_ready`). 아이템에 붙을 수 있는 것은 READY뿐(`ck_item_image_item`).
- **아이템당 사진 하나**: 부분 유니크 인덱스 `ux_item_image_item (item_id) WHERE item_id IS NOT NULL`.
- 인덱스: `ix_item_image_user_created (user_id, created_at)`(하루 한도 집계), `ix_item_image_cleanup (status, created_at) WHERE item_id IS NULL`(정리 작업).

## 5. 오브젝트 키

| 키 | 내용 | 수명 |
|---|---|---|
| `uploads/{userId}/{imageId}` | 앱이 올린 원본 그대로 | complete가 끝나면 지운다. 못 지우면 정리 작업이 지운다 |
| `users/{userId}/items/{imageId}/original.jpg` | 긴 변 `original-max-side`(1600) 이하 JPEG (품질 0.8) | 아이템 사진으로 쓰는 동안 |
| `users/{userId}/items/{imageId}/thumb.jpg` | 긴 변 `thumb-max-side`(400) JPEG (품질 0.8) | 〃 |

회원 탈퇴는 `users/{userId}/`와 `uploads/{userId}/` 접두사를 통째로 지운다 (`deletePrefix`는 `/`로 끝나는 접두사만 받는다).

## 6. API

모두 로그인이 필요하다. **남의 이미지·없는 이미지·`DELETED`·형식이 틀린 `imageId`는 404** `NOT_FOUND`. 코드: `ImageController`, `ImageUploadService`, `ItemImageService`.

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| POST | `/api/v1/images/upload-url` | `{ purpose: 'ITEM', contentType: 'image/jpeg' \| 'image/png', size }` | 200 `UploadUrlResponse` |
| POST | `/api/v1/images/{imageId}/complete` | 없음 | 200 `ImageResponse` |
| POST | `/api/v1/wardrobe/items/analyze` | JSON `{ imageId }` (내 READY 이미지). 기존 multipart도 그대로 | 200 `AnalyzeResponse` (기존과 같음) |
| POST · PATCH | `/api/v1/wardrobe/items`, `/{id}` (bulk 항목도) | 기존 + `imageId?: string \| null` | `ItemDto` (`image` 포함) |

```jsonc
// POST /images/upload-url  요청
{ "purpose": "ITEM", "contentType": "image/jpeg", "size": 482113 }

// 200 응답. 앱은 headers를 그대로 붙여 uploadUrl로 PUT한다 (Content-Type이 서명에 들어 있다)
{
  "imageId": "3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11",
  "uploadUrl": "http://localhost:9000/wearly-images/uploads/3/3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11?X-Amz-Algorithm=...&X-Amz-Signature=...",
  "method": "PUT",
  "headers": { "Content-Type": "image/jpeg" },
  "expiresAt": "2026-10-18T07:10:00.000Z"
}

// POST /images/{imageId}/complete  200 응답 (이미 READY면 같은 모양으로 새 서명 URL)
{
  "imageId": "3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11",
  "url": "http://localhost:9000/wearly-images/users/3/items/3f0c.../original.jpg?X-Amz-...",
  "thumbUrl": "http://localhost:9000/wearly-images/users/3/items/3f0c.../thumb.jpg?X-Amz-...",
  "width": 272,
  "height": 332,
  "expiresAt": "2026-10-18T08:00:00.000Z"
}

// POST /wardrobe/items/analyze  요청 (Content-Type: application/json)
{ "imageId": "3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11" }

// 아이템 등록·수정 요청에 imageId. PATCH에서 null이면 사진 빼기, 필드를 빼면 그대로
{ "name": "네이비 니트", "category": "TOP", "subType": "KNIT", "...": "...", "imageId": "3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11" }

// 아이템 응답 (목록·상세·등록·수정·retire·restore 모두). 사진이 없으면 "image": null
{
  "id": "42", "name": "네이비 니트", "...": "...",
  "image": {
    "imageId": "3f0c2a9e-8f1d-4c5b-9a57-2f6a0b6e1c11",
    "url": "http://localhost:9000/.../original.jpg?X-Amz-...",
    "thumbUrl": "http://localhost:9000/.../thumb.jpg?X-Amz-...",
    "expiresAt": "2026-10-18T08:00:00.000Z"
  }
}
```

- `url`·`thumbUrl`은 `download-url-ttl`(기본 1시간) 동안 유효한 GET 서명 URL이다. `expiresAt`은 둘 중 이른 쪽. 주소는 받을 때마다 달라지므로 **`imageId`로 캐시**한다.
- `upload-url`: 입력 오류는 **400 `VALIDATION_FAILED`**(`fieldErrors`: `purpose`가 `ITEM`이 아님, `contentType`이 jpeg·png가 아님, `size`가 1 미만이거나 `max-upload-bytes` 초과). 정상은 200이다(201 아님).
- `imageId` 형식이 UUID가 아니면 등록(POST)은 400 `VALIDATION_FAILED`(`imageId`), 수정(PATCH)은 형식 검사 없이 없는 이미지로 보고 404. 모양은 맞지만 없는·남의 이미지도 404.
- 응답 모양은 [05](05_백엔드_API.md) 6장 `ItemDto`·`ImageRef`와 같다. 앱 API 모듈은 `api.images.uploadUrl/put/complete`, `api.wardrobe.analyzeImage`.

### 오류 코드

| HTTP | code | 상황 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | upload-url 입력 오류, 등록 요청의 `imageId` 형식 오류 |
| 400 | `IMAGE_INVALID` | complete 처리 실패: 올린 크기가 `max-upload-bytes` 초과, 실제 바이트가 JPEG·PNG가 아님, 디코딩 실패(CMYK JPEG 포함), 화소 수 초과. **그 `imageId`는 버려진다**(`DELETED`, 업로드 원본 삭제) → upload-url부터 다시 |
| 400 | `IMAGE_NOT_UPLOADED` | complete인데 저장소에 올린 파일이 없다 (PUT을 못 했거나 만료). PENDING 그대로라 PUT 뒤 complete를 다시 부르면 된다. **PENDING 이미지를 아이템에 붙이거나 analyze하면** 같은 코드 |
| 404 | `NOT_FOUND` | 남의·없는·버린 이미지 |
| 409 | `IMAGE_IN_USE` | 다른 아이템에 붙은 이미지를 붙이려 함 (같은 아이템이면 그대로 200) |
| 429 | `IMAGE_UPLOAD_LIMIT` | 하루 upload-url 발급 한도 초과 |

기존 `IMAGE_TOO_LARGE`(413)·`UNSUPPORTED_MEDIA_TYPE`(415)는 multipart `analyze`에만 남는다.

## 7. 처리 규칙

### 7.1 올리기 (`createUploadUrl` → PUT → `complete`)

```
앱 ─ POST /images/upload-url ─▶ 백엔드  입력 검사 → 회원 advisory lock → 오늘(Asia/Seoul) 발급 수 < 한도 →
                                        PENDING 행 INSERT → PUT 서명 URL(Content-Type 포함, 10분)
앱 ─ PUT uploadUrl ───────────▶ 저장소  uploads/{userId}/{imageId}  (백엔드를 거치지 않는다)
앱 ─ POST /images/{id}/complete ▶ 백엔드  아래 순서
```

**complete 순서** (`ImageUploadService.complete`, 저장소 읽기·쓰기가 길어서 트랜잭션 없이 하고 행 저장만 짧게):

1. 내 이미지 찾기 (없음·남의 것·`DELETED` → 404). 이미 READY면 새 서명 URL만 만들어 같은 응답.
2. 업로드 객체의 크기 확인 (없으면 400 `IMAGE_NOT_UPLOADED`). `max-upload-bytes` 초과면 `IMAGE_INVALID`.
3. 바이트를 읽어 **실제 바이트로 형식 판별** (JPEG·PNG만. 선언한 Content-Type은 믿지 않는다).
4. 헤더의 가로×세로가 `max-pixels` 이하인지 확인 (디코딩 전에 막아 메모리 폭주를 피한다).
5. 디코딩 (긴 변이 목표의 2배를 넘으면 서브샘플링으로 줄여 읽는다).
6. EXIF Orientation(metadata-extractor로 읽음)을 적용한다.
7. 흰 배경 RGB로 바꿔 긴 변 1600(original, 품질 0.8)·400(thumb, 품질 0.8)로 줄이고 ImageIO JPEG 인코더로 **다시 인코딩**한다 (크기·품질은 3.1의 설정). 읽기·줄이기·쓰기는 `common/imaging/ImageCodec`이 하고, 저장용 `ImageIoProcessorAdapter`와 AI 전송용 `ImageIoAiImageResizer`가 같이 쓴다. 원본의 EXIF(위치 정보 포함)·ICC·XMP 같은 메타데이터는 옮기지 않는다 (기획서 p.31).
8. `original.jpg`·`thumb.jpg`를 저장소에 쓰고, 행을 READY로 저장한 뒤, `uploads/` 객체를 지운다 (지우기가 실패해도 응답은 성공, 정리 작업이 다시 지운다).

2~7 어디서든 실패하면 업로드 원본을 지우고 행을 `DELETED`로 바꾼 뒤 400 `IMAGE_INVALID`.

**10MB 검사는 complete에서 한다.** 서명 PUT URL은 본문 크기를 막지 못한다(선언한 `size`는 upload-url 때 검사할 뿐). 처리 동시 실행은 `processing-concurrency`(기본 2)로 제한한다.

### 7.2 아이템에 붙이기·교체·삭제

붙이기·빼기는 wardrobe 유스케이스의 트랜잭션 안에서 image 컨텍스트의 `ItemImageUseCase`를 부른다.

| 상황 | 동작 |
|---|---|
| 등록·수정에 `imageId` | 내 READY 이미지이고 다른 아이템에 안 붙었으면 붙인다. 붙이기가 실패하면 등록·수정이 통째로 되돌아간다 |
| 사진 교체 | 예전 이미지를 먼저 `DELETED`로 바꾸고(유니크 인덱스에 안 걸리게) 새 이미지를 붙인다. 예전 객체(`uploads/`·original·thumb)는 **커밋 뒤** 지운다 (롤백되면 그대로) |
| PATCH `imageId: null` | 사진 빼기. 예전 이미지는 같은 방식으로 `DELETED` + 커밋 뒤 객체 삭제 |
| PATCH에 `imageId` 없음 | 사진 그대로 |
| 아이템 완전 삭제 | 사진을 먼저 버린 뒤 아이템을 지운다 |
| 사용 중지(retire)·다시 사용 | 사진을 유지한다 ([13](13_옷_사용_중지.md)) |
| 회원 탈퇴 | 행은 FK CASCADE로 지워지고, user 컨텍스트의 `UserDeletedListener`를 받아 커밋 뒤 `users/{userId}/`·`uploads/{userId}/`를 통째로 지운다 |

### 7.3 정리 작업과 하루 한도

- **정리 작업** (`ImageCleanupScheduler`): 시작 5분 뒤 처음, 이후 `cleanup-interval`(1시간) 간격. 아이템에 안 붙은(`item_id IS NULL`) 이미지 중 `stale-after`(1일)가 지난 것을 지운다.
  - PENDING (올리다 만 것, `created_at` 기준)
  - 아이템에 안 붙은 READY (올리고 등록하지 않은 것, `ready_at` 기준)
  - DELETED (교체·삭제로 버린 것, 객체 삭제가 실패해 남은 것 포함)
  - 먼저 행을 `DELETED`로 바꿔(그사이 아이템에 붙은 것은 빠진다) 붙이기와 겹치지 않게 하고, 객체를 지운 뒤 **성공한 것만** 행을 지운다. 실패하면 `DELETED` 행이 남아 다음 번에 다시 한다. 200개씩 최대 50번.
- **하루 한도**: `daily-upload-limit`(200)은 **upload-url 발급 수**다. Asia/Seoul 날짜 기준이고 상태와 무관하다 (실패하거나 지운 것도 센다). 회원별 advisory lock으로 동시에 요청해도 한도를 넘지 않는다. AI 분석 한도와는 따로 센다.
- 버킷 수명 주기로 `uploads/`를 1일 뒤 지우게 해 두면 정리 작업이 놓친 업로드 원본도 지워진다 (선택, 8장).

### 7.4 AI 분석 `{ imageId }`

`AiAnalysisService.analyzeStored`가 `ImageContentUseCase.readOriginal`로 그 사진의 `original.jpg`를 읽어 기존 분석 흐름에 넣는다 ([10](10_백엔드_흐름.md) 3.4). 남의·없는 이미지 404, PENDING이면 400 `IMAGE_NOT_UPLOADED`. 한도·공급자·응답은 multipart와 같다.

**AI 전송 전 줄이기** (multipart·`{imageId}` 공통): 형식·크기 검사를 통과한 사진을 `AiImageResizePort.shrink`(`ImageIoAiImageResizer`)로 긴 변 `wearly.ai.image-max-side`(1024) 이하 JPEG(`image-quality`, 0.8)로 다시 인코딩해 보낸다. 줄이지 않고 **그대로 보내는** 경우는 다음과 같다 (`shrink`가 빈 값을 돌려준다).

- 실제 바이트가 JPEG·PNG가 아니다 (webp·heic는 ImageIO가 읽지 못한다)
- 헤더의 긴 변이 이미 `image-max-side` 이하다 (다시 인코딩하지 않는다)
- 헤더의 가로×세로가 `wearly.storage.max-pixels`를 넘는다 (디코딩하지 않는다)
- 읽기·쓰기에 실패했다 (경고 로그를 남기고 원본을 보낸다. 공급자가 판단한다)

줄인 결과에는 EXIF 방향이 적용되고 메타데이터가 없다. 동시에 줄이는 수는 `processing-concurrency`로 제한한다 (저장용과 따로 센다). `tb_ai_analysis_log`의 `image_bytes`·`image_sha256`은 **실제로 보낸(줄인) 사진** 기준이다. 크기·형식 검사(10MB, JPEG·PNG·webp·heic)는 올린 원본으로 한다.

### 7.5 분석 결과의 색 `colors` (이슈 #4)

사진 분석 결과(`suggestion`)에 `colors`(눈에 띄는 색 1~3개, 넓은 순)가 늘었다. 첫 번째는 `color`와 같다. 단색 옷은 하나만 준다. 허용 값은 활성 COLOR 코드이고(프롬프트의 허용 값 목록과 JSON 스키마의 enum), 1~3개·중복 없음·첫 번째 = `color`가 아니면 서버가 거부하고 다음 공급자로 넘어간다(`AiSuggestionValidator`). 목업 공급자도 보조 색을 만든다. 앱은 이 값을 옷 등록 폼의 색 칩(①②③)에 채운다. 관리자 시험 분석 화면에도 색상(1~3) 행이 있다. 아이템 쪽 규칙은 [05](05_백엔드_API.md) 6장 "옷장".

공통:

- 버킷을 **비공개**로 만든다 (익명 읽기·목록 금지). AWS IAM 권한은 그 버킷의 `s3:PutObject`·`s3:GetObject`·`s3:DeleteObject`·`s3:ListBucket`만.

- **버킷 CORS**: 네이티브 앱에는 필요 없고, Expo 웹(브라우저)이 서명 URL로 바로 PUT·GET하려면 웹 출처·`PUT`·`GET`·`Content-Type` 헤더를 허용한다.

  ```json

    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }]
  ```

- **수명 주기 규칙(선택)**: `uploads/` 접두사를 1일 뒤 지운다. 정리 작업이 놓친 업로드 원본의 안전망이다 (`users/` 접두사에는 걸지 않는다).
- 확인: 테스트 계정으로 upload-url → PUT → complete → 아이템 응답의 `thumbUrl` GET 200, 서명 없는 GET 403.

### 9.1 등록 (`item/new.tsx` 2단계)

1. 사진 고르기(카메라·앨범·쇼핑몰 캡처[24 문서]). 계정 모드는 선택기 압축을 끄고(quality 1) 다음 변환에서 한 번만 압축한다.
2. `expo-image-manipulator`로 **긴 변 1600 이하 JPEG(0.8)** 로 변환 (HEIC 대응, 용량 줄이기). 변환에 실패하면 원본이 JPEG·PNG일 때만 그대로 쓴다.
3. upload-url → `PUT`(서명 URL, 받은 `headers` 그대로. 본문은 바이트로 읽어 보낸다) → complete.
4. 올린 직후 기기 파일로 expo-image 디스크 캐시를 `img-{imageId}-full`·`img-{imageId}-thumb` 키로 채운다 (서버 주소를 처음 그릴 때 다시 받지 않게).
5. `analyzeImage({ imageId })`로 AI 분석 → 확인 화면 → 저장할 때 등록 요청에 `imageId`.
6. 올리기가 실패하면 2단계에 오류와 **"다시 시도"**. "직접 입력할게요"로 넘어가면 사진은 기기에 두고 나중에 옮긴다. 올린 사진이 붙지 않으면(`IMAGE_*`·404) 사진 없이 등록하고 기기에 둔 뒤 나중에 옮긴다.

옷 상세의 사진 바꾸기·빼기는 9.5장.

### 9.2 표시

- 목록은 `thumbUrl`(`variant='thumb'`), 상세는 `url`(`'full'`)을 expo-image로 그린다. 캐시 키는 **`img-{imageId}-thumb|full`**, `cachePolicy="memory-disk"`. 서명 URL이 바뀌어도 디스크 캐시를 다시 쓴다.
- 서버 사진을 못 그리면(서명 URL 만료 등) 그 아이템을 대상으로 **옷장을 다시 받아** 새 주소로 그린다. 같은 사진은 10분에 한 번, 다시 받기 사이는 최소 30초, 여러 사진이 한꺼번에 실패해도 목록 요청은 한 번(300ms로 모은다). 그동안은 기기 사진·일러스트를 보여 준다.
- 앱이 다시 활성이 되면 마지막 옷장 동기화가 2분 넘었을 때 옷장을 다시 받는다 (주소 유효 1시간보다 충분히 짧게).

### 9.3 기존 기기 사진 옮기기

계정 모드에서 앱이 시작하거나 복귀할 때, 서버 사진이 없고 기기 사진 파일(`file://`)이 남은 아이템의 사진을 위 흐름으로 올리고 PATCH `imageId`를 보낸다. 샘플 사진(`wearly-sample://`)과 웹 주소는 올리지 않는다.

| 규칙 | 값 |
|---|---|
| 한 번에 | 3장 |
| 재시도 간격 | 실패 n번 뒤 5분부터 두 배씩, 최대 하루 (5분·10분·20분 …) |
| 중단 | 한 사진이 8번 실패하면 더 시도하지 않는다 |
| 파일이 사라짐 | 건너뛰고 기록(`gone`)한다 |
| 실패로 세지 않고 이번 묶음만 멈춤 | 오프라인(`NETWORK`), 401, 하루 한도 `IMAGE_UPLOAD_LIMIT`·429 |
| 붙이려던 아이템이 서버에 없음 (404) | 그 사진은 건너뜀. 다음 동기화가 기기에서도 아이템을 지운다 |
| 성공 | 화면 캐시를 채운 뒤 기기 사진 참조를 지운다 (캐시를 못 채웠으면 서버 사진이 안 뜰 때를 위해 남긴다) |

옮기기 기록은 스토어 `photoSync` 필드(아이템 id별 `{ fails, lastAt, gone? }`)에 기기 저장소로 남는다.

### 9.4 게스트와 예전 서버

- **게스트 사진**: 고른 사진을 앱 문서 폴더 `Paths.document/photos/{itemId}.jpg`로 복사한다 (`keepPhotoLocally`). 시작할 때 선택기 캐시에 있는 기기 사진도 이 폴더로 옮기고, 어디서도 쓰지 않는 파일은 지운다.
- **게스트 파일 이름**: 처음 복사는 `photos/{itemId}.jpg`, 사진을 바꿀 때는 `photos/{itemId}-{버전}.jpg`로 새 이름을 쓴다 (같은 이름을 덮어쓰면 expo-image가 예전 사진을 그대로 보여 준다). 예전 파일은 바로 지우고, 실패하면 앱 시작 때 정리한다.
- **예전 서버**(사진 API가 없는 서버)는 upload-url에 404·405·501을 준다. 앱은 "기능 없음"으로 보고 10분 동안은 다시 묻지 않는다 (그 뒤 다시 시도). 이때 등록은 예전 방식(multipart 분석, 사진은 기기에 저장)으로 되돌아간다.

### 9.5 사진 바꾸기·빼기·AI 다시 분석 (이슈 #8, `f541fa0`)

| 파일 | 하는 일 |
|---|---|
| `src/lib/photoEditRules.ts` | 순수 규칙: 작은 사진 판단(`SMALL_PHOTO_MIN_SIDE = 600`, 긴 변 기준), 시트 선택지, `planPhotoChange`, 다시 분석에서 바뀌는 값 고르기·적용 |
| `src/lib/itemPhoto.ts` | `replaceItemPhoto`·`removeItemPhoto`·`reanalyzeItemPhoto` |
| `src/components/PhotoSheet.tsx` | 사진 시트 |
| `src/lib/mockAnalyze.ts` | 목업 분석 제안값 (`item/new.tsx`에서 옮김) |
| `tests/photoEdit.test.mjs` | 규칙 단위 테스트 13개 |

**바꾸기**: 옷 상세의 사진(카메라 배지)을 누르면 시트가 열린다. 선택지는 "카메라로 다시 찍기 / 앨범에서 고르기 / 쇼핑몰에서 가져오기 / 사진 빼기 / 취소"이고, 사진이 없으면 사진 빼기가 없다. 쇼핑몰에서 가져오기는 고를 쇼핑몰이 있고 웹 체험판이 아닐 때만 보인다 (24 문서).

- 계정 모드: 1600 JPEG 변환 → upload-url → PUT → complete → PATCH `imageId`. 서버가 예전 사진을 지운다(원본·thumb 모두 404가 된다).
- 진행 중에는 막이 덮고, 실패하면 지금 사진을 그대로 두고 `errorText` 문구와 오류 번호, **[다시 시도] [취소]** 를 보여 준다.
- 서버가 예전 서버(`IMAGES_UNSUPPORTED`)면 사진을 기기에 두고 나중에 옮긴다. PATCH가 404면 GET으로 확인해 "이미 삭제된 옷이에요"를 보여 준다.

**빼기**: 확인 창 뒤 PATCH `imageId: null`. 기기에만 있던 사진(서버에 안 올린 것)이면 서버를 부르지 않고 기기 파일만 지운다.

**옮기기와의 충돌**: 바꾸는 동안 `holdPhotoMigration`으로 그 아이템의 9.3 옮기기를 막고, 옮기기는 PATCH 직전에 다시 확인한다. 바꾸거나 빼면 옮기기 대기(`photos[id]`·`photoSync[id]`)를 정리한다.

**AI 다시 분석**: 새 사진을 올린 뒤 "새 사진으로 속성을 다시 분석할까요?"를 물어, **누를 때만** `POST /wardrobe/items/analyze { imageId }`를 부른다 (7.3 하루 한도 포함). 바뀌는 항목(종류·색상(순서 포함)·패턴·계절·스타일·격식)만 "이전 → 새 값"으로 미리 보여 주고, 적용하면 폼에 넣는다. 저장은 기존 저장 버튼이다. 이름은 자동 이름일 때만 새로 짓는다. 게스트는 목업 실행일 때만 제안한다.

**작은 사진 안내**: 긴 변이 600 미만이면 "사진이 작아서 흐리게 보일 수 있어요. 더 큰 사진이 있으면 바꿔 주세요."라고 안내한다 (`SMALL_PHOTO_TEXT`, 막지 않는다). 옷 등록 2·3단계에도 나온다.

**확인 (2026-10-18)**: 임시 계정으로 실서버에서 등록(A) → 교체(B, 예전 원본·thumb 404) → 재조회 B → 빼기(image null, URL 404). 백엔드 `ItemImageIntegrationTest` 14개, 앱 `typecheck`·`expo-doctor`·`check:errors`(서버 51)·`test:unit` 24개 통과. **시뮬레이터·실기기 조작은 아직 확인하지 않았다.**

## 12. 크기 줄이기 실측 (2026-10-18)

AI 분석에 보내는 사진을 얼마나 줄일지 정하려고 같은 사진으로 Claude `count_tokens`(모델 `claude-opus-5-5`)를 재 봤다. 사진은 3024×4032 원본(498KB)이고, 줄인 쪽은 긴 변만 바꾼 JPEG다.

| 긴 변 | 파일 크기 | 이미지 입력 토큰 |
|---|---|---|
| 원본 3024×4032 | 498KB | 4,752 |
| 2048 | 167KB | 4,082 |
| 1600 | 112KB | 2,506 |
| 1024 | 55KB | 1,048 |

- 2048 대비 1024는 이미지 토큰이 약 74% 줄었다 (4,082 → 1,048). 그래서 AI 전송 기본값을 1024로 했다.
- 저장 크기(1600)와 전송 크기(1024)를 따로 둔 이유: 저장한 사진은 앱 상세 화면에서 보고, AI는 옷 종류·색·무늬만 알아보면 된다.
- 실제 분석 1건(모델 `claude-haiku-5-5`): 498KB 사진을 올렸더니 AI에는 34KB가 갔고, 입력은 3,698토큰이었다 (사진 약 1천 + 질문 문장 약 2.7천). 결과는 "브라운 플레어 스커트 · `BOTTOM`/`SKIRT` · `brown` · `SOLID` · 0.85"로 알아본다.
- 이제 입력 토큰의 대부분이 질문 문장(허용 값 목록 포함)이다. 다음 절감 후보였던 프롬프트 캐싱은 같은 날 했다 (13장).

## 13. 프롬프트 캐싱 (2026-10-18, `5c457da` → `93b7209` 병합)

12장 끝에서 남은 입력 토큰의 대부분은 요청마다 똑같이 가는 긴 질문 문장(지시 + 허용 값 목록)이었다. 이것을 공급자의 프롬프트 캐시에 태워 두 번째 요청부터 싸고 빠르게 처리한다. 사진 분석(`ITEM_ANALYZE`)과 AI 코디 추천(`OUTFIT_RECOMMEND`, [09](09_AI_코디_추천.md)) 둘 다 적용했다.

### 13.1 프롬프트를 고정 부분과 바뀌는 부분으로 나눔

| 부분 | 내용 | 보내는 자리 |
|---|---|---|
| 고정 | 지시문, 허용 값 목록(활성 코드와 라벨), 점수 기준 | Claude `system`, OpenAI `instructions`, Gemini `systemInstruction` |
| 요청마다 바뀜 | 사진 + 짧은 요청 문장 (코디 추천은 옷장·조건·최근 착용 등) | 사용자 메시지 |

- 문장 내용은 그대로이고 자리만 나눴다 (`AnalysisPrompt`, `OutfitPrompt`).
- 캐시는 앞부분 바이트가 같아야 맞는다. 그래서 JSON 스키마 객체를 `Map.of`(JVM마다 키 순서가 달라질 수 있다) 대신 모두 **순서가 고정된 맵**으로 만든다. 허용 값 목록도 코드 순서로 만든다. 테스트가 고정 부분이 요청마다 바이트까지 같은지 확인한다.
- 관리자가 코드를 바꾸면 허용 값 목록이 바뀌어 첫 요청 한 번은 다시 쓰기가 된다 (정상).

### 13.2 공급자별 동작

| 공급자 | 캐시 | 캐시 토큰 읽기 |
|---|---|---|
| Claude | 고정 부분(system) 끝에 `cache_control`(ephemeral, 기본 5분)을 붙인다. 읽기는 입력 단가의 0.1배 안팎, 처음 쓰기는 조금 비싸다 | `cache_read_input_tokens`, `cache_creation_input_tokens` |
| OpenAI | 같은 앞부분을 공급자가 자동으로 캐시한다 (설정과 상관없음) | `input_tokens_details.cached_tokens` |
| Gemini | 같은 앞부분을 공급자가 자동으로 캐시한다 (설정과 상관없음) | `cachedContentTokenCount` |

- 설정 `wearly.ai.prompt-cache.enabled`(환경변수 `WEARLY_AI_PROMPT_CACHE_ENABLED`, 기본 `true`)로 Claude의 `cache_control`을 끌 수 있다. 꺼도 고정/바뀌는 부분 나눔은 그대로다 ([backend/README.md](../backend/README.md) 설정 표).
- **입력 토큰 기록**: `tb_ai_analysis_log.input_tokens`는 이제 공급자 사이에 같게 **캐시 읽기·쓰기를 포함한 입력 전체**다 (Claude 응답의 `input_tokens`는 캐시 밖 토큰만이라 서버가 `input_tokens + cache_read + cache_creation`을 더해 기록한다).
- **로그**: 호출이 성공하면 INFO 한 줄이 남는다 (`AiCallRunner`).

```
AI ITEM_ANALYZE 성공 provider=claude model=claude-haiku-5-5 ms=<지연> input=<입력 전체> output=<출력> cacheRead=<읽은 토큰> cacheWrite=<쓴 토큰>
```

공급자가 주지 않는 값은 `null`로 찍힌다. 로컬에서 `grep cacheRead`로 캐시가 맞았는지 바로 본다: `docker compose logs backend | grep "성공 provider"` ([15](15_터미널_명령.md)).

### 13.3 실측 (2026-10-18, `claude-haiku-5-5`, 같은 옷 사진 분석 2번 연속)

| | 1번째 요청 | 2번째 요청 |
|---|---|---|
| `cacheWrite` (캐시에 쓴 토큰) | 2,654 | 0 |
| `cacheRead` (캐시에서 읽은 토큰) | 0 | 2,654 |
| 응답 시간 | 약 3.8초 | 약 1.1초 |

- 두 번째 요청에서 고정 부분 2,654토큰을 캐시에서 읽었고, 입력 비용이 약 **85% 줄었다.** 응답은 3.8초에서 1.1초로 빨라졌다.
- 5분(기본 TTL) 안에 다시 요청해야 맞는다. 사용자가 적을 때는 첫 요청마다 쓰기 비용이 들 수 있으나(처음 쓰기는 보통 입력의 1.25배), 읽기 한 번이면 본전이다.

### 13.4 아직 하지 않은 것

| 항목 | 내용 |
|---|---|
| DB의 캐시 토큰 칸 | `tb_ai_analysis_log`에는 캐시 읽기·쓰기 토큰을 따로 담는 칸이 아직 없다. 지금은 로그 줄에만 있고, DB의 입력 토큰은 전체 합이다. 다음 단계에서 칸을 더한다 (Flyway **V19 예정**). 그때 관리자 AI 기록·대시보드에 캐시 절감을 보이게 한다 |
