# 17. 날씨 정보: 서버가 주기적으로 받아 저장하고 앱에 제공

> 2026-10-18. 대상: `backend/`(weather 컨텍스트, admin 컨텍스트의 날씨 API), `admin/`(날씨 메뉴), `mobile/`(날씨 표시·지역).
> **장소별 날씨(2026-10-18)**: 예정일 코디에서 다른 장소·먼 날짜의 날씨를 보는 기능을 더했다 → [19_장소별_날씨.md](19_장소별_날씨.md). 이 문서의 수집·저장 구조는 그대로이고, 아래 2·5·8장에 19 문서로 이어지는 내용을 덧붙였다.

## 1. 배경과 결정

앱의 날씨는 지금까지 목업이었다. `mobile/src/lib/weather.ts`가 서울 월평균 기온에 난수를 더해 만들었고, 이 값을 홈 화면, AI 코디 화면, 추천 엔진의 날씨 점수(20점)가 썼다.

실제 날씨로 바꾸되 **사용자 요청마다 외부 API를 부르지 않는다.** 사용자가 늘면 성능이 나빠지고, 공급자도 호출 횟수를 제한하기 때문이다. 대신 서버가 정해진 지역 목록의 날씨를 일정 주기로 받아 DB에 저장하고, 앱은 서버 API로 저장된 값만 읽는다.

| 항목 | 결정 |
|---|---|
| 공급자 | [WeatherAPI.com](https://www.weatherapi.com/) 하나. 예비 공급자(OpenWeatherMap)와 자동 전환은 **다음 단계**에 붙인다 (8장) |
| 위치 | 정해진 지역 목록(코드 그룹 `REGION`, 시·도 17개)에서 고른다. 앱은 위치 권한이 있으면 가장 가까운 지역을 기기 안에서 고른다 |
| 예보 기간 | 공급자가 주는 기간만 실제 예보로 쓴다 (관리자 설정, 기본 3일). 그 뒤 날짜는 지금처럼 체감 온도를 직접 고른다 |
| 주기 | 기본 30분. 관리자 화면에서 바꾸면 서버를 다시 띄우지 않아도 다음 실행부터 반영된다 |
| 키 | 서버 설정에만 둔다 (`wearly.weather.keys.WEATHERAPI_KEY`). 웹 입력 키는 이번 범위에서 뺐다 |
| 지역 저장 | 앱 기기에 저장한다. 프로필(`tb_user_profile.region_code`)에 넣는 것은 다음 단계 |

| 테이블 | 내용 |
|---|---|
| `tb_weather_place_snapshot` | REGION 밖 장소의 최신 예보. 격자 키(`"37.6,127.0"`, 소수 첫째 자리)별 한 행. 좌표 요청 때 공급자를 한 번 불러 채우고 3시간 캐시. `current`·`days`는 `tb_weather_snapshot`과 같은 모양 |
| `tb_weather_climate` | 격자·월별 평년값(Open-Meteo 과거 기상 자료로 지난 10개 완결 연도를 계산). PK `(grid_key, month)` |
| `tb_weather_call_log` (변경) | `run_id`·`region_code` NULL 허용. `call_kind` 값이 4개로: `FORECAST`(위 주기 수집, 실행 안), `ON_DEMAND`(좌표 요청 예보), `SEARCH`(장소 검색), `CLIMATE`(평년값 자료). 뒤의 셋은 `run_id`가 NULL이고 `provider_code`는 `WEATHERAPI`·`OPEN_METEO`(평년값)·`OPEN_METEO_GEO`(검색) |

- `current` = `{temp, feelsLike, cond, condText, observedAt}`, `days` = `[{date, temp, min, max, rainProb, cond, condText}]`. 기온은 섭씨, `cond`는 `SUNNY`·`CLOUDY`·`RAIN`(앱 `Weather.cond`와 같다), `rainProb`는 0~100.
- **월 사용량**: 공급자별로 이번 달(한국 시간) `tb_weather_call_log` 행 수. 실패한 호출도 센다 (공급자 쪽 사용량에 들어가므로). 장소별 날씨(19 문서): 같은 공급자 행으로 기록한 호출(`ON_DEMAND`, 지오코딩 대신 WeatherAPI로 한 `SEARCH`)이 이 달 사용량에 들어간다. Open-Meteo 호출(`CLIMATE`·`OPEN_METEO_GEO`)은 WeatherAPI 한도와 무관하다.
- **이력 보관**: `wearly.weather.log-retention-days`(기본 90일)보다 오래된 실행과 그 호출 이력을 매일 04:00(한국 시간)에 지운다.
- **날씨 이력** (`WeatherHistoryRecorder`): 스냅샷은 덮어쓰므로 지난 날씨는 따로 남긴다. AI 코디 검증처럼 "그날 실제 날씨"가 필요할 때 쓴다.
  - 받기에 성공할 때마다 스냅샷 저장 바로 뒤에 기록한다. 예보는 받은 `days` 중 **오늘(한국 날짜)** 칸으로 오늘 행의 예보 칸을 덮어쓴다 (그날 마지막 예보가 남는다).
  - 현재 날씨는 **관측 시각(`observedAt`)의 한국 날짜** 행에 더한다. 23:55 관측을 00:05에 받으면 전날 행에 들어간다. 이미 더한 관측(`last_observed_at`)보다 늦은 것만 더하므로 같은 관측을 두 번 받아도 한 번만 센다.
  - 날짜가 바뀌면 그 행은 더 바뀌지 않아 그대로 지난 날씨가 된다. 자정에 옮기는 작업이 없어서 서버가 자정에 꺼져 있어도 잃지 않는다. 그날 한 번도 받지 못한 지역은 행이 없다.
  - 이력 저장이 실패해도 스냅샷·실행 결과는 그대로다(경고 로그만). 시험 호출은 이력을 남기지 않는다.
  - **지우지 않는다** (`log-retention-days` 대상 아님). 지역 17개면 한 해 약 6천 행.

## 3. 스케줄

```
[스케줄러] 다음 실행 = 직전 실행이 끝난 시각 + DB의 interval_minutes (매번 다시 읽는다)
  └ 서버 시작 10초 뒤 첫 실행(STARTUP): 저장값이 주기보다 새것이면 건너뛴다. 이때 서버가 멈춰 RUNNING으로 남은 실행을 FAILED로 닫는다
  └ 꺼짐 → SKIPPED(DISABLED) / 부를 공급자 없음 → SKIPPED(NO_PROVIDER) / 다른 실행 중 → SKIPPED(LOCKED)
  └ Valkey 잠금 SET wearly:weather:refresh:lock <owner> NX EX 300 (서버가 여러 대여도 하나만 돈다)
  └ 활성 REGION마다 공급자를 부른다 (4장) → 성공하면 스냅샷 저장 + 오늘 날씨 이력 갱신(2장), 실패하면 이전 값은 두고 오류만 남긴다
```

- 외부 HTTP를 부르는 동안 DB 트랜잭션을 잡지 않는다. 호출 기록·공급자 상태·스냅샷은 그때그때 따로 저장한다 (중간에 멈춰도 받은 값은 남는다).
- 관리자 "지금 실행"(MANUAL)은 스케줄이 꺼져 있어도 돈다. 같은 잠금을 쓰므로 주기 실행과 겹치지 않는다. 요청은 실행 ID만 바로 돌려주고 실행은 다른 스레드에서 돈다.
- 서버 설정 `wearly.weather.scheduler-enabled=false`면 주기·시작 실행과 이력 정리를 하지 않는다 (테스트용). "지금 실행"은 된다.
- 호출량(17개 지역, 30분 주기): 하루 816회, 한 달 약 2.5만 회. 관리자 화면이 "예상 월 호출 수"를 보여 준다.

## 4. 공급자 호출과 차단

**순서**: 지역마다 부를 수 있는 공급자를 `priority` 순으로 시도하고, 실패하면 같은 지역을 다음 공급자로 시도한다. 한 지역의 현재 날씨와 예보는 한 공급자의 값만 쓴다. 지금은 공급자가 하나라 실패하면 그 지역은 이전 값을 그대로 둔다.

**부를 수 있는 공급자** = 켜짐 + 키 있음 + 차단 아님 + 이번 달 사용량에 이번 호출을 더해도 한도 이내.

**상태 전이** (`ProviderHealth`):

| 상태 | 뜻 | 실행 |
|---|---|---|
| `OK` | 정상 | 부른다. 실패하면 연속 실패 +1, `failure_threshold`에 닿으면 `OPEN` |
| `OPEN` | 연속 실패로 차단 (`circuit_open_until`까지) | 건너뛴다 |
| `HALF_OPEN` | 차단 시간이 끝남 | 다음 실행의 첫 지역 하나로 시험한다. 성공하면 `OK`, 실패하면 바로 다시 `OPEN` |
| `KEY_INVALID` | 401·403 (키가 틀렸거나 막힘) | 쿨다운으로 낫지 않으므로 건너뛴다. 관리자가 키를 고친 뒤 "차단 해제" |

**WeatherAPI.com** (`WeatherApiClient`)

- `GET {base}/forecast.json?key=…&q={lat},{lon}&days={n}&lang=ko&aqi=no&alerts=no`. 호출 한 번으로 현재 날씨와 일별 예보를 받는다. `n = min(설정 forecast_days, 공급자 max_forecast_days)`.
- 매핑: `current.temp_c`·`feelslike_c`·`condition`·`last_updated_epoch` → current. `forecastday[].day`의 `avgtemp_c`·`mintemp_c`·`maxtemp_c`, `rainProb = max(daily_chance_of_rain, daily_chance_of_snow)`.
- 상태 코드 → 앱 상태: `1000` → SUNNY, `1003·1006·1009·1030·1135·1147`(구름·안개) → CLOUDY, 그 밖(비·눈·진눈깨비·뇌우) → RAIN. 설명(`condText`)은 `lang=ko`의 `condition.text`.
- 오류 코드: 시간 초과 `TIMEOUT`, 연결 실패 `CLIENT`, 401·403 `AUTH`, WeatherAPI 오류 코드 2007(월 한도 초과) `QUOTA`, 429 `HTTP_429`, 그 밖 4xx `HTTP_4XX`, 5xx `HTTP_5XX`, 응답 모양이 다름 `PARSE`.
- 키가 쿼리 파라미터라서 오류 문구·호출 이력에서 지운다(`key=***`). 인증 오류는 공급자 메시지를 쓰지 않는다.

**목업**: `WEARLY_WEATHER_PROVIDER=mock`이면 모든 공급자를 목업 날씨로 대신한다 (키 상태 `MOCK`). 앱 목업과 같은 식(서울 월평균 + 날짜별 고정 난수, 위도가 낮을수록 조금 따뜻하게). 통합 테스트는 이 모드로 돈다.

## 5. 앱 API와 앱

### `GET /api/v1/weather?region=SEOUL` (인증 불필요)

DB에 저장된 값만 읽는다. `region`이 없으면 서울. 코드·앱 설정 API와 같게 `ETag`를 주고 `If-None-Match`가 같으면 304.

```json
{
  "region": { "code": "SEOUL", "label": "서울" },
  "current": { "temp": 18.3, "feelsLike": 17.6, "cond": "SUNNY", "condText": "맑음", "observedAt": "2026-10-17T02:55:00Z" },
  "days": [
    { "date": "2026-10-17", "temp": 15.9, "min": 10.2, "max": 21.4, "rainProb": 0, "cond": "SUNNY", "condText": "맑음" }
  ],
  "fetchedAt": "2026-10-17T03:00:11.508Z",
  "stale": false
}
```

- `days`는 그 지역의 오늘(한국 날짜)부터. 기온은 소수 첫째 자리.
- `stale`: 저장 시각이 주기의 3배보다 오래됐으면 true (앱이 "업데이트 지연"을 작게 보여 준다).
- 공급자 이름은 주지 않는다. 예비 공급자로 받아도 앱은 같은 모양으로 받는다.
- 오류: 없는 지역 400 `VALIDATION_FAILED`(`region` `NOT_FOUND`), 그 지역을 한 번도 받지 못했으면 503 `WEATHER_UNAVAILABLE`(`params` 없음). 오류 응답은 코드값만 보낸다(20 문서).

### `GET /api/v1/weather/day`, `GET /api/v1/weather/places` (장소별 날씨, 19 문서)

위 `GET /weather?region=`은 그대로이고(앱 홈이 쓴다), 예정일 코디를 위해 두 API를 더했다. 계약 전체는 [19_장소별_날씨.md](19_장소별_날씨.md) 3·4장.

| API | 인증 | 요약 |
|---|---|---|
| `GET /weather/day?region=SEOUL&date=YYYY-MM-DD` | 공개 | 한 지역·한 날짜의 날씨. 저장된 스냅샷만 읽는다(외부 호출 없음). 예보에 그 날이 있으면 `source: FORECAST`, 없으면 그 달 평년값 `CLIMATE` |
| `GET /weather/day?lat=..&lon=..&date=..` | 로그인 | REGION 밖 좌표. 격자 캐시(3시간), 오래됐으면 공급자를 한 번 불러 채운다. 회원 하루 한도(기본 30) 넘으면 예전 캐시 → 평년값 → 429 `WEATHER_LIMIT` |
| `GET /weather/places?q=` | 로그인 | 장소 검색(시·도 이름 맞추기 + Open-Meteo 지오코딩, 한글). 최대 10개, 하루 100회 한도 |

- 이 17 문서의 원칙 "사용자 요청마다 외부 API를 부르지 않는다"는 REGION(`region` 방식)에 그대로이고, REGION 밖 좌표만 격자 캐시·잠금·회원 한도로 절충한 예외 경로다.
- 오류: 400 `VALIDATION_FAILED`(`date`·`region`·`lat`·`lon`·`q`), 401 `UNAUTHORIZED`(좌표 방식·검색에 토큰 없음), 429 `WEATHER_LIMIT`(`params.kind`: `ON_DEMAND` 좌표 날씨 · `SEARCH` 장소 검색), 503 `WEATHER_UNAVAILABLE`(`params.kind: SEARCH`면 장소 검색을 지금 할 수 없음, 없으면 날씨 자체). 자세한 `params`는 20 문서 2장.

### 앱 (`mobile/`)

- `store/useWeatherStore.ts`: 고른 지역과 마지막 응답·ETag를 기기에 저장한다 (`wearly-weather-v1`).
- `lib/weatherSync.ts`: 앱 시작·앱이 다시 활성이 될 때·지역을 바꿀 때 `GET /weather`. 실패하면 조용히 저장값을 쓴다. 목업 실행에서는 부르지 않는다.
- `lib/weather.ts`: `forecast(date)`는 서버 예보에 그 날짜가 있으면 그 값(기온은 정수로 반올림), 없으면 목업 날씨. `hasForecast(date)`는 서버 예보를 받았으면 서버가 준 날짜만(보통 3일), 아니면 목업 기간(10일). 그 밖의 날짜는 체감 온도를 직접 고른다. `Weather` 타입은 그대로라 추천 엔진은 바뀌지 않았다.
- 홈: 날씨 카드에 지역 이름, 오늘이면 "지금 18° 맑음"과 `stale`일 때 "업데이트 지연".
- 더보기 → 날씨 → "날씨 지역"(`app/region.tsx`): 지역 목록(코드 `REGION`)에서 고르거나 "가까운 지역 찾기"(`expo-location` 위치 권한, 하버사인 거리로 기기 안에서 계산, 위치는 서버로 보내지 않는다). 권한을 거부하면 목록에서 고른다. 목업 실행에서는 숨긴다.

- 예정일 코디의 장소·평년값·다시 확인(앱 화면, `lib/planWeather.ts`·`lib/placeWeather.ts`, `store/usePlaceStore.ts`, `app/place.tsx`)은 19 문서 9장. `app/region.tsx`의 '날씨 지역'(내 지역)과는 별개다.

## 6. 관리자 API (`/api/v1/admin/weather`, ADMIN 전용)

| API | 내용 |
|---|---|
| `GET /settings` | `{ setting, nextRunAt, running, lastRun, activeRegions, schedulerEnabled }`. `setting` = `{enabled, intervalMinutes, forecastDays, failureThreshold, cooldownMinutes, updatedBy, updatedAt}` |
| `PUT /settings` | 본문은 `setting`의 다섯 값(전부 필수). 범위를 벗어나면 400 `VALIDATION_FAILED`(fieldErrors). 응답은 GET과 같다. 값이 바뀌면 변경 이력 `WEATHER_SETTING_UPDATE` |
| `GET /providers` | 공급자 목록: `code, displayName, enabled, priority, keyName, keyState(CONFIGURED·MISSING·MOCK·UNSUPPORTED), status(OK·OPEN·HALF_OPEN·KEY_INVALID), consecutiveFailures, circuitOpenUntil, lastSuccessAt, lastFailureAt, lastError, monthUsage, monthlyQuota, maxForecastDays, callsPerFetch, usable`. 키 값은 없다 |
| `PATCH /providers/{code}` | `enabled`, `priority`(0~10000), `monthlyQuota`(0 이상, null = 한도 없음), `maxForecastDays`(1~14). 변경 이력 `WEATHER_PROVIDER_UPDATE` |
| `POST /providers/{code}/reset` | 차단 해제 (연속 실패·차단을 비운다). 변경 이력 `WEATHER_PROVIDER_RESET` |
| `POST /providers/{code}/test` | 본문 `{regionCode}`(필수). 그 공급자로 한 지역을 부른다. 사용 여부·차단과 상관없이 부르고, 스냅샷·공급자 상태는 바꾸지 않는다. 실행 이력에 `TEST`로 남는다. 키가 없으면 409 `WEATHER_NO_PROVIDER` |
| `POST /refresh` | 본문 `{regionCode?}`(없으면 활성 지역 전체). 202 `{runId}`. 실행 중이면 409 `WEATHER_REFRESH_RUNNING`, 부를 공급자가 없으면 409 `WEATHER_NO_PROVIDER`. 변경 이력 `WEATHER_REFRESH`(targetId = 실행 ID) |
| `GET /runs?trigger&status&page&size` | 실행 목록 (최신순, `requestedByEmail` 포함) |
| `GET /runs/{runId}` | `{ run, calls }` (호출은 호출한 순서) |
| `GET /calls?providerCode&callKind&regionCode&success&fallback&errorCode&from&to&page&size` | 호출 이력 (최신순). `from`·`to`는 `YYYY-MM-DD`(한국 날짜) 또는 ISO 시각. `callKind` = `FORECAST`·`ON_DEMAND`·`SEARCH`·`CLIMATE`(대소문자 무관, 19 문서 7장). 그 밖의 값은 400 `VALIDATION_FAILED`(`callKind` `NOT_ALLOWED`, `params.allowed` = 4개) |
| `GET /calls/summary` | `{ today: {calls, failures, fallbacks, avgDurationMs}, months: [{providerCode, displayName, used, quota}], auxiliaryMonths: [{providerCode, displayName, used}] }`. `auxiliaryMonths`는 공급자 표 밖 보조 공급자의 이번 달(한국 시간) 호출 수(실패 포함, 한도 없음): `OPEN_METEO`(평년값 "Open-Meteo 평년값")·`OPEN_METEO_GEO`(장소 검색 "Open-Meteo 장소 검색")는 0이어도 늘 나오고, 이력에만 있는 다른 공급자 코드가 이름순으로 뒤에 붙는다 |
| `GET /snapshots` | 모든 REGION 코드(비활성 포함)와 저장값. 받은 적 없으면 `current`·`fetchedAt`이 null. `raw`는 null |
| `GET /snapshots/{regionCode}` | 위와 같고 `raw`(공급자 원본)까지 |
| `GET /history?regionCode&from&to&page&size` | 날씨 이력 (최신 날짜순, 같은 날짜는 지역 코드순). `from`·`to`는 `YYYY-MM-DD`(한국 날짜, 둘 다 포함). 없으면 `to` = 오늘, `from` = `to` 기준 최근 30일. 형식이 틀리거나 `from > to`면 400 `VALIDATION_FAILED`. 한 줄 = `{regionCode, regionLabel, date, providerCode, forecast: {date, temp, min, max, rainProb, cond, condText} \| null, forecastFetchedAt, observed: {min, max, avg, count, rainCount} \| null, firstObservedAt, lastObservedAt}` |

변경 이력 대상 종류: `WEATHER_SETTING`(targetId `default`), `WEATHER_PROVIDER`(공급자 코드), `WEATHER_REFRESH`(실행 ID).

### 관리자 사이트 (`admin/src/pages/weather/`)

왼쪽 메뉴 **날씨**, 탭 4개.

1. **스케줄**: 상태(켜짐·다음 실행 예정·마지막 실행), 설정 폼(예상 월 호출 수 = 활성 지역 수 × 지역당 호출 수 × 하루 실행 수 × 30, 1순위 공급자 한도를 넘으면 경고, 예보 일수가 공급자 최대보다 크면 안내, 저장 확인 대화상자), 지금 실행(전체 또는 한 지역, 끝날 때까지 기다려 결과 알림), 최근 실행 10건(누르면 호출 목록).
2. **공급자**: 사용 스위치, 상태·키 배지, 상태 설명, 차단 해제, 이번 달 사용량 막대(80% 주황, 100% 빨강), 수정 패널(월 한도·최대 예보 일수·우선순위), 시험 호출(현재 날씨·일별 예보·원본). 표 아래 **"Open-Meteo (보조 공급자)" 카드**: 평년값·장소 검색에 서버가 고정으로 쓰는 공급자(공급자 표 밖, 키·월 한도·차단·우선순위 없음)의 이번 달 호출 수(`auxiliaryMonths`)와 호출 이력 바로가기. 무료 API는 비상업 용도만 허용(하루 1만 회 이하)이라 상용 출시 전에는 유료 플랜이 필요하다는 안내가 붙는다.
3. **호출 이력**: 요약 칩, 필터(URL 쿼리), 표, 행 상세(오류 전문, 실행 열기). **종류** 칸과 필터가 있다: 정기·수동 실행(`FORECAST`, 트리거를 작게 붙임)·다른 장소 날씨(`ON_DEMAND`)·장소 검색(`SEARCH`)·평년값(`CLIMATE`). 종류 필터는 서버의 `callKind`로 거른다(받은 페이지 안에서만 거르지 않는다). 실행 밖 호출(`run_id` 없음)은 실행 열기가 없고, 지역 칸은 격자 키를 "좌표 35.7, 139.7"로(검색은 "—") 보여 준다. 요약 칩에는 보조 공급자(Open-Meteo 평년값·장소 검색)의 이번 달 호출 수(월 한도 없음)가 `auxiliaryMonths`로 나오고, 오늘 호출·이번 달 사용량 칩에는 "다른 장소·검색 포함"이 붙는다. 5xx 오류는 오류 번호(`traceId` 앞 8자)가 함께 보인다(20 문서 7장).
4. **저장된 날씨**: 지역별 표(비활성 흐리게, 오래됨 배지, 마지막 오류), 상세(일별 예보 원문 상태 → 앱 상태, 앱 응답 미리보기, 원본, "이 지역 새로 받기").

그 밖에 코드 관리 `REGION`에 위도·경도 입력칸, 대시보드에 날씨 카드, 변경 이력에 날씨 탭.

## 7. 설정

`application.yml` (운영값은 DB와 관리자 화면에 있다):

```yaml
wearly:
  weather:
    provider: ${WEARLY_WEATHER_PROVIDER:db}        # db | mock
    timeout: ${WEARLY_WEATHER_TIMEOUT:PT10S}
    log-retention-days: ${WEARLY_WEATHER_LOG_RETENTION_DAYS:90}
    scheduler-enabled: ${WEARLY_WEATHER_SCHEDULER_ENABLED:true}
    base-urls:
      WEATHERAPI: https://api.weatherapi.com/v1
    keys:
      WEATHERAPI_KEY: ${WEATHERAPI_KEY:}
```

실제 키는 `backend/config/application-local.yml`(git 제외)의 `wearly.weather.keys.WEATHERAPI_KEY`에 넣는다 (견본: `application-local.example.yml`). `backend/.env`는 읽지 않는다 (08 문서 6장). 키가 없으면 공급자 상태가 "키 없음"이고 주기 실행은 `SKIPPED(NO_PROVIDER)`로 남는다.
