# 22. 관리자 계정 관리: 지금 구현, 일반적인 방식, 단계별 계획

> 결정 문서 · 2026-10-18 · 대상: `backend/`(`admin` 컨텍스트), `admin/`
> 회사에는 아직 계정 시스템(IdP)이 없다. 나중에 회사 계정과 연동할 때 참고하도록 결정과 순서를 남긴다.
> **1단계(앱 DB 방식 보완)는 구현했다** (2026-10-18, `3b84994`, `dev`에 `f3fbfae`로 병합). 4.1장에 구현 상세가 있다. 2단계(OIDC/Keycloak)는 진행 중이다.
> 관리자 역할·API는 [07](07_관리자_사이트.md), 세션은 [16](16_세션_Valkey.md).

## 1. 질문과 결론

질문: 이런 앱은 관리자 계정을 보통 어디서 관리하나?

| 항목 | 결론 |
|---|---|
| 흔한 방식 | 초기에는 앱 DB의 역할(role), 회사가 커지면 회사 IdP와 SSO, 운영에서는 네트워크 차단을 더한다 |
| 원칙 | 고객 계정과 직원(관리자) 계정은 다른 체계로 나눈다 |
| Wearly 지금 | 앱 DB 방식. 아래 2장의 구멍을 막았다 (1단계, 구현함 — 4.1장) |
| Wearly 다음 | 범용 OIDC 로그인. 로컬은 Keycloak으로 시험하고 운영은 설정만 바꿔 회사 IdP에 연결한다 (2단계) |
| 운영 배포 때 | 관리자 사이트를 접근 프록시나 VPN 뒤에 둔다 (3단계) |

## 2. 보완 전 Wearly 구현과 문제점

> 이 장은 1단계 보완 **전**의 모습이다. 아래 문제 a~d는 모두 4.1장의 구현으로 막았다.

구현 (`AdminBootstrap` → `AdminAccountService.ensureAdmin`):

- 설정 `wearly.admin.email`·`password`·`name`이 있으면 서버 시작 때 실행한다. 설정 파일은 `backend/config/application-local.yml`(git 제외).
- 그 이메일 회원이 없으면 `ADMIN`으로 새로 만든다. 감사 기록 `ADMIN_BOOTSTRAP_CREATE`.
- 이미 있는 회원이면 `ADMIN`으로 올린다. 감사 기록 `ADMIN_BOOTSTRAP_PROMOTE`. 비밀번호는 첫 생성 때만 쓴다.
- 관리자 로그인은 일반 `/auth/login`이고, 사이트가 `user.role`이 `ADMIN`인지 본다.

문제점:

| | 문제 | 왜 문제인가 |
|---|---|---|
| a | 같은 이메일로 먼저 가입한 일반 회원이 자동으로 관리자가 된다 | 가입 API가 공개이고 이메일 인증이 없다. 공격자가 관리자 이메일로 먼저 가입해 두면 다음 시작 때 관리자가 된다 |
| b | 파일의 비밀번호를 바꿔도 반영되지 않고, 평문으로 남는다 | 첫 생성 때만 쓰므로 파일 값과 실제 비밀번호가 달라진다. 파일이 새면 위험하다 |
| c | 관리자를 늘리거나 해제하는 방법이 없다 | 설정 파일을 고치고 DB를 직접 만져야 한다 |
| d | 2단계 인증과 관리자 로그인 기록이 없다 | 비밀번호만 알면 들어온다. 누가 언제 들어왔는지 모른다 |

## 3. 일반적인 관리 방식 세 가지

| | 방식 | 어울리는 때 | 장점 | 단점 |
|---|---|---|---|---|
| ① | 앱 DB에 역할(role) | 초기 스타트업·소규모 | 간단하다. 추가 시스템이 없다 | 퇴사자 정리·비밀번호 정책·2FA를 직접 만들어야 한다. 고객과 같은 로그인 경로라 공격 대상이다 |
| ② | 회사 IdP와 SSO (OIDC/SAML) | 직원이 늘고 회사 계정이 있을 때 | 퇴사 때 회사 계정만 막으면 끝. 2FA·비밀번호 정책·로그인 기록을 IdP가 맡는다 | IdP가 있어야 한다. IdP 장애 때 로그인이 막힌다 |
| ③ | 관리자 사이트 네트워크 차단 | 운영 서버를 공개 인터넷에 둘 때 | 직원 기기가 아니면 로그인 화면도 안 보인다 | 혼자서는 계정 관리가 안 된다. ①·②와 함께 쓴다 |

### 3.1 ① 앱 DB에 역할

`tb_user.role`이 `ADMIN`이면 관리자다. 지금 방식이다. 직원 계정이 고객과 같은 표, 같은 로그인 API에 있으므로 비밀번호 대입 공격의 표적이 된다. 그래서 최소한 2FA와 로그인 기록을 넣는다.

### 3.2 ② 회사 IdP와 SSO

- 관리자 사이트는 "회사 계정으로 로그인" 버튼만 둔다. 비밀번호를 앱이 받지 않는다.
- 권한은 IdP 그룹으로 정한다. 예: `wearly-admins`(전체 권한), `wearly-viewers`(조회만).
- IdP 예: Microsoft Entra ID(예전 Azure AD), Google Workspace, Okta, Keycloak(직접 운영).
- 프로토콜은 OIDC가 새 앱에 맞다. 오래된 사내 시스템은 SAML을 쓴다.

AD와의 관계:

| 구성 | 설명 |
|---|---|
| 사내 AD + Entra Connect | 사내 AD 계정을 Entra ID로 동기화한다. 앱은 Entra ID와 OIDC로 붙는다 |
| 사내 AD + ADFS | AD가 직접 토큰을 발급한다. 앱은 OIDC나 SAML로 붙는다 |
| 사내 AD + Keycloak | Keycloak이 AD를 LDAP으로 읽는다(User Federation). 앱은 Keycloak과 OIDC로 붙는다 |

운영 규칙:

- 퇴사자는 AD 계정만 막으면 관리자 사이트에도 못 들어온다.
- SCIM을 지원하는 IdP면 계정 생성·삭제가 앱에 자동 동기화된다.
- IdP 장애에 대비해 로컬 비상 계정(break-glass) 하나를 유지한다. 비밀번호는 금고에 보관하고 쓸 때마다 알림을 남긴다.

### 3.3 ③ 네트워크 차단

관리자 사이트(와 `/api/v1/admin/**`)를 VPN이나 접근 프록시 뒤에 둔다. 인증된 직원 기기에서만 열린다.

- 접근 프록시: Cloudflare Access, Google IAP, Tailscale 등.
- 프록시가 회사 계정으로 먼저 인증하므로 ②와 잘 맞는다.
- 프록시가 뚫려도 앱 자체 로그인이 한 번 더 막는다 (이중 방어).

#### 4.1.1 시작할 때 관리자 만들기 (`AdminBootstrap` → `AdminAccountService.ensureAdmin`)

- 설정 `wearly.admin.email`·`password`가 둘 다 있고 **관리자(`ADMIN`)가 한 명도 없을 때만** 그 계정을 만든다 (이름 `wearly.admin.name`, 기본 "관리자"). 감사 기록 `ADMIN_BOOTSTRAP_CREATE`.
- 그 이메일로 이미 가입한 일반 회원이 있으면 **관리자로 올리지 않는다.** WARN 로그만 남긴다(이메일은 가려서). 예전의 `ADMIN_BOOTSTRAP_PROMOTE`는 없어졌다.
- 관리자가 이미 있으면 설정 값은 쓰지 않는다. 설정 비밀번호는 첫 생성에만 쓰므로, 만든 뒤에는 파일에서 지워도 된다 (비밀번호는 4.1.2로 바꾼다).
- 설정이 없으면 "관리자 계정 설정 없음" INFO 로그만 남기고 시작한다.
- 시작 로그로 확인한다: `docker compose logs backend | grep -E "관리자 2단계 인증|관리자 계정"` → "관리자 2단계 인증: 필수 (issuer=Wearly)", "관리자 계정: 관리자가 이미 1명 있어 설정 계정(wearly.admin.email)은 쓰지 않아요" (2026-10-18 실제 로그).

#### 4.1.2 비밀번호 변경 `POST /api/v1/admin/me/password`

- 요청 `{ currentPassword, newPassword }` → 204. 현재 비밀번호가 틀리면 403 `REAUTH_FAILED`, 새 비밀번호가 가입 규칙(8~64자, 영문과 숫자 포함, `PasswordPolicy`)에 맞지 않으면 400 `VALIDATION_FAILED`(`newPassword` `INVALID_FORMAT`).
- 바꾸면 **지금 세션을 뺀 이 관리자의 다른 세션을 모두 끊는다** (로그인 이력에는 `FORCED_LOGOUT`). 감사 기록 `ADMIN_PASSWORD_CHANGE`(`after.endedSessions`).
- 관리자 사이트: "내 계정" 화면(`/me`)의 비밀번호 바꾸기.

#### 4.1.3 관리자 지정·해제 `PATCH /api/v1/admin/users/{id}` `{ role }`

- 사이트의 "회원" 화면에서 누른다. 감사 기록 `USER_ROLE_CHANGE`(역할이 바뀔 때, 그 밖의 정지·해제는 `USER_UPDATE`).
- 자기 자신의 역할은 못 바꾼다 (400 `role` `SELF_NOT_ALLOWED`).
- 정지(`SUSPENDED`)한 회원은 관리자로 지정할 수 없다 (400 `role` `CONFLICT`).
- 해제하면 쓸 수 있는 관리자(`ADMIN`·`ACTIVE`)가 한 명도 남지 않게 될 때 **409 `LAST_ADMIN`**.
- 해제하면 그 회원의 로그인 세션을 모두 끊는다.

#### 4.1.4 2단계 인증 (TOTP, RFC 6238)

**누가 대상인가.** 관리자 사이트에서 로그인하는 관리자(`X-Wearly-Client: admin`). 설정 `wearly.admin.mfa.required`(기본 `true`)가 켜져 있거나 이미 TOTP를 등록한 관리자는 코드를 확인해야 한다. `false`면 등록하지 않은 관리자는 예전처럼 비밀번호만으로 들어오고, 등록한 관리자는 그래도 코드를 확인한다 (로컬 개발·하네스).

**로그인 흐름** (`AuthService.login` → `MfaService`):

```
관리자 사이트 ── POST /auth/login {email, password} ──▶ 서버
   ◀── 200 { mfa: { required: true, enrolled }, mfaToken, mfaTokenExpiresIn: 300 }   (토큰 대신 대기 토큰)

[enrolled = false: 처음 등록]
   ── POST /auth/mfa/setup {mfaToken} ──▶ { secret, otpauthUrl }     (QR로 그리고 수동 입력 키도 보여 준다)
   인증 앱(Google Authenticator 등)에 등록
   ── POST /auth/mfa/verify {mfaToken, code} ──▶ 토큰 + recoveryCodes(10개, 이때 한 번만) + recoveryCodesLeft

[enrolled = true]
   ── POST /auth/mfa/verify {mfaToken, code | recoveryCode} ──▶ 토큰 + recoveryCodesLeft
```

- 비밀번호가 맞을 때만 대기 토큰을 준다. 대기 토큰은 5분, Valkey(`wearly:mfa:pending:{tokenHash}`)에 SHA-256 해시로만 두고, 관리자 API에는 쓸 수 없다. 응답에 `accessToken`이 없는 것이 일반 로그인과의 차이다 (`LoginResponse` = `AuthResponse` 또는 `MfaChallengeResponse`).
- 코드 확인에 성공해야 세션이 "2단계 인증을 거친 세션"으로 만들어진다. 거치지 않은 세션(앱 로그인 등)으로 `/admin/**`를 부르면 **403 `MFA_REQUIRED`** (앱 API는 그대로 쓴다).
- TOTP: 6자리, 30초, SHA-1, 앞뒤 1단계 허용. **같은 30초 단계의 코드는 한 번만** 받는다 (`last_used_step`).
- 복구 코드: 10개, `abcde-fghjk` 모양(헷갈리는 0·1·l·o 제외). 등록할 때 한 번만 보여 주고 DB에는 `SHA-256("{user_id}:{정규화한 코드}")` hex만 둔다. 한 번 쓰면 다시 못 쓴다.
- **틀림·잠금**: 코드를 5번 틀리면 15분 잠근다 (`MFA_LOCKED`, `params.retryAfterSeconds`). 횟수는 회원별로 Valkey에 두므로 다시 로그인해도 이어지고, 마지막 실패에서 15분이 지나면 잊는다. 잠기면 대기 토큰도 지운다. 틀릴 때마다 `MFA_CODE_INVALID`(`params.remainingAttempts`).
- 등록 중인 비밀은 마스터 키(`wearly.secret-key`)로 암호화해 Valkey(`wearly:mfa:setup:{userId}`)에 10분 둔다. 마스터 키가 없으면 등록을 시작할 수 없다 (409 `SECRET_KEY_MISSING`) — 켜려면(`required: true`) 마스터 키가 꼭 있어야 한다.

**내 계정에서** (`/api/v1/admin/me/mfa`, 로그인한 관리자):

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/admin/me/mfa` | `{ enrolled, enrolledAt, recoveryCodesLeft, required }` |
| POST | `/admin/me/mfa/setup` | 등록 시작 `{ secret, otpauthUrl }` (이미 등록했으면 409 `MFA_ALREADY_ENROLLED`) |
| POST | `/admin/me/mfa/enable` | `{ code }` → `{ recoveryCodes }` (등록 마침, 이 세션을 "거친 세션"으로) |
| POST | `/admin/me/mfa/reset` | `{ currentPassword, code \| recoveryCode }` → 204. 내 TOTP·복구 코드를 지우고 다른 세션을 끊는다. 이어서 setup → enable로 다시 등록 (등록 안 했으면 409 `MFA_NOT_ENROLLED`) |
| DELETE | `/admin/users/{id}/mfa` | **다른 관리자**의 2단계 인증 초기화 → 204. 그 회원의 세션을 모두 끊는다. 자기 자신은 400 (`id` `SELF_NOT_ALLOWED`, 내 것은 위 `reset`) |

**저장** (Flyway `V15__admin_mfa.sql`): `tb_user_mfa`(비밀 암호문 `secret_cipher`·`secret_nonce` 12바이트·`key_version`·`last_used_step`·`enrolled_at`), `tb_user_mfa_recovery_code`(`code_hash`·`used_at`). 비밀은 AI 키와 같은 AES-256-GCM이고 AAD가 `mfa:{user_id}`라 다른 회원 행에 붙여 넣으면 복호화되지 않는다. 마스터 키를 바꾸거나 잃으면 복구 코드로 들어와 다시 등록한다.

**설정**:

| yml | 환경변수 | 기본값 | 뜻 |
|---|---|---|---|
| `wearly.admin.mfa.required` | `WEARLY_ADMIN_MFA_REQUIRED` | `true` | 모든 관리자에게 2단계 인증을 강제. 로컬 개발이 번거로우면 `false` |
| `wearly.admin.mfa.issuer` | `WEARLY_ADMIN_MFA_ISSUER` | `Wearly` | 인증 앱에 보이는 발급자 이름 |
| `wearly.secret-key` | `WEARLY_SECRET_KEY` | (없음) | TOTP 비밀 암호화 마스터 키 (base64 32바이트). `required: true`면 꼭 필요 |

#### 4.1.5 관리자 로그인 기록 `GET /api/v1/admin/auth-events`

- 쿼리 `userId`·`type`·`from`·`to`·`page`·`size`. 항목 `{ id, userId, email, name, role, type, sessionId, client, ip, userAgent, createdAt }`, 최신순 전체 목록.
- `type`: 기존 `LOGIN`·`LOGOUT`·`REFRESH_REUSED`·`FORCED_LOGOUT`에 `LOGIN_FAILED`(가입한 이메일로 비밀번호가 틀림, 없는 이메일은 남기지 않는다)·`MFA_SUCCESS`·`MFA_FAILED`·`MFA_LOCKED`를 더했다 (`V16__auth_event_mfa.sql`, `tb_auth_event`의 CHECK와 최신순 인덱스 `ix_auth_event_created`).
- 관리자 사이트 메뉴 "관리자 로그인 기록" (`/auth-events`).

#### 4.1.6 처음 로그인 안내 (새 서버를 세울 때)

1. `backend/config/application-local.yml`에 `wearly.admin.email`·`password`와 마스터 키 `wearly.secret-key`(`openssl rand -base64 32`)를 넣는다. 비밀번호는 8~64자, 영문과 숫자를 함께.
2. 백엔드를 시작하면 관리자가 없을 때 그 계정이 만들어진다 (이미 그 이메일로 가입한 일반 회원이 있으면 만들지 않고 WARN만 남긴다 — 다른 이메일을 쓴다).
3. 관리자 사이트(`http://localhost:5173`)에서 로그인하면 `mfa.enrolled = false`라 **인증 앱 등록 화면**이 나온다. QR(또는 수동 입력 키)을 인증 앱에 등록하고 6자리 코드를 넣는다.
4. **복구 코드 10개**가 한 번만 나온다. "저장했어요"를 체크해야 들어갈 수 있다. 안전한 곳(비밀번호 관리자 등)에 둔다.
5. 들어가면 "내 계정"에서 비밀번호를 바꾸고, 설정 파일의 `password`는 지워도 된다.
6. 로컬 개발에서 번거로우면 `wearly.admin.mfa.required: false`로 끈다 (등록한 관리자는 그래도 코드를 확인한다).

#### 4.1.7 휴대폰을 잃어버렸을 때

| 상황 | 방법 |
|---|---|
| 복구 코드가 남아 있다 | 로그인 2단계에서 "복구 코드로 들어가기" → 코드 하나 입력 (한 번 쓰면 못 쓴다). 들어간 뒤 "내 계정"의 다시 등록(지금 비밀번호 + 코드 또는 복구 코드)으로 새 휴대폰에 등록하고 새 복구 코드를 받는다 |
| 복구 코드도 없다, 다른 관리자가 있다 | 다른 관리자가 "회원" 화면에서 그 관리자의 2단계 인증을 초기화한다 (`DELETE /admin/users/{id}/mfa`, 감사 `USER_MFA_RESET`, 그 회원의 세션 모두 끊김). 다음 로그인 때 다시 등록한다 |
| 혼자뿐이고 다 잃었다 | API로는 풀 수 없다. DB에서 그 회원의 `tb_user_mfa`와 `tb_user_mfa_recovery_code` 행을 지우고(`DELETE FROM tb_user_mfa WHERE user_id = …`) 다시 로그인해 등록한다 — [14](14_DB_명령.md) |
| 5번 틀려 잠겼다 | 15분 기다린다 (`MFA_LOCKED`의 `retryAfterSeconds`). 바로 풀어야 하면 Valkey의 `wearly:mfa:lock:{userId}`와 `wearly:mfa:fail:{userId}`를 지운다 ([14](14_DB_명령.md) 7장). 보통은 기다린다 |

#### 4.1.8 오류 코드와 감사 기록

| 코드 | 상태 | 언제 |
|---|---|---|
| `LAST_ADMIN` | 409 | 해제로 쓸 수 있는 관리자가 남지 않게 될 때 |

### 4.2 2단계: 범용 OIDC 로그인 (진행 중)

- 백엔드가 OIDC 표준(authorization code + PKCE)으로 관리자 로그인을 받는다. 특정 회사 제품에 묶지 않는다.
- 로컬: `docker-compose.yml`에 Keycloak을 띄워 시험한다. AD/LDAP 연동도 Keycloak에서 흉내 낼 수 있다.
- 운영: 발급자(issuer) 주소·client id·secret 설정만 바꿔 Entra ID, Google Workspace 등에 연결한다.
- 관리자 권한은 IdP 그룹 클레임으로 정한다 (`wearly-admins` 등). 그룹 이름은 설정으로 바꿀 수 있게 한다.
- 로컬 비상 계정 하나는 계속 둔다 (1단계의 TOTP를 켠 계정, 4.1.4).
- IdP로 들어온 관리자도 감사 기록·세션([16](16_세션_Valkey.md)) 규칙을 그대로 따른다.

### 4.3 3단계: 접근 프록시나 VPN

운영 배포 때 관리자 사이트 주소를 접근 프록시나 VPN 뒤에 둔다. 어느 제품을 쓸지는 운영 환경(클라우드)과 회사 IdP가 정해진 뒤 고른다.

## 5. 회사 IdP를 정할 때 확인할 것

| 확인 | 이유 |
|---|---|
| 쓰는 협업 도구 | Microsoft 365면 Entra ID, Google Workspace면 Google 계정이 자연스럽다 |
| 사내 AD 유무와 동기화 방식 | Entra Connect, ADFS, Keycloak 중 무엇이 맞는지 정한다 |
| 그룹 이름 규칙 | `wearly-admins`처럼 앱 권한에 쓸 그룹을 만들 수 있는지 |
| MFA 정책 | IdP가 MFA를 강제하면 앱 자체 TOTP는 비상 계정에만 쓴다 |
| SCIM 지원 | 계정 생성·삭제를 자동 동기화할 수 있는지 |
| 비상 계정 보관 방법 | 비밀번호 금고, 사용 알림 담당자 |

## 6. 용어

| 용어 | 뜻 |
|---|---|
| IdP (Identity Provider) | 직원 계정을 갖고 로그인을 대신 확인해 주는 시스템. Entra ID, Google Workspace, Okta, Keycloak |
| SSO (Single Sign-On) | 한 번 로그인해 여러 사이트에 들어가는 방식 |
| OIDC (OpenID Connect) | OAuth 2.0 위에 만든 로그인 표준. JSON·JWT 기반이라 새 앱에 맞다 |
| SAML | XML 기반의 오래된 SSO 표준. 사내 시스템에 많다 |
| SCIM | IdP가 앱에 계정을 만들고 지우는 것을 자동으로 동기화하는 표준 |
| TOTP | 30초마다 바뀌는 6자리 숫자를 인증 앱으로 확인하는 2단계 인증 |
| break-glass | IdP 장애에 대비해 따로 보관하는 비상 로컬 관리자 계정 |
| 접근 프록시 | 회사 계정 인증을 통과한 사람에게만 내부 사이트를 열어 주는 중간 서버 (Cloudflare Access, Google IAP 등) |
