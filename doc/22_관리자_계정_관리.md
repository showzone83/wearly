# 22. 관리자 계정 관리: 지금 구현, 일반적인 방식, 단계별 계획

> 결정 문서 · 2026-10-18 · 대상: `backend/`(`admin` 컨텍스트), `admin/`
> 회사에는 아직 계정 시스템(IdP)이 없다. 나중에 회사 계정과 연동할 때 참고하도록 결정과 순서를 남긴다.
> **1단계(앱 DB 방식 보완)는 구현했다** (2026-10-18, `3b84994`, `dev`에 `f3fbfae`로 병합). 4.1장에 구현 상세가 있다. **2단계(범용 OIDC 로그인 + 로컬 Keycloak)도 구현했다** (2026-10-18, `302aaca`). 4.2장에 구현 상세가 있다. 3단계(접근 프록시·VPN)만 운영 배포 때 남았다.
> 관리자 역할·API는 [07](07_관리자_사이트.md), 세션은 [16](16_세션_Valkey.md).

## 1. 질문과 결론

질문: 이런 앱은 관리자 계정을 보통 어디서 관리하나?

| 항목 | 결론 |
|---|---|
| 흔한 방식 | 초기에는 앱 DB의 역할(role), 회사가 커지면 회사 IdP와 SSO, 운영에서는 네트워크 차단을 더한다 |
| 원칙 | 고객 계정과 직원(관리자) 계정은 다른 체계로 나눈다 |
| Wearly 지금 | 앱 DB 방식. 아래 2장의 구멍을 막았다 (1단계, 구현함 — 4.1장) |
| Wearly 다음 | 범용 OIDC 로그인(2단계, 구현함 — 4.2장). 로컬은 Keycloak으로 시험하고 운영은 설정만 바꿔 회사 IdP에 연결한다 |
| 운영 배포 때 | 관리자 사이트를 접근 프록시나 VPN 뒤에 둔다 (3단계) |

## 2. 보완 전 Wearly 구현과 문제점

> 이 장은 1단계 보완 **전**의 모습이다. 아래 문제 a~d는 모두 4.1장의 구현으로 막았다.

구현 (`AdminBootstrap` → `AdminAccountService.ensureAdmin`):

- 설정 `wearly.admin.email`·`password`·`name`이 있으면 서버 시작 때 실행한다. 설정 파일은 `backend/config/application-local.yml`(git 제외).
- 그 이메일 회원이 없으면 `ADMIN`으로 새로 만든다. 감사 기록 `ADMIN_BOOTSTRAP_CREATE`.
- 이미 있는 회원이면 `ADMIN`으로 올린다. 감사 기록 `ADMIN_BOOTSTRAP_PROMOTE`. 비밀번호는 첫 생성 때만 쓴다.
- 관리자 로그인은 일반 `/auth/login`이고, 사이트가 `user.role`이 `ADMIN`인지 본다.

문제점:

| | 문제 | 왜 문제인가 |
|---|---|---|
| a | 같은 이메일로 먼저 가입한 일반 회원이 자동으로 관리자가 된다 | 가입 API가 공개이고 이메일 인증이 없다. 공격자가 관리자 이메일로 먼저 가입해 두면 다음 시작 때 관리자가 된다 |
| b | 파일의 비밀번호를 바꿔도 반영되지 않고, 평문으로 남는다 | 첫 생성 때만 쓰므로 파일 값과 실제 비밀번호가 달라진다. 파일이 새면 위험하다 |
| c | 관리자를 늘리거나 해제하는 방법이 없다 | 설정 파일을 고치고 DB를 직접 만져야 한다 |
| d | 2단계 인증과 관리자 로그인 기록이 없다 | 비밀번호만 알면 들어온다. 누가 언제 들어왔는지 모른다 |

## 3. 일반적인 관리 방식 세 가지

| | 방식 | 어울리는 때 | 장점 | 단점 |
|---|---|---|---|---|
| ① | 앱 DB에 역할(role) | 초기 스타트업·소규모 | 간단하다. 추가 시스템이 없다 | 퇴사자 정리·비밀번호 정책·2FA를 직접 만들어야 한다. 고객과 같은 로그인 경로라 공격 대상이다 |
| ② | 회사 IdP와 SSO (OIDC/SAML) | 직원이 늘고 회사 계정이 있을 때 | 퇴사 때 회사 계정만 막으면 끝. 2FA·비밀번호 정책·로그인 기록을 IdP가 맡는다 | IdP가 있어야 한다. IdP 장애 때 로그인이 막힌다 |
| ③ | 관리자 사이트 네트워크 차단 | 운영 서버를 공개 인터넷에 둘 때 | 직원 기기가 아니면 로그인 화면도 안 보인다 | 혼자서는 계정 관리가 안 된다. ①·②와 함께 쓴다 |

### 3.1 ① 앱 DB에 역할

`tb_user.role`이 `ADMIN`이면 관리자다. 지금 방식이다. 직원 계정이 고객과 같은 표, 같은 로그인 API에 있으므로 비밀번호 대입 공격의 표적이 된다. 그래서 최소한 2FA와 로그인 기록을 넣는다.

### 3.2 ② 회사 IdP와 SSO

- 관리자 사이트는 "회사 계정으로 로그인" 버튼만 둔다. 비밀번호를 앱이 받지 않는다.
- 권한은 IdP 그룹으로 정한다. 예: `wearly-admins`(전체 권한), `wearly-viewers`(조회만).
- IdP 예: Microsoft Entra ID(예전 Azure AD), Google Workspace, Okta, Keycloak(직접 운영).
- 프로토콜은 OIDC가 새 앱에 맞다. 오래된 사내 시스템은 SAML을 쓴다.

AD와의 관계:

| 구성 | 설명 |
|---|---|
| 사내 AD + Entra Connect | 사내 AD 계정을 Entra ID로 동기화한다. 앱은 Entra ID와 OIDC로 붙는다 |
| 사내 AD + ADFS | AD가 직접 토큰을 발급한다. 앱은 OIDC나 SAML로 붙는다 |
| 사내 AD + Keycloak | Keycloak이 AD를 LDAP으로 읽는다(User Federation). 앱은 Keycloak과 OIDC로 붙는다 |

운영 규칙:

- 퇴사자는 AD 계정만 막으면 관리자 사이트에도 못 들어온다.
- SCIM을 지원하는 IdP면 계정 생성·삭제가 앱에 자동 동기화된다.
- IdP 장애에 대비해 로컬 비상 계정(break-glass) 하나를 유지한다. 비밀번호는 금고에 보관하고 쓸 때마다 알림을 남긴다.

### 3.3 ③ 네트워크 차단

관리자 사이트(와 `/api/v1/admin/**`)를 VPN이나 접근 프록시 뒤에 둔다. 인증된 직원 기기에서만 열린다.

- 접근 프록시: Cloudflare Access, Google IAP, Tailscale 등.
- 프록시가 회사 계정으로 먼저 인증하므로 ②와 잘 맞는다.
- 프록시가 뚫려도 앱 자체 로그인이 한 번 더 막는다 (이중 방어).

#### 4.1.1 시작할 때 관리자 만들기 (`AdminBootstrap` → `AdminAccountService.ensureAdmin`)

- 설정 `wearly.admin.email`·`password`가 둘 다 있고 **관리자(`ADMIN`)가 한 명도 없을 때만** 그 계정을 만든다 (이름 `wearly.admin.name`, 기본 "관리자"). 감사 기록 `ADMIN_BOOTSTRAP_CREATE`.
- 그 이메일로 이미 가입한 일반 회원이 있으면 **관리자로 올리지 않는다.** WARN 로그만 남긴다(이메일은 가려서). 예전의 `ADMIN_BOOTSTRAP_PROMOTE`는 없어졌다.
- 관리자가 이미 있으면 설정 값은 쓰지 않는다. 설정 비밀번호는 첫 생성에만 쓰므로, 만든 뒤에는 파일에서 지워도 된다 (비밀번호는 4.1.2로 바꾼다).
- 설정이 없으면 "관리자 계정 설정 없음" INFO 로그만 남기고 시작한다.
- 시작 로그로 확인한다: `docker compose logs backend | grep -E "관리자 2단계 인증|관리자 계정"` → "관리자 2단계 인증: 필수 (issuer=Wearly)", "관리자 계정: 관리자가 이미 1명 있어 설정 계정(wearly.admin.email)은 쓰지 않아요" (2026-10-18 실제 로그).

#### 4.1.2 비밀번호 변경 `POST /api/v1/admin/me/password`

- 요청 `{ currentPassword, newPassword }` → 204. 현재 비밀번호가 틀리면 403 `REAUTH_FAILED`, 새 비밀번호가 가입 규칙(8~64자, 영문과 숫자 포함, `PasswordPolicy`)에 맞지 않으면 400 `VALIDATION_FAILED`(`newPassword` `INVALID_FORMAT`).
- 바꾸면 **지금 세션을 뺀 이 관리자의 다른 세션을 모두 끊는다** (로그인 이력에는 `FORCED_LOGOUT`). 감사 기록 `ADMIN_PASSWORD_CHANGE`(`after.endedSessions`).
- 관리자 사이트: "내 계정" 화면(`/me`)의 비밀번호 바꾸기("다음에 바꿀 날" 표시). 기한이 지나면 모든 화면 위에 안내 띠(바꾸기·연장, 28 문서 4단계).
- 변경 주기([28](28_비밀번호_변경주기.md), 이슈 #21): 관리자에게도 앱 회원과 같은 주기(기본 90일)를 적용한다. 바꾸면 주기를 지금부터 다시 세고 로그인 이력에 `PASSWORD_CHANGED`가 남는다. `GET /api/v1/admin/me/password` → `{ changedAt, dueAt, due, intervalDays }`, `POST /api/v1/admin/me/password/postpone` → 지금부터 주기만큼 연장(감사 기록 `ADMIN_PASSWORD_POSTPONE`, before·after `dueAt`). 비밀번호가 없는 계정(SSO만)은 `due = false`이고 연장은 404.

#### 4.1.3 관리자 지정·해제 `PATCH /api/v1/admin/users/{id}` `{ role }`

- 사이트의 "회원" 화면에서 누른다. 감사 기록 `USER_ROLE_CHANGE`(역할이 바뀔 때, 그 밖의 정지·해제는 `USER_UPDATE`).
- 자기 자신의 역할은 못 바꾼다 (400 `role` `SELF_NOT_ALLOWED`).
- 정지(`SUSPENDED`)한 회원은 관리자로 지정할 수 없다 (400 `role` `CONFLICT`).
- 해제하면 쓸 수 있는 관리자(`ADMIN`·`ACTIVE`)가 한 명도 남지 않게 될 때 **409 `LAST_ADMIN`**.
- 해제하면 그 회원의 로그인 세션을 모두 끊는다.

#### 4.1.4 2단계 인증 (TOTP, RFC 6238)

**누가 대상인가.** 관리자 사이트에서 로그인하는 관리자(`X-Wearly-Client: admin`). 설정 `wearly.admin.mfa.required`(기본 `true`)가 켜져 있거나 이미 TOTP를 등록한 관리자는 코드를 확인해야 한다. `false`면 등록하지 않은 관리자는 예전처럼 비밀번호만으로 들어오고, 등록한 관리자는 그래도 코드를 확인한다 (로컬 개발·하네스).

**로그인 흐름** (`AuthService.login` → `MfaService`):

```
관리자 사이트 ── POST /auth/login {email, password} ──▶ 서버
   ◀── 200 { mfa: { required: true, enrolled }, mfaToken, mfaTokenExpiresIn: 300 }   (토큰 대신 대기 토큰)

[enrolled = false: 처음 등록]
   ── POST /auth/mfa/setup {mfaToken} ──▶ { secret, otpauthUrl }     (QR로 그리고 수동 입력 키도 보여 준다)
   인증 앱(Google Authenticator 등)에 등록
   ── POST /auth/mfa/verify {mfaToken, code} ──▶ 토큰 + recoveryCodes(10개, 이때 한 번만) + recoveryCodesLeft

[enrolled = true]
   ── POST /auth/mfa/verify {mfaToken, code | recoveryCode} ──▶ 토큰 + recoveryCodesLeft
```

- 비밀번호가 맞을 때만 대기 토큰을 준다. 대기 토큰은 5분, Valkey(`wearly:mfa:pending:{tokenHash}`)에 SHA-256 해시로만 두고, 관리자 API에는 쓸 수 없다. 응답에 `accessToken`이 없는 것이 일반 로그인과의 차이다 (`LoginResponse` = `AuthResponse` 또는 `MfaChallengeResponse`).
- 코드 확인에 성공해야 세션이 "2단계 인증을 거친 세션"으로 만들어진다. 거치지 않은 세션(앱 로그인 등)으로 `/admin/**`를 부르면 **403 `MFA_REQUIRED`** (앱 API는 그대로 쓴다).
- TOTP: 6자리, 30초, SHA-1, 앞뒤 1단계 허용. **같은 30초 단계의 코드는 한 번만** 받는다 (`last_used_step`).
- 복구 코드: 10개, `abcde-fghjk` 모양(헷갈리는 0·1·l·o 제외). 등록할 때 한 번만 보여 주고 DB에는 `SHA-256("{user_id}:{정규화한 코드}")` hex만 둔다. 한 번 쓰면 다시 못 쓴다.
- **틀림·잠금**: 코드를 5번 틀리면 15분 잠근다 (`MFA_LOCKED`, `params.retryAfterSeconds`). 횟수는 회원별로 Valkey에 두므로 다시 로그인해도 이어지고, 마지막 실패에서 15분이 지나면 잊는다. 잠기면 대기 토큰도 지운다. 틀릴 때마다 `MFA_CODE_INVALID`(`params.remainingAttempts`).
- 등록 중인 비밀은 마스터 키(`wearly.secret-key`)로 암호화해 Valkey(`wearly:mfa:setup:{userId}`)에 10분 둔다. 마스터 키가 없으면 등록을 시작할 수 없다 (409 `SECRET_KEY_MISSING`) — 켜려면(`required: true`) 마스터 키가 꼭 있어야 한다.

**내 계정에서** (`/api/v1/admin/me/mfa`, 로그인한 관리자):

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/admin/me/mfa` | `{ enrolled, enrolledAt, recoveryCodesLeft, required }` |
| POST | `/admin/me/mfa/setup` | 등록 시작 `{ secret, otpauthUrl }` (이미 등록했으면 409 `MFA_ALREADY_ENROLLED`) |
| POST | `/admin/me/mfa/enable` | `{ code }` → `{ recoveryCodes }` (등록 마침, 이 세션을 "거친 세션"으로) |
| POST | `/admin/me/mfa/reset` | `{ currentPassword, code \| recoveryCode }` → 204. 내 TOTP·복구 코드를 지우고 다른 세션을 끊는다. 이어서 setup → enable로 다시 등록 (등록 안 했으면 409 `MFA_NOT_ENROLLED`) |
| DELETE | `/admin/users/{id}/mfa` | **다른 관리자**의 2단계 인증 초기화 → 204. 그 회원의 세션을 모두 끊는다. 자기 자신은 400 (`id` `SELF_NOT_ALLOWED`, 내 것은 위 `reset`) |

**저장** (Flyway `V15__admin_mfa.sql`): `tb_user_mfa`(비밀 암호문 `secret_cipher`·`secret_nonce` 12바이트·`key_version`·`last_used_step`·`enrolled_at`), `tb_user_mfa_recovery_code`(`code_hash`·`used_at`). 비밀은 AI 키와 같은 AES-256-GCM이고 AAD가 `mfa:{user_id}`라 다른 회원 행에 붙여 넣으면 복호화되지 않는다. 마스터 키를 바꾸거나 잃으면 복구 코드로 들어와 다시 등록한다.

**설정**:

| yml | 환경변수 | 기본값 | 뜻 |
|---|---|---|---|
| `wearly.admin.mfa.required` | `WEARLY_ADMIN_MFA_REQUIRED` | `true` | 모든 관리자에게 2단계 인증을 강제. 로컬 개발이 번거로우면 `false` |
| `wearly.admin.mfa.issuer` | `WEARLY_ADMIN_MFA_ISSUER` | `Wearly` | 인증 앱에 보이는 발급자 이름 |
| `wearly.secret-key` | `WEARLY_SECRET_KEY` | (없음) | TOTP 비밀 암호화 마스터 키 (base64 32바이트). `required: true`면 꼭 필요 |

#### 4.1.5 관리자 로그인 기록 `GET /api/v1/admin/auth-events`

- 쿼리 `userId`·`type`·`from`·`to`·`page`·`size`. 항목 `{ id, userId, email, name, role, type, sessionId, client, ip, userAgent, createdAt }`, 최신순 전체 목록.
- `type`: 기존 `LOGIN`·`LOGOUT`·`REFRESH_REUSED`·`FORCED_LOGOUT`에 `LOGIN_FAILED`(가입한 이메일로 비밀번호가 틀림, 없는 이메일은 남기지 않는다)·`MFA_SUCCESS`·`MFA_FAILED`·`MFA_LOCKED`를 더했다 (`V16__auth_event_mfa.sql`, `tb_auth_event`의 CHECK와 최신순 인덱스 `ix_auth_event_created`).
- 관리자 사이트 메뉴 "관리자 로그인 기록" (`/auth-events`).

### 4.2 2단계: 범용 OIDC 로그인 (구현함, 2026-10-18)

관리자 사이트에 "회사 계정으로 로그인" 버튼을 더했다. 특정 회사 제품에 묶지 않고 OIDC 표준(Authorization Code + PKCE)만 쓴다. 로컬은 Keycloak으로 시험하고, 운영은 `wearly.sso.providers.<id>` 설정(발급자 주소·client id·secret·관리자 그룹)만 바꿔 Entra ID, Google Workspace 등에 연결한다. 기본은 **꺼짐**(`wearly.sso.enabled: false`)이고, 켜도 1단계의 이메일·비밀번호 + TOTP 로그인은 비상 계정(break-glass)으로 그대로 남는다.

#### 4.2.1 로그인 흐름

서버가 주도하는 Authorization Code + PKCE(S256)다. 토큰은 브라우저 주소(URL)에 싣지 않는다 — 주소에는 한 번만 쓰는 교환 코드만 실린다.

```
관리자 사이트 ── (브라우저 이동) GET /auth/sso/{p}/start?redirect=<사이트 /sso/callback> ──▶ 백엔드
   백엔드: state·nonce·PKCE verifier를 만들어 Valkey에 5분 저장, 쿠키 wearly_sso_state(= state) 심기
   ◀── 302 ── IdP authorize (response_type=code, state, nonce, code_challenge S256)

IdP: 회사 계정으로 로그인(MFA는 IdP가 맡는다)
   ── 302 ──▶ GET /auth/sso/{p}/callback?code&state[&iss]   (IdP에 등록한 백엔드 콜백)
   백엔드: 콜백 확인(4.2.2) → 계정 연결·관리자 그룹 확인(4.2.3) → 교환 코드 발급(Valkey 1분, 1회)
   ◀── 302 ── 관리자 사이트 /sso/callback?code=<교환 코드>      (실패면 ?error=<코드>&status=…&traceId=…)

관리자 사이트(SsoCallbackPage) ── POST /auth/sso/exchange {code} ──▶ 백엔드 (교환 코드는 1회용)
   ◀── 200 /auth/login과 같은 모양 (토큰, 또는 trust-idp-mfa=false일 때 MFA 대기 토큰)
```

**API** (`SsoController`, `/api/v1/auth/sso`, 모두 로그인 없이 부른다):

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/providers` | 켜진 공급자 `{ enabled, providers: [{ id, displayName }] }`. 꺼져 있으면 `{ enabled: false, providers: [] }`. 로그인 화면 버튼 |
| GET | `/{p}/start?redirect=` | IdP 로그인으로 302. `redirect`는 그 공급자 `redirect-allowlist`에 정확히 있는 관리자 사이트 주소여야 한다(없으면 400 `VALIDATION_FAILED` `redirect` `NOT_ALLOWED`) |
| GET | `/{p}/callback` | IdP가 돌려보내는 주소(`code`·`state`·`error`·`iss`). 늘 302. 성공은 `redirect`에 `?code=`, 실패는 `?error=<오류 코드>&status=<HTTP 상태>[&reason=…]&traceId=…`를 붙인다(브라우저 이동 중이라 JSON을 줄 수 없다). state 쿠키는 지운다 |
| POST | `/exchange` | `{ code }` → 200 `/auth/login`과 같은 모양(`AuthResponse` 또는 `MfaChallenge`). 코드가 없거나 만료(1분)·사용됨이면 401 `SSO_EXCHANGE_INVALID` |
| GET | `/{p}/logout?redirect=` | IdP의 `end_session_endpoint`로 302(`client_id`·`post_logout_redirect_uri`). 그런 주소가 없는 IdP(Google)나 IdP에 닿지 못하면 `redirect`로 바로 |

- SSO가 꺼져 있거나 없는 공급자 ID면 `start`·`callback`·`exchange`·`logout`은 404 `NOT_FOUND`다. `providers`만 200으로 빈 목록을 준다.
- 모든 응답은 `Cache-Control: no-store`. 응답의 `state` 쿠키는 `wearly_sso_state`, HttpOnly, SameSite=Lax, 경로 `/api/v1/auth/sso/`, 5분(HTTPS 요청이면 Secure).
- SSO로 만든 세션은 요청 헤더와 상관없이 늘 관리자 사이트 기기(`client = admin`)로 기록한다.

#### 4.2.2 콜백 확인 순서 (`SsoService.callback`, 하나라도 어긋나면 거부)

1. **state** 를 Valkey에서 꺼낸다(`GETDEL`, 한 번만). 없거나 만료·사용됨이면 `SSO_STATE_INVALID`. 돌아갈 주소를 모르면 그 공급자 `redirect-allowlist`의 첫 주소로 보낸다.
2. **state 쿠키**가 콜백의 state와 같은지(시간 차이 없는 비교). 다르면 다른 브라우저에서 시작한 로그인(로그인 CSRF)이거나 쿠키가 막힌 것이라 `SSO_STATE_INVALID`.
3. IdP가 `error`를 돌려보냈으면 `SSO_IDP_ERROR`(`reason` = OAuth error 값, 형식이 다르면 `other`).
4. 인가 응답에 `iss`가 있으면 설정의 `issuer-uri`와 같아야 한다(RFC 9207, 다른 IdP 응답이 섞이는 mix-up 방지). 인가 코드가 없으면 `SSO_TOKEN_INVALID`.
5. **토큰 교환**(`POST token_endpoint`, `client_secret`·`code_verifier`). 거절되면 `SSO_TOKEN_INVALID`, IdP에 닿지 못하면 `SSO_PROVIDER_UNAVAILABLE`.
6. **ID 토큰 확인**(`IdTokenVerifier`, Nimbus): 서명은 IdP JWKS의 비대칭 키로만(RS256/384/512·PS256/384/512·ES256/384/512, `none`·HS 계열은 거부), `iss`는 설정과 글자 그대로 같음(끝 `/`도 그대로), `aud`에 client_id가 있고 여럿이면 `azp`도 client_id, `exp`·`iat`(시계 오차 60초), `nonce`는 시작 때 만든 값, `sub` 있음. 어긋나면 `SSO_TOKEN_INVALID`.
7. 계정 처리(4.2.3). 성공하면 교환 코드(Valkey `SHA-256` 해시 키, 1분, 1회)를 만든다.

Valkey 키는 `ValkeyKeys`(`ValkeySsoStoreAdapter`)가 정한다. state·교환 코드 모두 원문이 아니라 해시로만 둔다.

#### 4.2.3 계정 연결과 권한 (`SsoAccountService`)

IdP 계정은 **발급자(`iss`) + `sub`**로 찾는다(`tb_user_sso`, `V22__admin_sso.sql`, `(issuer, subject)` 유니크, 회원 삭제 시 함께 삭제).

| 상황 | 처리 |
|---|---|
| 이미 연결됨 + 관리자 그룹 | 그 회원으로 로그인. `last_login_at`·이메일을 갱신. 일반 회원(`USER`)이던 연결 계정이면 `ADMIN`으로 올리고 `USER_ROLE_CHANGE` 기록 |
| 처음 로그인, 이메일이 검증되지 않음 | 403 `SSO_EMAIL_UNVERIFIED` (이메일이 없거나 `email_verified`가 true가 아님. `assume-email-verified`를 켜면 `email_verified` 클레임이 **아예 없을 때만** 믿는다) |
| 처음 로그인, 같은 이메일의 **관리자**가 있음 | 그 회원과 연결(`SSO_ACCOUNT_LINK`) |
| 처음 로그인, 같은 이메일의 **일반 회원(고객)**만 있음 | **승격하지 않는다.** 비밀번호 없는 관리자 회원을 새로 만든다(`SSO_ACCOUNT_CREATE`). 고객 계정과 직원 계정을 나누고, 고객 비밀번호가 관리자 로그인 경로가 되지 않게 하며, 2장 a(자동 승격)와 같은 문제를 막기 위해서다. 같은 이메일 행이 `tb_user`에 둘 생길 수 있다(이메일 유일 제약은 로컬 비밀번호 표 `tb_user_local_credential`에만 있고, SSO 관리자는 거기에 행이 없다) |
| 처음 로그인, 그 이메일 회원이 없음 | 비밀번호 없는 관리자 회원을 새로 만든다(`SSO_ACCOUNT_CREATE`). 이름은 IdP의 이름 클레임 |
| 정지(`SUSPENDED`)한 회원 | 403 `ACCOUNT_SUSPENDED` |

**관리자 그룹 확인.** 로그인마다 `roles-claim`(기본 `groups`, 점으로 중첩 경로 가능 예: `realm_access.roles`)에 `admin-groups` 중 하나가 있거나(대소문자 구분), 검증된 이메일이 `admin-emails`에 있으면(대소문자 무시) 관리자다. 아니면 **403 `SSO_NOT_ADMIN`**. 이때 이미 연결된 회원이면:

- 로그인 기록 `SSO_DENIED`를 남긴다.
- 그 회원이 관리자(`ADMIN`)면 `USER`로 내리고 로그인 세션을 모두 끊는다(`USER_ROLE_CHANGE`, 시스템이 한 일). 단 쓸 수 있는 관리자가 그 사람뿐이면(마지막 관리자) 역할은 그대로 두고 WARN만 남긴다.

**세션.** 교환 코드를 받으면 정지·역할 해제 여부를 한 번 더 확인하고 세션을 만든다. `trust-idp-mfa: true`(기본)면 IdP가 MFA를 맡은 것으로 보고 이 세션을 "2단계 인증을 거친 세션"으로 표시해 앱 TOTP 없이 `/admin/**`를 쓴다. `false`면 비밀번호 로그인처럼 그 관리자에게 앱 2단계 인증이 필요한 경우 `MfaChallenge`(대기 토큰)를 주고 4.1.4의 `/auth/mfa/*`로 이어진다. Refresh 토큰·세션·강제 로그아웃은 [16](16_세션_Valkey.md) 규칙 그대로다.

**기록.**

| 어디 | 값 |
|---|---|
| 로그인 기록 `tb_auth_event.type` (`V22`가 CHECK에 추가) | `SSO_LOGIN`(새 세션), `SSO_DENIED`(이미 연결된 회원이 관리자 그룹이 아니라 거부). 컬럼 `sso_provider`(공급자 ID)·`sso_amr`(IdP가 알려 준 인증 방법, 예: `pwd,otp`)를 더했다. `trust-idp-mfa: false`면 앱 TOTP를 거친 뒤 기록이 `SSO_LOGIN`이 아니라 `LOGIN`·`MFA_SUCCESS`로 남는다(한계 표) |
| 변경 이력 `tb_admin_audit_log` | `SSO_ACCOUNT_CREATE`·`SSO_ACCOUNT_LINK`·`USER_ROLE_CHANGE`(`after.source = SSO`, `admin_user_id` 없음 = 시스템). 관리자 사이트는 관리자 칸에 "시스템 (회사 계정)"으로 보인다 |

#### 4.2.4 설정 `wearly.sso.*` (`SsoProperties`)

| yml | 환경변수 | 기본값 | 뜻 |
|---|---|---|---|
| `wearly.sso.enabled` | `WEARLY_SSO_ENABLED` | `false` | SSO 전체 켜기 |
| `wearly.sso.trust-idp-mfa` | `WEARLY_SSO_TRUST_IDP_MFA` | `true` | IdP가 MFA를 맡는다고 보고 앱 TOTP를 묻지 않는다. `false`면 앱 TOTP도 거친다 |
| `wearly.sso.http-timeout` | `WEARLY_SSO_HTTP_TIMEOUT` | `PT10S` | IdP(discovery·token·JWKS) 호출 제한 시간 |
| `wearly.sso.backchannel-rewrites` | — | 없음 | 서버끼리 부르는 IdP 주소 바꾸기 `[{ from, to }]` (docker 프로필: `http://localhost:8180` → `http://keycloak:8080`) |
| `wearly.sso.providers.<id>.*` | 아래 | — | 공급자. `<id>`는 영문 소문자·숫자·하이픈 1~50자(경로 `/auth/sso/<id>/…`에 쓰인다) |

공급자 키(`application-local.yml`에 적는다 — `application-local.example.yml`의 `sso:` 주석 블록이 견본):

| 키 | 필수 | 뜻 |
|---|---|---|
| `display-name` | | 로그인 화면 버튼 이름 (기본 `<id>`). 버튼은 "<display-name> 로그인" |
| `issuer-uri` | O | 발급자(`iss`). ID 토큰의 `iss`와 discovery 문서의 `issuer`가 이 값과 글자 그대로 같아야 한다 |
| `discovery-uri` | | 기본 `issuer-uri` + `/.well-known/openid-configuration` |
| `client-id`, `client-secret` | O | IdP에 등록한 클라이언트 (비밀은 로그에 안 나온다) |
| `scopes` | | 기본 `openid profile email` (`openid`는 늘 넣는다) |
| `roles-claim` | | 그룹·역할 클레임 이름, 기본 `groups` |
| `admin-groups` | 둘 중 하나 | 이 중 하나가 클레임에 있으면 관리자 |
| `admin-emails` | 둘 중 하나 | 그룹 클레임이 없는 IdP용: 검증된 이메일이 이 목록에 있으면 관리자 |
| `redirect-allowlist` | O | 로그인 뒤(`…/sso/callback`)·로그아웃 뒤(`…/login`) 돌아갈 관리자 사이트 주소. 정확히 같은 주소만(열린 리디렉트 방지, 쿼리·`#` 있는 주소는 무시) |
| `callback-uri` | | IdP에 등록한 백엔드 콜백 주소. 비우면 요청 주소로 만든다. 프록시 뒤라 요청 주소가 실제 주소와 다르면 꼭 적는다 |
| `assume-email-verified` | | `email_verified` 클레임을 주지 않는 IdP(Entra ID)의 이메일을 검증된 것으로 볼지 (기본 `false`) |
| `enabled` | | `false`면 이 공급자만 끈다 |

- **환경변수는 Spring 규칙**을 따른다: 점은 `_`, 하이픈은 뺀다. 그래서 `client-secret`은 `WEARLY_SSO_PROVIDERS_KEYCLOAK_CLIENTSECRET`이다(`_CLIENT_SECRET`은 묶이지 않는다).
- **설정이 모자란 공급자는 서버를 멈추지 않고 빼며** ERROR 로그를 남긴다(`관리자 SSO: 공급자 … 설정이 모자라 뺍니다: …`). SSO는 선택 기능이고 비상 계정 로그인은 유지돼야 하기 때문이다. 켜졌는데 쓸 수 있는 공급자가 없으면 WARN.
- 시작 로그로 확인한다: `docker compose logs backend | grep "관리자 SSO"` → "관리자 SSO: 꺼짐" 또는 "관리자 SSO 공급자 keycloak: issuer=… admin-groups=[wearly-admins]" · "관리자 SSO: 켜짐, 공급자 1개, IdP MFA 믿기=true".

#### 4.2.5 로컬 Keycloak으로 시험하기

`docker-compose.yml`의 `keycloak` 서비스(`quay.io/keycloak/keycloak:26.8.1`, **profile `sso`**라 평소 `docker compose up`에는 뜨지 않는다). 계정·비밀번호는 모두 **로컬 전용 시험 값**이다.

| 항목 | 값 |
|---|---|
| 실행 | `docker compose --profile sso up -d keycloak` (dev 모드, DB 없이 컨테이너 안 H2, 시작 때 `infra/keycloak/wearly-realm.json`을 들여옴) |
| 주소 | `http://localhost:8180` (호스트 8180 → 컨테이너 8080), 관리 콘솔 `admin` / `wearly-keycloak-local` |
| realm / client | `wearly` / `wearly-admin` (secret `wearly-admin-local-secret`, PKCE S256, redirect URI `http://localhost:8080/api/v1/auth/sso/keycloak/callback` 외 하네스용 18080·18081, 로그아웃 뒤 `http://localhost:5173/login`) |
| 그룹 | `wearly-admins`(관리자), `wearly-viewers`(조회만 = 지금은 거부). 토큰 `groups` 클레임(`oidc-group-membership-mapper`, 경로 없이 이름만) |
| 시험 계정 | `admin@wearly.local` / `WearlyAdmin1!` (wearly-admins, 로그인 성공), `viewer@wearly.local` / `WearlyViewer1!` (wearly-viewers, 403 `SSO_NOT_ADMIN`) |

켜는 법:

1. `backend/config/application-local.yml`에 `application-local.example.yml`의 `sso:` ① 블록 주석을 풀어 넣는다(`enabled: true`, `providers.keycloak` 아래 `display-name: "회사 계정 (Keycloak)"`, `issuer-uri: http://localhost:8180/realms/wearly`, `client-id: wearly-admin`, `client-secret`, `admin-groups: [wearly-admins]`, `redirect-allowlist`에 `http://localhost:5173/sso/callback`·`http://localhost:5173/login`).
2. `docker compose up -d --build backend`로 백엔드를 다시 빌드·시작한다.
3. `http://localhost:5173` 로그인 화면에 **"회사 계정 (Keycloak) 로그인"** 버튼이 생긴다. 누르면 Keycloak 로그인 → 관리자 화면. 아래쪽에 "또는 비상 관리자 계정"과 이메일·비밀번호 입력이 남는다.

**issuer 불일치 해결.** 브라우저는 Keycloak을 `localhost:8180`으로 보지만 컨테이너 안의 백엔드는 닿지 못한다(`localhost`는 자기 자신). 그래서 (a) Keycloak에 `KC_HOSTNAME=http://localhost:8180`, `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`로 토큰 `iss`를 늘 `http://localhost:8180/realms/wearly`로 고정하고, (b) `application-docker.yml`의 `wearly.sso.backchannel-rewrites`가 서버끼리 부르는 주소(discovery·token·JWKS)만 `http://keycloak:8080`으로 바꾼다. 설정의 `issuer-uri`는 `localhost:8180` 그대로라 `iss` 글자 비교가 맞는다. 백엔드를 Mac에서 직접 돌릴 때(`bootRun`)는 `localhost:8180`에 바로 닿으므로 rewrite가 필요 없다.

**끄기·초기화.**

```bash
docker compose --profile sso stop keycloak      # 멈춤 (realm 변경은 컨테이너 안에 남음)
docker compose --profile sso rm -sf keycloak    # 지움. 다음 up에서 realm.json으로 처음 상태가 된다
```

`docker compose down`이 profile 서비스(keycloak)도 내리는지는 compose 버전마다 다르다 — 확실히 끄려면 위 명령을 쓴다. backend는 keycloak을 기다리지 않는다(SSO는 선택 기능이라 Keycloak이 없어도 백엔드는 뜨고, 그 공급자의 시작은 관리자 사이트 `/sso/callback?error=SSO_PROVIDER_UNAVAILABLE&status=502`로 돌아온다).

#### 4.2.6 Entra ID · Google Workspace로 바꾸기

같은 코드에 설정만 바꾼다(`application-local.example.yml`의 ②·③ 견본). IdP에 등록하는 redirect URI는 **백엔드 콜백** `https://<백엔드 주소>/api/v1/auth/sso/<공급자 ID>/callback`이다.

| | Microsoft Entra ID | Google Workspace |
|---|---|---|
| `issuer-uri` | `https://login.microsoftonline.com/<테넌트 ID>/v2.0` (**단일 테넌트만**. 여러 테넌트 공용 `common` 발급자는 `iss`가 사용자마다 달라 글자 비교가 맞지 않아 지원하지 않는다) | `https://accounts.google.com` |
| 클라이언트 만들기 | 앱 등록 → 인증: 웹 redirect URI = 백엔드 콜백, 인증서 및 비밀 → 클라이언트 비밀 | Google Cloud 콘솔 → OAuth 클라이언트(웹 애플리케이션), 승인된 리디렉션 URI = 백엔드 콜백 |
| 관리자 정하기 | **앱 역할**(App roles, 예: `Wearly.Admin`)을 만들어 사용자·그룹에 할당하고 `roles-claim: roles`, `admin-groups: [Wearly.Admin]`을 권한다. `groups` 클레임은 이름이 아니라 그룹 개체 ID(GUID)로 오므로 쓰려면 `admin-groups`에 GUID를 적는다 | ID 토큰에 그룹 클레임이 없다 → `admin-emails: [admin@yourcompany.com]`(검증된 이메일 목록) |
| 이메일 | `email_verified`를 주지 않는다 → 같은 이메일의 기존 관리자와 처음 연결하려면 `assume-email-verified: true`(회사 테넌트가 이메일을 관리할 때만). 이메일을 받으려면 토큰 구성에서 `email` 선택적 클레임을 더한다 | `email_verified`를 준다 |
| 로그아웃 | `end_session_endpoint` 지원 | `end_session_endpoint`가 없어 **이 사이트에서만** 로그아웃된다(Google 계정은 그대로) |

#### 4.2.7 관리자 사이트 (`admin/`)

- 로그인 화면 `LoginPage`의 `SsoButtons`: `GET /auth/sso/providers`로 켜진 공급자마다 버튼을 그린다. 꺼져 있거나 서버에 닿지 못하면(옛 서버 404 포함) 아무것도 안 보인다. 누르면 `useAuthStore.startSso` → `window.location`을 `…/auth/sso/{id}/start?redirect=<origin>/sso/callback`으로 옮긴다(공급자 ID는 `sessionStorage`에 적어 둔다).
- `/sso/callback`(`SsoCallbackPage`): `?code`가 있으면 `POST /auth/sso/exchange`(같은 코드는 한 번만 보낸다 — 개발 모드 effect 두 번 실행 대비) 후 화면으로 들어간다. `?error=`가 있으면 `ApiError`로 만들어 `/login`에 오류 문구(오류 번호 포함)를 보인다. `trust-idp-mfa: false`라 MFA 대기가 오면 로그인 2단계 화면으로 이어진다.
- 로그아웃하면 SSO로 들어온 세션은 `…/auth/sso/{id}/logout?redirect=<origin>/login`으로 IdP 로그아웃까지 한다.
- "내 계정"은 로그인 방식("회사 계정 (keycloak)" / "이메일·비밀번호")을 보이고, SSO로 들어왔으면 비밀번호·2단계 인증은 IdP에서 바꾼다는 안내를 보인다. 관리자 로그인 기록은 `SSO_LOGIN`(회사 계정 로그인)·`SSO_DENIED`(회사 계정 거부) 배지와 공급자·`amr`를 보인다. 변경 이력은 `SSO_ACCOUNT_CREATE`(회사 계정으로 관리자 생성)·`SSO_ACCOUNT_LINK`(회사 계정 연결)을 보인다.

#### 4.2.8 오류 코드

새 오류 코드 7개 (`error-codes.json`, 전체 44 → 51개, [20](20_오류_응답.md) 13장):

| 코드 | 상태 | 언제 |
|---|---|---|
| `SSO_NOT_ADMIN` | 403 | IdP 인증은 됐지만 관리자 그룹·관리자 이메일이 아님 |
| `SSO_EMAIL_UNVERIFIED` | 403 | 처음 로그인인데 이메일이 없거나 검증되지 않음 |
| `SSO_STATE_INVALID` | 400 | 콜백의 state가 없거나 만료(5분)·사용됨, 또는 state 쿠키가 다름 |
| `SSO_TOKEN_INVALID` | 401 | 토큰 교환 거절, ID 토큰의 서명·iss·aud·exp·nonce 불일치, 인가 코드 없음, 인가 응답 `iss` 불일치 |
| `SSO_IDP_ERROR` | 400 | IdP가 오류로 돌려보냄 (`params.reason`) |
| `SSO_PROVIDER_UNAVAILABLE` | 502 | IdP(discovery·token·JWKS)에 닿지 못했거나 discovery의 issuer가 설정과 다름 |
| `SSO_EXCHANGE_INVALID` | 401 | 교환 코드가 없거나 만료(1분)·사용됨 |

콜백의 오류는 JSON이 아니라 관리자 사이트 주소의 `?error=`로 오고, 교환·시작·로그아웃의 오류(404·400·401)는 보통 JSON 오류 응답이다.

#### 4.2.10 알려진 한계

| 한계 | 설명·대처 |
|---|---|
| 그룹에서 빠진 사람은 **다음 SSO 로그인 때만** 관리자에서 내려간다 | 이미 열린 세션은 Refresh 토큰이 살아 있는 동안 남는다. 퇴사자는 관리자 화면의 해제·세션 끊기로 바로 정리하거나 SCIM(IdP가 앱에 자동 동기화)이 필요하다 |
| `trust-idp-mfa: false`면 로그인 기록이 `LOGIN`·`MFA_SUCCESS` | 비밀번호 로그인처럼 MFA 대기 → 앱 TOTP를 거치므로 `SSO_LOGIN`·`ssoProvider`가 남지 않는다 |
| SSO로 만든 관리자는 이 사이트의 비밀번호가 없다 | 비밀번호 변경·앱 2단계 인증은 쓸 수 없다. 비상 로그인이 필요하면 따로 만든 비상 관리자(1단계 계정)를 쓴다 |
| 같은 브라우저에서 두 탭이 동시에 시작하면 앞 탭은 `SSO_STATE_INVALID` | state 쿠키가 하나(마지막 시작)라서. 다시 시도한다 |
| 프록시·로드밸런서 뒤에서는 `callback-uri`가 필요하다 | 요청 주소로 만든 콜백이 IdP에 등록한 주소와 달라 IdP가 거절한다 |
| `docker compose down`이 profile 서비스를 내리는지는 버전마다 다르다 | 4.2.5의 `stop`·`rm`을 쓴다 |
| 한 이메일의 `tb_user` 행이 둘일 수 있다 | 고객 계정(비밀번호)과 SSO 직원 계정(비밀번호 없음)은 의도적으로 따로다 |

### 4.3 3단계: 접근 프록시나 VPN

운영 배포 때 관리자 사이트 주소를 접근 프록시나 VPN 뒤에 둔다. 어느 제품을 쓸지는 운영 환경(클라우드)과 회사 IdP가 정해진 뒤 고른다.

## 5. 회사 IdP를 정할 때 확인할 것

| 확인 | 이유 |
|---|---|
| 쓰는 협업 도구 | Microsoft 365면 Entra ID, Google Workspace면 Google 계정이 자연스럽다 |
| 사내 AD 유무와 동기화 방식 | Entra Connect, ADFS, Keycloak 중 무엇이 맞는지 정한다 |
| 그룹 이름 규칙 | `wearly-admins`처럼 앱 권한에 쓸 그룹을 만들 수 있는지 |
| MFA 정책 | IdP가 MFA를 강제하면 앱 자체 TOTP는 비상 계정에만 쓴다 |
| SCIM 지원 | 계정 생성·삭제를 자동 동기화할 수 있는지 |
| 비상 계정 보관 방법 | 비밀번호 금고, 사용 알림 담당자 |

### 5.1 실제 회사 IdP를 연결할 때 할 일 (코드는 바꾸지 않는다)

| 순서 | 할 일 |
|---|---|
| 1 | IdP에 클라이언트(앱 등록)를 만든다. 종류는 웹 애플리케이션(비밀이 있는 기밀 클라이언트), 흐름은 Authorization Code. redirect URI는 **백엔드 콜백** `https://<백엔드 주소>/api/v1/auth/sso/<공급자 ID>/callback` |
| 2 | 관리자 권한 그룹(또는 Entra 앱 역할)을 만들고 관리자 사람들을 넣는다. ID 토큰에 그 그룹이 실리는지 확인한다(`roles-claim`). 그룹 클레임이 없는 IdP(Google)는 `admin-emails` |
| 3 | `application-local.yml`(운영은 환경변수·비밀 저장소)에 `wearly.sso.enabled: true`와 공급자를 적는다(4.2.4). `issuer-uri`는 IdP의 discovery 문서 `issuer`와 **글자 그대로** 같게. `client-secret`은 환경변수 `WEARLY_SSO_PROVIDERS_<ID>_CLIENTSECRET`로 |
| 4 | `redirect-allowlist`에 관리자 사이트의 `/sso/callback`과 `/login` 주소를 정확히 적는다. 프록시·로드밸런서 뒤라 요청 주소가 실제 주소와 다르면 `callback-uri` |
| 5 | 백엔드를 다시 시작하고 `grep "관리자 SSO"` 로그로 공급자가 올라왔는지, ERROR(설정 모자람)가 없는지 본다. `GET /api/v1/auth/sso/providers`가 공급자를 돌려주는지 본다 |
| 6 | 관리자 그룹 사람 1명으로 로그인해 보고, 그룹 밖 사람은 `SSO_NOT_ADMIN`이 나오는지 확인한다. 로그인 기록 `SSO_LOGIN`·`SSO_DENIED`와 변경 이력 `SSO_ACCOUNT_CREATE`·`SSO_ACCOUNT_LINK`를 본다 |
| 7 | IdP에서 MFA를 강제하고, `trust-idp-mfa: true`(기본)를 유지할지 정한다. IdP MFA를 못 믿으면 `false` |
| 8 | 비상 계정(1단계의 TOTP 켠 관리자)이 SSO 장애 때 들어올 수 있는지 한 번 시험하고, 비밀번호는 금고에 둔다 |
| 9 | 퇴사자 정리 절차를 정한다: 그룹에서 빼는 것만으로는 이미 열린 세션이 남는다(4.2.10). 관리자 화면에서 해제·세션 끊기를 같이 하거나 SCIM을 쓴다 |
| 10 | 운영 배포 때 3단계(접근 프록시·VPN) |

## 6. 용어

| 용어 | 뜻 |
|---|---|
| IdP (Identity Provider) | 직원 계정을 갖고 로그인을 대신 확인해 주는 시스템. Entra ID, Google Workspace, Okta, Keycloak |
| SSO (Single Sign-On) | 한 번 로그인해 여러 사이트에 들어가는 방식 |
| OIDC (OpenID Connect) | OAuth 2.0 위에 만든 로그인 표준. JSON·JWT 기반이라 새 앱에 맞다 |
| SAML | XML 기반의 오래된 SSO 표준. 사내 시스템에 많다 |
| SCIM | IdP가 앱에 계정을 만들고 지우는 것을 자동으로 동기화하는 표준 |
| TOTP | 30초마다 바뀌는 6자리 숫자를 인증 앱으로 확인하는 2단계 인증 |
| break-glass | IdP 장애에 대비해 따로 보관하는 비상 로컬 관리자 계정 |
| 접근 프록시 | 회사 계정 인증을 통과한 사람에게만 내부 사이트를 열어 주는 중간 서버 (Cloudflare Access, Google IAP 등) |
