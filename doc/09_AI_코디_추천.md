# 09. AI 코디 추천

> 백엔드(`backend/`)와 앱(`mobile/`)이 함께 따르는 계약이다. 2026-10-17 결정.

## 1. 배경

"AI 코디" 탭은 지금까지 앱 안의 규칙 엔진(`mobile/src/lib/recommend.ts`)이 조합을 만들고 점수를 매겼다. 이름과 달리 AI를 부르지 않았다. 이제 **AI가 점수 기준에 맞춰 내 옷장에서 코디 후보를 고르고, 앱의 규칙 엔진이 같은 5개 기준으로 점수를 매겨** 순서대로 보여 준다.

| 단계 | 누가 | 내용 |
|---|---|---|
| 후보 고르기 | 서버 → AI 공급자 | 옷장·상황·날씨·취향·최근 착용을 주고, 점수 기준(아래 2장)에 맞는 코디 후보 5개와 이유를 받는다 |
| 검증 | 서버 | 내 옷인지, 칸이 맞는지, 고정·중심·제외 조건을 지켰는지 확인하고 틀린 후보를 버린다 |
| 점수 | 앱 | 규칙 엔진 `evaluate()`로 5개 기준 점수를 매기고 높은 순으로 3개를 보여 준다 |

- **홈 탭의 오늘 추천은 규칙 엔진 그대로** 둔다(화면을 열 때마다 AI를 부르면 비용·지연이 크다).
- AI 코디 탭의 "오늘 코디"와 "예정일 코디"가 AI 추천을 쓴다.
- AI 추천이 실패하면 목업으로 대신하지 않는다. 오류를 보여 주고 "규칙 엔진으로 추천 받기" 버튼을 따로 준다(규칙 엔진은 목업이 아니라 원래 있던 추천 방식이다). 결과 화면에 어느 방식인지 배지로 표시한다.

## 2. 점수 기준 (AI에게 그대로 준다)

기획서 p.24 점수 모델. 앱 엔진과 같은 기준이다.

| 기준 | 비중 | 높은 점수 조건 |
|---|---|---|
| 색상 조화 | 30% | 잘 어울리는 색 짝(COLOR `attrs.pairs`), 뉴트럴 위주에 포인트 색 하나, 상하의 밝기 대비 |
| 상황 적합 | 25% | 상황(출근·회의·외근·회식·데일리 등)과 격식(1~3)에 맞는 아이템 격식, 원하는 분위기 |
| 날씨 적합 | 20% | 기온에 맞는 계절·보온(SUB_TYPE `attrs.warmth`) 합, 비 오면 젖어도 되는 신발, 일교차가 크면 아우터 |
| 개인 취향 | 15% | 프로필 선호 스타일·선호 색, 사용자가 좋아한 아이템 |
| 다양성 | 10% | 최근 7일에 입은 조합과 겹치지 않음, 덜 입은(잠자는) 옷 활용 |

## 3. API

### `POST /api/v1/outfits/recommendations` (로그인 필요)

```ts
interface OutfitRecommendRequest {
  context: {
    date: string;                       // YYYY-MM-DD
    occasion: string;                   // COMMUTE | MEETING | FIELD | DINNER | DAILY | INTERVIEW | WEDDING | DATE | TRAVEL | GATHERING
    mood: string;                       // NEAT | COMFY | CHIC
    formality: string;                  // CASUAL | BIZ_CASUAL | FORMAL
    weather?: { temp: number; min: number; max: number; rainProb: number; cond: 'SUNNY' | 'CLOUDY' | 'RAIN' };
    anchorItemId?: string;              // 꼭 넣을 중심 아이템
    fixed?: Partial<Record<Slot, string>>; // 칸 고정
    avoidColors?: string[];             // 피하고 싶은 COLOR 코드
    concepts?: string[];                // 예정일 컨셉 (STYLE 코드)
    timeOfDay?: 'AM' | 'PM' | 'EVENING';
    memo?: string;                      // 예정일 메모 (200자 이하)
  };
  excludeItemIds?: string[];            // 최근 착용 제외 등 앱이 계산한 제외 목록
  recent?: { date: string; items: Partial<Record<Slot, string>> }[]; // 최근 7일 코디 (착용 기록은 기기에만 있어서 앱이 보낸다)
  likedItemIds?: string[];              // 앱 affinity > 0
  dislikedItemIds?: string[];           // 앱 affinity < 0
  count?: number;                       // 후보 수, 기본 5, 1~6
}
type Slot = 'TOP' | 'BOTTOM' | 'DRESS' | 'OUTER' | 'SHOES' | 'BAG';

interface OutfitRecommendResponse {
  candidates: {
    items: Partial<Record<Slot, string>>; // 아이템 id
    reason: string;                       // 한국어 한두 문장 (80자 이하)
    aiScores: { color: number; occasion: number; weather: number; taste: number; diversity: number }; // AI가 매긴 0~100 예상 점수(참고용)
  }[];
  provider: string;                       // 공급자 ID
  model: string | null;
  remainingToday: number;                 // 코디 추천 남은 횟수
}
```

### 서버가 AI에게 주는 것

- 사용자 옷장 중 **추천 가능한 옷**(ITEM_STATUS `recommendable`, CATEGORY `slot`이 있는 것): id, 이름, 종류·세부 종류(라벨 포함), 칸(slot), 색(라벨·neutral·light), 패턴, 계절, 스타일, 격식, 보온(warmth), 볼륨, 착용 횟수, 마지막 착용일.
- 프로필(선호 스타일·색·드레스 코드), 요청 context, recent, liked/disliked, 2장 점수 기준, 색 짝 목록(사용자 옷에 나온 색만).
- 규칙: 코디는 `TOP+BOTTOM` 또는 `DRESS` 중 하나, `SHOES` 필수, `OUTER`는 날씨에 따라, `BAG`은 있으면 넣는다. 주어진 id만 쓴다. 고정·중심 아이템 포함, 제외·피하고 싶은 색 금지. 후보끼리 겹치지 않게.
- 구조화된 JSON 출력: 칸별 값은 그 칸에 들어갈 수 있는 id의 enum. `reason`·`aiScores` 포함.

### 검증·응답

- 후보마다: id가 그 사용자 것인지, 칸이 아이템 종류의 slot과 맞는지, 추천 가능한 상태인지, `TOP+BOTTOM` xor `DRESS`, `SHOES` 있음, 고정·중심 포함, 제외·피하고 싶은 색 없음, 중복 후보 아님. 틀린 후보는 버린다.
- 남은 후보가 0개면 다음 공급자를 시도한다(07 문서 3장 순서). 모두 실패하면 502 `AI_UNAVAILABLE`.
- 추천 가능한 옷이 모자라 코디를 만들 수 없으면(상의·하의나 원피스, 신발이 없음) AI를 부르지 않고 400 `WARDROBE_INSUFFICIENT`(`message`에 모자란 칸).
- 기록: `tb_ai_analysis_log`에 `feature = 'OUTFIT_RECOMMEND'`(마이그레이션으로 CHECK에 추가). 결과 JSON에는 후보 id·이유·점수, 이미지 관련 칸은 NULL.
- 한도: 코디 추천은 사진 분석과 따로 센다. `WEARLY_AI_OUTFIT_DAILY_LIMIT`(기본 20). 초과 429 `AI_LIMIT_EXCEEDED`. 성공한 호출만 센다.
- 관리자: 대시보드·AI 기록·공급자 `today`에 이 기능도 포함(기록의 `feature`로 구분). 관리자 시험 분석은 사진 분석만 그대로 둔다.

## 4. 공급자 구현

- 07 문서 3장의 공급자(CLAUDE·OPENAI·GEMINI)와 우선순위를 그대로 쓴다. 공급자 포트에 "이미지 없는 구조화 JSON 생성"을 더한다(사진 분석과 같은 구조화 출력 방식).
- 프롬프트·스키마 만들기와 응답 검증은 공급자와 무관한 애플리케이션 계층에 둔다(08 문서 구조).
- 목업 실행(`WEARLY_AI_PROVIDER=mock`)이면 목업 공급자가 규칙에 맞는 후보를 결정적으로 만든다(하네스용).

## 5. 앱

- `api.outfits.recommend(req)` 추가(순수 TS API 모듈).
- AI 코디 탭(오늘·예정일): 조건 입력 → 서버 호출 → 후보마다 `evaluate()`로 점수 → 높은 순 3개 → 결과 화면. 같은 점수면 AI 순서.
- 결과 화면: 배지 "AI 추천 · 공급자 이름"(규칙 엔진이면 "규칙 추천"), 카드마다 AI 이유(맨 위) + 엔진 점수 내역 + 엔진 추천 이유. 남은 횟수 표시.
- 진행 표시: AI 응답은 수 초 걸린다. "옷장을 살펴보는 중 → 조합을 고르는 중 → 점수를 매기는 중" 단계 표시.
- 오류: 429 → 한도 안내, 400 `WARDROBE_INSUFFICIENT` → 모자란 칸 안내와 옷 등록 버튼, 502·네트워크 → "AI 추천을 받지 못했어요" + "규칙 엔진으로 추천 받기" 버튼. 목업 실행(`MOCK_MODE`)에서 서버가 없으면 규칙 엔진으로 바로 간다.
