## D1. 출시 형태: PWA → 네이티브 앱

웨어리는 '매일 아침 습관'이 핵심인 서비스다. 그런데 습관을 만드는 도구(푸시, 위젯)를 PWA가 가장 약하게 지원한다.

| 웨어리 핵심 기능 | PWA | 네이티브 앱 |
|---|---|---|
| 아침 코디 푸시, D-1 알림 (재방문 핵심) | iOS는 홈 화면에 설치한 사용자만 받을 수 있음 | 바로 가능 |
| 홈·잠금화면 위젯 ("출근 전 10초" 경험) | 불가 | 가능 |
| 앱스토어 노출 (기획서의 '발견' 단계) | 앱스토어에 올라가지 않음 | 가능 |
| 기기 안 바로 진단 (온디바이스 AI) | WebGPU/WASM, 기기별 편차가 크고 느림 | Core ML·TFLite로 빠르고 안정적 |
| "이 기기에만 보관"하는 진단 결과 | iOS Safari는 설치하지 않은 사이트의 저장 데이터를 일정 기간 사용이 없으면 지울 수 있음 | 앱 저장소에 안정적으로 보관 |
| 카메라로 옷 여러 벌 연속 촬영 | 가능하지만 UX가 투박함 | 연속 촬영, 배경 제거 등이 매끄러움 |
| 경쟁사 | 에이클로젯·Alta·Whering 모두 앱 | 동등한 출발선 |

**PWA의 장점**(빠른 배포, 심사 없음, 링크 하나로 체험)은 버리지 않고 역할을 나눈다.

- **메인 서비스**: React Native(Expo) 앱. 푸시는 Expo Notifications(APNs/FCM), 위젯은 P1~P2.
- **웹**: 랜딩 + "내 옷 바로 진단" 체험판. SNS 광고 링크 → 설치 없이 진단 → "앱에서 내 옷장 만들기"로 전환. 기획서의 로컬 진단을 **유입 장치**로 쓴다.

**예외**: 베타를 지인 수십 명에게만 돌려 추천 품질만 빠르게 보려면 PWA로 먼저 검증해도 된다. 단, 푸시를 못 보내니 주간 재방문율이 실제보다 낮게 나올 수 있다.

**일정 영향**: 스토어 심사, 푸시 설정, 기기 테스트로 약 1~2주 추가 (7~9주 → 8~11주). 아침 푸시는 P1에서 P0로 올린다.

## D2. 앱 프레임워크: React Native (Expo) vs Flutter

| 기준 | React Native (Expo) | Flutter |
|---|---|---|
| 팀 기술 스택 (기획서: React + TS + React Query) | ✅ 언어·상태 관리·API 코드를 그대로 활용 | Dart를 새로 배워야 함 |
| 웹 체험판과 코드 공유 | ✅ API 타입, 검증 로직, 훅 공유 가능 | Flutter Web은 첫 로딩이 무겁고 검색 노출에 약함 |
| 출시 후 빠른 수정 | ✅ EAS Update로 JS 수정은 스토어 심사 없이 배포 | Shorebird(외부 유료 서비스) 필요 |
| 카카오 로그인 | 커뮤니티 라이브러리(`@react-native-seoul`) | ✅ 카카오 공식 SDK |
| 구글·애플 로그인 | 동등 | 동등 |
| 온디바이스 AI | TFLite, ML Kit, ExecuTorch 지원 | ML Kit 플러그인이 조금 더 성숙 |
| 홈 위젯 | 위젯 자체는 Swift/Kotlin으로 작성 | 동일 (home_widget 패키지) |
| UI 성능·애니메이션 | 새 아키텍처 이후 대부분 충분 | ✅ 화면을 직접 그려 더 매끄럽고 일관됨 |

**결론: React Native (Expo).** 웨어리는 사진 목록·카드·폼 중심이라 Flutter의 렌더링 강점이 크게 드러나지 않는다. 반면 React 코드와 인력 재사용, 웹 체험판 코드 공유, 심사 없는 즉시 수정은 짧은 일정에서 직접적인 시간 절약이 된다.

**Flutter가 나은 경우**: 팀에 React 경험자가 없을 때, 화려한 커스텀 인터랙션이 브랜드 핵심일 때, 웹 체험판 없이 앱만 낼 때.

## D3. 데이터베이스: MySQL → PostgreSQL

### 기획서 기준 점검

| 기획서 요소 | PostgreSQL | 비고 |
|---|---|---|
| 테이블 11개 (USER, WARDROBE_ITEM, OUTFIT, DAILY_LOOK, DIAGNOSIS 등) | ✅ | 일반 관계형 구조라 그대로 옮길 수 있음 |
| Spring Boot + Mapper(MyBatis) | ✅ | 드라이버와 방언 설정만 변경 |
| 사용자별 소유권 검사 | ✅ 더 강함 | Row Level Security로 DB 단에서도 차단 |
| 일·주·월 진단, 옷장 활용률 집계 | ✅ 더 편함 | 윈도 함수, `generate_series`, 머티리얼라이즈드 뷰 |
| 관리형 서비스 | ✅ | AWS RDS/Aurora, 네이버클라우드, Supabase, Neon 등 |

### PostgreSQL을 고른 이유

1. **pgvector (가장 큰 이유)**: 옷 이미지 임베딩으로 비슷한 옷 찾기. "새 옷 → 내 옷장 코디 미리보기", "어울리는 새 옷 추천", "중복 니트 정리 후보"를 별도 벡터 DB 없이 구현한다. MySQL도 9.x부터 VECTOR 타입이 있지만, 무료 커뮤니티 버전에는 벡터 검색 인덱스가 없다(유료 HeatWave에서만 제공).
2. **JSONB**: AI 분석 결과, 진단 상세 점수, 리포트처럼 구조가 자주 바뀌는 데이터를 컬럼 추가 없이 저장하고 인덱스까지 건다.
3. **배열 타입**: 감정 태그, 피하고 싶은 색, 스타일 태그를 별도 테이블 없이 다룬다.
4. **부분 인덱스**: '세탁 중이 아닌 아이템'에만 인덱스를 걸어 추천 후보 조회를 빠르게 한다.

### 바꿀 때 주의할 점

- **테이블 이름은 소문자 snake_case로 통일**한다. PostgreSQL은 따옴표 없는 이름을 소문자로 바꾸므로 `TB_USER`는 `tb_user`가 된다. `"TB_USER"`처럼 따옴표를 쓰기 시작하면 모든 SQL에 따옴표가 필요해진다.
- **SQL 문법 차이** (MyBatis XML)

  | MySQL | PostgreSQL |
  |---|---|
  | `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` |
  | `IFNULL()` | `COALESCE()` |
  | `GROUP_CONCAT()` | `string_agg()` |
  | `DATE_FORMAT()` | `to_char()` |
  | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT ... DO UPDATE` |
  | 백틱 `` ` `` | 큰따옴표 `"` |

- **대소문자 비교**: PostgreSQL은 문자열 비교 시 대소문자를 구분한다. 이메일은 `lower(email)` 인덱스나 `citext` 타입으로 처리한다.
- **커넥션**: 연결 하나가 프로세스 하나라 비용이 크다. HikariCP 풀 크기를 적당히 잡고, 사용자가 늘면 PgBouncer를 붙인다.
- **시점**: 아직 DDL 확정 전(기획서 다음 단계 02)이라 지금 바꾸는 비용이 가장 적다.

## D4. API 키·보안 관리 (네이티브 앱)

**원칙: 앱 안에는 비밀 키를 절대 넣지 않는다.** 앱 파일(APK/IPA)은 누구나 풀어볼 수 있고, 난독화나 환경변수(`EXPO_PUBLIC_*`, react-native-config)도 JS 번들에 그대로 들어간다.

### 구조: 앱은 우리 서버만 호출

```
[앱] ──(사용자 토큰)──▶ [Spring Boot API] ──(비밀 키)──▶ AI API / 날씨 API / 스토리지
```

- AI·날씨·스토리지 키는 서버에만 둔다(AWS Secrets Manager/Parameter Store 또는 서버 환경변수, git 제외).
- 날씨는 지역별로 서버에서 캐싱해 호출 비용을 줄인다.
- **AI 키 웹 입력 (2026-10-17 추가)**: 관리자 사이트에서 AI 공급자 키를 넣을 수 있다. 쓰기 전용이고 DB에는 AES-256-GCM으로 암호화해 저장하며, 마스터 키(`WEARLY_SECRET_KEY`)는 서버 환경변수(운영은 KMS·Secrets Manager)에만 둔다. 웹 키가 없으면 환경변수 키를 쓴다. 출시 전 조건: 관리자 2단계 인증, 마스터 키 KMS 이전. 상세는 [07 문서 6장](07_관리자_사이트.md).

### 무엇을 어디에 두나

| 종류 | 예시 | 위치 | 이유 |
|---|---|---|---|
| 비밀 키 | AI API 키, 날씨 API 키, DB 비밀번호, S3 Secret | 서버 전용 | 노출 시 요금 폭탄·데이터 유출 |
| 공개 식별자 | 카카오 네이티브 앱 키, Firebase 설정, Google SDK 키 | 앱에 넣어도 됨 | 콘솔에서 번들 ID·패키지명·서명 해시로 사용 범위 제한 |
| 사용자 토큰 | Access/Refresh Token | Keychain(iOS)/Keystore(Android) | `expo-secure-store` 사용, AsyncStorage 금지 |
| 빌드용 키 | Sentry 업로드 토큰, 스토어 배포 키 | EAS Secrets / CI 비밀값 | 빌드할 때만 사용, 앱 번들에 넣지 않음 |

### 사용자 인증 (토큰)

- 소셜 로그인 결과를 서버가 검증한 뒤 서버가 자체 토큰을 발급한다.
- **Access Token** 15~30분(JWT), **Refresh Token** 2~4주. 쓸 때마다 새로 발급하고 이전 것은 폐기(Rotation). 서버 DB에 저장해 로그아웃·탈퇴·기기 분실 시 강제 만료한다.
- 앱은 axios 인터셉터에서 401을 받으면 자동 갱신하고, 갱신도 실패하면 로그아웃한다.

### 서버(Spring Security) 쪽 방어

- **소유권 검사**: 모든 API에서 `item.userId == 토큰의 userId` 확인. PostgreSQL RLS로 이중 방어.
- **요청 제한**: 사용자별 하루 횟수 제한(Bucket4j + Redis). 기획서 등급 정책(무료회원 서버 분석 하루 1회)이 이 장치로 구현된다.
- **이미지**: Presigned URL은 5분 내 만료, 파일 형식·크기 제한, 비공개 버킷, 조회도 만료 서명 URL, 서버에서 EXIF 제거.
- **로그**: 토큰·이메일·이미지 URL은 로그와 Sentry에서 마스킹.

### 정품 앱 검증 (권장)

AI 분석 API는 호출마다 비용이 든다. **iOS App Attest + Android Play Integrity**(Firebase App Check로 한 번에)로 정품 앱 요청만 받는다. MVP에서는 AI 분석·추천 API에만 적용한다.

### MVP에서는 보류

- 인증서 피닝: 인증서 교체 시 앱 업데이트 전까지 접속 불가 위험. 금융 앱 수준이 아니면 나중에.
- 루팅·탈옥 탐지: 옷장 앱에서는 비용 대비 효과가 낮다.

## D5. 소셜 로그인

### 지원 수단

| 우선순위 | 수단 | 이유 |
|---|---|---|
| P0 | 카카오 | 국내 가입 전환율 1위 |
| P0 | 애플 (iOS) | 앱스토어 심사 규정 4.8: 외부 로그인을 제공하면 개인정보 보호 기준을 갖춘 로그인도 함께 제공해야 함. 애플 로그인이 가장 간단한 충족 방법 |
| P0 | 구글 | 안드로이드·지메일 사용자 |
| P1 | 네이버 | 30~40대 직장인 비중이 높음, 베타 반응 보고 추가 |
| 제외 | 이메일·비밀번호 | 비밀번호 관리·찾기·유출 대응 부담 |

화면 배치는 iOS는 애플·카카오·구글 순, 안드로이드는 카카오·구글 순. 카카오 버튼은 공식 디자인 가이드를 따른다.

### 로그인 흐름

```
① 앱: 카카오/구글/애플 SDK로 로그인 → ID 토큰 받음
② 앱 → 서버: POST /api/v1/auth/social/{provider}  { idToken, nonce }
③ 서버: 각 사의 공개키(JWKS)로 서명 검증 (발급자·대상·만료·nonce)
④ 서버: 회원 조회 또는 신규 생성 → 웨어리 자체 Access/Refresh 토큰 발급
⑤ 앱: 토큰을 Keychain/Keystore에 저장
```

- 앱 라이브러리: 카카오 `@react-native-seoul/kakao-login`, 구글 `@react-native-google-signin/google-signin`, 애플 `expo-apple-authentication`. 셋 다 네이티브 모듈이라 **Expo Go가 아닌 Expo Dev Build**로 개발해야 한다.
- 카카오는 콘솔에서 **OIDC(ID 토큰) 사용**을 켜야 구글·애플과 같은 방식으로 검증할 수 있다.

### 데이터 설계: 이메일을 회원 식별 키로 쓰지 않는다

카카오 이메일은 선택 동의라 비어 있을 수 있고, 애플은 이메일 숨기기 시 가짜 주소(`@privaterelay.appleid.com`)를 준다. 소셜 계정 테이블을 분리하고 각 사의 고유 ID(`sub`)로 식별한다.

```sql
CREATE TABLE tb_user_social (
  social_id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id          BIGINT NOT NULL REFERENCES tb_user(user_id) ON DELETE CASCADE,
  provider         VARCHAR(20) NOT NULL,   -- KAKAO, GOOGLE, APPLE, NAVER
  provider_user_id VARCHAR(255) NOT NULL,  -- 각 사의 고유 ID(sub)
  email            VARCHAR(255),           -- 참고용, 없을 수 있음
  connected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (provider, provider_user_id)
);
```

같은 이메일이라도 자동으로 계정을 합치지 않는다(탈취 위험). "마이 > 계정 연결"에서 사용자가 직접 연결한다.

### 놓치기 쉬운 필수 사항

- **앱 안 회원 탈퇴 필수** (애플 심사 규정 5.1.1(v), 구글 플레이도 계정 삭제 경로 요구). 탈퇴 시 **애플 토큰 철회(revoke) API, 카카오 연결 끊기(unlink) API** 호출. 옷·착장 사진과 진단 데이터도 함께 삭제.
- **카카오 이메일 필수 동의**는 비즈 앱 전환(사업자 정보 등록)이 필요하다. 개인 개발 단계에서는 이메일을 선택으로 두고, 이메일 없이도 서비스가 동작하게 설계한다.
- **구글**: `openid email profile` 범위만 요청하면 까다로운 앱 검증 없이 출시 가능. iOS·Android·Web(서버 검증용) 클라이언트 ID를 각각 만든다.
- **개인정보 동의**: 필수·선택 항목 동의 화면, 만 14세 미만 가입 제한(개인정보보호법).
- **비회원 → 회원 전환**: '바로 진단' 결과 중 사용자가 고른 것만 가입 후 업로드.

### 추가 API

| API | 용도 |
|---|---|
| `POST /api/v1/auth/social/{provider}` | 소셜 로그인 / 자동 가입 |
| `POST /api/v1/auth/refresh` | 토큰 갱신 |
| `POST /api/v1/auth/logout` | Refresh Token 폐기 |
| `GET/POST/DELETE /api/v1/users/me/social-accounts` | 계정 연결·해제 |
| `DELETE /api/v1/users/me` | 회원 탈퇴 (연결 끊기 + 데이터 삭제) |

**일정**: 카카오·구글·애플 3종 기준 3~5일 추가(개발자 콘솔 설정, 애플 심사 대응 포함). 각 사 API 키 발급이 필요하므로 목업 앱에서는 제외했다.
