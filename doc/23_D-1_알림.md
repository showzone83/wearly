# 23. 예정 코디 D-1 알림: 기기 로컬 알림 + 서버 푸시

> 구현함, 2026-10-18 (`a4aad23`, `dev`에 `d28e382`로 병합). 대상: `mobile/`(`lib/planNotify.ts`, `planNotifyRules.ts`, `store/useNotifyStore.ts`), `backend/`(`notify` 컨텍스트, `V17__push_token.sql`), `harness/`(시나리오 57).
> 예정 코디 저장은 [21](21_예정_코디_저장.md), 장소별 날씨(전날 다시 확인)는 [19](19_장소별_날씨.md). 기획서의 "예정 코디 → D-1 알림 → 최신 예보로 재확인·수정 제안" 흐름 중 알림 부분이다.

## 1. 배경과 결정

예정일 코디(캘린더)를 저장해 두면 **예정 전날 저녁**에 "내일 예정 코디" 알림을 보내고, 그 사이 예보가 바뀌었으면 "예보가 바뀌었어요"로 알린다. 알림을 누르면 그 예정의 PLAN 모드(코디 다시 확인·수정)가 열린다. 그 전에는 다시 확인한 결과를 앱을 열 때 배지로만 알렸다 ([19](19_장소별_날씨.md) 11장).

| 결정 | 이유 |
|---|---|
| **기기 로컬 알림을 기본으로, 서버 푸시는 따로** | 로컬 알림은 서버·EAS·Apple/Google 계정 없이 iOS Expo Go에서도 동작한다(안드로이드 Expo Go는 8장). 지금은 실제 휴대폰 원격 푸시를 쓸 준비(9장)가 안 돼 있으므로 로컬이 먼저 쓸 수 있어야 한다 |
| 서버 푸시는 기본 꺼짐 | `wearly.notify.push.enabled=false`. 토큰은 받아 두되 D-1 작업을 예약하지 않는다. 켜면 서버가 알림을 보내고 앱은 로컬 D-1 알림을 끈다 (둘이 겹쳐 두 번 울리지 않게) |
| 알림 시각 | 앱 로컬: 예정 전날 **설정 시각(기본 20:00, 30분 단위, 기기 시간대)**. 서버: 매일 **19:30 KST** 한 번 (`wearly.notify.day-before.time`) |
| 푸시 전달 | Expo Push API (`provider=expo`). 기본 공급자 `log`는 보내지 않고 건수만 로그에 남긴다 (로컬 확인용) |
| 중복 방지 | 같은 예정은 하루(한국 날짜)에 한 번만 보낸다. 보내기 전에 발송 기록 행을 먼저 넣어(`ON CONFLICT DO NOTHING`) 서버가 여러 대여도 한 번만 보낸다 |
| 설정 | 켜기·끄기는 프로필 알림 설정 `notify.dMinus1`(기존 필드, 계정 모드는 서버와 동기화). 시각·권한 여부는 기기에만 둔다 |

## 2. 구조 한눈에

```
[A. 기기 로컬 알림]  앱이 예정마다 전날 20:00(설정 시각)에 알림 하나를 예약
  예정 저장·수정·동기화·지우기 / 앱 시작·복귀 → 예약 목록을 예정 목록과 맞춘다 (reconcile)
  예정 전날(알림 시각 전)에는 그 장소 날씨를 하루 한 번 다시 받아 문구에 반영

[B. 서버 푸시]  개발용·정식 빌드 + EAS 설정이 있을 때만
  앱 ── PUT /me/push-token {token, platform, deviceId} ──▶ 서버 (tb_push_token)
        응답 serverPush=true ──▶ 앱은 로컬 D-1 알림을 모두 취소
  서버 매일 19:30 ── 내일 예정 → 알림 켠 회원 → 토큰 → 날씨 다시 확인 → Expo Push 로 보내기
```

둘 다 같은 `data`(`type: plan-d1`)로 알림을 보내므로, 누르면 같은 코드(`planNotify.ts`의 알림 누르기 처리)가 그 예정의 PLAN 모드를 연다.

## 3. 앱 로컬 알림 (`lib/planNotify.ts`, 규칙은 `lib/planNotifyRules.ts`의 순수 함수)

### 3.1 예약 규칙

- 알림 id는 `plan-d1:<예정 id>`. 이 접두사로 시작하는 것만 다룬다 (다른 알림과 섞이지 않게).
- 예정마다 알림 하나, 시각은 **예정 날짜의 전날 + 설정 시각**(기기 시간대). 이미 지난 시각은 예약하지 않는다.
- **iOS는 앱마다 예약 알림을 64개까지만** 둔다. 그래서 가까운 순으로 **60개(`MAX_SCHEDULED`)**만 예약하고, 앱을 열 때마다 다시 맞추므로 뒤의 예정도 차례가 되면 예약된다.
- 맞추기(`reconcilePlanNotifications`): 지금 예약된 알림과 예약해야 할 알림을 비교해 고아 알림은 취소하고 새로 필요한 것은 예약한다. 내용이 바뀌었는지는 `data.sig`로 본다. 동시에 여러 번 불러도 하나씩 돌고, 예정이 한꺼번에 바뀌면 400ms 기다렸다 한 번 맞춘다 (`scheduleReconcile`). 예외를 던지지 않는다.
- 알림을 껐거나(`notify.dMinus1`), 서버가 대신 보내거나(`serverPush`), 권한이 없으면 우리 알림을 모두 취소한다.
- 맞추는 때: 예정·알림 설정·계정이 바뀔 때(저장·수정·동기화·다시 확인·지우기·로그아웃), 앱 시작, 앱이 다시 활성이 될 때.

### 3.2 문구 (서버 푸시와 같다)

| 경우 | 제목 | 본문 |
|---|---|---|
| 보통 | 내일 예정 코디 | `내일 ‘결혼식 하객’ 예정이에요 · 도쿄 · 예보 18°C` |
| 예보가 바뀜 | 예보가 바뀌었어요 | `내일 ‘결혼식 하객’ · 도쿄 · 예보 18°C (저장할 때 14°C) · 비 소식이 있어요 · 코디를 다시 확인해 보세요` |

- 날씨 출처 표시: 예보 / 평년 / 직접 입력. 장소가 없으면(앱의 "내 지역") 장소 칸을 뺀다(앱은 내 지역 이름을 넣는다).
- "바뀜" 기준: 다시 확인한 기온이 저장된 값과 **3°C 이상** 다르거나 **비 여부**(강수 확률 50% 이상)가 달라졌을 때 (`RECHECK_TEMP_DIFF`, `RAIN_PROB_LINE`, 앱 `planWeather.ts`와 서버 `DayBeforeWeather`가 같은 규칙). 비 여부가 바뀌었으면 "비 소식이 있어요"·"비 소식이 없어졌어요"를 붙인다.
- 직접 고른 날씨(`MANUAL`)는 다시 확인하지 않는다.

### 3.3 전날 날씨 다시 확인

예정 전날(알림 시각 전)에 그 장소 날씨를 **예정마다 하루 한 번** 다시 받아 기기에 둔다(`useNotifyStore.fresh`). 알림 문구가 이 값을 쓴다. 못 받으면(로그인 필요·한도·네트워크·목업 실행·예전 서버) 저장된 날씨와 출처로 알린다. 날짜가 바뀌면 버린다.

### 3.4 권한

- 처음 예정을 저장하거나 마이 화면에서 "D-1 예정일 알림"을 켤 때 **한 번** 권한을 묻는다. 안드로이드 13 이상은 권한을 묻기 전에 알림 채널(`plan-d1`)이 있어야 해서 채널을 먼저 만든다.
- 거부하면 다시 묻지 않고 마이 화면에 "알림 권한 허용하기"(기기 설정 열기)를 보인다. 웹 미리보기는 로컬 알림을 지원하지 않는다(`notificationsSupported()`가 false).

### 3.5 마이 화면 설정

더보기(마이) 탭 알림 영역의 "D-1 예정일 알림" 토글 아래에 **전날 알림 시각**(± 버튼으로 30분씩, 오전/오후 표시)이 있고, 권한이 거부돼 있으면 "알림 권한 허용하기"(기기 설정 열기)로 바뀐다. 서버가 대신 보내는 기기(`serverPush`)에서는 시각 줄 없이 토글 설명에 서버 시각("전날 19:30쯤 최신 예보로 알려 드려요")이 나온다. 웹 미리보기에서는 "알림이 오지 않아요"로 안내한다.

### 3.6 알림 누르기

알림(로컬·서버 푸시 모두)을 누르면 `data.planId`의 예정을 찾아 PLAN 모드로 연다. 서버 푸시의 `planId`는 기기 예정 id(`clientId`, 없으면 `srv-서버ID`)다. 아직 동기화 전이거나 지운 예정이면 캘린더로 간다. 앱을 알림으로 연 경우(종료 상태)도 마지막 응답으로 그 예정을 연다.

## 4. 서버 푸시 토큰 API

모두 로그인 필요 (`PushTokenController`, 05 문서 6장 "푸시 토큰"과 같다).

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| PUT | `/api/v1/me/push-token` | `{ token, platform, deviceId }` | 200 `{ deviceId, platform, serverPush, dayBeforeTime }` |
| DELETE | `/api/v1/me/push-token?deviceId=` | — | 204 (없어도 204, `deviceId` 없으면 400) |

| 필드 | 검증 (`PushTokenRules`) | 틀리면 |
|---|---|---|
| `token` | Expo 푸시 토큰 `ExponentPushToken[…]` 또는 `ExpoPushToken[…]`, 255자까지 | `REQUIRED` · `TOO_LONG{max: 255}` · `INVALID_FORMAT{format: "ExponentPushToken[…]"}` |
| `platform` | `ios` · `android` | `REQUIRED` · `NOT_ALLOWED{allowed}` |
| `deviceId` | 앱이 처음 실행할 때 만든 기기 ID. 1~64자, 영문·숫자·`. _ : -` | `REQUIRED` · `TOO_LONG{max: 64}` · `INVALID_FORMAT` |

- 회원·기기당 토큰 하나(`UNIQUE(user_id, device_id)`)이고 같은 토큰은 한 행만 둔다(`UNIQUE(token)`). 한 기기에서 다른 계정으로 로그인하면 토큰이 새 계정 쪽으로 옮겨진다.
- `serverPush`: 서버 설정이 `enabled=true`이고 `provider=expo`일 때만 `true`. 앱은 이 값으로 로컬 D-1 알림을 끌지 정한다. `dayBeforeTime`은 서버 작업 시각 `HH:mm`.
- 앱은 로그아웃 전에 지우고(`unregisterPushToken`), 탈퇴할 때는 서버가 함께 지운다(`ON DELETE CASCADE`). Expo가 `DeviceNotRegistered`로 답한 토큰도 서버가 지운다.
- 앱이 보내는 때(`syncPushToken`): 계정 모드 + 개발용·정식 빌드 + 알림 권한 허용 + EAS `projectId` 있음일 때만 토큰을 받아 등록하고, 하루가 지나면 다시 등록한다. 하나라도 안 되면 조용히 건너뛰고 로컬 알림만 쓴다. 이 API가 없는 예전 서버(404)·오프라인도 로컬 알림으로 간다.

## 5. 서버 `notify` 컨텍스트와 D-1 작업

패키지: `notify/adapter/in/web`(`PushTokenController`), `adapter/in/schedule`(`DayBeforeScheduler`), `adapter/out/persistence`(JPA·MyBatis), `adapter/out/push`(`ExpoPushSenderAdapter`, `LogPushSenderAdapter`), `application/service`(`PushTokenService`, `DayBeforeNotifyService`), `domain`(`DayBeforeMessage`, `DayBeforeWeather`, `PushTokenRules`, `PushPlatform`, `PushSettings`), `config`(`NotifyConfig`, `NotifyProperties`). 다른 컨텍스트에서는 `plan`의 `PlanReminderUseCase`(날짜별 예정)와 `user`의 `NotifySettingUseCase`(D-1 알림을 켠 활성 회원)를 `port.in`으로만 부른다 ([08](08_백엔드_구조.md), [10](10_백엔드_흐름.md) 3.13).

### 5.1 작업 순서 (`DayBeforeNotifyService.runDayBefore`)

1. `enabled=false`면 아무것도 하지 않고 끝 (스케줄러도 만들지 않는다).
2. 내일(한국 날짜) 예정을 모두 읽는다.
3. 예정을 가진 회원 중 D-1 알림을 켠 활성 회원만 추리고, 그 회원들의 토큰을 읽는다.
4. 예정마다: 토큰이 없으면 건너뜀. **발송 기록을 먼저 잡는다**(`claim`, 이미 있으면 `alreadySent`).
5. 저장된 날씨와 비교하려고 **날씨를 다시 확인**한다 — `GET /weather/day`와 같은 유스케이스. 직접 고른 날씨(`MANUAL`)와 장소가 없는 예정(서버는 앱의 "내 지역"을 모른다)은 확인하지 않는다. 한도·공급자 실패 등으로 못 받으면 저장된 날씨로 보낸다. 같은 장소는 한 번만 묻는다.
6. 문구(`DayBeforeMessage`)를 만들어 모든 기기에 보낸다. 어댑터가 100개씩 나눠 보낸다. `data`: `type=plan-d1`, `planId`, `serverId`, `date`, `changed`.
7. 결과: 한 기기라도 성공하면 보냄. 모든 기기에 실패한 예정은 발송 기록을 풀어 다음에 다시 보낼 수 있게 한다. `DeviceNotRegistered` 토큰은 지운다. 보낸 지 30일 지난 발송 기록을 지운다.
8. INFO 요약 한 줄: `D-1 알림 2026-10-19: 예정 N개, 보냄 N개(예보 바뀜 N), 이미 보냄 N, 건너뜀 N, 실패 N, 푸시 N건, 지운 토큰 N, 지운 기록 N`. 예정 제목·토큰 같은 입력 값은 로그에 남기지 않는다.

외부 호출(날씨·푸시)이 길 수 있어 전체를 한 트랜잭션으로 묶지 않는다. 각 포트·유스케이스 호출이 자기 트랜잭션을 쓴다. 전송 중 예외가 나면 잡아 둔 발송 기록을 모두 풀어 중복도 누락도 없게 한다(기록을 못 풀면 그날은 다시 보내지 않는다 — 중복 발송보다 낫다).

### 5.2 Expo Push 어댑터

`POST {base-url}/--/api/v2/push/send`, 본문은 메시지 배열(요청당 100개까지), 응답 `data`는 보낸 순서의 티켓이다. 티켓 `ok`는 "Expo가 받았다"는 뜻이고 기기 도착은 영수증으로 알 수 있는데 **영수증 확인은 아직 하지 않는다.** 티켓의 `DeviceNotRegistered`만 토큰 삭제로 처리한다. 로그에는 토큰·문구를 남기지 않는다. `access-token`은 Expo의 enhanced push security를 켰을 때만 넣고, 비우면 `Authorization` 헤더를 보내지 않는다.

## 6. 설정 (`wearly.notify.*`, `application.yml`)

| yml | 환경변수 | 기본값 | 뜻 |
|---|---|---|---|
| `wearly.notify.push.enabled` | `WEARLY_NOTIFY_PUSH_ENABLED` | `false` | 서버 푸시 사용. false면 토큰은 받지만 D-1 작업을 예약하지 않고 `serverPush`는 `false` |
| `wearly.notify.push.provider` | `WEARLY_NOTIFY_PUSH_PROVIDER` | `log` | `expo`(Expo Push API로 보냄) · `log`(보내지 않고 건수만 로그에 남김). 그 밖은 `log`로 본다 |
| `wearly.notify.push.expo.base-url` | `WEARLY_NOTIFY_EXPO_BASE_URL` | `https://exp.host` | Expo Push API 주소 |
| `wearly.notify.push.expo.access-token` | `WEARLY_NOTIFY_EXPO_ACCESS_TOKEN` | (없음) | Expo 대시보드에서 enhanced push security를 켰을 때만. 실제 값은 `config/application-local.yml`에 |
| `wearly.notify.push.expo.timeout` | `WEARLY_NOTIFY_EXPO_TIMEOUT` | `PT10S` | Expo 호출 제한 시간 |
| `wearly.notify.day-before.time` | `WEARLY_NOTIFY_DAY_BEFORE_TIME` | `19:30` | D-1 작업 시각 `HH:mm` (한국 시간) |
| `wearly.notify.day-before.scheduler-enabled` | `WEARLY_NOTIFY_DAY_BEFORE_SCHEDULER_ENABLED` | `true` | false면 작업을 예약하지 않는다 (테스트용) |

견본은 `backend/config/application-local.example.yml`의 `notify:` 주석 블록이다. 로컬에서 서버 푸시 경로를 눈으로만 보려면 `enabled: true`, `provider: log`로 두면 작업이 돌고 "푸시 N건"이 로그에 찍히지만 실제로는 보내지 않는다. 이때 토큰 등록 응답의 `serverPush`는 `false`다(앱은 로컬 알림을 계속 쓴다).

## 7. DB (`V17__push_token.sql`)

| 테이블 | 칸 | 설명 |
|---|---|---|
| `tb_push_token` | `push_token_id`, `user_id`(CASCADE), `device_id`(64), `platform`(`IOS`·`ANDROID`), `token`(255), `created_at`, `updated_at` | `UNIQUE(user_id, device_id)`, `UNIQUE(token)` |

## 8. Expo Go에서 되는 것, 안 되는 것

| | Expo Go iOS | Expo Go 안드로이드 | 개발용·정식 빌드 | 웹 미리보기 |
|---|---|---|---|---|
| 로컬 D-1 알림 (예약·권한·누르면 PLAN 모드) | 된다 | **안 된다.** 알림 모듈을 불러오지 않고 D-1 알림을 끈다 (아래) | 된다 | 안 된다 (`notificationsSupported()`가 false) |
| 원격 푸시 토큰 받기 (`getExpoPushTokenAsync`) | **안 된다 (iOS·안드로이드 모두).** Expo Go는 SDK 53부터 원격 푸시를 지원하지 않는다는 Expo 안내에 따라 앱이 `isRunningInExpoGo()`일 때 토큰 받기를 건너뛴다 | 〃 | 된다 (EAS `projectId` + 9장 준비 필요) | 안 된다 |
| 서버 푸시 | 못 받는다 (iOS는 로컬 알림만) | 못 받는다. 알림 없음 | `serverPush=true`일 때 받는다 | 안 된다 |
| 목업 실행 | 로컬 알림 되고 전날 날씨 다시 확인은 서버가 없어 건너뜀 | 알림 없음 | — | — |

- 지금 확인한 것: 서버 쪽 토큰 등록·D-1 작업·Expo 어댑터(가짜 서버)는 자동 테스트로, 토큰 API는 하네스(57)로 확인했다. **앱의 로컬 알림은 시뮬레이터·실제 휴대폰에서 아직 눈으로 확인하지 않았다** (타입 점검만 통과). 규칙 함수(`planNotifyRules.ts`)의 앱 단위 테스트도 아직 없다.
- 시뮬레이터에서 로컬 알림을 보려면 알림 시각을 가까운 시각으로 바꾸고 내일 예정을 만든 뒤 앱을 백그라운드로 보낸다 (앱이 앞에 있어도 배너로 보이도록 알림 처리 방식을 정해 두었고 소리·배지는 없다).

### 8.1 안드로이드 Expo Go: 알림 모듈 지연 로드 (이슈 #9, f2cd9bc)

- Expo 공식 문서는 Expo Go에서도 로컬 알림이 된다고 하지만, 이 저장소의 SDK 57 안드로이드 Expo Go에서는 `expo-notifications`를 불러오면 네이티브 모듈 `ExpoTopicSubscriptionModule`을 찾지 못해 앱 시작 때 오류가 나고 모든 화면이 뜨지 않았다 (2026-10-18 확인).
- 그래서 `expo-notifications`를 정적 `import`하지 않고, 처음 필요할 때 한 번만 `require`한다 (`planNotify.ts`의 `loadNotifications`). 앱 시작 때 모듈이 평가되지 않으므로 모듈이 없어도 앱은 뜬다.
- 안드로이드 + Expo Go(`isRunningInExpoGo()`)면 모듈을 아예 불러오지 않고 D-1 로컬 알림을 끈다. 경고 로그: `[plan-notify] Android Expo Go에서는 알림 모듈이 없어 D-1 알림을 꺼요`.
- 불러온 모듈에 `setNotificationHandler`·`scheduleNotificationAsync`가 없으면(개발 모드에서 초기화에 실패하면 undefined가 올 수 있다) 같은 방식으로 알림만 끈다.
- 알림을 쓸 수 없으면 `notificationsSupported()`가 false이므로 예약·권한·토큰 등록을 모두 건너뛰고, 마이 화면 "D-1 예정일 알림" 설명이 알림이 오지 않는다는 안내로 바뀐다 (웹 미리보기와 같은 문구).
- 안드로이드에서 D-1 알림을 쓰려면 개발용 빌드가 필요하다 (9장 2번). iOS(Expo Go 포함)와 개발용 빌드는 그대로 동작한다.
- 확인: 안드로이드 휴대폰 Expo Go에서 오류 없이 앱이 뜸 (사용자 확인), iOS 시뮬레이터 정상, 앱 typecheck·단위 테스트 24개.

## 9. 실제 휴대폰으로 원격 푸시를 받으려면 (준비 단계)

> 아래는 Expo·Apple·Google 문서 기준의 순서이고 **이 저장소에서 아직 해 보지 않았다.** 계정·결제가 필요한 일이 있어 지금은 하지 않기로 했다 (CHANGELOG "진행 중"). 순서는 위에서 아래다.

1. **EAS 프로젝트 만들기**: `npm i -g eas-cli` → `eas login` → `cd mobile && eas init`. `app.json`의 `expo.extra.eas.projectId`가 생긴다 (앱이 이 값으로 `getExpoPushTokenAsync({ projectId })`를 부른다. 없으면 토큰 받기를 건너뛴다).
2. **개발용 빌드(dev client)**: Expo Go로는 원격 푸시를 못 받으므로 `expo-dev-client`를 추가(`npx expo install expo-dev-client`)하고 `eas.json`에 `development` 프로필을 만들어 `eas build --profile development --platform ios|android`로 설치용 빌드를 만든다. 이 앱은 `app.json`에 `app.wearly.mobile`(iOS bundleIdentifier·Android package)이 있다.
3. **iOS: APNs**: Apple Developer Program 가입(유료) → EAS가 푸시 권한이 있는 프로비저닝/APNs 키를 만들거나 올려 둔다 (`eas credentials`). 실제 기기 등록(`eas device:create`)이 필요하다.
4. **안드로이드: FCM**: Firebase 프로젝트를 만들고 Android 앱(`app.wearly.mobile`)을 등록해 `google-services.json`을 받는다. FCM V1 서비스 계정 키(JSON)를 EAS 자격 증명에 올린다. `app.json`의 `android.googleServicesFile`로 `google-services.json`을 가리킨다.
5. **서버 설정**: `config/application-local.yml`에 `wearly.notify.push.enabled: true`, `provider: expo`. 보안 강화를 켠 Expo 계정이면 `expo.access-token`도. 서버를 다시 띄우면 시작 로그에 "D-1 알림 작업을 매일 19:30 (한국 시간)에 실행해요"가 나온다.
6. **확인 순서**: 빌드를 설치한 휴대폰에서 로그인 → 알림 권한 허용 → 토큰 등록 응답이 `serverPush: true`인지(마이 화면에서 서버 시각으로 안내) → 내일 예정을 만든다 → D-1 작업 시각 근처에 알림이 오는지. 바로 보려면 `WEARLY_NOTIFY_DAY_BEFORE_TIME`을 몇 분 뒤로 잡는다.
7. **영수증 확인**(필수는 아님): 5.2장처럼 지금은 티켓만 본다. 도착 여부·실패 사유를 알려면 Expo 영수증(`getReceipts`) 확인을 더한다 (다음 단계).

## 10. 옷장 도우미 알림 (26 문서 3단계)

같은 푸시 경로를 D-1 알림 말고 **옷장 도우미**도 쓴다. 이 문서의 D-1 알림 규칙은 그대로다.

- `PushMessage`에 선택 필드 `channelId`·`ttlSeconds`를 더했다 (비우면 `plan-d1`·12시간). 옷장 도우미 알림은 채널 `closet-helper`, TTL 24시간. 앱은 같은 ID의 채널을 만들어야 안드로이드에서 알림이 보인다.
- 일반 알림 입력 포트 `PushNotifyUseCase.notifyUser(userId, PushNoticeDto)`: 회원의 모든 기기로 보내고 죽은 토큰을 지운다. 서버 푸시가 꺼져 있거나 토큰이 없으면 조용히 건너뛴다.
- 알림 종류(`data.type`): `closet-pairing-request`(주인에게 연결 요청) · `closet-pairing-accepted`(돕는 사람에게 연결됨) · `closet-pairing-rejected` · `closet-pairing-ended` · `closet-helper-digest`(대리 작업 묶음, 마지막 작업 뒤 15분 또는 첫 작업 뒤 1시간). 알림을 누르면 앱이 옷장 도우미 화면(`/helper`)을 연다.
- 묶음 알림 예약 작업은 `wearly.notify.push.enabled=true`일 때만 돈다. 설정과 시각은 [26](26_옷장_도우미.md) 3단계.
- `tb_push_send_log`는 예정 코디 전용이라 옷장 도우미는 쓰지 않는다. 중복 방지는 `tb_closet_proxy_action.notified_at`(`UPDATE … RETURNING`)이 한다.
